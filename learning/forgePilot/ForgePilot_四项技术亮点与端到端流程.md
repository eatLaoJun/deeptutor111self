## 一、项目主线与职责边界

主线是：**把 Bug 单变成带验证证据、可人工审核的 PR**，不是把“模型生成了一段代码”等同于交付。

| 层次 | 职责 | 与截图的关系 |
| --- | --- | --- |
| 工作台与接入 | 提交任务、补充信息、查看进度、确认交付；按用户和项目授权 | 截图已有 |
| Harness | 校验需求、组装上下文、执行确定性路由、落实预算和审批规则 | 截图已有职责，本文补充执行协议 |
| 插件装配 | 按项目配置装配 Agent、模型、检索器与工具；沿用截图中的 Cordis 命名 | 截图已有 |
| Agent Loop | 模型提出行动，执行器调用工具，工具结果回到模型；默认沿用 Pi 命名 | 截图已有 |
| 状态与制品 | 保存任务状态、检查点、工具事件、工作区快照、测试结果和外部操作凭据 | 本文补充 |
| 两套评估 | Review 缺陷发现能力评估；SWE-bench 补丁修复能力评估 | 本文补充 |

任务理解依然可以使用模型，但不设独立的本地训练、量化与部署方案。模型分类也不能代替权限判断。

Harness 决定“当前允许进入哪个阶段”，Agent Loop 决定“在当前阶段下一步读什么、查什么或怎么改”。不要把每一次模型调用都建成独立业务工作流节点。

## 需要始终区分的四种数据

| 数据 | 回答的问题 | 不能替代什么 |
| --- | --- | --- |
| 会话事件 | 用户、模型和工具分别说过什么、做过什么 | 不能直接恢复工作区和运行进程 |
| 模型上下文 | 下一次模型调用实际看到哪些信息 | 不是完整审计记录 |
| 任务检查点 | 当前做到哪一步，哪些动作已有可靠结果 | 不是数据库与外部系统的统一事务 |
| 代码与测试制品 | 修改了什么，在哪个版本上验证过 | 不能单靠自然语言摘要重建 |

长期记忆只保存通过筛选的可复用知识，例如某项目的可信构建约定；不用于记录正在执行的测试进程，也不把模型猜测直接写成事实。

<a id="intent-routing"></a>
## 意图识别与入口路由

### 识别意图，不等于先调用一个独立分类模型

本方案选择：**显式入口和任务状态优先，必要的语义理解合入 Agent Loop 的首轮模型决策，最终由 Harness 校验和分发。** 不沿用截图中的独立本地分类模型，也不固定增加一轮“先分类、再调用主模型”的流程。

需要区分三件事：

| 层次 | 回答的问题 | 本方案由谁完成 |
| --- | --- | --- |
| 任务意图 | 用户是要了解代码、修复 Bug，还是评审 PR | 显式入口已知则直接使用；自然语言请求由首轮模型理解 |
| 任务参数 | 操作哪个项目、哪个任务、哪个 PR，现象与预期是什么 | 入口和已有状态提供确定值，模型补充提取；缺失或歧义时澄清 |
| 执行决策 | 当前阶段下一步读哪个文件、调用哪个工具 | 阶段受限的 Agent Loop 决策，Harness 校验后执行 |

模型可以根据用户请求与工具定义返回结构化工具调用，再由应用代码执行。利用这个机制，工具选择本身就可以承载业务路由，不必额外输出一份独立分类结果。[Tool use 官方说明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

### 一次请求的处理顺序

```text
用户输入 + 工作台模式 + 当前任务标识
  -> Harness 校验用户、项目、任务状态及显式控制事件
  -> 已知模式直接限定处理范围；只挂载当前可用的入口工具
  -> 首轮模型理解语义、提取参数，提出回答、澄清或业务动作
  -> Harness 校验 Schema、参数来源、目标资源、状态与权限
  -> 创建或更新任务，进入受阶段约束的执行循环
```

“首轮”指需要语义理解的入口决策。任务已有明确类型后，不在每次读文件或运行测试前重新做一次全局意图分类。

- 在任务模式提交 Bug，已知目标是修复，不必再用模型判断这是修复还是 Review；模型主要提取问题与约束。
- 在评审模式选择 PR，入口已经提供 PR 标识；后端仍校验其所属项目及访问权限。
- 点击查询进度、取消等按钮时，明确事件可直接交给 Harness，不必先进入模型循环。
- 对自由输入“停一下”“继续那个任务”，模型可以提出控制动作，但必须绑定明确任务并通过状态校验。
- 审批绑定具体变更包及代码指纹，通过明确确认事件完成；不能把一句含糊的“可以”自动当成发布授权。
- 日志、代码或工单引用中出现“取消任务”等文字，不是用户控制事件，不能用关键词扫描直接执行。

### 需要区分哪些业务类型

| 逻辑类型 | 示例 | 处理方式 |
| --- | --- | --- |
| code_qa | “解释一下这个分页逻辑” | 允许必要的只读检索与回答，不因此开放改码 |
| bug_fix | “修复整除时多算一页的问题” | 创建或补齐任务，进入修复—验证流程 |
| pr_review | “看看这个 PR 是否有问题” | 读取对应版本与 diff，生成评审结果，不自动修改代码 |
| task_query | “刚才那个任务做到哪了” | 读取有权限的任务状态，不创建新修复任务 |
| task_control | “取消这个任务”“暂停后继续” | 解析目标和动作，由确定性状态规则处理 |
| unknown / out_of_scope | 目标不清、多个候选或超出平台范围 | 追问或说明范围，不强行选择最相近的写操作 |

这些类型用于设计处理边界和记录决策，并不要求训练一个六分类模型。“请求澄清”是处理动作，不需要与修复、评审并列成为正式业务能力。

例如，可定义 `submit_bug_task`、`request_pr_review`、`get_task_status`、`request_task_control`、`ask_clarification` 等逻辑入口工具。名字只是本方案的接口示意，不代表 Pi 或 Cordis 已提供这些 API。问答允许直接回答或选择只读工具，也不必为了记录一个标签而强制调用分类工具。

这里的 `pr_review` 是实际评审请求，不是离线运行 Review 效果评估；SWE-bench 同样是受控评估入口，不把普通用户请求默认路由去跑基准实验。

### 有了意图，为什么还不能直接改码

以“修复课程列表分页问题”为例，模型提出修复请求并提取现象与预期，Harness 仍需核实项目、仓库、分支、用户写权限与任务约束。确定值优先来自已授权的入口和当前配置，不让模型凭空补出一个仓库或扩大允许修改范围。

通过校验后才进入 PREPARE 等阶段，并挂载阶段内可用的工具。**工具挂载限制可见能力，每次执行仍需重新检查权限和状态。** 分类为 bug_fix 不是写权限凭据，也不能越过构建验证、人工确认或发布规则。

同一任务中的“先不要改前端”属于约束更新，不应新建修复任务。更新通过带版本的任务事件在安全边界应用；如果影响当前方案，就暂停或调整执行，相关验证与审批按实际变化重新确认。目标任务不明确时先问清楚，不能猜一个正在运行的任务来控制。

### 什么时候才增加独立 Router

当业务类型很多、不同类型确实需要不同提示词或执行器，或者实测表明独立路由可以改善准确率与成本时，再增加独立分类调用。Routing 可以由 LLM 或传统分类算法完成，并不天然要求本地小模型。[Routing 模式说明](https://www.anthropic.com/engineering/building-effective-agents)

对当前这套范围，先采用入口与状态规则加首轮语义决策即可。首轮与独立 Router 两种方案都要评估：路由正确性、参数完整性、应澄清但误执行的情况、端到端延迟及成本；不能只看分类标签是否正确。

## 二、单个 Bug 的端到端流程

### 2.1 用一个具体例子走通

以下均为教学示例：课程列表接口在记录总数恰好被每页条数整除时，多返回一个总页数。输入 `total=40, page_size=20`，实际 `total_pages=3`，预期为 `2`。

这个例子只用于贯穿数据流，不表示真实线上事故，也不表示平台只支持这种简单 Bug。

```text
提交 Bug 单
  -> 校验权限、明确预期与目标代码版本
  -> 创建独立任务工作区，检查构建和测试环境
  -> 在未修复版本上确认问题
  -> 检索定位、生成最小修改、保留修改制品
  -> 运行复现用例和相关回归，失败则在预算内返回修复
  -> 整理变更、风险和验证证据，等待人工确认
  -> 推送任务分支并创建或关联 PR
  -> 标记已交付，等待正常研发评审与合并
```

### 2.2 每个阶段的输入、产物与边界

| 阶段 | 关键输入 | 产物与进入下一阶段的条件 | 异常处理 |
| --- | --- | --- | --- |
| PREPARE | 工单、用户权限、仓库、目标分支、项目配置 | 固定 `base_commit`，准备工作区和工具权限 | 信息不足等待补充；权限失败直接拒绝对应操作 |
| REPRODUCE | 未修复代码、复现步骤、可信测试入口 | 复现证据；区分原有测试失败与目标缺陷 | 环境失败不冒充代码失败；不能复现时补充信息或转人工 |
| REPAIR | 问题证据、检索上下文、约束 | 有来源的诊断假设、最小 diff、必要新增测试 | 无进展或超预算则暂停，不无限循环 |
| VERIFY | 补丁、独立验证配置、工作区指纹 | 补丁可应用、构建及所需测试通过，结果绑定代码指纹 | 目标缺陷未解决返回 REPAIR；环境故障单独处理 |
| PACKAGE | diff、测试报告、剩余风险 | 可审核变更包；人工确认的是该版本的内容 | 修改了代码后原验证与审批不再自动有效 |
| PUBLISH | 已确认的变更包、任务分支、PR 目标 | 分支推送与 PR 资源核对成功，记录 PR 标识 | 响应不确定时先查询核对，不盲目重建 |
| DONE | PR、制品、事件轨迹 | 标记已交付并保存总结 | 已交付不代表已合并、已发布或业务效果已验证 |

示例中，未修复版本应先出现目标用例失败，修复后再通过。同时覆盖零条记录、非整除等边界；具体期望值以业务约定为准。不能只让模型新增一个必然通过的测试，就宣称问题解决。

### 2.3 工作区与验证隔离

任务使用独立分支和工作目录，不在用户正在编辑的目录里直接运行修复。Git worktree 可以为同一仓库提供多个工作树，但它不是安全沙箱；本方案仍要求受限执行环境、路径权限、资源预算及凭据隔离。[Git worktree 官方文档](https://git-scm.com/docs/git-worktree)

可信项目配置决定构建、测试命令和允许修改范围。Agent 可以提出测试建议，但不能通过删测试、改验证配置、扩大写权限来使自己通过验收。代码、工单与日志中的文本都作为数据处理，不能覆盖系统授权规则。

### 2.4 最小持久化记录

| 记录 | 最少保存什么 | 为什么需要 |
| --- | --- | --- |
| Task | 任务与项目标识、`base_commit`、生命周期状态、阶段、预算、取消标记、状态版本 | 决定任务当前允许做什么 |
| WorkspaceSnapshot | 基线、当前 HEAD、tracked diff、必要未跟踪文件、内容哈希与恢复引用 | 恢复实际代码，而不只是恢复聊天 |
| ToolOperation | 语义操作键、输入指纹、尝试次数、执行状态、退出码、输出制品、外部资源标识 | 重试与副作用核对 |
| Checkpoint | 阶段、下一安全动作、工作区引用、已完成操作、待核对操作、上下文状态、剩余预算 | 从已确认边界恢复 |
| Verification | 被测代码指纹、环境与命令版本、测试结果和日志引用 | 防止“测的是旧代码，交的是新代码” |
| Review / EvalRun | 输入版本、配置版本、输出报告、标签或测试结果、成本记录 | 离线比较和问题回放 |

上述为逻辑记录，不强制每一项都建独立表。初期可以采用持久化关系库保存状态与索引、制品存储保存大日志和快照；数据库品牌不是简历亮点。

## 三、亮点一：上下文管理与压缩

### 3.1 真正要解决的问题

修复过程中会不断累积文件内容、搜索结果、测试日志和失败尝试。全部保留会挤占模型上下文；只保留一个自然语言摘要，又容易丢失目标约束、已尝试的方案和工具结果。

因此不是“消息多了就总结”，而是把**不可丢的任务状态、近期完整交互、可压缩历史、可按需读取制品**分开管理。

### 3.2 一次模型调用看到什么

按下列顺序组装，不是机械按消息时间截断：

1. 固定约束：目标任务、权限边界、允许操作、验收条件。
2. 结构化当前状态：代码版本、阶段、已确认事实、已尝试操作、阻塞点、待验证假设。
3. 近期完整交互：保留能解释当前行动的消息及工具请求—结果关系。
4. 历史摘要：已完成轮次的关键结论、失败原因、对应证据引用。
5. 本轮所需代码与日志片段：保留路径、版本、行号和原始制品入口。

“已确认事实”必须有证据，例如测试输出或文件位置；模型提出的根因先标为假设，不能因为进入摘要就变成事实。

### 3.3 如何触发和执行压缩

- 输入预算按 `模型上下文上限 - 预留输出 - 安全余量` 计算；系统提示、工具定义和代码片段也计入。
- 每次请求前估算总量，超过预算才逐层处理，不假设固定轮次适用于所有任务。
- 先处理工具输出：测试日志保留命令、退出码、失败用例和关键错误，完整输出存为制品。
- 再移除重复且版本相同的代码片段；代码改变后旧片段不能冒充当前证据。
- 对已经结束的较早交互窗口生成摘要，近期上下文尽量保留完整。
- 工具调用按逻辑组处理：保留请求与对应结果，不留无来源的结果，也不截断正在等待的调用。
- 如果必要约束与当前证据本身已超预算，就缩小子问题或请求人工介入，不靠无限压缩硬塞。

分层裁剪的意思是“完整内容外置、关键内容进入本轮”，不是先删除日志再希望摘要能复原它。

### 3.4 保存与恢复什么

结构化状态至少包含：`task_id`、目标与限制、代码版本、当前阶段、确认事实及引用、已尝试方案、待验证假设、下一动作。状态更新带版本号，并在安全边界与检查点关联。

压缩后可以根据文件路径或制品引用重新读取证据，但**不能从摘要还原任意原始文件**。文件与日志保存在独立制品中，恢复时校验其版本与内容哈希。

### 3.5 怎样证明这条有效

对相同任务分别使用“仅截断”“只有摘要”“结构化状态加分层压缩”，比较任务完成情况、关键约束遗漏、重复行动、输入 Token 与总成本。总成本包含摘要模型调用，不能只统计压缩后的主模型输入。

没有对照记录时，简历写清机制，不写“压缩后成功率提高多少”。

<a id="review-eval"></a>
## 四、亮点二：PR Review 效果评估

### 4.1 它与平台的评审模式不是一回事

评审模式可以为人展示变更目的、影响范围和验证证据；效果评估则回答：**评审器指出的问题是否成立，已知问题有没有漏掉。** 两者可以共享输入制品，但不共享“生成了报告就算成功”的标准。

### 4.2 历史 Bug 与修复 PR 怎么变成评估集

1. 从历史缺陷关联出修复提交，再确认缺陷发生的代码状态与业务条件。
2. 对 PR 缺陷发现评估，优先找到**引入缺陷的 PR**，保存其 `base_sha`、`head_sha` 和 diff。
3. 修复 PR 与工单只作为人工建立参考标签的证据，不能让评审模型提前看到答案。
4. 如果只能得到修复前快照，就标为“代码快照审查”样本，不混称为引入缺陷 PR 的评估。
5. 标签按缺陷记录位置、触发条件、错误行为、根因及证据；人工区分真正修复与重构、格式化、无关调整。
6. 加入经过人工审查的非缺陷变更样本，并记录标签覆盖范围与不确定项。

关键点：**修复 PR 中改过的每一行，不等于一个 Bug；修复前存在缺陷，也不代表缺陷在被评审的 diff 中引入。** 必须固定评估目标是“本次变更引入的问题”，还是“整个代码快照中的问题”。

### 4.3 分层匹配，而不是一上来交给 Judge

```text
评审输出规范化与同根因去重
  -> 校验文件、提交版本及 old/new diff 侧
  -> 通过代码区间或函数位置生成匹配候选
  -> 独立 Judge 核对是否为相同错误行为、条件与根因
  -> 一对一问题匹配，避免一条泛化报告命中多个缺陷
  -> 争议项与新发现进入人工仲裁
  -> 汇总指标和失败归因
```

位置匹配只用于缩小候选，不代表语义正确。跨函数影响或根因与表现位置不同的样本，需要单独允许证据链匹配，不能只靠行号判错。

Judge 采用独立调用、固定提示词与版本；条件允许时使用不同模型或配置，但“不同模型”也不等于可靠金标准。其结果要经过人工抽检和争议仲裁，不把模型对自身输出的打分当最终事实。

### 4.4 指标的准确口径

- `TP`：经核对正确且唯一匹配的缺陷发现。
- `FP`：经核对不成立、超出预先定义范围或错误诊断的发现。
- `FN`：参考集中明确存在、但没有被正确报告的缺陷。
- `Precision = TP / (TP + FP)`；分母为零时记为不适用，而不是填满分。
- `Recall = TP / (TP + FN)`；相对于当前已标注缺陷集合，不声称覆盖未知缺陷。
- 误报占比可以用 `FP / (TP + FP)`；它不是需要负例总体的 False Positive Rate。
- 新发现但标签集没记录的问题先仲裁，不直接算 FP；未决项单独报告，不隐藏其数量。

仲裁确认的新缺陷进入新版本标签集后，应对所有对照组按同一版本重算，不能只给发现该问题的一组修改计分口径。

标签集不完整时，Precision 和 Recall 都有覆盖边界。不得为了提高指标，把有争议的问题直接删除，或把同一缺陷的多条重复提示都记成 TP。

### 4.5 输出怎样帮助迭代

按定位错误、缺少跨文件上下文、误解业务条件、重复报告、泛化建议冒充缺陷等原因归类。策略改动在开发集调试，固定测试集留作比较；关联提交与近重复缺陷分组，避免同时进入开发集和测试集。

产物包括：样本清单、标签及版本、原始评审输出、候选匹配、Judge 记录、人工裁决、指标报告。质量好坏从这些证据回放，不从报告文字是否流畅判断。

<a id="durability"></a>
## 五、亮点三：长任务可靠执行

### 5.1 状态驱动，阶段与生命周期分开

阶段使用第二节中的 `PREPARE / REPRODUCE / REPAIR / VERIFY / PACKAGE / PUBLISH / DONE`。生命周期另设 `QUEUED / RUNNING / WAITING_INPUT / WAITING_APPROVAL / PAUSED / CANCELLING / CANCELLED / FAILED / DELIVERED`。

例如，阶段 `PACKAGE`、状态 `WAITING_APPROVAL`，表示变更包已经准备好但尚未允许交付；阶段 `VERIFY`、状态 `PAUSED`，可以表示验证预算不足等待人工决定。

重要约束：

- 测试失败且仍有预算：回到 REPAIR；基础设施失败：先排查环境，不无意义改码。
- 审批只对指定变更包和代码指纹有效；重新改码或重放到新基线后，需要重新验证与确认。
- 只有 PUBLISH 阶段确认外部资源及制品后，才进入 `DONE + DELIVERED`。
- 状态变化使用版本检查，过期执行器不能覆盖更新后的取消或暂停状态。

### 5.2 检查点放在哪里

在可确认的边界持久化，例如工作区准备完成、一次改码制品落盘、一次验证结果记录完成，以及发布外部操作前后。检查点引用实际代码制品与操作记录，而不只保存消息数组。

持久化图状态与跨线程长期记忆是两类不同机制；这与官方持久化文档区分 checkpointer 与 store 的思路一致，但不表示本方案必须使用 LangGraph 或截图框架自动具备这些能力。[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)

外部动作前先记录操作意图和待执行状态；动作完成后保存结果凭据。两步之间仍可能崩溃，所以还需要幂等识别与恢复核对，不能宣称检查点使所有外部动作自动恰好执行一次。

### 5.3 为什么幂等键不能只用 tool_call_id

模型重新生成请求时，`tool_call_id` 可能变化，但语义上仍是同一次创建 PR 或同一份补丁应用。应使用包含任务、操作类型、目标资源、输入版本与代码指纹的稳定操作键；一次操作的网络重试与尝试编号另行记录。

输入、任务约束或补丁确实发生变化时产生新的语义操作版本。不能因为历史上调用过一次“测试”，就永久复用旧结果。

| 动作 | 可复用结果的前提 | 结果不确定时怎么办 |
| --- | --- | --- |
| 读取或检索 | 目标版本、权限和查询条件一致 | 可按规则重试；返回前核对当前版本 |
| 应用补丁 | 原始输入指纹一致，且当前代码与已记录结果吻合 | 检查工作区实际 diff，禁止重复叠加 |
| 运行测试 | 代码、环境、命令一致且结果仍有效 | 先确认原进程是否结束；测试有副作用时不能盲目并发重跑 |
| 推送分支 | 目标分支及预期提交一致 | 查询远端分支并核对提交 |
| 创建 PR | 任务、仓库、head/base 和外部资源标记一致 | 先查已有 PR，核对后关联或继续处理 |

GitHub API 支持按 head 和 base 查询 PR，可作为外部核对手段；本方案的操作记录、互斥与资源标识仍需自行落实，不能把“先查再建”当成跨进程的原子事务。[GitHub PR API 文档](https://docs.github.com/en/rest/pulls/pulls)

### 5.4 并发、超时和取消如何收敛

- 同一任务保持一个有效执行租约，租约代次随接管递增；数据库写入检查版本，工具执行入口也验证当前代次与取消状态。
- 锁过期不代表旧进程已经停止。接管前要回收或隔离旧执行器，并核对在途外部操作；数据库锁本身不能阻止已发出的远程请求生效。
- 对超时的有副作用操作，先标记为结果未知并查询资源。不能把“没收到响应”等同于“没有执行”。
- 重试预算按任务持久化，区分网络重试、环境重试和修复迭代。进程重启不会重置剩余次数与成本。
- 取消先进入 CANCELLING，停止后续调度并终止受控任务进程；等待在途请求核对后再进入 CANCELLED。
- 已经创建的分支、PR 或代码制品要保留并展示。取消不代表自动删除它们，更不意味着已经发生的外部效果回滚。

### 5.5 崩溃恢复的准确顺序

1. 加载任务、取消标记、预算和最后检查点，取得新的执行租约。
2. 核验代码基线、工作区快照、环境与项目配置；版本不一致时不得直接套用旧测试结论。
3. 处理状态未知的操作，确认旧进程与外部资源，必要时转人工。
4. 恢复结构化任务状态、近期交互与证据引用。
5. 从下一安全动作继续；如果代码指纹变化，重新验证，不重放已确认的副作用。

重点验收三个故障位置：改码后但未记结果、测试完成后但未推进阶段、PR 已创建但响应丢失。故障注入应有固定基线与恢复轨迹，不以“重新跑一遍最终成功”代替去重验证。

<a id="swebench"></a>
## 六、亮点四：SWE-bench 修复 Agent 评估

### 6.1 这项评估到底测什么

PR Review 评估发现缺陷的能力，SWE-bench 评估生成补丁解决问题的能力。后者使用问题、仓库和基线提交驱动修复，再由独立测试评判，而不是让 Judge 阅读补丁后决定成功。[SWE-bench Evaluation Guide](https://www.swebench.com/SWE-bench/guides/evaluation/)

### 6.2 先固定实验定义

| 项目 | 需要固定和记录的内容 |
| --- | --- |
| 数据 | 数据集标识、revision、split、明确的 instance_id 清单；只跑子集就写子集 |
| 输入 | 问题描述和 `base_commit` 对应代码；生成阶段不读取答案补丁、隐藏测试或评估标签 |
| 模型 | 提供商、模型标识或快照、生成参数；同组间尽量控制随机性并记录重复次数 |
| 工具 | Agent 与插件版本、工具集合、代码检索配置 |
| 预算 | 每任务 Token、墙钟时间、工具调用、修复迭代上限与重试规则 |
| 环境 | 镜像或依赖版本、资源限制、测试 Harness 版本 |
| 制品 | 生成补丁、运行轨迹、成本、官方报告与失败日志 |

数据中含有参考修复、测试补丁及 `FAIL_TO_PASS / PASS_TO_PASS` 等评估字段；这些应由评估端隔离管理，不作为生成输入。[SWE-bench 数据结构文档](https://www.swebench.com/SWE-bench/guides/datasets/)

公开基准本身还可能存在模型训练数据污染；隔离本次答案和调参集是必要控制，不等于证明模型从未见过题目。

### 6.3 基线与增强组怎么比较

- **基线组：** 相同 Agent、主模型和基础读文件、文本搜索、编辑、测试工具。
- **增强组：** 在相同预算下增加代码检索与结构上下文供给，不给额外答案或人工定位提示。
- 可比较的增强包括符号检索、相关调用关系与函数级代码片段，但要写清具体工具产物，不笼统称为“代码智能”。
- 调用关系如果来自静态分析，应说明动态调用、反射和跨语言等覆盖边界；没有实际对照，就不在最终简历中声称调用图增益。
- 各组共同保持上下文压缩和可靠性策略一致，先隔离代码上下文增强的作用；再通过单变量实验研究压缩策略。
- 做消融时一次去掉一种增强，不能同时更换模型、工具、预算和重试次数后把全部收益归于检索。

没有检索增强不等于不允许基线搜索代码。否则比较的不是增强收益，而是人为削弱基线。

### 6.4 成功标准与统计口径

以锁定版本的官方 Harness 报告为准。典型判定同时要求需要修复的 `FAIL_TO_PASS` 用例通过、原本应保持通过的 `PASS_TO_PASS` 用例不退化；“补丁成功应用”“命令退出成功”都不等于问题解决。[SWE-bench 官方判定实现](https://github.com/SWE-bench/SWE-bench/blob/main/swebench/harness/grading.py)

- 保留官方结果，再对事先冻结的任务清单计算 `resolved / N`，明确 N 的定义。
- 空补丁、无法应用、超时、环境错误与测试失败分别记数，不能只保留成功运行的样本。
- 如另报“可评估样本中的解决率”，必须同步报告被排除数量和原因，不能替代主口径。
- 主比较按预先确定的每任务运行次数；不能给增强组更多尝试后只挑最好的一次。
- 需要估计随机波动时，对各组采用相同重复方案；相同随机参数也不保证所有 API 输出完全确定。
- 成本包含成功与失败尝试，记录输入/输出 Token、工具次数、墙钟时间；价格未知时保留用量，不编造金额。
- 使用不同补丁或配置重新评估时更换运行标识，防止命中旧结果缓存。[官方评估与缓存说明](https://www.swebench.com/SWE-bench/guides/evaluation/)

### 6.5 哪些结论不能跨过去

SWE-bench 的结果可以支持“在该公开任务集和预算下的修复效果”，不能直接推出“公司 Bug 平均耗时下降多少”。企业交付还包含权限、构建系统、协作、人工审核等环节。

同样，正常执行的 SWE-bench 分数不能单独证明任务恢复能力。恢复机制要用第五节的故障注入实验独立验证。

## 七、面试追问与口述

### 7.1 一分钟讲清项目

以下是方案介绍口径，不是已经落地的经历声明：

> 这个项目面向研发中的 Bug 修复，目标不是让模型自由改代码，而是把工单、定位、改码、验证和 PR 交付串起来。底层复用 Agent 的模型—工具循环，上层由 Harness 管理权限、阶段和预算。我重点围绕四个方向展开：上下文长了怎么保留关键约束；任务中断后怎么恢复且避免重复操作；Review 指出的缺陷怎么评估真假和遗漏；代码检索增强对实际修复有没有帮助。前两项属于运行机制，后两套评估分别检查评审质量与修复效果，最终交付仍保留人工审核。

### 7.2 每一条至少能回答的追问

| 追问 | 回答主线 |
| --- | --- |
| 为什么不用通用 Coding Agent 就结束？ | 复用改码能力，补项目配置、权限、验证与可审核交付；不是宣称自研模型更聪明 |
| 你自己负责什么，框架负责什么？ | Agent Loop 处理模型和工具循环；自定义方案聚焦上下文策略、持久化执行协议与评估闭环，职责以实际参与范围为准 |
| 只有摘要为什么不够？ | 摘要可能丢约束和状态，需要结构化任务状态及可读取的原始证据 |
| 工具输出裁剪后怎么恢复？ | 裁剪的是本轮输入，不是删除原始制品；按引用和版本重新读取 |
| 保存会话能不能恢复任务？ | 不能，还要恢复代码、阶段、预算以及在途动作的真实状态 |
| 创建 PR 超时了怎么处理？ | 结果可能已生效，先查任务对应的分支与 PR，再决定关联、等待或重试 |
| 锁过期了能不能立即接管？ | 不能仅凭锁到期判断旧执行器已停止，必须隔离旧进程并核对在途动作 |
| 测试通过后又改了一行呢？ | 验证证据与代码指纹不再一致，需要重新验证，必要时重新确认 |
| 修复 PR 能直接当 Review 标准答案吗？ | 不能，需人工识别缺陷语义，并确认被评审输入是否真正包含该缺陷 |
| Judge 说对就算对吗？ | 不算，独立调用只是匹配辅助，争议与新发现需要人工仲裁 |
| 为什么使用 SWE-bench？ | 用独立可执行测试评估补丁，不只评价模型文字；同时明确公开基准和企业任务的差别 |
| 没有真实效果数字怎么讲？ | 讲问题、机制、取舍和可回放证据；有测量后再补指标，不借用博主数字 |
