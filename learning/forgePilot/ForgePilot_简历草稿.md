# ForgePilot 简历草稿

更新日期：2026-10-19。

> 本文为四项亮点的设计目标稿，不含本地模型应用。以下文案用于确定项目表达范围，尚不代表这四项已经由用户实现；定稿时，按实际完成内容确定责任动词与结果数据。

## 一、项目定位

**项目名称：ForgePilot｜研发 Bug 修复与评审辅助平台**

**项目概述：** 面向研发 Bug 处理场景，串联工单理解、代码定位、自动修改、构建测试与 PR 交付，通过上下文管理和可恢复执行支撑长任务推进，并以 PR Review 离线评估与 SWE-bench 对照实验分别衡量评审质量和修复效果，保留人工审核与合并环节。

这段先说明业务闭环，不预设覆盖全公司，也不宣称平台能够自动合并或上线。

## 二、四条简历候选文案

### 1. 上下文管理与压缩

针对长任务上下文膨胀、压缩后约束与执行状态丢失的问题，设计分层上下文管理机制，保留近期完整交互与工具调用关系，按预算压缩已完成历史；通过结构化任务状态、工具输出分层裁剪和原始制品引用，支持关键信息按需恢复。

### 2. PR Review 效果评估

针对评审质量难量化、误报漏报难定位的问题，设计基于历史缺陷与人工标注的离线评估链路，以文件及代码区间生成匹配候选，结合独立 LLM Judge 与人工仲裁核对缺陷语义，输出 Precision、Recall 及误报漏报归因，为评审策略迭代提供可回放依据。

### 3. 长任务可靠执行

针对修复任务重复触发、执行中断和外部操作结果不确定的问题，设计状态驱动的修复—验证流程，通过持久化检查点、操作幂等键、并发租约和重试预算控制任务推进；结合工作区快照、测试证据及 PR 状态核对，支持断点续跑与取消后的状态收敛。

### 4. SWE-bench 修复 Agent 评估

针对代码检索增强对修复效果的收益难判断的问题，设计基于 SWE-bench 固定样本的基线与增强方案对照，控制模型、环境及执行预算，使用官方测试评估补丁有效性，并结合任务解决率、Token 消耗、工具调用及执行轨迹分析质量—成本取舍。

## 三、四条不是四个独立项目

| 亮点 | 服务于哪个问题 | 面试展开位置 |
| --- | --- | --- |
| 上下文管理与压缩 | 一次修复越做越长，模型如何继续理解当前任务 | [上下文方案](ForgePilot_四项技术亮点与端到端流程.md#context) |
| PR Review 效果评估 | 评审器提出的问题是否真实，已知问题有没有漏掉 | [评审评估](ForgePilot_四项技术亮点与端到端流程.md#review-eval) |
| 长任务可靠执行 | 任务中断、重试、取消后如何避免丢失和重复操作 | [可靠执行](ForgePilot_四项技术亮点与端到端流程.md#durability) |
| SWE-bench 修复 Agent 评估 | 生成的补丁是否解决问题，增强方案是否值得成本 | [修复评估](ForgePilot_四项技术亮点与端到端流程.md#swebench) |

一句话组织：**上下文管理与可靠执行保障修复过程，Review 评估检验“看问题”的质量，SWE-bench 评估检验“改问题”的效果。**

## 四、技术栈怎么写

- 参考截图中的技术选型：React / TypeScript、Harness、Cordis 插件装配、Pi Agent Loop。
- 配套设计涉及：Git 工作区、制品存储、持久化任务状态、LLM Judge、SWE-bench Evaluation Harness。
- 最终技术栈只保留实际使用的组件。Cordis 不等于推理引擎，Pi 不等于任务持久化平台。
- 不因模板里出现而自动加入 MCP、调用图、某个数据库或某款模型。没有对应链路，就不堆这个词。
- 不纳入 LoRA、GGUF、llama.cpp 或本地小模型训练部署；任务理解可以保留为普通模型能力，不需要另设本地模型亮点。

## 六、面试开场的主线

作为方案介绍，可以这样开场：

> ForgePilot 不是让模型直接接管研发流程，而是把 Bug 修复放进一个可控闭环：先明确任务和代码版本，再由 Agent 定位、改码和测试，最后生成带验证证据的 PR，由人审核。技术上重点解决两件事：任务长了以后上下文不能丢，进程中断后也不能重复执行有副作用的动作。另外用两套评估区分评审能力与修复能力，避免只看模型输出就判断系统有效。
