# ForgePilot 项目背景与立项说明

更新日期：2026-10-21。

本文单独整理“为什么做、为谁做、与现成工具是什么关系、业务流程怎么讲”。上下文压缩、可靠执行和评估等技术细节见 [四项技术亮点与端到端流程](ForgePilot_四项技术亮点与端到端流程.md)。不新增未经提供的立项经历、实际接入记录或效果数据。

## 一、一句话定位

**ForgePilot 是面向内部研发工程师的 Bug 自动修复与交付平台，不是重新做一个 Codex，也不只是记录操作的审计平台。**

主线是：接收工单，组织问题上下文，准备项目环境，执行代码修复和验证，最终提交带验证证据、可供人工审核的 PR。

## 二、项目背景和立项逻辑

一个 Bug 从提出到交付，不只是“让模型修改几行代码”，还涉及三个方面：

- 上下文组织：工单描述、评论、日志、附件和对应代码版本分散，需要明确现象、预期及修改约束。
- 工程交付：不同项目有各自的依赖环境、构建与测试命令，生成补丁不等于完成验证。
- 质量与协作：修复进度需要跟踪，中断后需要恢复，PR 需要证据和人工审核，效果也需要持续评估。

因此，立项目标不是证明“现有工具不会写代码”，而是**减少 Bug 处理过程中的人工衔接，把修复能力组织成可以跟踪、恢复和验收的交付流程**。

面试可以这样说：

> ForgePilot 面向内部研发工程师，主要解决 Bug 修复中的流程衔接问题。一个 Bug 从工单到交付，除了改代码，还需要整理工单和日志、确定代码版本、准备运行环境、执行测试，再提交 PR 供人工审核。这些信息和操作分散在不同系统里，模型改完代码不代表任务已经交付。所以我们把工单上下文、项目约束、修复验证、状态跟踪和 PR 交付串起来。我主要负责上下文管理、长任务可靠执行，以及修复和 Review 的效果评估。

这段表达不额外假定个人发起了整个项目立项、组织访谈或供应商采购。没有相应经历，不补这些个人贡献。

## 三、已有 Codex、Claude Code，为什么还要做

**不是替代成熟 Coding Agent，而是把它们所代表的代码执行能力接入公司的任务和交付规则。**

不能用“它们没有自动化、工具接入、会话恢复或权限控制”作立项理由。Codex 官方文档说明可以通过 SDK 接入内部工具及 CI/CD，并继续或恢复会话；Claude Agent SDK 也提供工具、上下文管理、会话、权限和 hooks。[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)、[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)。

企业平台需要落实的是：

| 要回答的问题 | 企业侧需要做的工作 |
| --- | --- |
| 当前应该修什么 | 将工单、评论、日志和指定代码版本整理为有来源的任务输入 |
| 在什么边界内修 | 固定授权资源、工作区、允许的工具、构建命令和执行预算 |
| 什么情况下算完成 | 对齐验收条件、测试结果、代码改动和 PR，最后由人审核 |
| 中断后继续什么 | 核对任务状态、工作区、测试制品及外部 PR 操作，而不只是恢复聊天 |
| 是否值得持续投入 | 用业务任务比较交付效果、人工投入和总成本，分析 Review 误报漏报 |

被追问时可以这样回答：

> 我们不是认为 Codex 或 Claude Code 不会修 Bug，也不追求把它们的能力全部重做。现成 SDK、项目规则、工具连接和 CI 能解决的部分优先复用。我们重点做的是公司的任务接入和交付约束：一个工单对应哪个仓库，用什么环境验证，任务执行到哪一步，中断后怎么恢复，以及什么条件下才能交给工程师审核。

这里说明的是平台职责和可选接入方式，**不代表项目已经实际集成了 Codex 或 Claude Agent SDK**。底层运行时和 SDK 的描述应与实际链路一致。

## 四、用一个 Bug 说明平台怎么工作

下面是帮助理解的示意例子，不是实际线上事故记录。

工单描述：“课程列表共有 20 条数据，每页 10 条，却显示有 3 页，第三页为空。”

没有打通流程时，工程师需要自己整理复现步骤、找到仓库和版本、准备环境，把信息交给编程工具；改完后再运行测试、提交 PR 并回填工单。这里不是说工具不能集成，而是说这些衔接尚未完成时需要人来处理。

平台将这条流程组织起来：

1. 读取授权范围内的工单信息，明确实际现象和预期；信息不足就要求补充。
2. 按项目配置准备对应代码版本和隔离工作区，交给 Agent 定位、修改分页逻辑。
3. 确认问题能够复现，并验证补丁；例如检查 10、11、20 条数据时页数分别为 1、2、2，再执行相关测试。
4. 验证通过后推送修复分支，创建带问题原因、改动说明和测试结果的 PR，交给工程师审核。

**以前由人衔接的步骤，由平台按规则推进；人仍负责信息补充、异常处理和最终审核。** 创建 PR 是提交代码合并申请，不等于已经合并或上线。

## 五、外部系统集成，面试讲到什么程度

集成是支撑能力，不作为本项目最核心的技术亮点。能说明“工单怎么进来、代码从哪里拿、结果怎么回去、权限怎么控制”即可，不必背具体 API 名称和参数；被追问时再展开实现。

可以这样口述：

> 我们通过接口接入公司的工单系统和代码托管平台。工单可以由工程师主动提交，也可以通过事件通知进入平台；后端读取任务详情，按项目配置找到对应仓库和代码版本，在隔离工作区准备环境。Agent 修复并通过构建、测试后，平台推送修复分支、创建 PR，再将链接和处理进度回填工单，最后由工程师审核。权限由平台后端和外部系统共同校验，不让模型自行决定能操作哪些资源。

记住这组分工即可：**API 负责业务交互，Webhook 负责事件通知，Git 负责代码传输，平台负责权限、任务状态和失败处理。**

工单平台已有接口时优先复用，不要求一定新增接口；不同代码托管平台的差异通过适配器处理。GitLab、云效 Codeup 的接口说明及失败处理细节，集中放在 [外部系统集成技术说明](ForgePilot_四项技术亮点与端到端流程.md#system-integration)，不在本文重复展开；示例供应商不等同于实际已部署的集成。

## 六、立项范围和投入取舍

- 先覆盖可复现、改动范围可控、能够通过测试验证的 Bug；不承诺任意需求全自动交付，不自动合并上线。
- 如果只是个人在本地交互改码，或已有工具配置就能满足团队需求，不必另建完整平台。
- 需要稳定接入工单、统一工程环境、管理跨人员长任务和持续评估时，平台化才有投入价值；专人维护的是接入、执行可靠性和质量闭环，而不只是页面与 Prompt。
- SWE-bench 是辅助评估手段，不是业务立项的起点；企业真实任务上的交付与总成本才是投入判断依据。

对于“是不是套壳”的追问，重点说明确定性的项目约束、可恢复的任务和制品状态、可回放的评估机制；不宣称模型本身比通用编程工具更强。

## 七、指标口径和面试准备重点

现简历沿用用户确认的数据：500+ 名工程师使用；2026 年 Q2 组内累计修复 71 个 Bug；单 Bug 平均处理时间由 178 分钟缩短至 53 分钟，降低约 70%。不把组内数量扩大为全平台数量，也不追加未经提供的效果指标。

面试前需要按真实记录说清：

- 500+ 是累计使用还是活跃使用。
- 71 个 Bug 的完成条件是提交 PR、合并还是验收。
- 178/53 分钟是端到端历时还是人工操作工时，是否包含验证和审核。

**178→53 分钟不能直接改述为“比 Claude Code 快约 70%”**，除非确实做过对应对照。比较平台增益时，尽量固定底层模型/Agent、任务样本、环境和预算，并计入失败重试与人工审核成本。

面试准备重点放在自己负责的**上下文管理、长任务恢复、修复验证和效果评估**，讲清楚问题、机制、取舍和验证方式，而不是只罗列接入了哪些系统。
