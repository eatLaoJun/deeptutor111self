## 三条最重要的结论

1. **pi 没有 Python 库。** 从 Python 驱动 pi 的唯一方式是把它当外部可执行程序
   （JSON 模式一次性 / RPC 模式长驻），或放弃 pi 改用 [tau](05-tau-HuggingFace的Python版pi.md)。
2. **"进程内调用"才是最不安全的选择。** pi 的工具以进程 OS 权限直接执行、无沙箱
   （`docs/security.md`），模型可驱动任意命令，因此它必须待在可丢弃的隔离故障域里。
   "子进程"不是架构缺陷，是故障域隔离的最小实现。
3. **企业级的正确形态是控制面 / 执行面分离。** 不是"业务后端 fork pi"，而是
   "一个任务 = 一个沙箱，pi 只活在沙箱里"。详见 04。
4. **pi 是「内核固定、边缘自由」，不是「一切皆插件」。** 内核（agent loop / session /
   compaction）不可替换，但工具、provider、MCP、上下文变换、工具授权全部是 extension。
   dsh 基于 Cordis 才是真正的一切皆插件（无特权内核 + 可逆 effect）。详见 08。
5. **dsh 的官方 Python SDK 本身就是「子进程 + stdio JSONL JSON-RPC」。** 所以用子进程驱动
   agent 运行时是行业标准做法，不是偷懒。但 dsh 的插件层只有 TS，无 Python 出口。详见 09。
6. **Python 侧挂不上 agent 进程内的钩子。** 四条亮点里只有「上下文压缩策略注入」受影响，
   解法是用**阶段边界压缩**（结构化状态 DB + 新 session 注入），全在 Python 里完成。详见 09。
7. **pi 「改得好」不靠提示词和工具数量，靠三件事**：`edit` 的精确字符串替换（唯一性 +
   原子批处理）、可自我修复的错误信息、`bash` 提供的验证闭环。详见 10。
