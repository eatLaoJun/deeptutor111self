# 企业级架构：控制面 / 执行面分离

> 针对质疑：「你要有一个 pi 子进程，然后我在 Python 项目里调用？这是企业级项目，不能这样做。」

## 一、先分清两个问题

质疑里混了两件事：

| 问题 | 是不是真问题 |
| --- | --- |
| ①「后端进程 `subprocess.Popen` 一个 pi」这个形态 | **是真问题**，那是 demo 形态，不能上生产 |
| ②「用子进程 / 进程外执行」这个隔离方式 | **不是问题**，它恰恰是企业级的必要条件 |

## 二、关键论证：进程内调用才是最不安全的选择

`docs/security.md` 明确写了：**pi 的工具以 pi 进程的 OS 权限直接执行，不做沙箱。**

> Enabled tools use the operating-system permissions of the Pi process.
> Extensions execute inside that process.

也就是说你交给它的不是一个函数库，是**一个可以被模型驱动执行任意 shell 命令的东西**。

| 做法 | 后果 |
| --- | --- |
| API 进程内 `import` agent 库 | 模型可以让 `rm -rf`、装恶意包、死循环 curl 跑在**业务进程**里。一次 OOM 带崩整个 API |
| 独立进程 / 独立容器 | 崩了只死一个任务；`kill` 干净；权限可按任务收窄 |

**结论：这跟 pi 有没有 Python 库无关。** 就算换成纯 Python 的 agent 库（`tau`、Claude Agent SDK、
LangGraph），只要它能让模型执行命令，就必须放进一次性可丢弃的沙箱里跑。
各家 coding agent 产品的形态都一样：**一个任务 → 一个沙箱 → 里面跑 agent 运行时。**

## 三、企业级正确形态

```
┌─ 控制面（无状态，k8s Deployment，N 副本） ─────────────────┐
│  API Gateway / 鉴权                                         │
│  Task Service → 阶段状态机、预算、审批门                     │
│  Queue (Redis / SQS / Kafka)                                │
│  DB: Task / Checkpoint / ToolOperation / Artifact 元数据    │
│  ← 这个镜像里没有 Node，没有 pi，纯 Python                   │
└─────────────────────────────────────────────────────────────┘
                  │ 消费任务（幂等键 + 租约）
┌─ 执行面（一个任务 = 一个一次性沙箱，k8s Job / FC / 容器）──┐
│  Sandbox Pod（跑完即回收）                                   │
│   ├─ /workspace        git worktree @ base_commit            │
│   ├─ runner.py         ← 平台代码                            │
│   │     └─ agent runtime（pi RPC 子进程 / tau in-process）   │
│   ├─ 只挂 scoped 短期凭据（只够推一个分支）                   │
│   └─ 网络策略：只放行模型 API + 代码托管域名                 │
└─────────────────────────────────────────────────────────────┘
```

**关键变化：agent 不属于"你的后端"，它属于"任务沙箱"。**
控制面干净、无状态、可水平扩展；执行面按队列深度扩缩容；pod 销毁 = 故障域彻底回收
（僵尸进程、内存泄漏、临时凭据全没了）。

## 四、逐条回答企业级关切

| 关切 | 答案 |
| --- | --- |
| 部署单元 | 两个镜像：`control`（无 Node）+ `runner`（含 runtime），互不耦合 |
| 水平扩展 | 控制面加副本；执行面加 pod。瓶颈在队列，不在进程 |
| 崩溃隔离 | pod 挂掉 = 单任务 FAILED，进重试预算。M2 故障注入可直接 `kubectl delete pod` |
| 权限 | 沙箱内只有 scoped token；平台凭据永不进入。模型搞穿也只能推一个分支到一个仓库 |
| 可观测性 | agent 的 JSONL 事件流整条落盘 = 天然的分布式 trace（每次工具调用有时长、入参、结果） |
| 版本灰度 | runner 镜像 tag 锁定 runtime 版本，天然满足 SWE-bench "固定模型与工具版本"的要求 |
| 审计 | 事件流 + `ToolOperation` 表 = 谁在哪个 commit 上做了什么、外部动作是否生效 |
| 多租户配额 | pod 级 resource limit；token 预算按任务持久化 |
| 取消收敛 | 控制面写 `CANCELLING` → pod 收到 → `abort` → `agent_settled` → 核对在途外部操作 → pod 退出 |

## 五、必须承认的真实代价

1. **引入 Node 运行时（若选 pi 路线）** → 镜像多一层 base、依赖扫描多一条 CVE 链。
   缓解：固定版本、bun 编译单文件二进制、镜像 SBOM 扫描。
2. **跨进程协议要自己维护** → 但如果全 TS 用 SDK，代价是业务代码变成 TS。二选一，没有免费午餐。
3. **容器化 RPC 需要一层桥** → pi 的 RPC 是 stdin/stdout，跨 pod 不可直连，
   需 ~100 行 Python 桥（容器内：网络 socket ↔ 子进程 stdio）。
   折中方案：不跨网络，控制面通过 k8s Job manifest 注入任务参数，
   runner 跑完把事件流和产物写到对象存储，控制面只读结果（代价：失去实时中断能力）。

## 六、如果执行面改用 tau（in-process）

执行面里的"子进程"这一层就消失了，但**故障域隔离仍然靠容器**：

| 层 | pi 路线 | tau 路线 |
| --- | --- | --- |
| 进程隔离 | 容器 + 子进程（双层） | 仅容器（单层） |
| 故障域 | 子进程崩溃可重启 | 容器崩溃重启整个任务 |
| 语言栈 | Python 控制面 + Node 执行面 | 全 Python |
| 跨进程协议 | 需维护 JSONL 桥 | 无 |

这也是面试讲"为什么选 tau"的落点：**进程隔离需求已由容器满足，
进程内再套一层子进程只是多一个故障点和 IPC 成本。**
但前提是执行面确实被强制放进容器 —— 否则就是偷懒。

## 七、必须留在抽象层的东西

不管选哪条路，都要有一个 `AgentRuntime` 协议，让 `TauRuntime` 和 `PiRpcRuntime` 都是它的实现：

```
业务层
  └── AgentRuntime (Protocol)          ← 你自己写的，稳定
        ├── TauRuntime      in-process 默认
        └── PiRpcRuntime    subprocess 对照 / 降级 / 需要 pi 扩展生态时切换
```

**这是"选择权"，也是面试里"我做了取舍且留了后路"的证据。**
