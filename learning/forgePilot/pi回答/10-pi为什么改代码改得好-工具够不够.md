# pi 为什么「改代码改得好」？只有几个工具够不够？

> 数据来源：本机 pi 源码 checkout `/d/workfile/piagent/packages/coding-agent/src/`
> （与已安装的 `@earendil-works/pi-coding-agent` 1.4.0 同源）。
> 本文所有引用都标注了文件路径，可在面试时现场打开。

## 〇、一句话回答

**不是靠提示词长，也不是靠工具多。靠三件事：
① `edit` 的精确字符串替换设计；② 错误信息可自我修复；③ `bash` 提供的验证闭环。**

关于"只有几个工具够不够"：**这个前提本身就是错的。**
pi 默认给的不是"几个文件操作"，而是**两条腿：改（read/edit/write）+ 验（bash）**。
**`bash` 才是让 agent 改得好的核心工具**，因为它是唯一的"客观反馈来源"。

## 一、先纠正一个直觉：pi 的 system prompt 极短

`core/system-prompt.ts` 里默认 prompt 就那么几段（第 135 行附近）：

```ts
promptSections.preamble =
  "You are an expert coding assistant operating inside pi, a coding agent harness. " +
  "You help users by reading files, executing commands, editing code, and writing new files.";

promptSections.tools = `${visibleTools.map((n) => `- ${n}: ${toolSnippets[n]}`).join("\n")}
  ...`;
promptSections.rules = buildRules(...);
```

每个工具只贡献**一句话 snippet + 几条 guideline**（`core/tools/*.ts` 里的
`xxxToolSystemPromptContribution`）：

| 工具 | snippet | guidelines |
| --- | --- | --- |
| `read` | `Read file contents` | `Use read to examine files instead of cat or sed.` |
| `edit` | `Make precise file edits with exact text replacement, including multiple disjoint edits in one call` | 4 条，见下 |
| `bash` | `Execute bash commands (ls, grep, find, etc.)` | `You can inspect PI_* environment variables...` |

整个默认 system prompt 加上 `cwd`，也就十几行。**所以"pi 靠提示词工程"这个假设是错的。**

## 二、真正来源 1：`edit` 是精确字符串替换，不是行号 patch

`core/tools/edit.ts` 的 schema：`{ path, edits: [{ oldText, newText }] }`。

### 设计要点

| 设计 | 代码证据 | 为什么这决定了"改得好" |
| --- | --- | --- |
| **精确字符串匹配**，不是行号 | `oldText` / `newText` | 模型不用数行号，行号会漂移；也不需要输出整个文件 |
| **唯一性强制** | `countOccurrences(...) > 1` → 报错 | 逼模型"证明自己定位到了唯一位置"，从源头防止改错地方 |
| **一次调用可多个不相交编辑** | `edits[]` 数组 | 一处逻辑改动涉及多个分散位置时，一次成型，减少往返 |
| **全部对同一份原文匹配**，然后**逆序应用** | `matchedEdits.sort(by matchIndex)` + 逆序替换 | 保证前面编辑不会移动后面编辑的 offset —— 这是行号 patch 最经典的坑 |
| **重叠检测** | `previous.matchIndex + previous.matchLength > current.matchIndex` → 报错 | 防止"两个编辑各改一半"产生不可预期的结果 |
| **原子性** | 任一 edit 不匹配 → 抛错，不写文件 | **绝不产生半对半错的文件**。这点对无人值守平台比什么都重要 |
| 把 diff 和 unified patch 作为 `details` 返回 | `generateDiffString` / `generateUnifiedPatch` | 平台侧不用再算 diff，直接入库做审计 |

### 写进 guideline 的四条（`edit.ts` 第 45–50 行原文）

```
- Use edit for precise changes (edits[].oldText must match exactly)
- When changing multiple separate locations in one file, use one edit call with multiple entries in edits[] instead of multiple edit calls
- Each edits[].oldText is matched against the original file, not after earlier edits are applied.
  Do not emit overlapping or nested edits. Merge nearby changes into one edit.
- Keep edits[].oldText as small as possible while still being unique in the file.
  Do not pad with large unchanged regions.
```

第四条尤其重要：**"尽可能小但仍唯一"**。太大的 oldText 容易因为无关缩进/换行差异失配，
太小的 oldText 会命中多处。这条 guideline 是在教模型**怎么选锚点**。

## 三、真正来源 2：错误信息是"可自我修复的"（性价比最高的一环）

`core/tools/edit-diff.ts` 里四类失败，每条都告诉模型**下一步该怎么办**：

```ts
// 找不到
`Could not find the exact text in ${path}. The old text must match exactly
 including all whitespace and newlines.`

// 命中多处
`Found ${occurrences} occurrences of the text in ${path}. The text must be unique.
 Please provide more context to make it unique.`

// 编辑区间重叠
`edits[${prev}] and edits[${cur}] overlap in ${path}.
 Merge them into one edit or target disjoint regions.`

// 替换后内容没变
`No changes made to ${path}. The replacement produced identical content.
 This might indicate an issue with special characters or the text not existing as expected.`
```

**对比一下常见的糟糕做法：** `Edit failed.` / `500 Internal Error` — 模型拿到这种信息只能瞎猜重试，
浪费 token 并且可能越改越乱。

**这四条错误信息构成了 agent 的自我纠错语料。** 你的平台如果想提升修复成功率，
**优化工具的错误可读性比换更强的模型更划算** —— 这句话面试可以直接讲。

## 四、真正来源 3：一层容错归一化（模型不可能完美复现字符）

模型输出的 `oldText` 几乎必然和文件有细微差异。pi 的处理（`edit-diff.ts`）：

### 1. 匹配前先归一化（`normalizeForFuzzyMatch`）

按顺序做：

- `NFKC` 归一化
- 逐行去掉行尾空白
- 智能单引号 `‘’‚‛` → `'`，智能双引号 `“”„‟` → `"`
- 各种 Unicode 连字符 `‐‑‒–—―−` → `-`
- 各种特殊空格 `U+00A0 / U+2002–U+200A / U+202F / U+205F / U+3000` → 普通空格

### 2. BOM 剥离

```ts
// Strip BOM before matching. The model will not include an invisible BOM in oldText.
const { bom, text: content } = splitBom(rawContent);
```

### 3. 换行归一化后再恢复

```ts
const originalEnding = detectLineEnding(content);
const normalizedContent = normalizeToLF(content);       // 匹配用 LF
const finalContent = bom + restoreLineEndings(newContent, originalEnding);  // 写回保持 CRLF
```

### 4. fuzzy 命中后只覆盖变更行

```ts
const newContent = usedFuzzyMatch
  ? applyReplacementsPreservingUnchangedLines(normalizedContent, replacementBaseContent, matchedEdits)
  : applyReplacements(replacementBaseContent, matchedEdits);
```

**未变更的行保留原始字节** —— 否则一次模糊匹配就会把整个文件的引号/空格"顺手改掉"，
产生巨大的假 diff。

> 这一节是"工程细节决定成败"的最佳例子。**真正让 agent 改得好的，是这些看起来不性感的
> 字符串处理。**

## 五、真正来源 4：并发与输出治理

### 1. 同一文件的变更串行化

```ts
return withFileMutationQueue(absolutePath, async () => { ... });
```

并且有个很硬的注释（`edit.ts` 第 164–167 行）：

```
// Do not reject from an abort event listener here: that would release the
// mutation queue while an in-flight filesystem operation may still finish.
// Checking signal.aborted after each await observes the same aborts while
// keeping the queue locked until the current operation has settled.
```

**取消语义与锁语义的交互**：如果在中止事件里直接 reject，就可能在文件操作还在写的时候
释放队列锁，另一个编辑立刻进来 → 文件损坏。所以改成"每个 await 之后检查 `aborted`"，
锁一直持有到当前操作落定。

**这正是 ForgePilot 第③条亮点（取消后收敛）必须处理的同类问题**，面试可以直接引用。

### 2. 输出截断（上下文的守门员）

| 位置 | 上限 | 超限行为 |
| --- | --- | --- |
| `read` | `DEFAULT_MAX_LINES = 2000` 行 / `DEFAULT_MAX_BYTES = 50 * 1024` | 加提示 `Use offset=${nextOffset} to continue.`；单行就超限时直接给兜底命令 `sed -n 'Np' file \| head -c 51200` |
| `bash` | 1 MiB | 保留首尾各 512 KiB，中间用省略标记 |

注意两者的差别：**read 的截断是"可续读"的**（告诉模型怎么接着读），
**bash 的截断是"保头保尾"的**（错误通常在尾部）。这是按工具语义分别设计的，不是一刀切。

## 六、真正来源 5（最关键）：`bash` = 验证闭环

**这是"够不够"这个问题的正面回答。**

| 腿 | 工具 | 提供什么 |
| --- | --- | --- |
| 改 | `read` / `edit` / `write` | 局部、可验证、原子的代码变更 |
| **验** | **`bash`** | **跑测试、构建、lint、复现脚本 —— 唯一的客观反馈** |

模型内部无法判断"我改对了没有"。**`bash` 把判断权交给了编译器、测试框架和程序本身。**

于是 agent loop 变成：

```
读代码 → 提出假设 → edit → bash 跑测试 → 看失败信息 → 修正假设 → 再 edit → 再跑
```

**这就是 "coding agent" 和 "一次性代码生成" 的本质区别。**
所以：
- **不是"只有几个工具够不够"的问题**，而是"有没有 `bash` 这个反馈通道"的问题
- 有 `bash` + `edit`，模型可以自己把测试从红变绿
- 没有 `bash`，再强的模型也只是盲写

### 对"工具数量"的正确理解

`grep / find / ls` 在 pi 里是**可选优化品**，不是必需品。看 `buildRules` 的逻辑
（`system-prompt.ts`）：

```ts
if ((hasBash || hasPowerShell) && !hasGrep && !hasFind && !hasLs) {
  addRule("Use bash for file operations like ls, rg, find");
}
```

**只给 `bash` 时，pi 会主动教模型"用 bash 做文件搜索"。** 也就是说
**官方设计就把 `bash` 当成文件操作的通用后备**，`grep/find/ls` 只是让常见操作更省 token、
更安全（不用拼 shell 命令）的便利品。

## 七、上下文侧也参与"改得好"

`docs/compaction.md` 的 Cut Point Rules 原文：

```
Valid cut points are:
- User messages
- Assistant messages
- BashExecution messages
- Custom messages

Never cut at tool results (they must stay with their tool call).
```

**绝不从 tool result 处切分** —— 否则模型会看到一个"没有来源的工具结果"，
或者一个"没有结果的工具调用"，上下文逻辑直接断裂。

另外 `buildRules()` 会**按当前启用的工具动态生成规则**：只装了 read 和 edit 时，不会教它
"用 bash 搜文件"；装了 powershell 就教 powershell。**提示词是装配出来的，不是写死的。**

## 八、回到 ForgePilot：该学什么、该加什么

### 该学的（pi 已经做对的）

1. **精确字符串替换 + 唯一性 + 原子批处理** —— 你的 REPAIR 阶段的补丁应用应该同构
2. **可自我修复的错误信息** —— 成本最低、收益最高的一项，务必抄
3. **归一化层**（BOM / CRLF / NFKC / 智能引号 / 特殊空格）—— 处理中文注释、复制粘贴的代码片段时是刚需
4. **同一文件变更串行化 + 取消语义与锁的交互** —— 直接对上第③条亮点
5. **输出截断按工具语义分别设计**（read 可续读 / bash 保头保尾）

### 该加上的（pi 不会做，正是你的差异化）

| 你的机制 | 为什么 pi 不够 |
| --- | --- |
| **REPRODUCE 阶段：先让缺陷复现失败** | pi 只会一路把测试改绿。它分不清"修好了"和"测试本来就没覆盖到"。**你的平台必须先证明缺陷存在**，否则容易交出一个"改了个假 Bug"的 PR |
| **可信测试命令来自项目配置** | 不能让它自己写测试证明自己对（`docs/security.md` 的威胁模型里就有这条） |
| **VERIFY 绑定代码指纹** | pi 不校验"测的是不是要交的那一版代码" |
| **按阶段裁剪工具集** | PREPARE 阶段不该给 `edit`/`write` |
| **补丁作为制品入库** | pi 的 `details.patch` 直接给了 unified patch，入库即可做审计和回放 |
| **禁止删测试/改验证配置来"通过"** | 这是 agent 最常见的行为偏差，必须在平台侧硬拦 |

## 九、面试话术（约 45 秒）

> "pi 的编辑能力不是靠一个大提示词，它的默认 system prompt 只有十几行。
> 真正让它改得好的有三件事：
>
> 第一，`edit` 是精确字符串替换而不是行号 patch —— 要求 `oldText` 唯一、不重叠，
> 一批编辑全部对同一份原文匹配之后逆序应用，任一失败就整批不写，
> 所以不会产生半对半错的文件。
>
> 第二，它的错误信息是可自我修复的。找不到就告诉你'必须连空白和换行都完全一致'，
> 命中多处就告诉你'提供更多上下文让它唯一'，重叠就告诉你'合并成一个编辑'。
> 模型拿到这种错误能自己修，比拿到一个 500 有用得多。
>
> 第三，也是最关键的：真正让它改得好的是 `bash` —— 它能自己跑测试拿反馈再修。
> 所以 agent 和一次性代码生成的区别不在工具数量，在于有没有客观验证通道。
>
> 我在 ForgePilot 里的投入也不在造更多工具，而在让验证更快更可信：先复现让缺陷失败、
> 测试命令来自可信项目配置、验证结果绑定代码指纹、按阶段裁剪工具集。
> pi 自己只会把测试改绿，它分不清'修好了'和'测试没覆盖到'。"
