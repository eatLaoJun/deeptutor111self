# DeepTutor 三层记忆多时长介绍

> 使用边界：本文描述的是 DeepTutor Memory 的目标架构和设计演进，用于面试口述。
> 当前仓库正式实现仍是 Snapshot/Trace + L2/L3 Markdown，归并主要由 Workbench/API 触发；
> 下述关系库表结构、Flash 自动标注和定时任务尚未完整接入正式链路，不能全部说成已上线功能。
> `learning/demos/memory_hybrid_demo.py` 中的向量召回和版本链属于早期探索，不属于当前目标方案。

## 统一口径

### 两次版本迭代

```text
V1：对话记录 + 滚动用户总结
    保存当前会话历史，并维护一份长期总结
    实现简单，但总结缺少来源，短期现象容易被写成长期结论

V2：关系数据库中的三层记忆
    L1 原始事件与语义标签
      → L2 带 L1 来源引用的场景记忆
      → L3 基于新增 L2 更新的综合用户模型
```

Conversation History 与长期记忆需要分开。“刚刚这个是什么意思”由最近 10 轮原始对话解决；
当前 Session 的 L2 用来压缩本会话中更早的内容，L3 则提供跨会话仍然有价值的偏好、目标、
学习状态和稳定事实。

### 触发与数据流

一轮对话定义为“一条用户消息 + 对应的最终 Assistant 回复”，不包含 Agent 内部工具调用。

```text
每轮完成
  → 业务库同步保存用户消息、模型回复、工具调用和执行结果
  → 创建 L1 原始事件
  → 异步调用 Flash 模型生成 summary、tags、importance 等结构化标签

当前 Session 累计 10 个尚未进入 L2 的完整回合
  → 轻量模型按场景汇总新增 L1
  → 每条 L2 作为新记录追加到数据库
  → 通过关联表保存该 L2 使用的全部 L1 IDs

会话结束或连续 30 分钟没有新回合
  → 先将不足 10 轮的 L1 尾批生成 L2
  → 使用“当前 L3 + 新增 L2”增量更新 L3

每天凌晨 3 点
  → 扫描仍有未处理 L1/L2 的用户
  → 补偿 L2 尾批和 L3 更新任务
```

### L1：原始事件与 Flash 标签

L1 的原始事件先由代码落库，不能依赖模型调用是否成功：

```text
l1_event
- id
- user_id
- session_id
- turn_id
- scene
- event_type
- source_id
- raw_content 或业务数据引用
- created_at
```

随后通过阿里云百炼 Flash 模型的非思考模式和 JSON Schema 异步生成：

```json
{
  "summary": "用户近期因胃部不适不能吃辣",
  "tags": ["饮食", "健康约束"],
  "importance": 0.9,
  "memory_worthy": true
}
```

原始事件是审计证据，模型标签是派生标注。标注失败只记录 `annotation_status=pending` 并重试，
不影响对话回答和原始事件保存。模型 ID、Prompt 版本和标签结果需要一起记录，便于评测和重跑。

### L2：追加式场景记忆

L2 不负责维护复杂版本链，而是对当前 Session 中尚未处理的 L1 标签和原文按场景进行批量提炼。
默认累计 10 个完整回合执行一次；会话结束时处理不足 10 轮的尾批。每条新 L2 都追加到数据库：

```text
l2_memory
- id
- user_id
- session_id
- scene
- type
- content
- created_at

l2_l1_source
- l2_id
- l1_id
```

使用关联表是因为一条 L2 可能由多个 L1 支撑；同一条 L1 也可能被多个 L2 引用。例如一轮内容
同时包含“函数定义域容易出错”和“希望先给提示”两个信息，它可以分别支撑 Quiz 场景和 Chat
场景的 L2。这里不是复制 L1，而是让多个 L2 通过关联表引用同一条原始证据。服务端只做 JSON
Schema、用户归属和 L1 ID 存在性校验，不引入复杂的规则引擎和 `supersedes_id` 版本管理。

### L3：基于新增 L2 更新综合用户模型

L3 包含当前有效的用户偏好、学习目标、知识边界和稳定学习特点。增量更新不能只把新增 L2
交给模型，还要同时提供当前 L3：

```text
当前 L3 + 上次处理后新增的 L2
  → 较强模型归并
  → 新的当前 L3
```

通过 `last_processed_l2_id` 或独立处理记录保存游标，避免每次重新读取全部历史 L2。没有新增 L2
时不调用模型。L3 可以按槽位保存在关系库中，例如 `recent/profile/scope/preferences`。

### 运行时读取

每次对话都会从关系数据库读取三部分内容并组装进 `UnifiedContext`：

1. 按 `session_id` 读取最近 10 个完整回合的原始消息，写入 `conversation_history`。
2. 按 `session_id` 读取当前会话已经生成的全部 L2，与当前用户的 L3 一起组装进 `memory_context`。
3. Chat Prompt 组装时同时注入最近 10 轮、当前 Session L2 和当前用户 L3。
4. 需要追溯时，再通过 `l2_l1_source` 从 L2 回到原始 L1。

`Token Budget` 是整个模型请求的长度约束，不是只限制 L3。正常情况下三部分都会进入上下文；
如果极长 Session 导致接近模型窗口，应先压缩当前 Session L2 或 L3 的表达，同时为模型回答预留空间。
当前方案不需要 Qdrant，因为这三部分都能通过 `session_id` 或 `user_id` 精确读取。

只有未来单用户积累大量 L2、标签查询无法覆盖同义表达，并且召回评测证明 SQL 查询不足时，
才考虑增加 `pgvector` 或独立向量库。向量检索是可选的查询优化，不是三层记忆成立的前提。

## 3 分钟版

> DeepTutor 的长期记忆方案经历了两次设计迭代。第一版比较简单：关系数据库保存当前对话，
> 同时维护一份滚动用户总结。这个方案很快能实现跨回合个性化，但测试时暴露出两个问题。
> 第一，存储不等于召回，用户问“刚刚这个是什么意思”时，如果最近几轮没有稳定进入 Prompt，
> 系统仍然无法理解指代；所以当前 History 必须独立保留。第二，滚动总结会丢失来源，也容易把
> 一次答错写成长期能力问题。
>
> 第二版把长期记忆拆成 L1、L2 和 L3，并统一保存在关系数据库中。L1 是原始事件和语义标签层。
> 每个完整回合结束后，业务库先保存用户消息、模型回复、工具调用和执行结果，Memory 再创建
> L1 事件；后台异步调用阿里云 Flash 模型，通过 JSON Schema 生成摘要、标签和重要度。原始事件
> 是审计证据，模型标签只是派生结果，因此标注失败可以重试，不会影响正常回答。
>
> L2 是场景记忆层。普通情况下累计 10 个尚未处理的完整回合后，轻量模型读取新增 L1 标签和
> 原文，按 Chat、Quiz、Partner 等场景生成可复用的偏好、目标、约束和学习问题。每条 L2 都作为
> 新记录追加到数据库，并通过 `l2_l1_source` 关联所有来源 L1 IDs。用户不足 10 轮就结束会话时，
> 系统会先处理尾批，避免数据长期停留在 L1。
>
> L3 是综合用户模型。它在会话结束或用户空闲后执行，并由每天凌晨 3 点的任务兜底。更新时
> 不会重新读取全部 L2，而是把当前 L3 和上次处理后新增的 L2 一起交给较强模型，归并出用户偏好、
> 学习目标、知识边界和稳定学习特点；处理完成后更新 `last_processed_l2_id` 游标。
>
> 每次对话都会构造一份 `UnifiedContext`：从业务库读取当前 Session 最近 10 个完整回合的原始消息，
> 再读取当前 Session 已生成的 L2 和当前用户的 L3。最近 10 轮解决局部指代，L2 压缩本会话更早的
> 内容，L3 提供跨会话个性化。三部分都能按 session id 或 user id 精确查询，因此暂时不引入 Qdrant。

### 3 分钟记忆点

1. V1：对话记录 + 滚动总结，问题是召回未打通和总结不可追溯。
2. V2：L1 原始事件与标签、L2 场景记忆、L3 综合用户模型。
3. L1：每轮先保存原始事件，再由 Flash 异步生成结构化标签。
4. L2：默认每 10 轮执行，追加存储，并关联全部来源 L1 IDs。
5. L3：读取当前 L3 与新增 L2，结束/空闲触发，凌晨 3 点补偿。
6. 运行时：最近 10 轮原文 + 当前 Session L2 + 当前用户 L3。

## 5 分钟版

> DeepTutor 是一个面向学习场景的 Agent 平台。长期记忆最初采用两层方案：关系数据库保存
> 对话记录，另外维护一份滚动用户总结。这个版本实现成本低，但随着使用时间增加，两个问题
> 逐渐明显。一个是消息虽然已经存储，运行时如果没有稳定带上最近几轮，用户问“刚刚这个
> 是什么意思”仍然回答不了，所以 Conversation History 和长期记忆必须分开处理。另一个是
> 滚动总结没有来源引用，短期现象容易被归纳成长期特点，出现问题也无法定位原始对话。
>
> 第二版因此改成 L1、L2、L3 三层。这不是数据库冷热分层，而是信息从原始事件到场景记忆，
> 再到综合用户模型的逐级提炼。三层全部先使用关系数据库保存，保证链路简单且可以追溯。
>
> L1 在每个完整用户回合结束后产生。一轮指一条用户消息和对应的最终 Assistant 回复，不包含
> Agent 内部工具调用。业务库先保存消息、工具调用和执行结果，Memory 再记录 event id、user id、
> session id、scene、source id 和时间。随后后台异步调用阿里云 Flash 模型，使用非思考模式和
> JSON Schema 生成 summary、tags、importance 和 memory_worthy。模型调用失败时只把标注状态
> 设为 pending，不影响原始数据落库和用户回答。
>
> L2 是追加式场景记忆。默认当前 Session 累计 10 个尚未处理的完整回合后，轻量模型批量读取这些
> L1 标签和必要原文，按 Chat、Quiz、Partner 等场景提炼偏好、目标、约束和学习问题。模型输出
> 必须携带参与总结的 L1 IDs；服务端校验这些 ID 是否存在并属于当前用户，然后把每条 L2 作为
> 新记录追加到 `l2_memory`，再通过 `l2_l1_source` 关联来源。这里不维护复杂版本链，也不让
> 新总结覆盖历史 L2。一条 L2 可以由多个 L1 支撑；如果一轮原始内容同时包含学习薄弱点和回答
> 偏好，同一条 L1 就可以被 Quiz L2 和 Chat L2 分别引用。这里不是复制 L1，而是通过关联表让
> 多个 L2 指向同一条证据，因此来源关系使用多对多结构，而不是把 ID 列表塞进不可查询的字符串字段。
> 会话结束或连续 30 分钟没有新回合时，先处理不足 10 轮的尾批。
>
> L2 是异步任务，所以还要处理失败和重复执行。任务以 user id 和排序后的本批 L1 IDs 哈希组成幂等键；
> L2、来源关联和 L1 已处理标记在同一个数据库事务中提交。模型超时就保留原游标等待重试，
> 已经成功提交的批次再次投递时则直接跳过，避免生成重复 L2。
>
> L3 保存当前综合用户模型，包括近期状态、稳定偏好、学习目标、知识范围和学习特点。L3 更新
> 不能只看新增 L2，否则模型不知道原画像应该保留什么；正确输入是“当前 L3 + 新增 L2”。
> 较强模型完成归并后更新当前 L3，并记录 `last_processed_l2_id`。这样下一次只读取游标之后的
> L2，不需要重复扫描全部历史。会话结束或连续 30 分钟没有新回合时触发更新，每天凌晨 3 点扫描仍有
> 未处理数据的用户作为补偿；没有新增 L2 就不调用模型。执行时先确定本批最大的 L2 ID，模型
> 返回后再用事务同时写入新 L3 和推进游标。只要任一步失败，游标就不前进，补偿任务可以安全重试。
>
> 运行时每轮都会从关系库准备三部分数据：当前 Session 最近 10 个完整回合的原始消息、当前
> Session 已经生成的 L2，以及当前用户的 L3。它们分别写入 `UnifiedContext` 的
> `conversation_history` 和 `memory_context`，再由 Chat Prompt 统一组装。最近 10 轮负责精确指代，
> Session L2 负责压缩本会话更早的上下文，L3 负责跨会话的用户偏好和学习状态。
>
> 目前没有引入 Qdrant，因为当前查询主要是按 Session 读取最近 10 轮和 L2、按用户读取 L3、
> 按关联表追溯 L1，这些都是关系数据库擅长的精确查询。只有未来单个用户积累大量 L2，并且标签、场景
> 和时间过滤无法满足自然语言召回时，才会根据评测结果增加 pgvector 或独立向量索引。

### 5 分钟记忆点

1. 只有两次迭代：两层简单方案 → 关系库三层方案。
2. 最近 10 轮负责指代，Session L2 压缩早期上下文，L3 负责跨会话信息。
3. L1 每轮落原始证据，Flash 异步输出 JSON 标签。
4. L2 每 10 轮批量总结，追加存储，通过关联表引用 L1。
5. L3 使用当前 L3 + 新增 L2，通过游标增量更新。
6. 会话结束先处理 L2 尾批，凌晨 3 点补偿未完成任务。
7. 当前查询用关系数据库即可，Qdrant 只作为未来可选优化。

## 面试官可能怎么问

面试官通常不会继续让候选人完整复述三层，而是从“是不是实际做过、为什么这样拆、失败后怎么办、
效果怎么证明”四个方向验证方案。下面的回答都按目标架构口径组织；当前正式代码与目标方案的边界
必须如实说明。

### 一、架构边界

#### 这套三层记忆已经全部上线了吗？

> 不能说全部上线。DeepTutor 当前正式实现是 Snapshot/Trace 加 L2/L3 Markdown，目标方案是在此基础上
> 设计的关系库演进：L1 Flash 标注、十轮触发、处理游标和自动补偿还没有完整接入正式链路。

#### 为什么一定要拆成三层，两层不够吗？

> L1 保留不可丢失的原始证据，L2 把当前 Session 的一批事件提炼成可复用的场景结论，L3 保存跨会话
> 用户模型。运行时只读取最近 10 轮 L1 原文、当前 Session L2 和当前 L3，不会注入全部历史原文。

#### History、RAG 和 Memory 分别解决什么问题？

> 最近 10 轮 History 解决当前连续性和“刚刚这个”等指代；当前 Session L2 压缩更早的会话内容；
> L3 保存跨会话的偏好、目标和学习状态；RAG 则提供教材、笔记等外部知识。

#### 为什么 L1 已经有标签，L2 还要再总结一次？

> L1 标签只描述单个事件，主要用于筛选和定位；L2 要跨多轮判断哪些现象重复出现，并形成场景级
> 结论。例如一次答错只能是事件，多次同类错误才可能形成“端点判断不稳定”的 L2 记忆。

### 二、触发与模型

#### 为什么选择每 10 轮生成 L2，10 是怎么来的？

> 10 轮是单个 Session 内成本、实时性和样本量之间的初始工程参数，不是业务定理，也应该可配置。轮数太少容易
> 过度归纳且调用频繁，太多又会让记忆更新滞后；会话结束时处理尾批，避免短会话永远不进入 L2。
> 上线后应根据平均会话长度、延迟、单次 Token 和总结准确率调整阈值。

#### L1、L2、L3 分别用什么模型？

> L1 和 L2 都是结构化抽取任务，优先使用阿里云托管 Flash 轻量模型和 JSON Schema；L3 涉及旧画像
> 与新增事实的取舍，使用能力更强的模型。模型 ID 通过配置管理，不把具体型号写死在代码里。

#### L1 标注失败会不会阻塞 L2？

> 不阻塞用户回答，也不影响 L1 原始事件落库。标注先进入 pending 并异步重试；L2 到期执行时可对
> 少量仍未完成的事件读取必要原文作为降级输入，不能因为一个标注任务让整批数据永久卡住。

#### L3 为什么由会话结束和凌晨 3 点同时触发？

> 会话结束或连续 30 分钟没有新回合时触发，保证新记忆尽快可用；凌晨任务负责补偿进程重启、模型超时等原因留下的 pending
> 数据。凌晨任务不是全量重算，只扫描存在未处理 L1 或新增 L2 的用户。

### 三、数据设计与可靠性

#### 关系数据库最少需要哪些表？

> 核心表包括 `l1_event`、`l2_memory`、`l2_l1_source`、`l3_profile` 和处理任务或游标表。
> L1 标注可以放在 `l1_event` 的独立字段中，也可以拆成 `l1_annotation`。关键关系是 L2 到 L1 的
> 多对多来源关联，以及每个用户的 L1/L2 处理位置。

#### 为什么 `l2_l1_source` 要单独建关联表？

> 一条 L2 可能由多条 L1 支撑；同一条 L1 也可能被不同场景的 L2 共同引用。关联表可以做外键、
> 归属校验和反向追溯；如果把 ID 数组拼成字符串，后续查询、删除和一致性检查都会变复杂。

#### 模型返回一个不存在或属于其他用户的 L1 ID 怎么办？

> 模型只能引用本次输入中提供的候选 ID，服务端仍要校验 ID 存在、属于当前用户且位于本批输入集合。
> 校验失败则整批不提交，记录错误后重试，不能把模型输出直接当成可信数据库操作。

#### 定时任务和会话结束任务同时执行，怎么避免重复 L2？

> 使用 user id 加排序后的本批 L1 IDs 哈希生成幂等键，并对该任务做唯一约束或抢占。`l2_memory`、来源关联和
> 已处理标记在同一事务中提交；重复投递会命中已完成任务，不会再生成一份 L2。

#### L3 已经生成，但更新游标失败怎么办？

> 模型调用完成后，在同一数据库事务中写入新 L3 并把游标推进到本批最大 L2 ID。事务失败则两者都
> 不提交，补偿任务会使用相同输入重试。还可对 L3 加 revision 做条件更新，避免两个任务互相覆盖。

#### 用户纠正或删除原始信息时，派生记忆怎么处理？

> 先根据 L1 找到 `l2_l1_source` 中受影响的 L2，将其失效或重新生成，再用剩余有效 L2 刷新 L3。
> 用户要求删除时还要按关联关系清理派生数据。这里不需要先设计复杂版本链，但必须保留来源关系。

### 四、读取与效果

#### 运行时是不是把 L1、L2、L3 都放进 Prompt？

> 不是把三层全量注入，而是固定读取三个范围：当前 Session 最近 10 个完整回合的 L1 原文、当前
> Session 已生成的 L2、当前用户的 L3。三部分先进入 `UnifiedContext`，再组装到 Prompt；更早的 L1
> 原文不会进入。Token Budget 约束的是整个请求，不是只限制 L3。

#### L3 越写越长怎么办？

> L3 应是有长度上限的结构化当前状态，不是历史日志。recent 设置时效和条数上限，profile、scope、
> preferences 做去重归并；超过预算时重新压缩，而完整历史仍保留在 L1/L2 中。

#### 怎么证明三层方案真的比第一版好？

> 分层评测：L1 看 JSON 合法率和关键信息漏标率，L2 看来源引用正确率、总结准确率和重复处理率，
> L3 看新增信息覆盖率与过度归纳率。端到端用固定对话集比较 V1/V2 的个性化回答准确率、可追溯率、
> 平均 Token 和更新成本，不能只说“感觉回答更准”。

### 五、技术选型

#### 为什么暂时不用 Qdrant？以后什么情况下会用？

> 当前是按 session id 读取最近 10 轮和当前 L2、按 user id 读取 L3、按关联表追溯 L1，都是关系数据库的精确查询。
> 当单用户 L2 大量增长，并且场景、标签和时间过滤的召回评测无法覆盖同义表达时，再增加 pgvector
> 或独立向量索引。向量检索只优化查找，不能代替 L1 到 L3 的提炼与来源关系。

#### 为什么不用 Redis 或 MongoDB？

> Redis 更适合缓存和短期状态，不适合作为这条可审计链路的唯一事实库；MongoDB 可以保存文档，
> 但当前最关键的是事务、唯一约束、游标和多对多追溯，关系数据库实现更直接。是否加缓存应由延迟
> 和 QPS 决定，而不是为了凑技术栈。

#### 为什么不做复杂版本管理？

> 当前先通过追加存储、来源关联、失效状态和可重跑保证基本纠错能力。只有实际冲突率和状态变化已经
> 明显影响回答时，才值得增加 supersedes 之类的版本链，避免在没有数据支撑时扩大系统复杂度。

## 练习建议

1. 开场明确只有两次迭代，不再讲 Qdrant 第三版。
2. 不要把“刚刚这个”归因于长期记忆，要说它由最近 History 解决。
3. 稳定说清“L1 每轮、L2 十轮、L3 结束/空闲与凌晨 3 点补偿”。
4. 强调每条 L2 都有 L1 来源关联，L3 输入是当前画像加新增 L2。
5. 当前目标方案仍未完整接入正式代码，面试时不要把设计全部说成生产事实。
