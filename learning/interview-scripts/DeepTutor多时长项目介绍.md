## 15 秒版本

> 我参与了 DeepTutor 智能学习平台的开发，主要涉及 Agent 多轮对话、长期记忆、
> 工具调度和 Skill 按需加载，让模型能够结合用户上下文调用工具并持续完成学习任务。

适用场景：自我介绍中快速带过项目，等待面试官选择感兴趣的方向追问。

## 30 秒版本

> DeepTutor 是一个面向智能学习场景的 Agent 平台，支持普通对话、知识检索、深度
> 解题和研究等能力。我参与的重点是 Agent 核心运行链路，包括统一组装当前消息、
> 历史记录和记忆，根据用户请求选择对应能力，再通过 Function Calling 让模型与工具
> 进行多轮协作，并把执行过程和最终结果流式返回给前端。

适用场景：面试官说“简单介绍一下这个项目”。

## 60 秒版本

> DeepTutor 是一个面向智能学习场景的 Agent-Native 平台，同时支持命令行、Web 和
> Python SDK。它把扩展能力分成两类：一类是由模型按需调用的单次工具，例如知识检索、
> 搜索和深度推理；另一类是可以接管整个回合的多阶段能力，例如深度解题和研究。
>
> 我参与的工作主要包括多轮对话、三层长期记忆、工具调度和 Skill 加载。一次对话会先
> 统一整理当前问题、历史消息、记忆和可用工具，再选择对应能力。模型返回工具调用后，
> 系统执行工具并把结果放回上下文，让模型继续下一轮，直到生成最终回答，整个过程通过
> WebSocket 流式返回。同时通过最大轮次、工具异常回填和上下文折叠，避免长任务无限循环
> 或上下文持续膨胀。

适用场景：技术面试开场，完整交代项目架构和自己的主要工作。

## 90 秒版本

> DeepTutor 是一个面向智能学习场景的 Agent-Native 平台，统一支持命令行、WebSocket
> API 和 Python SDK。项目采用 Tool 与 Capability 两层扩展模型：Tool 是模型按需调用的
> 单次能力，例如知识检索、搜索和推理；Capability 是能够接管整个回合的多阶段任务，
> 例如深度解题、深度研究和可视化。
>
> 我参与的第一部分是多轮对话核心链路。系统会把当前消息、历史记录、长期记忆、附件和
> 可用工具整理成统一上下文，再根据用户选择路由到对应能力。模型通过 Function Calling
> 发起工具调用，系统执行工具后把结果按协议回填，下一轮模型继续基于结果回答，过程事件
> 则实时推送给前端。
>
> 第二部分是长期记忆。项目将记忆分为三层：第一层保留原始交互事件，第二层按对话、
> 知识库等场景形成带来源的结构化总结，第三层再聚合成跨会话的用户画像、近期状态和偏好，
> 并按需注入新对话。
>
> 此外我还参与了 Tool 和 Skill 的集成。Skill 默认只向模型提供名称和简介，匹配任务后
> 才读取完整内容，减少无关上下文占用；运行时则通过轮次限制、工具失败降级、上下文折叠
> 和 TRACE 日志提高稳定性与可观测性。

适用场景：面试官明确要求“详细介绍一下项目和你的职责”。

## 3 分钟版本

> DeepTutor 是一个面向智能学习场景的 Agent-Native 平台。它解决的核心问题不是简单地
> 调用一次大模型，而是让模型能够结合历史、长期记忆、知识库和外部工具，持续完成解题、
> 研究和内容生成等复杂任务。项目支持命令行、WebSocket API 和 Python SDK，不同入口
> 最终进入同一套运行链路。
>
> 项目把扩展能力分为 Tool 和 Capability 两层。Tool 是搜索、知识检索和推理等单次调用；
> Capability 负责深度解题、研究和可视化等完整任务。这样普通对话可以按需使用工具，复杂
> 任务也可以拥有独立的多阶段流程。
>
> 我参与的第一部分是多轮对话核心链路。请求进入后，系统先加载历史消息、长期记忆、附件、
> Skill 和可用工具，形成当前回合的统一上下文，再根据请求选择具体能力。进入 Chat 后，
> 模型运行在多轮循环中：直接返回正文时结束本回合；返回工具调用时，系统执行工具并按照
> Function Calling 协议回填结果，再让模型继续下一轮。思考过程、工具状态和最终内容会作为
> 不同事件流式返回，前端可以分别展示执行进度和最终答案。
>
> 第二部分是长期记忆。我们没有把全部历史永久塞进 Prompt，而是采用三层结构：第一层保留
> 原始事件，第二层按对话、Notebook 和知识库等场景生成带来源的结构化总结，第三层再聚合
> 成用户画像、近期状态和长期偏好。新对话只按需读取相关记忆，从而兼顾个性化、Token 成本
> 和可追溯性。
>
> 第三部分是 Tool 和 Skill。Tool 会转换成模型能够理解的 Function Schema，模型给出调用
> 名称和参数后由统一调度层执行，结果再回填给下一轮模型。Skill 默认只提供名称和简介，
> 匹配任务后才读取完整内容，避免把所有说明一次性加入上下文。
>
> 稳定性方面，系统通过最大轮次、强制收尾、上下文折叠和工具异常回填避免长任务失控。
> 我还参与补充了 Agent 主链和公共工具入口的 TRACE 日志，并对 Token、Cookie、API Key
> 等敏感参数脱敏，方便定位一次请求在哪个环节出现问题。这些工作让我完整实践了 Agent
> 的上下文管理、能力路由、Function Calling、长期记忆、流式事件和运行时稳定性。

适用场景：项目深挖，或者面试官给出两到三分钟完整介绍时间。

## 第一条职责的 30 秒专项版

> 我参与了 Agent 多轮对话核心链路的建设。一次请求进入系统后，会先组装当前消息、历史
> 对话、记忆和可用工具，再根据请求选择相应能力。进入 Chat 后，模型通过 Function Calling
> 决定是否调用工具；工具结果会回填给下一轮模型，直到得到最终答案，过程和结果则通过
> 事件流实时返回前端。

## 第一条职责的 60 秒专项版

> 多轮对话链路主要解决三个问题：不同入口的数据如何统一、模型和工具如何持续协作，以及
> 执行过程如何实时返回。请求进入后，运行时先加载历史、记忆、附件和可用工具，组装当前
> 回合上下文；随后根据用户选择路由到对应能力。Chat 内部维护一份持续增长的消息列表，
> 每轮调用模型后，如果没有工具请求就把正文作为最终答案；如果存在工具请求，就执行工具、
> 回填结果并继续下一轮。与此同时，思考、工具调用、执行结果和最终回答会被包装成不同事件
> 流式推送给前端。为了防止异常循环，还增加了最大轮次、工具失败降级和强制收尾机制。

## 第一条职责的 5 分钟专项版：Agent Runtime

> 我在 DeepTutor 项目中主要参与了 Agent Runtime 核心链路的建设。这里的 Agent Runtime，
> 可以理解为位于大模型和业务能力之间的一层执行引擎。它解决的不是“怎么调用一次大模型”，
> 而是模型如何在一个用户回合中持续决策、调用工具、观察结果、处理异常，并最终稳定地完成任务。
>
> 之所以需要这层 Runtime，是因为复杂任务通常无法通过一次 LLM 请求完成。比如用户要求分析
> 一份资料并验证其中的计算结果，模型可能需要先读取资料，再检索知识库，然后执行代码，最后
> 根据所有结果组织答案。如果这些步骤都写成固定流程，扩展性会比较差；如果完全交给模型，
> 又容易出现重复调用、无限循环或者异常后无法收尾。因此我们的设计是：模型负责做决策，
> Runtime 负责执行和约束。
>
> 整个执行链路从 `UnifiedContext` 开始。不同入口提交的请求，会先被整理成统一上下文，其中
> 包含当前问题、近期对话、记忆上下文、知识库、附件、用户启用的工具以及当前 Capability 等
> 信息。之后由 `ChatOrchestrator` 选择本轮要执行的 Capability，再进入对应的 Agent Loop。
> 这样 CLI、WebSocket 和 Python SDK 可以复用同一套执行逻辑。
>
> 这里需要区分两层上下文。`UnifiedContext` 是回合级输入，负责把进入 Runtime 的信息统一起来；
> Agent Loop 内部的 `messages` 则是本轮不断变化的工作上下文。Loop 启动时，会根据
> `UnifiedContext` 组装 system prompt、历史消息和当前用户问题。如果挂载了知识库或附件，
> 还会把预检索结果和资料分析摘要加入当前消息。
>
> 进入循环以后，每一轮都是一次 LLM 调用。模型可以直接回答，也可以通过原生 Tool Calling
> 返回一个或多个工具调用。如果这一轮没有 Tool Call，那么 Runtime 就认为模型已经完成任务，
> 本轮文本直接作为最终答案；如果产生了 Tool Call，Runtime 会保存这一轮的 assistant 消息，
> 执行工具，再把结果转换成标准的 `role=tool` 消息追加回 `messages`，然后进入下一轮模型调用。
>
> 因此整个过程形成了“模型决策、工具执行、结果观察、再次决策、最终回答”的闭环。例如用户
> 让 Agent 调研一个技术方案，第一轮模型可能同时调用知识库检索和 Web Search；第二轮读取这些
> 工具结果后，发现还需要验证某段代码，于是调用 Code Execution；第三轮材料已经充分，模型
> 停止调用工具并输出最终结论。这个过程不是提前写死的 Pipeline，而是模型根据每一步的观察
> 结果动态决定下一步。
>
> Tool Runtime 是其中比较重要的一部分。所有工具都通过 `ToolRegistry` 注册，并统一实现
> `BaseTool` 协议。模型看到的只是工具名称、描述和参数 Schema，真正的工具实现始终运行在
> 服务端。执行时，Runtime 会解析模型给出的 JSON 参数，并注入一些模型不应该控制的服务端
> 参数，例如用户身份、沙箱目录、知识库名称范围和任务工作区。
>
> 如果模型在一轮中调用多个工具，Runtime 会使用 `asyncio.gather` 并发执行，单批最多处理
> 8 个工具。这里使用的是单事件循环上的协作式 I/O 并发，不是简单创建 8 个线程。工具在等待
> 网络、数据库或异步子进程时会让出控制权，事件循环可以继续推进其他工具。如果某个工具内部
> 是同步阻塞操作，则需要通过 `asyncio.to_thread` 或外部进程执行，否则仍然会阻塞事件循环。
>
> 在错误隔离方面，单个工具执行失败不会直接导致整批任务失败。Tool Runtime 会捕获异常，
> 将其转换成 `success=False` 的标准 `ToolResult`，再作为 `role=tool` 消息返回给模型。同批
> 其他工具仍然可以正常完成。下一轮模型看到错误结果后，可以选择重试、更换工具，或者使用
> 已有信息继续回答。这体现了 Tool Runtime 和 Agent Runtime 的边界：Tool Runtime 负责把
> 工具执行结果可靠地交付出来，Agent Runtime 负责根据结果决定后续策略。
>
> 上下文规模也是 Runtime 需要处理的问题。因为每轮都会追加 assistant Tool Call 和 Tool
> Result，长任务的 `messages` 会持续增长。我们一方面通过 Context Window Guard 裁剪较早的
> 大段工具结果；另一方面，某些分步任务可以通过 Context Checkpoint，把已经完成的中间过程
> 折叠成简短摘要。这样既保留关键结论，又避免原始工具输出不断占用模型窗口。
>
> 最后是任务收敛和异常恢复。正常情况下，“模型不再调用工具”就是结束条件。为了避免模型不断
> 调用工具，我们设置了最大执行轮次；达到上限后，Runtime 会禁用工具并追加停止探索的指令，
> 通过 Forced Finish 强制模型基于已有材料生成答案。如果模型中途调用失败，但前面已经收集了
> 一些工具结果，Runtime 也会尝试走 Forced Finish，而不是直接丢失整轮工作。对于空响应，
> 还会额外提示模型继续执行；对于 `ask_user`，Runtime 可以暂停当前回合，等待用户补充信息后
> 继续同一个 Agent Loop。
>
> 在我看来，这套 Agent Runtime 最核心的价值，是把模型的智能决策和系统的确定性控制分开：
> 模型决定“下一步做什么”，Runtime 保证“这一步能够被安全执行、结果能够回填、异常能够隔离、
> 任务最终能够结束”。在这个基础上，Chat、Deep Solve 和 Mastery 等场景可以复用相同的执行
> 链路，只需要增加自己的提示词、工具和状态约束，而不需要为每个场景重新实现一套 Agent 循环。

速记主线：

> `UnifiedContext` 统一输入，Agent Loop 驱动决策，Tool Runtime 执行动作，Context 管理
> 控制规模，Forced Finish 保证收敛。

## 练习方式

1. 先熟练 30 秒版本，不要逐字背诵，只记“项目是什么、我负责什么、怎么实现”。
2. 再练 90 秒版本，确保多轮对话、长期记忆、Tool/Skill 三部分都能自然展开。
3. 最后练 3 分钟版本，并分别准备多轮对话、Tool 调度和三层记忆的追问。
4. 每次录音后只检查三件事：是否超时、是否堆名词、是否把团队成果说成个人原创。
