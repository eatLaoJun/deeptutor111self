# DeepTutor 多时长项目介绍

> 使用原则：短版本讲“项目、职责、价值”，长版本再讲技术机制。不要主动堆内部类名；
> 面试官追问实现时，再用具体代码对象证明自己确实理解。
>
> 时长按每分钟约 280～320 个中文字符的自然面试语速估算，实际录音允许上下浮动 10 秒。

## 简历中的一句话

> 参与 Agent 多轮对话核心链路建设，完成会话上下文组装、能力模块路由，并基于
> LLM Function Calling 实现模型与工具的多轮协同调用及对话结果流式返回。

## 15 秒版本

> 我参与了 DeepTutor 智能学习平台的开发，主要涉及 Agent 多轮对话、长期记忆、
> 工具调度和 Skill 按需加载，让模型能够结合用户上下文调用工具并持续完成学习任务。

适用场景：自我介绍中快速带过项目，等待面试官选择感兴趣的方向追问。

## 30 秒版本

> DeepTutor 是一个面向智能学习场景的 Agent 平台，支持普通对话、知识检索、深度
> 解题和研究等能力。我参与的重点是 Agent 核心运行链路，包括统一组装当前消息、
> 历史记录和记忆，根据用户请求选择对应能力，再通过 Function Calling 让模型与工具
> 进行多轮协作，并把执行过程和最终结果流式返回给前端。

适用场景：面试官说“简单介绍一下这个项目”。

## 60 秒版本

> DeepTutor 是一个面向智能学习场景的 Agent-Native 平台，同时支持命令行、Web 和
> Python SDK。它把扩展能力分成两类：一类是由模型按需调用的单次工具，例如知识检索、
> 搜索和深度推理；另一类是可以接管整个回合的多阶段能力，例如深度解题和研究。
>
> 我参与的工作主要包括多轮对话、三层长期记忆、工具调度和 Skill 加载。一次对话会先
> 统一整理当前问题、历史消息、记忆和可用工具，再选择对应能力。模型返回工具调用后，
> 系统执行工具并把结果放回上下文，让模型继续下一轮，直到生成最终回答，整个过程通过
> WebSocket 流式返回。同时通过最大轮次、工具异常回填和上下文折叠，避免长任务无限循环
> 或上下文持续膨胀。

适用场景：技术面试开场，完整交代项目架构和自己的主要工作。

## 90 秒版本

> DeepTutor 是一个面向智能学习场景的 Agent-Native 平台，统一支持命令行、WebSocket
> API 和 Python SDK。项目采用 Tool 与 Capability 两层扩展模型：Tool 是模型按需调用的
> 单次能力，例如知识检索、搜索和推理；Capability 是能够接管整个回合的多阶段任务，
> 例如深度解题、深度研究和可视化。
>
> 我参与的第一部分是多轮对话核心链路。系统会把当前消息、历史记录、长期记忆、附件和
> 可用工具整理成统一上下文，再根据用户选择路由到对应能力。模型通过 Function Calling
> 发起工具调用，系统执行工具后把结果按协议回填，下一轮模型继续基于结果回答，过程事件
> 则实时推送给前端。
>
> 第二部分是长期记忆。项目将记忆分为三层：第一层保留原始交互事件，第二层按对话、
> 知识库等场景形成带来源的结构化总结，第三层再聚合成跨会话的用户画像、近期状态和偏好，
> 并按需注入新对话。
>
> 此外我还参与了 Tool 和 Skill 的集成。Skill 默认只向模型提供名称和简介，匹配任务后
> 才读取完整内容，减少无关上下文占用；运行时则通过轮次限制、工具失败降级、上下文折叠
> 和 TRACE 日志提高稳定性与可观测性。

适用场景：面试官明确要求“详细介绍一下项目和你的职责”。

## 3 分钟版本

> DeepTutor 是一个面向智能学习场景的 Agent-Native 平台。它解决的核心问题不是简单地
> 调用一次大模型，而是让模型能够结合历史、长期记忆、知识库和外部工具，持续完成解题、
> 研究和内容生成等复杂任务。项目支持命令行、WebSocket API 和 Python SDK，不同入口
> 最终进入同一套运行链路。
>
> 项目把扩展能力分为 Tool 和 Capability 两层。Tool 是搜索、知识检索和推理等单次调用；
> Capability 负责深度解题、研究和可视化等完整任务。这样普通对话可以按需使用工具，复杂
> 任务也可以拥有独立的多阶段流程。
>
> 我参与的第一部分是多轮对话核心链路。请求进入后，系统先加载历史消息、长期记忆、附件、
> Skill 和可用工具，形成当前回合的统一上下文，再根据请求选择具体能力。进入 Chat 后，
> 模型运行在多轮循环中：直接返回正文时结束本回合；返回工具调用时，系统执行工具并按照
> Function Calling 协议回填结果，再让模型继续下一轮。思考过程、工具状态和最终内容会作为
> 不同事件流式返回，前端可以分别展示执行进度和最终答案。
>
> 第二部分是长期记忆。我们没有把全部历史永久塞进 Prompt，而是采用三层结构：第一层保留
> 原始事件，第二层按对话、Notebook 和知识库等场景生成带来源的结构化总结，第三层再聚合
> 成用户画像、近期状态和长期偏好。新对话只按需读取相关记忆，从而兼顾个性化、Token 成本
> 和可追溯性。
>
> 第三部分是 Tool 和 Skill。Tool 会转换成模型能够理解的 Function Schema，模型给出调用
> 名称和参数后由统一调度层执行，结果再回填给下一轮模型。Skill 默认只提供名称和简介，
> 匹配任务后才读取完整内容，避免把所有说明一次性加入上下文。
>
> 稳定性方面，系统通过最大轮次、强制收尾、上下文折叠和工具异常回填避免长任务失控。
> 我还参与补充了 Agent 主链和公共工具入口的 TRACE 日志，并对 Token、Cookie、API Key
> 等敏感参数脱敏，方便定位一次请求在哪个环节出现问题。这些工作让我完整实践了 Agent
> 的上下文管理、能力路由、Function Calling、长期记忆、流式事件和运行时稳定性。

适用场景：项目深挖，或者面试官给出两到三分钟完整介绍时间。

## 第一条职责的 30 秒专项版

> 我参与了 Agent 多轮对话核心链路的建设。一次请求进入系统后，会先组装当前消息、历史
> 对话、记忆和可用工具，再根据请求选择相应能力。进入 Chat 后，模型通过 Function Calling
> 决定是否调用工具；工具结果会回填给下一轮模型，直到得到最终答案，过程和结果则通过
> 事件流实时返回前端。

## 第一条职责的 60 秒专项版

> 多轮对话链路主要解决三个问题：不同入口的数据如何统一、模型和工具如何持续协作，以及
> 执行过程如何实时返回。请求进入后，运行时先加载历史、记忆、附件和可用工具，组装当前
> 回合上下文；随后根据用户选择路由到对应能力。Chat 内部维护一份持续增长的消息列表，
> 每轮调用模型后，如果没有工具请求就把正文作为最终答案；如果存在工具请求，就执行工具、
> 回填结果并继续下一轮。与此同时，思考、工具调用、执行结果和最终回答会被包装成不同事件
> 流式推送给前端。为了防止异常循环，还增加了最大轮次、工具失败降级和强制收尾机制。

## 被追问代码时再使用的名称

不要在开场全部念出来，只在面试官追问对应环节时说明：

| 通俗描述 | 代码证据 |
| --- | --- |
| 统一的回合上下文 | `UnifiedContext` |
| 能力模块路由 | `ChatOrchestrator`、`CapabilityRegistry` |
| Chat 执行准备 | `AgenticChatPipeline` |
| LLM 与工具多轮循环 | `AgentLoop` |
| 工具统一执行与回填 | `tool_dispatch.py` |
| 流式事件通道 | `StreamBus` |

## 练习方式

1. 先熟练 30 秒版本，不要逐字背诵，只记“项目是什么、我负责什么、怎么实现”。
2. 再练 90 秒版本，确保多轮对话、长期记忆、Tool/Skill 三部分都能自然展开。
3. 最后练 3 分钟版本，并分别准备多轮对话、Tool 调度和三层记忆的追问。
4. 每次录音后只检查三件事：是否超时、是否堆名词、是否把团队成果说成个人原创。
