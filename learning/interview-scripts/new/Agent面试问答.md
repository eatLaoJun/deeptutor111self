## 1. Agent 死循环怎么熔断？海量用户并发下怎么实现？不能用内存存状态怎么办？

### 两分钟面试口述

我会把这个问题分成单任务保护和服务级熔断两层。

在知识点学习 Agent 的设计里，外层工作流管理诊断、讲解、练习和补救，内层 Agent Loop
负责当前阶段的模型决策和工具调用。这两层都可能出现循环。

内层可能反复检索相同内容，所以我会设置最大执行步数、单次调用超时、整体 deadline
和费用预算，同时检测重复调用且没有新增证据的情况。外层则限制补救次数，不能因为学生
一直没学会，就无限重复讲解和出题。整个学习任务还有总预算，不能每进入一个阶段就重置。

这些限制由程序在模型和工具调用前检查，不依赖模型自己判断是否停止。触发后禁止新调用，
尝试取消在途执行，保存已有结果并给出明确反馈。例如总结学生已经掌握的内容和仍需巩固的
知识点，而不是硬说学习成功。如果预算已经耗尽，就用已有结果或模板收尾，不再额外调用模型。

海量并发下，我会在入口增加用户级限流、并发限制和有界队列。如果是题库或模型服务持续失败，
则对这个依赖做服务级熔断，冷却后只允许少量探测请求，避免影响扩大。

多实例下，控制状态不能只存在本机内存。我会把任务状态、剩余预算和取消标记放到 Redis
或数据库，每次执行前原子检查并预留额度，避免多个 worker 同时超额执行。恢复时沿用原任务
预算，并通过版本控制和业务幂等，避免重复出题或重复记分。

核心就是：单任务有界执行，故障依赖隔离，多实例共享一致的控制状态。

### 追问要点

- 最大轮数不等于最大工具调用数，一轮可能包含多个工具调用；内部重试也应计入预算。
- 重复调用不一定是死循环，正常轮询需要结合工具类型、结果变化和业务进度判断。
- 不能使用本机内存，不等于不能使用 Redis；如果外部内存型存储也不允许，可以采用数据库条件更新和事务。
- 预算检查与预留必须原子执行，不能先检查、执行后才扣减。
- 数据库事务只覆盖状态操作，不跨越耗时的模型请求。
- 状态存储不可用时，对昂贵操作应暂停或拒绝，不能默认预算无限。

## 2. 熔断是不是直接暂停，然后进行兜底回答？

基本方向对，但更准确的说法是：停止继续消耗资源，再按原因降级或结束。

| 概念 | 含义 |
| --- | --- |
| 暂停 | 保存等待点，之后可以恢复，例如等待学生回答 |
| 死循环保护 | 终止当前异常执行，不能恢复后又原样继续循环 |
| 服务熔断 | 暂时不再请求故障依赖，冷却后少量探测恢复 |
| 兜底回答 | 停止之后的一种处理方式，不是熔断本身 |

服务熔断器的状态是 Closed（正常放行）、Open（快速拒绝）、Half-Open（少量探测）。
单个学生的任务循环异常，不应直接熔断所有用户共享的模型服务。

只把数据库状态改成停止，不代表在其他机器执行的任务已经停止。需要持久化取消标记、
通知执行节点，并在调用边界检查；在途请求还需要超时和取消机制。

## 3. 用户级限流、并发限制和有界队列怎么做？用 Python 队列还是 Celery？

不是二选一，它们解决不同问题。

| 控制 | 解决的问题 | 可选实现 |
| --- | --- | --- |
| 用户级限流 | 每个用户单位时间能启动多少请求 | Redis 令牌桶，原子检查和扣减 |
| 并发限制 | 同时允许多少个任务或模型调用执行 | 本地 Semaphore、共享执行配额 |
| 有界队列 | 最多等待多少任务、等待多久 | 本地有界 Queue，或外置任务队列加准入控制 |
| 后台任务执行 | 任务如何投递、分发给 worker | Celery + Redis/RabbitMQ Broker |

适合本项目的补充方案：实时对话由异步服务执行；记忆提炼、画像更新、教材解析等后台任务
交给 Celery；共享准入控制由 Redis 或数据库实现。

`asyncio.Queue(maxsize=100)` 可以做单进程短时缓冲，但不跨实例共享，进程重启会丢失内容，
不能作为可恢复任务的唯一来源。队列满时使用 `put_nowait()` 拒绝，或设置入队等待期限；
无限等待 `put()` 会把积压转移到等待入队的请求上。

`asyncio.Semaphore(20)` 只限制本进程同时执行的数量，不限制等待协程数。
部署 4 个进程，各自限制 20，并不等于全局只允许 20。

Celery 的 worker 并发配置限制单个 worker 的执行池，任务 rate_limit 也不是天然的全局
用户限流。Celery 不会自动让队列有界：仍需投递前原子申请待处理容量，满了就拒绝或降级。
不能仅通过“查队列长度，再投递”控制容量，这两个操作之间存在并发竞争。

任务落库和投递之间可用 Outbox 处理漏投，重复投递则依靠业务幂等；预留容量需要失败释放和
异常对账。后台任务队列也不能代替学习工作流的业务状态库。

结合学习场景：等待学生回答时保存任务等待点并释放执行资源，收到回答再恢复，不能让一个
worker 一直占着执行名额等待学生。

面试收束：Redis 管能不能进，执行配额管能跑多少，队列管能等多少，Celery 管后台任务怎么分发执行。

## 4. 多实例共享执行名额怎么做？

可以理解为：在 Redis 中放一个所有实例共用的座位表。

假设某个模型全局最多发放 100 个有效执行名额：

1. 每个实际调用生成唯一调用 ID，调用前申请名额。
2. Lua 脚本原子清理过期名额、检查数量、有空位则登记。
3. 申请成功才调用模型；失败则短暂等待或返回繁忙，不能无限堆积。
4. 调用结束，在 `finally` 中按调用 ID 释放名额。
5. 名额附带租约，宕机后可回收；长调用定期续租，失去租约后停止继续执行并尝试取消。

一种实现是 ZSET：key 为 `slots:model-A`，member 为唯一调用 ID，score 为租约到期时间。
各节点应采用一致的时间基准，例如在脚本中使用 Redis 服务端时间，避免本机时钟偏差影响租约。

注意：租约过期只代表名额可回收，不代表旧的远程调用已经停止。因此它直接限制的是有效名额，
不是无条件保证真实远程并发永远不超过 100。严格保护还需结合调用超时、取消和执行端控制。

面试一句话：通过 Redis 实现分布式信号量，所有实例用 Lua 原子申请带租约的名额，完成释放，
宕机回收，长调用续租。

## 5. 最多 100 个模型调用，是 ZSET 能设置最多 100 个 key 吗？

不是。这里是 1 个 Redis key，里面最多允许登记 100 个 member。
ZSET 本身没有“最多 100 个成员”的容量设置，这个限制由应用的 Lua 脚本实现。

```text
Redis key: slots:model-A
  ZSET:
    call-001 -> 租约到期时间
    call-002 -> 租约到期时间
    ...最多登记 100 个有效调用
```

申请流程：

```text
ZREMRANGEBYSCORE：清理租约到期的成员
ZCARD：查询当前成员数量
如果数量 < 100：
    ZADD：登记本次调用 ID 和到期时间
    返回成功
否则：
    返回失败
```

这几个操作必须放在同一个 Lua 脚本中原子执行。否则两个实例都看到数量为 99，各加一个，
就会变成 101。所有调用必须经过这条准入路径，直接绕过脚本添加成员或调用模型会破坏限制。

生产实现还需处理同一次申请因网络超时而重试：若调用 ID 已存在，应识别已有预留，避免重复
扣名额；该 ID 必须绑定一次实际执行，不能被多个执行者共享后同时调用模型。

## 6. ZSET 的结构是什么样的？是 key-value 吗？

Redis 整体是 key-value 结构，ZSET 是其中一种 value 类型。

```text
key                         value（一个 ZSET）
slots:model-A  ------------> member         score
                            call-001       1750000030
                            call-002       1750000040
                            call-003       1750000050
```

- member：成员，必须唯一；这里存调用 ID。
- score：数值分数，可以重复；这里用作租约到期时间。
- ZSET 按 score 排序，因此适合按时间查找和清理过期名额。

示例命令（时间戳仅示意，实际应计算当前时间加租期）：

```redis
ZADD slots:model-A 1750000030 call-001
ZCARD slots:model-A
ZRANGE slots:model-A 0 -1 WITHSCORES
ZREM slots:model-A call-001
```

依次表示：添加成员、查询成员数量、按分数升序查看全部成员及分数、删除成员。

记忆方式：外面是 key 指向 ZSET，里面是多组 member 和 score，不是每个 member 都是 Redis key。

## 7. member 和 score 是 Redis 自带的吗？

是，member 和 score 是 ZSET 原生的数据结构概念，具体值由应用填写。

```redis
ZADD slots:model-A 1750000030 call-001
```

| 部分 | 示例 | 由谁决定 |
| --- | --- | --- |
| key | slots:model-A | 应用指定集合名字 |
| score | 1750000030 | 应用填写数值，这里代表到期时间 |
| member | call-001 | 应用填写成员，这里代表调用 ID |

Redis 原生负责成员唯一、按分数排序、增删和计数。应用规定调用 ID、租约语义和名额上限。

特别注意：把 score 写成到期时间，不会自动删除该成员，仍需脚本清理。
对整个 key 设置过期时间，也不等于给每个 member 设置独立过期时间。

## 8. 如果出现大量超时，你会怎么办？

### 两分钟面试口述

我不会先把超时时间调大或者让所有请求重试，而是先止损，同时定位超时发生在哪一层。

首先按链路拆开看排队耗时、连接池等待、模型首 Token 时间、生成耗时和工具耗时，再结合
超时率、P95/P99、在途请求数、队列长度和最近发布判断：是本机资源耗尽、下游服务变慢，
还是超时配置与正常业务耗时不匹配。不能把排队超时都归因于模型故障。

如果已经影响大量用户，我会降低故障依赖的准入量和并发上限，限制排队时间，停止启动已经
过期的任务，避免越积越多。达到熔断条件就暂时停止请求该依赖；只有备用服务独立且还有
容量时才限量切换。若与刚发布的变更相关，优先考虑回滚。

重试只针对可恢复的瞬时错误，采用有限次数、指数退避和随机抖动，并受整个任务 deadline
与重试预算约束。SDK、工具层、Agent Loop 不能各自叠加重试，否则会把故障流量放大。

结合学习工作流，教材检索失败时不编造教材依据，而是明确降级为一般讲解或保存进度后结束。
组卷、提交答案等有副作用操作，超时不代表外部没有执行成功，要先按业务幂等键查结果或对账，
不能盲目重做。学生已有答案先保存，判分暂不可用时展示处理中，而不是直接判错。

最后通过少量探测确认恢复，逐步放量，观察延迟和积压是否真正回落，再根据根因优化慢查询、
连接池、模型输入长度或服务容量，而不是用扩大超时掩盖问题。

### 容易被追问的细节

- 排队、连接、读取空闲和整体 deadline 是不同计时边界；流式请求不断收到 Token，也不能无限延长总预算。
- 等待学生作答属于业务等待状态，不算模型请求超时，也不应长期占执行名额。
- 本地超时不保证远程调用停止，要尝试取消和清理；租约回收也不是远程取消的证明。
- 重试等待和新一轮执行都计入总 deadline；如果剩余预算不足，不再发起重试。
- 本地 worker 是瓶颈且下游有余量时可扩容；下游已经过载时，增加 worker 可能恶化故障。
- 若正常请求本来就需要更长时间，可以根据延迟分布和用户等待目标调整超时，但必须同时验证容量影响。
- 熔断后采用受限 Half-Open 探测和逐步放量，不能同时释放全部积压任务。

记忆提纲：先止损、再定位；有限重试、业务降级；幂等对账、逐步恢复。

## 9. 模型出现大量超时时，怎么重试和降级？

### 面试口述

我会区分偶发超时和模型服务持续异常。按模型服务维护一个时间窗口内的调用数、超时数，
以及一个熔断状态标记，而不是每次超时都无条件重试。

如果没有达到熔断阈值，并且当前请求还有重试次数和时间预算，就进行有限重试，重试之间
加退避和随机抖动。如果窗口内超时达到阈值，就打开熔断标记，在冷却期间停止请求这个
故障模型，直接走降级，避免所有用户一起重试，把模型服务进一步压垮。

结合学习业务，有独立且有容量的备用模型时，可以受控切换，继续当前讲解；没有可用备用
模型时，就保存学习进度和已有内容，返回固定提示，例如“当前讲解服务暂时不可用，学习
进度已保存，请稍后继续”。只有实际保存成功后才能这样提示，不再调用故障模型生成兜底文案，
也不把未完成的讲解标记成学习完成。

冷却结束后，不是一次放开所有请求，而是只允许少量探测调用。恢复正常后再逐步放量，
探测仍然超时就继续熔断。多实例部署时，窗口统计和熔断状态放在 Redis 等共享存储中，
通过原子操作更新状态和争抢探测名额，保证不同节点遵守同一套规则。

### flag、计数器和重试预算的区别

- 窗口统计：记录最近一段时间发生多少次调用、多少次超时，不是永久累计。
- 熔断 flag：记录当前是否允许请求该模型；完整实现通常是 Closed、Open、Half-Open 三种状态。
- 请求重试预算：限制单个请求还能尝试多少次，不能因为全局阈值没达到就无限重试。

```text
调用前检查熔断状态
  ├─ Open：直接降级，不请求故障模型
  ├─ Half-Open：只有拿到探测名额的请求可以调用
  └─ Closed：正常调用
       └─ 超时：原子更新窗口统计并判断阈值
            ├─ 达到阈值：打开熔断，降级
            └─ 未达到：剩余次数和 deadline 允许才退避重试，否则降级
```

每次重试前也重新检查熔断状态；等待退避期间，其他请求可能已经触发熔断。

### 阈值怎么解释

简单版本可以按窗口内超时次数触发；流量变化较大时，更适合采用“最低调用样本量 +
超时比例”，必要时再结合连续超时阈值，避免高流量时正常的小比例超时触发误熔断。
窗口长度、阈值和冷却时间需要结合服务目标及监控确定，不把示例参数当成已验证配置。

统计按实际下游调用尝试统一计数，避免同一个超时在 SDK、工具层和 Agent 层重复上报；
排队超时和用户主动取消不能不加区分地计为模型服务超时。

记忆提纲：窗口统计判异常，状态标记控调用；偶发有限重试，持续异常降级，冷却少量探测。

## 10. ReAct 和 CoT 的区别是什么？业务中如何选型？（题单第 5 题）

### 核心区别

CoT（Chain-of-Thought，思维链）强调通过中间推理步骤解决问题；经典纯 CoT 不以外部工具
反馈循环为核心。ReAct（Reasoning + Acting）强调推理、行动和观察交替，根据工具或环境返回
的新证据调整下一步。二者不是互斥选项，ReAct 的决策过程可以包含推理。

```text
CoT：问题及已有信息 → 分步推理 → 答案
ReAct：判断下一步 → 调用工具 → 观察实际结果 → 再决策 → 回答或继续行动
```

不能简单说 CoT 是一次调用、ReAct 是多次调用：调用次数不是定义上的根本区别。
也不是使用一次 Function Calling 就必然构成 ReAct，关键是行动反馈是否进入后续决策。
不要求把内部思维过程暴露给用户；业务上记录工具调用、证据和结果，展示简洁的解题解释即可。

### 两分钟面试口述

我理解 CoT 和 ReAct 的区别不在于谁更高级，而在于解决问题时是否需要通过行动获取新的反馈。

CoT 是把问题分解成中间推理步骤，适合题目和材料已经齐全的分析任务。ReAct 是推理和行动
交替，模型决定调用什么工具，拿到真实结果后再决定下一步，适合信息不完整、执行路径需要
动态调整的任务。两者可以组合，不是只能选一个。

结合知识点学习业务，如果已经有题目、标准答案和学生解题过程，只需要分析漏乘、符号错误
等错因，我会优先用一次受约束的模型分析，输出错因候选和对应证据，不必启动工具循环。
信息不足时也不能靠多想几步补出事实，应由工作流追问或补充证据。

如果讲解需要按教材版本检索定义和例题，而且第一次检索结果不足，需要根据返回结果调整
查询或补查前置知识，我才使用 ReAct 式 Agent Loop。工具负责取回材料，模型根据材料决定
继续查还是结束回答，并受步数、时间和费用预算限制。

但如果流程固定为检索一次再讲解，我会直接用确定性工作流，不为了使用 Agent 引入自由循环。
整个诊断、讲解、练习和补救的教学阶段仍由外层工作流管理，ReAct 只在需要灵活处理的阶段内使用。

选型时我看输入是否充分、是否需要外部行动和反馈、路径是否固定，再用业务正确率、证据质量、
延迟、成本和无效工具调用率验证。原则是能直接处理的不启动循环，固定流程用工作流，动态探索
才用 ReAct。

### 对比与常见追问

| 维度 | CoT / 基于已有材料的推理 | ReAct 式循环 |
| --- | --- | --- |
| 重点 | 多步分析 | 推理与行动反馈结合 |
| 外部信息 | 纯 CoT 不主动检索补齐 | 可通过工具获取新证据 |
| 业务例子 | 基于完整题目和作答分析错因 | 根据检索结果动态补查教材材料 |
| 主要风险 | 推理错误、基于不足信息猜测 | 额外增加工具失败、无效循环和执行副作用风险 |
| 成本 | 推理也会消耗 Token，不必然便宜 | 多轮模型与工具调用通常增加成本和延迟，需实测 |

- ReAct 不等于一定更准确。检索返回错误内容，或者模型误读结果，同样会错。
- CoT 不等于“模型真实内部思考的完整记录”，也不是可验证的正确性证明。
- RAG 不等于 ReAct。固定检索后生成属于 RAG；模型根据观察动态选择下一步检索才体现 ReAct 式闭环。
- 标准答案能够确定性计算或校验时，优先用代码和规则，不必强制在 CoT 与 ReAct 中二选一。

## 11. SSE 流式输出原理，和普通 HTTP 有什么区别？用户中途断开，后端是否继续请求模型？（题单第 1 题）

### 原理与边界

SSE 本身建立在 HTTP 上，不是与 HTTP 并列的另一种传输协议。与常见的非流式 JSON 响应相比，
它使用 `Content-Type: text/event-stream`，在同一个尚未结束的响应中持续发送 UTF-8 文本事件，
前端解析完整事件后增量显示。事件之间以空行分隔，网络分块不保证与事件边界或 Token 边界一致。

```text
id: 42
event: delta
data: {"text":"先看括号外的系数"}

```

`id` 是事件标识，`event` 是应用定义的事件类型，`data` 是载荷。SSE 是服务端到客户端单向推送，
学生提交答案或取消任务需另发请求。普通 HTTP 也能流式传输，HTTP keep-alive 则是连接复用，
不等于响应持续推送。SSE 改善的是首段内容的可见时间，不保证模型更快完成全部生成。

部署时避免代理缓冲聚合事件，设置合理的空闲超时，按需发送注释心跳，并限制慢客户端的
输出缓冲。心跳不是业务进度，不能无限延长任务 deadline。

### 两分钟面试口述

SSE 是基于 HTTP 的服务端单向事件流。普通非流式接口一般等完整结果生成后再返回，而 SSE
会保持当前响应未结束，使用 text/event-stream 持续发送事件，前端收到后增量渲染。因此模型
开始输出时，学生就能看到讲解，不用等整段回答生成完。

用户断开连接时，我会区分显示连接和业务任务的生命周期，不把断线直接等同于取消。
学生明确点击停止生成，我会记录取消状态，阻止新的模型和工具调用，并尝试关闭当前上游流、
取消执行，保存已有内容并标记未完成。单纯关闭前端流不保证模型服务已经停止生成或计费。

如果只是断网或刷新，实时讲解可以保留一个有上限的重连宽限期，期间继续生成并缓冲事件，
超过期限仍没有订阅者就取消，避免无人查看时持续花费。对于已经受理的异步组卷、判分任务，
则与连接解耦，继续受控执行并落库，用户回来后查询原任务结果，不重复提交。

恢复时通过任务 ID 重新订阅，再按最后接收的事件 ID 补发缺失事件，而不是重新调用一次模型。
服务端必须保存可回放事件或结果快照，并做任务归属校验。多实例下这些恢复状态需要共享存储。

所以我的原则是：断线只代表用户暂时收不到输出；是否继续模型调用，要由任务类型、明确的
取消意图、剩余预算和恢复策略共同决定。

### 断连处理细节

- Python ASGI 服务可通过框架断连通知、发送失败或任务取消感知断连；Starlette 提供
  `request.is_disconnected()`。具体响应实现是否自动取消生产任务需要验证，不能一概而论。
- 明确取消建议使用独立的幂等取消接口。仅收到连接断开通常无法区分刷新、网络故障和停止按钮。
- 继续运行的任务应由独立任务运行时或 worker 托管，不仅是请求协程随手创建的后台 task。
- 原生 EventSource 使用 GET，支持自动重连和 Last-Event-ID；服务端仍需实现回放，重连不等于自动续算。
- 如果用 fetch POST 携带聊天输入并读取 SSE 格式响应，需要自行实现解析、重连和游标传递。
  更清晰的另一种设计是 POST 创建任务，GET 订阅已有任务的事件。
- 原生 EventSource 的自动重连不代表业务重新发起。终态事件后前端应主动关闭订阅；连接 EOF
  不应直接被当作业务成功，`done` 等业务事件由应用自行定义。
- 流已经发送响应头后，通常不能改成另一个 HTTP 错误状态；连接仍可用时发送业务错误事件，
  并持久化失败状态。断线后无法再向该连接发送兜底文本。
- 回放窗口已过期时返回结果快照或明确的重新同步提示，不静默重跑任务；客户端按事件 ID 去重。

记忆提纲：SSE 属于 HTTP，事件增量推送；连接不等于任务，取消不等于断线，重连不等于重跑。

## 12. Rerank 重排的收益和性能代价是什么？如何平衡？（题单第 9 题）

### 直观理解

召回先从大量教材片段中找出一批可能相关的内容，重排再判断这批候选谁更能回答当前问题。
例如学生问“为什么括号前是负号，去括号后每一项都要变号”，初排可能把“负数的定义”排在
前面，而真正解释去括号规则的片段排在后面；重排的目标是把后者提到最终上下文前列。

项目材料中的链路是：教材元数据过滤 → Dense + BM25 双路召回 → RRF 融合 → Qwen-Rerank
重排候选 → 最终 Top 5 证据。RRF 按排名融合，语义 Rerank 则读取问题与候选正文重新评分。
模型具体 ID 和生产参数仍需确认，不将材料中的完整链路收益归因于重排单项。

### 两分钟面试口述

Rerank 的主要收益，是把已经召回但初排靠后的有效证据提升到前面。向量检索和关键词检索
负责快速找到可能相关的材料，重排模型进一步结合问题和候选正文，判断谁更能回答问题。

结合教材问答，提到同一个知识点不代表能解释学生的具体困惑。重排可以减少最终上下文里的
无关材料，把有限的 Top 5 位置留给更有用的定义、规则和例题。但如果正确材料根本没有被
召回，或者知识库里就没有，重排无法补救，仍要解决召回或语料覆盖问题。

代价是多了一次在线模型评分阶段。常见的联合评分模型需要处理每个问题与候选片段的组合，
候选越多、正文越长，计算量和资源消耗通常越大。API 模式还涉及网络耗时和调用费用，高并发
时还要看排队和 P95/P99，不能只看单请求推理时间。

平衡上，我会先按教材版本过滤，再将双路候选融合、去重，只对有限候选重排，不对整个库
逐条打分。候选数量和文本长度通过评测确定，避免盲目扩大候选或截掉关键证据。

评测时固定语料、查询集、候选集和最终 Top K，对比开关重排后的排序质量、答案证据支持、
端到端延迟和成本。重排服务超时则在保留权限和教材过滤的前提下回退到 RRF 排序；材料不足
仍然要澄清或明确证据不足，不因为降级就强行回答。最终选择质量收益与响应预算之间的平衡点。

### 平衡手段和验证边界

- 候选规模：可实验比较 20、40、80 个候选重排后取 Top 5，数字仅为实验档位，不是已上线配置。
- 输入控制：去重并保留标题、教材信息和关键正文；裁剪要检查答案是否被截掉。
- 模型与批处理：评估更小模型、批量评分或受控动态批处理；批处理可能增加等待延迟，不能只看吞吐。
- 按需调用：固定题目或已验证的高置信命中可尝试跳过，但策略需离线验证，初排分数不天然等于正确概率。
- 缓存：缓存键要包含查询、候选内容或版本、重排模型版本及必要的权限作用域，避免串用户或沿用旧结果。
- 超时降级：回退到已过滤的融合结果；不无限重试，不取消教材和权限限制。
- 成本口径：若更少但更精确的证据足以回答，可能节省生成输入 Token；若上下文数量和长度不变，
  不能声称重排必然省 Token。总成本应包含重排和生成，延迟包含排队和网络开销。

重排可以提高最终 Top 5 的证据命中，但不增加重排输入候选集本身的覆盖。
区分候选集 Recall@N 与最终 Top K 的 Recall、MRR、nDCG；若口径是“至少有一条有效证据的
问题比例”，应明确这是 Hit@K 式指标。不能把整个混合检索改造的提升当成单独 Rerank 的提升。

记忆提纲：召回保覆盖，重排提排序；候选数和长度控成本，消融评测定收益，超时回退保可用。

## 13. 向量数据库索引怎么选型，如何适配高并发业务？

### 先区分三层

- 数据库：如 Qdrant，负责存储、查询、过滤、分片和副本等。
- 索引算法：如 HNSW、IVF，负责加速近邻搜索。
- 压缩方式：如 PQ、标量量化，负责降低向量存储和计算开销，可与部分索引组合使用。

不能把所有算法当成每个数据库都支持的可选开关。项目材料使用 Qdrant，HNSW 加 payload
索引是适合优先验证的方向；实际参数、量化和副本部署不能在未核对配置时说成已落地。

### 索引对比

| 方案 | 原理与适用方向 | 代价 |
| --- | --- | --- |
| Flat 精确扫描 | 逐条计算距离；适合小候选集、精确检索基线 | 大范围扫描计算量高，但强过滤后可能很划算 |
| HNSW | 多层邻近图搜索；适合低延迟、高召回要求的在线检索 | 图结构和向量占资源，构建和更新有成本 |
| IVF-Flat | 向量分簇，只搜索部分簇 | 需要训练；搜索簇过少会漏召回，分布变化可能需重训 |
| IVF-PQ | 分簇并压缩向量；适合内存受限的大规模数据 | 量化误差、训练和参数调优，可能需要原向量复核 |

索引没有固定的数据量分界线；需要同时看向量维度、硬件、过滤后的候选规模、目标召回率和
流量。PQ 不是与 HNSW 完全互斥的概念，具体组合由实现支持情况决定。

### 两分钟面试口述

我会先明确业务的查询峰值、目标 P95/P99 延迟、召回要求、向量规模和维度、元数据过滤条件，
以及读写比例，再选索引，而不是只根据数据条数决定。

结合教材 RAG，这类数据以读为主，查询需要限制教材版本、年级和学科，我会优先验证 Qdrant
的 HNSW 与 payload 索引组合。HNSW 用图结构减少距离计算，payload 索引帮助处理教材过滤。
如果过滤后只剩很少的片段，精确扫描也可能更合适，不强求所有请求都走 HNSW。

参数上，查询时的 hnsw_ef 控制搜索候选范围，调大通常能改善近邻召回，但增加计算和延迟。
建图的 m 和 ef_construct 则影响图结构、构建开销与检索表现。我会在相同数据和过滤条件下，
用精确搜索作为参照，对比不同参数的 ANN 召回率和并发下的延迟，再检查真实教材问答的证据质量。

高并发不能只靠换索引。读压力增长时，可以在独立资源上增加可分担查询的副本；数据容量
超出单机时再考虑分片，同时避免每次请求扇出到过多分片。入口还需要限流和有界排队，
热点查询缓存要包含教材范围、权限和索引版本。

如果内存成为瓶颈，再评估量化或磁盘方案，但要验证召回损失与冷数据访问时延。后台教材
导入和索引构建也要限制资源，避免影响在线查询。最终选择是在目标质量下满足延迟、吞吐
和成本，而不是单独追求最高 QPS。

### 高并发追问要点

- hnsw_ef 不是最终返回的 Top K，也不是最大并发数。
- 副本不是分片：副本复制数据，可支持高可用及读分担；分片拆分数据容量和工作量。
  是否真正提高吞吐取决于独立资源、路由、一致性配置和热点，不保证线性提升。
- 避免全库 Top K 后再过滤，可能导致有效候选不足；应传入可信过滤条件，并验证过滤感知检索效果。
- 内存粗估：N × d × 每维字节数只是原始向量。例如 32 万条、1024 维、float32 约 1.31 GB
  （十进制），不包括图、payload、索引、运行缓冲和副本；维度和条数在这里仅作容量示例。
- Qdrant 支持 HNSW、量化和磁盘存储等配置，不等于可直接切换成任意 IVF-PQ 实现。
- 压测要包含真实查询与过滤分布、冷暖缓存、读写混合、超时率及限流拒绝率，不只跑无过滤的平均延迟。
- ANN Recall@K 是对精确近邻结果的逼近程度，不等于业务证据命中率；向量近邻完全正确也可能检索不到答案。
- 排查完整链路：Query Embedding、BM25、重排也可能是真正瓶颈，不能只优化向量索引。

记忆提纲：先定质量和延迟目标，再选索引；过滤与参数做细，副本与准入抗并发，压测确认收益。

## 14. Qdrant 元数据索引怎么加？

这与 MySQL 给常用过滤字段建索引的思路相似，但调用的是 Qdrant 的 payload 索引接口，
不能直接套用 MySQL 的 B+ 树或联合索引最左前缀规则。

假设已存在 `textbook_chunks` Collection，Point 的 payload 包含 `book_id`、`subject`、
`edition` 字符串和整数 `grade`。下面是教学示例，不是已执行的生产变更：

```python
from qdrant_client import QdrantClient, models

client = QdrantClient(url="http://localhost:6333")

for field in ("book_id", "subject", "edition"):
    client.create_payload_index(
        collection_name="textbook_chunks",
        field_name=field,
        field_schema=models.PayloadSchemaType.KEYWORD,
        wait=True,
    )

client.create_payload_index(
    collection_name="textbook_chunks",
    field_name="grade",
    field_schema=models.PayloadSchemaType.INTEGER,
    wait=True,
)
```

KEYWORD 用于完整字符串匹配，INTEGER 对应整数匹配和范围过滤。类型必须和实际存储一致，
不能把字符串“七年级”当作整数 7。字段名称也必须与 payload 一致。

索引通常在 Collection 初始化或迁移时创建，不是每个用户请求都建一次；后续数据写入由
数据库维护索引。新库建议提前建常用 payload 索引，尤其是计划结合过滤感知 HNSW 时。

查询时仍必须显式携带过滤条件。例如：

```python
textbook_filter = models.Filter(must=[
    models.FieldCondition(
        key="book_id", match=models.MatchValue(value="math_g7_v1")
    ),
    models.FieldCondition(
        key="grade", match=models.MatchValue(value=7)
    ),
])
```

把该对象作为向量查询的 `query_filter` 传入。创建索引不会自动限制教材范围，也不会自动
完成权限校验；条件必须来自可信业务上下文。已明确唯一 book_id 时，其他教材条件可以按需
使用，不必冗余添加所有字段。

只给经常用于过滤、且确实有收益的字段加索引，不给全部元数据盲目建索引。可以通过
`client.get_collection("textbook_chunks").payload_schema` 查看索引字段与类型，再压测实际
过滤性能。该例连接独立 Qdrant 服务；Python 客户端本地模式不能用来验证服务端 payload
索引的加速效果。

## 15. Agent 的幻觉和普通大模型幻觉有什么区别？怎么工程化解决？（题单第 6 题）

### 核心区别

不是两种完全不同的底层机制，而是系统赋予模型工具、记忆和状态操作后，错误的传播范围
变大了。纯问答常表现为编造事实、引用或无依据结论；Agent 除了说错，还可能编造工具名、
参数或执行结果，并把错误判断转成行动、业务状态和长期记忆。

普通问答的错误也可能造成严重后果，不能说“普通模型只是说错，没有影响”。工具超时、
调度 bug、所有规划错误也不能统称幻觉；这里重点指缺乏事实依据却被当作真实的内容或判断。

### 两分钟面试口述

我认为 Agent 幻觉不是一种全新的模型问题，而是普通模型的无依据输出进入了执行链路。
普通问答主要表现为编造知识、引用或者结论；Agent 还可能选不存在的工具、编造参数，或者
工具没有成功却告诉用户任务完成。错误还会通过多轮调用和记忆继续传播。

结合学习业务，学生一道题做错，模型可以提出“可能没有掌握分配律”的假设，但不能直接
断言乘法基础薄弱，并写入长期画像。组卷接口超时，也不能直接告诉学生试卷已经生成。

工程上我会在输入、执行和结果三层控制。输入层提供匹配教材版本的证据，保留来源，对检索
不到或证据冲突的情况允许澄清和证据不足，不要求模型一定给出答案。

执行层只开放白名单工具，校验参数结构、对象存在性、用户归属和当前阶段。学生 ID 等可信
字段由服务端注入，不交给模型自由填写。模型只能提出行动和结论候选，最终业务状态由程序
依据真实工具回执和学习证据推进。

结果层核对引用和关键结论。能用计算器、规则或标准答案确定性校验的，就不用模型自评代替。
没有可靠结果时保留未知状态，不把超时当作成功，也不把系统失败当作学生答错。长期记忆只
写入有来源的事实，推断单独标记，避免一次猜测持续影响后续教学。

最后用包含检索为空、错版本、工具失败和学生证据不足的测试集做回归，既看答案质量，也看
虚假完成、错误状态更新和记忆污染。目标不是承诺零幻觉，而是降低发生概率，阻断错误落地，
并让错误可检测、可追溯、可恢复。

### 业务例子与防线

| 风险 | 工程防线 |
| --- | --- |
| 编造教材原文或页码 | 引用 ID 必须属于授权的实际检索结果；还需检查原文是否支持陈述 |
| 编造题目 ID 或操作其他学生数据 | Schema 校验之后继续做存在性、归属及权限校验 |
| 组卷超时却声称完成 | 根据真实回执、结果查询和持久化状态展示，不依赖模型自述 |
| 凭一次错误断言学生基础薄弱 | 错因先作为候选，结合追问和后续作答验证 |
| 模型判断“已掌握”就直接结束 | 程序按验证规则和有效作答证据校验状态转移 |
| 猜测写入画像后反复被引用 | 事实与推断分开，记录来源和版本，支持纠正与失效 |

### 容易说错的点

- RAG 提供证据，但召回可能错误、证据可能不足、生成也可能误读，不能保证消灭幻觉。
- JSON Schema 只约束结构，不证明参数、引用或事实真实。
- HTTP 200 不等于业务成功，需要检查业务回执；成功回执也不能证明题目教学质量合格。
- 低 temperature 不保证正确，只可能让错误更稳定；模型自报置信度不等于校准后的概率。
- 第二个模型审核可辅助筛查，但可能共享同类错误，关键结果仍应尽量对照独立证据与规则。
- 工具返回的文档是数据，不是系统指令；隔离提示注入是相关的安全防线，但提示注入与幻觉并非同一问题。
- 不编造具体幻觉下降百分比；生产指标需来自保留输入、证据、执行轨迹和最终状态的评测记录。

记忆提纲：普通模型可能编答案，Agent 还可能把编造变成行动和状态；证据约束、执行校验、
结果验证、记忆追溯和异常回归共同控制风险。


## 16. Harness 是什么？面试时如何解释？

Agent Harness 可以理解为包在模型外面的执行与控制系统，负责把模型接到工具、上下文和
运行规则上，使它不只是生成文本，而能受控地完成任务。它不是某个固定框架或模型，也没有
所有团队完全一致的组件边界；狭义可指模型调用及工具路由循环，广义还包含状态恢复、预算、
权限、观测和验证等工程能力。若上下文是 evaluation harness，则指运行测试和评分的评测设施，
不能与 Agent 执行系统直接混同。

### 一分钟面试口述

我理解 Agent Harness 是模型外面的一套执行和控制机制。模型负责提出下一步行动，Harness
负责准备上下文、执行允许的工具、回填结果，并控制超时、预算、取消和异常收尾。

对应我的项目，Agent Runtime 和 Agent Loop 承担其中的核心执行职责，工具注册、参数校验、
上下文管理和 Trace 都属于相关工程能力。在知识点学习工作流的设计中，任务状态和验证规则
进一步约束什么时候讲解、什么时候等待学生，以及什么情况下允许进入下一阶段。

比如模型认为材料不足、需要再查教材，程序先校验教材范围和剩余预算，再执行检索，把真实
结果返回给模型。模型说学生已经掌握，也不能直接修改状态，仍要检查作答和理解验证证据。

所以我不会把 Harness 当成一个新增的 Agent，而是把它理解为让 Agent 能够可靠运行的工程
支撑。项目里已有能力和设计中的恢复、校验机制，要按真实落地进度分别说明。

### 概念边界

| 概念 | 关注什么 |
| --- | --- |
| 模型 | 基于输入生成回答或行动建议 |
| Agent Loop | 模型决策、工具执行、结果回填的循环 |
| Agent Runtime | 回合执行、工具调度及运行生命周期，具体范围依项目而定 |
| Workflow | 业务阶段、分支、等待和状态推进规则 |
| Agent Harness | 围绕模型组织执行与控制能力的整体工程视角，与 Runtime 高度重叠 |
| Evaluation Harness | 测试输入、运行、环境重置和结果评分等评测设施 |

Harness 不要求多 Agent、独立进程或额外的模型调用，也不只是 Prompt 或 Guardrails。
使用 LangGraph 等框架可以实现其中部分机制，但工具授权、业务幂等和状态校验仍需要应用设计。

记忆句：Loop 让模型循环行动，Harness 让整个行动过程可控、可验证。
