# 三层记忆与知识点学习 Workflow：面试讲解

> 日期：2026-09-14。
> 依据：用户提供的简历记忆条目、`../DeepTutor三层记忆多时长介绍.md` 和本目录的知识点学习闭环指南。
> 边界：这是设计衔接和面试学习材料。原记忆文档注明关系库方案、自动标注和定时归并尚未全部进入正式链路；本文不将它们描述为已上线实现。
> 简历中的 37%、200 条、71% → 90% 尚未核实原始评测记录，以下说明如何解释和验证，不编造实验经过。

## 1. 如何对应简历的三条内容

| 简历条目 | 在 Workflow 中怎么体现 |
|---|---|
| L1/L2/L3 分层记忆 | 保存原始学习证据，形成场景事实，再维护跨任务画像 |
| UnifiedContext 与上下文治理 | 按当前节点需要装配任务状态、近期对话、相关记忆、教材证据和工具结果 |
| 跨会话效果 | 新会话查询过去的相关事实，帮助诊断和个性化；不单靠当前几轮对话 |

原简历“分成记忆”应改成“分层记忆”。“持续维护学习进度、知识掌握与偏好”也应区分：执行进度由任务状态负责，记忆记录学习经历和带证据的掌握判断，而不是用画像恢复执行游标。

## 2. 第一条核心边界：Workflow 管进度，Memory 管经历

| 信息 | 放在哪里 | 为什么 |
|---|---|---|
| 当前阶段、暂停状态、等待问题 | 任务状态记录 | 决定下一步执行什么 |
| 当前题组和练习轮次 | 任务及练习业务记录 | 保证答案关联正确，支持恢复和幂等 |
| 原始答案、提示、复述和判分 | 业务记录，L1 保存或引用 | 是后续判断的证据 |
| 某次练习暴露的问题及结果 | L2 场景事实 | 便于检索和追溯 |
| 近期学习范围、偏好与待复习方向 | L3 聚合画像 | 为跨会话个性化提供概览 |

同一事件既可以改变任务状态，也可以成为 L1 证据，但职责不同。比如暂停事件可以留证据，真正恢复时仍读任务状态，不让模型从记忆摘要推断停在哪一步。

**一句话：任务状态告诉系统接着做什么，学习记忆告诉系统以前发生过什么。**

## 3. 用一个分配律案例讲清三层

### 3.1 L1：先保存发生过什么

学生在 T1 中将 `3(x-2)` 写成 `3x-2`，解释“3 只乘 x”。随后首轮练习 A1 出错，补救轮 A2 达到本次条件。

L1 关联保存：原题和版本、错误步骤、诊断原话、两轮答案、提示使用、复述、评分及最终结果。至少通过用户、任务、练习轮次和知识点关联；原文或大对象可引用业务存储，不必重复复制。

原始证据先由程序可靠保存。轻量模型可以异步提取标签和摘要，失败不影响原始证据，也不能把模型标签当成原始事实。区分学生原话、系统评价和助手讲解，不能把助手说的“你已经会了”当成学生掌握的独立证据。

### 3.2 L2：提炼这次学习的场景事实

可形成如下记录：

> 在本次分配律学习任务中，学生首轮出现漏乘第二项；补救后使用新题验证并完成概念解释，达到本次规则要求。

同时保留 T1、A1/A2、知识点、时间、提示使用情况及 L1 来源引用。

不能只写“学生已经掌握分配律”，因为会丢掉补救过程与结论范围。也不能只写“分配律薄弱”，忽略后续已出现的新证据。未完成任务只记录已发生的情况，不提前生成最终成绩。

### 3.3 L3：维护当前可用的用户模型

用“当前 L3 + 新增 L2”增量归并，例如：

> 近期完成过分配律辅导，本次经补救达到验证条件；后续可安排复习，确认是否保持。

知识学习状态可归入原方案的 scope，近期关注点归入 recent，明确或多次体现的讲解偏好归入 preferences。学生只说一次“这次讲短一点”，未必应变成长期偏好。

L3 是带来源、可更新的概览，不是永久标签；新证据可以改变当前判断，但不能篡改 A1 的历史错误或抹去提示使用情况。

### 3.4 用户画像怎么存：关系数据库中的画像项

**本节统一采用“一个用户有多条画像项，每项通过关联表引用 L2”的设计。** 不再同时把来源复制到 JSON 的 source_refs 中，避免两套关联不一致。这是拟议表结构，不代表当前仓库已经实现。

用户画像不是一大段没有结构的总结，也不是聊天记录全集。比如同一个用户可以有“年级”“讲解偏好”“近期学习目标”“分配律学习状态”等不同画像项，每项独立更新、设置时效和追溯依据。

#### 3.4.1 画像项表 user_profile_item

| 字段 | 含义 | 示例或注意事项 |
|---|---|---|
| id | 画像项的唯一标识 | 301，标识某一项，不是整个用户 |
| user_id | 画像所属用户 | U1，所有查询和更新都要限制归属 |
| category | 画像分类 | profile、preferences、goals、scope、recent |
| item_key | 分类下的具体项目 | grade、explanation_style、knowledge_state |
| subject_key | 项目对应的对象键 | 分配律的稳定知识点 ID；无对象时用约定值 general |
| value_json | 结构化的画像内容 | 学习状态、适用范围、简短说明等，不复制全部原始答案 |
| evidence_type | 结论性质 | 用户明确自述、行为证据推断或混合；这是画像内容的性质，不是数据库来源表名 |
| record_status | 此项当前是否可用 | active、needs_confirmation、inactive；不同于任务 status |
| observed_at | 最新相关证据发生时间 | 学生实际完成练习的时间，不是后台归并的时间 |
| updated_at | 此画像项最后写入时间 | 归并和存储发生的时间 |
| expires_at | 当前判断需要失效或复核的时间 | 近期约束可设置；没有可靠时效规则时不能随意承诺永久有效 |
| version | 此画像项的并发更新版本 | 防止两个归并作业互相覆盖；不是学习轮次或任务 state_version |
| derivation_version | 提炼策略、Prompt 或模型配置的版本标识 | 用于解释结论如何产生、后续重跑 |
| created_at | 画像项首次创建时间 | 与最后修改时间分开 |

可以用 user_id、category、item_key、subject_key 的组合唯一约束表示同一个当前画像项，避免每次归并都新增一条等价的“当前分配律状态”。subject_key 使用规范化对象 ID，不能把“分配律”和“乘法分配律”随意当成两个不同对象。

这里存的是当前视图。若需要审计每次画像变化，可以另存更新历史；不能因为 L2 已追加保存，就声称所有 L3 历史版本也自动保存了。

#### 3.4.2 五类画像内容分别存什么

| category | 存什么 | value_json 可包含的字段 | 不应该放什么 |
|---|---|---|---|
| profile | 已确认的学习背景 | grade、textbook_id、confirmation_time 等 | 未确认的年级猜测，或不必要的敏感个人信息 |
| preferences | 相对稳定的交互偏好 | style、applicable_scene，例如先举例再解释 | 把一次临时要求直接永久化 |
| goals | 当前学习目标 | description、goal_status、target_date | 用目标 completed 代替某个任务执行完成 |
| scope | 知识点学习状态及范围 | assessment_summary、review_recommendation、policy_ref | 单次达标就标成永久掌握 |
| recent | 有时效的关注点或约束 | summary、applicable_scene，配合 expires_at | 永久保留已经过期的短期要求 |

record_status 表示画像项是否可使用，goal_status 表示某个学习目标是否进行中，Workflow status 则表示任务运行状态。这三个含义不同，不要共用一个状态字段。

未知信息可以不建画像项，不能为填满字段而猜测。若用户明确纠正背景或偏好，按新证据更新；当前请求“今天讲短一点”可作为本轮约束优先使用，不必立即覆盖长期偏好。

#### 3.4.3 来源关联表 profile_item_l2_source

| 字段 | 含义 |
|---|---|
| profile_item_id | 具体画像项 ID，例如 301 |
| profile_item_version | 这批来源支持的画像版本，避免更新后新旧来源混淆 |
| l2_id | 支撑该判断的场景事实，例如 201 |
| relation_type | 该证据是支持、纠正还是提供背景；应有明确枚举定义 |
| created_at | 建立关联的时间 |

画像项、L2 和 L1 必须属于同一合法用户范围，不能只确认 ID 存在。关联到具体画像项，才能回答“为什么认为分配律需要复习”，而不只是给出整份画像引用过的一大堆记录。

来源更新与画像新版本应可靠地一起提交。可以按当前版本查对应来源；若保留旧来源版本，也要明确是否另行保存了对应的旧画像内容。

### 3.5 任务 task_id=4 完成后怎样写入画像

假设用户 U1 在分配律任务 4 中，首轮 A1 出现漏乘，补救轮 A2 达到本次条件。

**第一步，保存任务事实和 L1。**

| L1 ID | task_id | attempt_id | 内容 |
|---|---|---|---|
| 101 | 4 | A1 | 学生解释“只乘第一项” |
| 102 | 4 | A1 | 第一轮练习出现漏乘 |
| 103 | 4 | A2 | 补救后新题作答结果 |
| 104 | 4 | A2 | 概念解释结果及其原始依据 |

**第二步，提炼 L2_201。** 内容为：“本次分配律学习首轮漏乘，经补救后达到本次验证条件。”通过 l2_l1_source 关联 101～104，保留任务及知识点来源。

**第三步，增量更新 L3 画像项。**

| 字段 | 本例内容 |
|---|---|
| id | 301 |
| user_id | U1 |
| category | scope |
| item_key | knowledge_state |
| subject_key | 分配律对应的规范知识点 ID |
| value_json | 最近经补救达到本次验证条件；建议后续复习确认保持情况 |
| evidence_type | 基于学习行为的推断 |
| record_status | active |
| observed_at | 本次任务验证完成时间 |
| version | 当前画像项更新版本 |

关联表将画像项 301 的本次版本与 L2_201 关联，沿 L2 再回查 L1 和 task_id=4。画像项不需要复制一整份任务状态，更不能只存 task_id=4 就代表有了用户画像。

将来另一个任务提供新证据时，仍更新同一用户的同一知识点画像项，保留来源关系；历史任务及原始成绩不覆盖。当前任务的 paper_id、等待问题、stage、state_version 保留在任务系统，不放在这条 L3 中。

**查数据时按问题选层：**

- “任务 4 到哪一步了？”查任务状态。
- “上次分配律具体错在哪里？”查相关 L2，必要时回查 L1。
- “近期应该优先复习什么？”参考 L3，再结合本次诊断。

### 3.6 画像更新的控制信息放哪里

归并处理游标或已处理批次另外保存，例如用户标识、成功处理批次、输入 L2 集合、处理状态和时间。它们是作业控制数据，不是用户画像的语义字段。

更新时读取当前画像和新增 L2，生成候选后校验字段、归属及来源，再按画像 version 提交。只有更新成功，才提交相应处理进度；失败不能先跳过输入。并发更新冲突需要重新读取，不能让旧候选覆盖新画像。若用递增 L2 ID 做游标，需确保不会因晚提交或并行处理漏掉记录；不满足该条件时使用独立处理记录。

来源 ID 真实不代表推断正确，语义质量仍需要评测。不要随意给画像加一个模型自报的“掌握概率 0.95”就当成可靠概率；确需置信信息时，应明确其来源和校准方法。

删除或纠正源记录时，相关画像需要重新计算、失效或清理，不能只删 L1 而保留无法追溯的长期结论。

### 3.7 面试口述：用户画像存什么

> 在目标设计里，L3 放在关系数据库，按用户和画像项组织，而不是只存一段总结。每项有分类、对象、结构化内容、证据性质、有效状态和更新时间，再通过来源表关联支持它的 L2。比如分配律学习状态引用本次任务的场景事实，需要时还能继续追溯到原始答案。
>
> 年级和教材属于背景，讲解方式属于偏好，近期学习目标和知识状态分别保存。L3 是当前可用的用户视图，任务进度仍在 Workflow 状态里。更新时根据当前画像和新增事实增量归并，保留时间与来源，不把一次答对写成永久掌握。

## 4. Workflow 在哪里读、在哪里写

| 阶段 | 读取 | 写入或产出 |
|---|---|---|
| 目标确认 | 学习背景、当前有效目标，必要时向用户确认 | 本次任务目标快照 |
| 诊断 | 当前错题、相关 L2、必要 L1 和近期对话 | 诊断回答及候选判断的原始记录 |
| 讲解 | 当前错因、相关偏好和教材证据 | 讲解与实际证据引用、提示曝光记录 |
| 答题与复述 | 当前题组、当前轮原始提交、评分规则 | 答案、解释和判定依据 |
| 综合评估 | 本轮有效证据及补救额度 | 本次结果，不用旧画像代替新证据 |
| 暂停恢复 | 权威任务状态，必要对话与证据 | 暂停/恢复状态及事件；不强制更新画像 |
| 正常收尾 | 完整任务事实 | 可靠保存结果，异步触发相关 L2 提炼和后续 L3 归并 |
| 下次学习 | 相关 L2 与当前 L3 | 选择诊断方向，仍以本次表现验证 |

教材 RAG 说明知识依据，学习记忆说明学生经历。读取历史只能决定优先问什么，不能跳过本次诊断。

## 5. 对旧方案做两处衔接，不重建一套记忆

### 5.1 保留批量归并，增加任务完成触发

旧目标方案是 L1 每轮采集，L2 累积十个完整回合归并，会话结束或空闲处理尾批，再更新 L3，定时任务补偿。十轮、空闲时间等是配置策略，不是正确性保证。

学习任务可能四轮结束，也可能跨多个 Session，因此增加：**任务完成后，处理该任务尚未归并的证据，形成必要的场景事实。** 不必等待对话凑够十轮，L3 仍可异步更新。

批量归并可能已经生成中间事实，因此完成时应记录最终结果或新增变化，不重复复制整段历史。同一事件允许支持多个不同事实，但重试或不同触发器不能反复生成等价记录；用稳定业务事件、处理批次和去重约束协调。跨会话任务通过 task_id 聚合，保留各源事件的 session_id，而不是丢掉来源。

评分完成等异步业务事件即使发生在对话回合之后，也应可靠采集，不能只依赖 Assistant 最终回复回调。结果与待发送记忆事件可靠提交后再异步处理，模型提炼失败可补偿，不阻塞已经完成的教学结果。

### 5.2 跨会话不能只读当前 Session 的 L2

旧方案读取最近十轮、当前 Session 的 L2 和用户 L3。结合 Workflow 后，再支持按用户、知识点和时间范围查询相关历史 L2，必要时回溯 L1。

先用关系库字段查询即可，不必为了分层而引入向量库。查询必须限定用户权限；L3 的概括不足以解释细节时，回看来源，不让模型补造历史。

## 6. 第二条简历：UnifiedContext 怎么装配上下文

UnifiedContext 可以理解为本次执行的输入包，不是长期数据库，也不是把所有层次全文永久拼到 Prompt。

不同节点取不同内容：

- 诊断节点：本次问题、错误步骤、少量相关历史事实和学生原话。
- 讲解节点：已确认错因、教材片段、必要的表达偏好。
- 判分节点：题目、答案、评分标准与提示记录；通常不需要大量历史画像。
- 恢复处理：原阶段、待回答对象和必要交互，不依赖全部聊天回放。

### 6.1 预算不足时怎么裁剪

先减少无关画像、重复记忆、已失效的长工具输出，再压缩更早的相关对话。保留当前指令、待回答问题、关键任务状态以及判断所必需的原文证据，并为回答和工具 Schema 预留空间。

摘要应标记覆盖范围，避免最近十轮和 L2 重复装入相同内容；保留来源供按需回查。Token 预算约束的是整个请求，不只是记忆字段。

### 6.2 “输入 Token 降低 37%”该怎么解释

这是待核实结果。需要明确“十轮以上”指会话已超过十轮，不是 Agent 内部工具循环十次；基线和优化方案应比较相同或可比阶段的完整输入 Token。

计算口径为：基线平均输入与优化后平均输入之差，除以基线平均输入。保留模型及 tokenizer、样本、Prompt、工具配置、统计窗口和调用日志，不能用字符数代替 Token。

同时观察回答质量、追溯成功和额外记忆提炼调用成本。只减少传入材料却丢失当前问题，不能算有效治理；单次调用输入变少也不自动等于系统总成本下降。

## 7. 第三条简历：跨会话评测怎么结合 Workflow

200 条评测与 71% → 90% 暂按待核实数字处理。需要区分三类问题：

| 样本类型 | 例子 | 应使用的依据 |
|---|---|---|
| 当前会话指代 | “你刚才说的第二种方法是什么？” | 最近对话，不把它全算长期画像功劳 |
| 跨会话事实回忆 | “上次我去括号主要错在哪里？” | 相关 L2，必要时回溯 L1 |
| 个性化表达 | “按我之前说的方式再解释一下” | 有证据的偏好及当前明确要求 |

“继续上次没做完的题”首先验证任务恢复，不宜只当画像命中。三个能力分别测，避免把查到任务进度说成 L3 记忆效果。

### 7.1 命中率必须定义到可判定的对象

如果每题只考一个目标事实，可以统计正确体现该事实的问题数占比；如果每题有多个目标事实，应说明按事实项还是按整题统计。71% 和 90% 在未确认口径前不能倒推出实际题数。

区分“相关事实进入上下文”和“回答正确使用事实”两个环节，命中上下文不代表回答正确。误用别人的事实、编造历史、使用已经失效的偏好也要计入失败分析。

### 7.2 比较方案与边界

可比较仅近期对话、增加相关 L2、再增加 L3 等方案，在相同问题和生成配置下看改善。样本包括无历史、历史冲突、最近纠正偏好、暂停未完成和补救后通过，不能只放容易记住的例子。

来源和期望事实由人工复核，开发样本与独立验收样本分开。综合启用 L2/L3 后的提升不能全归因于 L3；“回答一致性”也需要相应检查，不由命中率自动证明。

## 8. 高频追问

**问：为什么不只留一份用户总结？**

> 总结方便使用，但容易丢来源和过程。L1 保留证据，L2 提炼可追溯事实，L3 提供可复用概览。查到画像后能回溯，而不是只能相信一段总结。

**问：学生暂停时会写三层记忆吗？**

> 先保存任务状态和原始事件，恢复不等待记忆模型。暂停不等于完成，不强制刷新长期结论；任务完成或批处理时再提炼有价值的事实。

**问：L3 说薄弱，本次答对了怎么办？**

> 用本次证据评估当前任务，保留历史错误，增量更新当前判断，不让旧画像覆盖新表现。

**问：L2 还没生成，下一次提问怎么办？**

> 当前任务直接查已保存业务证据和近期对话；L2/L3 是派生视图，不应该成为事实访问的唯一通道。异步延迟不能导致伪造历史或丢失进度。

**问：有记忆了，为什么还要 RAG？**

> 记忆用于了解学生，教材检索用于获取知识依据。过去一次错误回答不能成为知识来源。

**问：记忆输出格式合法，就能相信吗？**

> 不能。程序检查身份、来源引用及格式，语义还需审核和评测；不能把推断写成原始事实，不能把助手评价当作学生独立掌握证据。

## 9. 一分钟面试口述

> 三层记忆和学习 Workflow 是通过业务事件衔接的。Workflow 保存阶段、题组和等待点，负责暂停恢复；L1 保存学生答案、提示使用和评估等原始证据；L2 按场景提炼本次学习事实，并引用 L1；L3 再结合已有画像和新增 L2，维护近期学习状态和偏好。
>
> 比如分配律任务中，学生首轮漏乘，补救后通过。原始两轮证据都保留，L2 记录完整过程，L3 只形成当前可用的学习判断，不直接标成永久掌握。下次学习读取相关记忆选择诊断方向，但仍以本次表现验证。
>
> 普通聊天可以批量归并，学习任务则增加完成事件触发，跨会话按知识点和任务关联查询。上下文按节点需要组装，不把全部历史反复塞入。这样把任务进度、原始证据和长期个性化分开。

按实际建设范围调整“保存”“增加”等动词；未完成的机制明确说设计方案，数字仅在有日志和评测依据时使用。

## 10. 面试前只记四句话

1. Workflow 管执行进度，Memory 管学习经历。
2. L1 留证据，L2 提炼场景事实，L3 维护可更新画像。
3. 开始时读相关记忆，过程中保存证据，结束时增量回流。
4. 历史决定先问什么，本次证据决定当前结论。
