先用一句话记忆各组件：Embedding 负责表示，Milvus 负责管理和搜索，BM25 负责词项相关性，RRF 负责融合名次，Rerank 负责重新判断候选正文，LLM 负责基于证据组织回答。

**Milvus 不等于 Embedding 模型，也不等于 HNSW 算法；BM25 不等于一个神经网络模型；RRF 不等于语义重排。**

## 3. 必备知识点清单

- [ ] 1024 维是一条向量的长度，不是向量条数、知识点数或模型输入长度。
- [ ] 先确定 Embedding 的实际输出，再设置 Collection 向量字段的 dim。
- [ ] 写入与查询要在同一可比较的向量空间，维度相同不代表不同模型能混用。
- [ ] BGE-M3 的三个 M 是多语言、多功能、多粒度，不是三种模态。
- [ ] BGE-M3 的 Dense 是 1024 维；8192 Token 是模型输入长度能力，不是输出维度。
- [ ] BGE-M3 learned sparse 不等于 BM25；使用 Dense 输出也不代表三种检索都已接入。
- [ ] BM25 是词项相关性评分，重点是词频饱和、逆文档频率和长度归一化。
- [ ] 倒排索引是词项定位候选的数据结构；BM25 是给候选评分的办法。
- [ ] Dense 与 BM25 原始分数不能不经处理就直接相加。
- [ ] RRF 不读取正文；Rerank 也不能找回候选集合之外的证据。
- [ ] Top K、RRF 平滑参数、HNSW ef、Embedding 维度是不同参数。
- [ ] 不使用 ANN 加速不等于 Milvus 向量字段完全不配索引；FLAT 是精确扫描方案。
- [ ] 年级和 user_id 过滤须覆盖所有召回路；索引不会自动完成权限判断。
- [ ] 单用户几千条不等于整库只需几千条向量的资源。
- [ ] ANN 近邻召回率不等于业务证据 Recall，业务证据命中也不等于回答正确。
- [ ] 同步失败、旧版本命中与删除传播需要明确处理，不能把向量库当权威事实源。

## 6. 项目技术定位

AI 应用工程与后端检索治理：通过模型表示、向量服务、词项召回和证据管理，支撑学生问答及跨会话任务记忆。面试重点是把业务约束落到检索链路，而不是宣称自研 Embedding 模型。

已实现业务的简化主链：

```text
离线教材：解析与清洗 → 按语义边界切分 → Embedding → Milvus 教材记录
                                   → 文本分析与关键词索引
离线记忆：任务结束或检查点 → L2 权威记录 → Embedding → Milvus 记忆索引

在线教材：问题 + 教材范围
          → Dense 召回与 BM25 召回（两路都保留范围限制）
          → 按同一片段标识去重 → RRF → Rerank → 少量教材证据

在线记忆：问题 + 可信用户身份
          → 精确查询或带用户过滤的 L2 语义召回
          → 回关系库核对状态与版本 → 必要时重排 → 少量历史经历

当前题目 + 教材证据 + 相关 L2 + 适用 L3 → LLM 组织回答
```

教材混合检索不等于 L2 必须再接一条 BM25 路。两类负载可以共享基础设施，但依据、排序目标和过滤条件不同。

## 7. 核心原理解析

### 7.1 表示选型：为什么先选模型，再谈 1024 维

**问题：** 学生问“为什么括号前是负号就要变号”，教材可能写“去括号法则”。单纯比较字符串可能错过相关材料。

**机制：** Embedding 将文本转换成定长数值表示，通过距离或相似度检索相关文本。维度是单条表示的长度；文档和查询必须由兼容的编码过程生成。数据库只检查字段规格并执行检索，不负责把任意长向量变成有效的 1024 维表示。[Milvus 稠密向量](https://milvus.io/docs/dense-vector.md)

**项目落点：** 教材片段与 L2 任务摘要是不同粒度的检索单元。1024 维可作为候选，而不是从百万条数据倒推出来的必选值。

模型选型看五项：中文和教育内容的召回表现、短问题与长片段匹配能力、输入长度、在线查询延迟和部署成本、版本及数据处理约束。通用榜单可以筛候选，但不能替代本项目的问题集。

维度更高通常增加向量存储和距离计算开销，但不保证质量更高。不同模型即使维度相同，也不能默认相互检索；改模型或输出维度通常需要重编码受影响的数据和重建索引。

### 7.2 BGE-M3：三个 M 与三种输出不要混淆

**问题：** 项目既有口语化中文问题，也有教材段落，面试官可能问为什么考虑 BGE-M3，而不是只说它效果好。

**机制：** 三个 M 分别对应多语言、多功能、多粒度；模型支持 Dense、learned sparse 和 ColBERT 式 multi-vector 检索。Dense 输出为 1024 维，支持最长 8192 Token 输入；模型卡说明其查询编码不需要照搬 BGE v1.5 的检索指令。[BGE-M3 官方模型卡](https://huggingface.co/BAAI/bge-m3)、[M3 原始论文](https://arxiv.org/abs/2402.03216)

| 模式 | 直观理解 | 需要额外考虑什么 |
| --- | --- | --- |
| Dense | 一段文本得到一个稠密向量，比较整体相关性 | 中文语义和精确术语能否兼顾 |
| Learned sparse | 对文本中的词项生成模型学习到的权重，做词项交互 | 这是神经模型输出，不是直接套 BM25 的 TF/IDF 公式 |
| Multi-vector | 一段文本得到多条向量，通过更细的交互评分 | 存储与检索开销更高，不能按单向量容量直接估算 |

**项目落点：** 本次将 BGE-M3 作为候选知识学习，不新增“生产已使用”结论。即使选它，也可以先只用 Dense 与已有 BM25 配合，不因模型有三种输出就全部启用。

8192 Token 是输入能力上限，不是建议每个 Chunk 都切到上限。切分还要兼顾证据粒度、重排开销、最终上下文与信息定位。

### 7.3 BM25：不是字符串相等，而是词项相关性排序

**问题：** 教材里有准确的知识点名称、篇名和章节术语，语义检索可能找到同主题却不是所问对象的片段。

**机制：** 文本先经分析器得到词项，倒排索引记录哪些片段含有这些词项。BM25 综合词频、词项在语料中的稀有程度和文档长度，给候选排序；不需要神经 Embedding 模型。词频增加有收益，但收益会饱和，不能靠重复关键词无限涨分。[BM25 原理](https://nlp.stanford.edu/IR-book/html/htmledition/okapi-bm25-a-non-binary-model-1.html)

常见形式仅用于理解：

```text
score(q, d) = sum_t IDF(t) * tf(t,d) * (k1+1)
                         / (tf(t,d) + k1 * (1-b+b*len(d)/avglen))
```

`tf` 是当前片段的词项频率；`IDF` 反映词项在整个索引语料中的稀有程度；`k1` 控制词频饱和，`b` 控制长度归一化。具体 IDF 形式和参数默认值因实现而异，不把某个库的默认值当数学定律。

**项目落点：** BM25 补充 Dense 的词项精度。对公式、题号、术语不能保证天然命中，要检查中文分词、OCR、上下标、符号和词典；部分精确标识还可走专用字段查询。

中文不能默认只按空格切词。“一元一次方程”被怎样切分，会影响命中；索引与查询的文本分析应兼容。合理的同义词或查询扩展可以补词项差异，但不得改变知识点含义。

当前 Milvus 文档提供内置 BM25 全文检索：文本分析后生成 BM25 稀疏表示，不要求外部神经模型。实际可用功能取决于部署版本；项目的 BM25 后端未确认，不能直接说已使用该内置能力。[Milvus 全文检索](https://milvus.io/docs/full-text-search.md)

### 7.4 混合检索：召回、融合、重排分三层

**问题：** Dense 更能覆盖换一种说法，BM25 更能定位出现的词项，单路都可能漏掉有效证据。

**机制：** 两路按相同业务范围召回候选，按稳定片段标识去重。RRF 使用名次而非原始分数融合；语义重排再读取查询与候选正文，判断谁更能回答问题。[Milvus RRF](https://milvus.io/docs/rrf-ranker.md)、[Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

```text
RRF(d) = sum_i 1 / (k_rrf + rank_i(d))
```

没在某路出现的候选，在该路不贡献分数。`k_rrf` 是平滑参数，不是最终 Top K；不同路的召回数量也是独立参数。

**项目落点：** 混合检索负责候选覆盖；RRF 稳定融合不同量纲；Rerank 争取把有效教材证据放进有限上下文。重排的候选数、模型和长度预算要按实际配置说明。

RRF 并非唯一方案。若能校准各路分数且有可靠调参集，可以评估加权融合；未经校准直接把 BM25 分数与余弦分数相加，容易被某一路的数值范围支配。

常见重排模型采用 Cross-Encoder 联合评分，比独立编码后比较向量更贵；并非所有 Reranker 都有同一结构。重排无法增加输入候选集合的覆盖，也无法补充知识库里缺失的材料。

### 7.5 范围治理：语义相关不能替代年级正确与用户权限

**问题：** 相似文本可能来自不同年级、教材版本或其他学生，相关不代表适用。

**机制：** 把可信业务条件传进每一路检索，再在符合条件的记录中取候选。标准过滤可以在 ANN 前约束范围，复杂条件还存在不同执行策略；具体性能要按实际过滤分布评估。频繁过滤的字段可考虑标量索引，但索引不会自动增加过滤条件。[Milvus 过滤检索](https://milvus.io/docs/filtered-search.md)、[INVERTED](https://milvus.io/docs/inverted.md)、[BITMAP](https://milvus.io/docs/bitmap.md)

**项目落点：** 教材以年级元数据确定范围，必要时结合学科和版本；用户私有记忆始终保持可信身份隔离。用户身份来自认证上下文，不由 LLM 或客户端任意指定。

低基数字段如年级、状态，可评估 Bitmap；基数较高的用户标识，可评估倒排等索引。只是候选建议，不是生产配置结论，也不是所有字段都应建索引。

避免先全库 Top K 后在应用层删除不合条件的结果，否则有效候选可能不足。回表校验是版本、权限和状态的额外防线，不是漏做检索隔离的理由。

### 7.6 索引与容量：找到最近的，不一定找到能回答的

**问题：** 百万级向量可以管理在单机服务中，但检索速度、内存和质量不能只靠条数判断。

**机制：** FLAT 精确计算距离；HNSW 在多层近邻图上搜索；IVF 先分簇再查部分簇；PQ 将向量分段量化压缩。ANN 用近邻结果的可接受损失换取开销下降。[HNSW](https://milvus.io/docs/hnsw.md)、[IVF_FLAT](https://milvus.io/docs/ivf-flat.md)、[IVF_PQ](https://milvus.io/docs/ivf-pq.md)

**向量索引是必须的吗？要分算法原理与数据库配置。** 原理上，不用 HNSW 或 IVF 这样的
近似加速结构，也可以把查询向量与范围内每条向量计算距离，再取最相近的 Top K。
仅距离计算的工作量大致随候选数与维度的乘积增长，还要考虑过滤、数据访问和结果选择开销。

Milvus 当前常规 Collection 搜索流程要求向量字段有索引，并加载 Collection 后再搜索。
不希望采用 ANN 时，可以配置 `FLAT`：它逐条进行精确距离计算，不训练聚类、不构建
HNSW 图，也不需要这类索引的调参。虽然原理上是暴力扫描，Milvus 仍把它作为一种
向量索引类型管理。创建时自动配置了索引，也不等于完全没有索引。
[Milvus 搜索流程](https://milvus.io/docs/search_patterns.md)、[FLAT 官方说明](https://milvus.io/docs/flat.md)

结合项目，L2 按用户过滤后最多大几千条，FLAT 是值得比较的基线；教材过滤后若候选仍多，
或者峰值查询较高，再比较 HNSW、IVF 等加速方案。不能据此承诺某种硬件下的延迟，
也不能把 FLAT 的精确近邻说成业务证据必然命中。元数据过滤负责限定范围，不能代替
相似度计算；小候选集也不保证已有 HNSW 字段会自动切换为 FLAT 搜索。

| 方案 | 必会参数或特征 | 主要取舍 |
| --- | --- | --- |
| FLAT | 精确扫描基线 | 范围大时计算多；小候选集可能很合适 |
| HNSW | M、efConstruction、ef | 图结构占内存；建图与搜索参数分别调节 |
| IVF_FLAT | nlist、nprobe | 训练分簇；少查簇会漏近邻，查更多会增加耗时 |
| IVF_PQ | 在 IVF 上压缩表示 | 节省空间，但增加量化误差和调参复杂度 |

HNSW 的 `M` 影响连接数量与图资源；`efConstruction` 影响建图时的候选搜索；`ef` 影响在线搜索范围。IVF 的 `nlist` 是分簇数，`nprobe` 是查询访问的簇数。不能把这些参数当成输出条数或最大并发数。

**项目落点：** 单机部署与百万级总量已确认，具体索引未确认。合理策略是以真实过滤分布、硬件和峰值流量比较候选索引，不机械规定“百万一定 HNSW”。L2 强用户过滤下，小候选集精确搜索也值得做基线，但不保证数据库会自动选择该路径。

相似度也是独立选项。COSINE 比方向，IP 是内积，L2 比距离；非零单位向量下，内积等于余弦，平方 L2 等于 `2-2*cosine`，因此精确排序关系一致。非归一化向量不能直接套该结论。Milvus 的 L2 返回平方距离，COSINE/IP 越大越相近，L2 越小越相近；分数都不是答案正确概率。[Milvus 相似度度量](https://milvus.io/docs/metric.md)

原始容量示例：100 万条、1024 维、float32，`N*d*4` 约 4.1 GB（十进制）；不是本项目实际维度，也不是总内存需求。图、元数据、文本、运行缓冲与部署组件另计，驻内存量还取决于配置。

## 8. 关键设计决策

| 决策 | 备选 | 取舍 | 风险 | 验证建议 |
| --- | --- | --- | --- | --- |
| Embedding | 中文专项模型、BGE-M3、托管候选 | 质量、长度、资源与版本稳定性 | 榜单好但教材问题不匹配 | 固定语料、标注问题和过滤条件，比较召回与延迟 |
| 检索表示 | Dense；Dense+BM25；learned sparse；multi-vector | 先用满足需求的最少模式 | 把 BGE-M3 能力当已启用，增加不必要开销 | 检索路逐项消融，记录新增成本与证据覆盖 |
| 融合 | RRF；经校准的加权融合 | RRF 少依赖分数标度；加权更依赖调参 | 候选量或去重错误影响排序 | 固定候选，比较最终排序指标 |
| 索引 | FLAT、HNSW、IVF、压缩方案 | 召回、资源、构建与更新成本 | 强过滤下质量下降，压缩漏证据 | 以同范围精确结果为 ANN 基线，再做业务评测 |
| 数据组织 | 按用途的 Collection 与元数据隔离 | 分开教材和记忆的配置、生命周期 | 给每个用户单建 Collection 导致管理负担 | 看隔离要求、用户倾斜、管理开销；不预设生产结构 |
| 记忆存储 | 权威记录与可重建索引分工 | 支持版本和来源追溯 | 跨库存储不自动形成同一个事务 | 检查事件幂等、同步重试、版本回表与删除传播 |

不要把“采用了 Milvus”讲成“已经采用某种 HNSW 参数、Bitmap、分区键、分片副本或内置 BM25”。数据库、索引、部署和业务查询策略是分开的决策。

### 8.1 Qdrant 与 Milvus：能胜任，不等于从零选型时最省事

**针对已确认的百万级总量、单机部署、教材按年级和 L2 按用户过滤，如果从零选型并优先
低运维复杂度，可以优先评估 Qdrant；这不等于 Milvus 已经选错，也不证明 Qdrant 必然更快或更省内存。**
判断重心是部署、过滤检索与维护需求，不是按照数据条数给两个数据库划定固定分界线。

Qdrant 单节点可以作为单个服务或容器运行，向量和 payload 一起管理，适合先建立较简单
的服务链路。但生产仍要做访问控制、持久化、备份恢复、监控与容量管理，不能把快速启动
等同于零运维。[Qdrant 单机入门](https://qdrant.tech/documentation/quickstart/)

教材的 grade 与记忆的 user_id 可作为 payload 条件，并为频繁查询字段评估索引。
官方多租户方案包含共享 Collection 配合租户字段过滤，适合较多的小租户，没必要仅因为
用户数量多就为每人建独立 Collection。用户身份与查询条件仍由服务端可信上下文控制，
payload 索引不是权限系统。[Qdrant 多租户](https://qdrant.tech/documentation/manage-data/multitenancy/)

Qdrant 支持过滤感知的 HNSW，并有根据过滤候选估计量及配置选择全扫描的规划机制。
因此单用户只有几千条候选的负载值得评估，但不能承诺“几千条一定走全扫描”：阈值还
涉及向量大小、字段索引及实际配置，不是统一的记录条数。小候选集也不会消除整库资源
需求。[Qdrant 索引与查询规划](https://qdrant.tech/documentation/manage-data/indexing/)

**Qdrant 有 FLAT 吗？有对应的精确扫描能力，但没有 Milvus 式的独立 FLAT 索引类型。**
Qdrant 常规稠密向量索引使用 HNSW，查询时可用 `models.SearchParams(exact=True)`
禁用近似搜索，执行精确全扫描。已带 user_id 条件时，结果范围仍受该用户过滤约束，
不能为了做精确基线去掉权限条件。下面只是参数概念对照，不是已执行的生产操作：

```text
Milvus：选择 index_type="FLAT"，配置精确扫描方案。
Qdrant：查询时设置 SearchParams(exact=True)，请求精确全扫描。
```

`exact=True` 是查询参数，不会删除或停建已有 HNSW 索引。默认查询也不代表一定遍历
HNSW，规划器可以依据候选估计量及配置选择扫描；强制精确与自动规划是不同选择。
精确描述的是当前向量和度量的近邻结果，不是回答正确率。若做原始向量精度基线，
还应明确是否存在量化以及量化的使用方式，避免把压缩表示的误差混入索引比较。
[Qdrant 精确搜索](https://qdrant.tech/documentation/search/search/)、
[量化查询设置](https://qdrant.tech/documentation/manage-data/quantization/)

Milvus 同样可以单机运行，并提供更多向量索引选择。部署复杂度必须结合版本和安装路径
比较，不能把所有 Milvus 都等同于分布式集群或必须维护外置服务；当前官方 RPM/DEB
Standalone 方式使用嵌入式元数据与消息组件来简化依赖。
[Milvus 单机包部署](https://milvus.io/docs/install_standalone-binary.md)

两者都可承接 Dense 与稀疏检索，具体 BM25 的编码、索引或服务位置仍要按版本及实际
实现确认；不能因数据库换名就说混合检索链路自动完成。整体比较还要计入文本分析、
Embedding、重排和其他服务的开销，而不只比较向量服务的容器数量。
[Qdrant 混合检索](https://qdrant.tech/documentation/search/hybrid-queries/)、
[Milvus 全文检索](https://milvus.io/docs/full-text-search.md)

结论分三种口径：从零搭建且重视简单运维，可以倾向 Qdrant；已有 Milvus 稳定服务业务，
没有明确收益不必只因规模迁移；简历与项目口述继续使用实际采用的技术，不通过选型讨论
改写生产事实。此处是候选方案对照，本次未确认迁移或替换，不改变前文的 Milvus 记录。

## 9. 量化与验证：准备口径，不编结果

### 9.1 三层质量与一层成本

| 层次 | 建议指标 | 它回答的问题 |
| --- | --- | --- |
| 向量索引 | ANN Recall@K，对照同一过滤范围的精确近邻 | 索引是否漏掉模型认为相近的记录 |
| 业务召回与排序 | Recall@K、Hit@K、MRR、nDCG | 正确证据有没有被找到，是否排在前面 |
| 最终回答 | 证据支持、事实正确性、教材适用性、记忆适用性 | 模型是否真的用对证据 |
| 资源与服务 | 分阶段 P95/P99、峰值 QPS、内存、超时和费用 | 质量是否在可接受的成本下实现 |

单题 `Recall@K=命中的相关证据数/全部标注相关证据数`；`Hit@K` 只判断前 K 是否至少命中一个。多题汇总说明采用逐题平均还是其他口径。MRR 看第一个相关结果的倒数名次；nDCG 关注位置和相关程度。无可回答证据的问题应单独检查拒答或澄清，不随意放进 Recall 分母。

### 9.2 建议评测步骤，未在本次执行

1. 收集口语化提问、精确术语、跨年级同主题、长片段与无答案问题；教材与 L2 分开标注。
2. 固定语料版本、片段标识、模型版本及业务范围，开发集调参，保留独立测试集。
3. 教材比较 Dense、BM25、混合融合、增加重排的逐步变化；L2 检查精确定位与语义检索边界。
4. 记录失败在语料覆盖、切分、文本分析、模型编码、过滤、ANN、融合、重排还是生成阶段。
5. 记录可选查询重写、Embedding、检索、融合、重排与生成的分段耗时，不把端到端慢全部归因于向量库。

真实待补信息：Embedding 模型 ID 与版本、输出维度、Milvus 版本、向量和标量索引、BM25 实现、机器配置、峰值 QPS、候选数、最终 Top K、真实评测口径。此处待补仅指配置和证据信息，不表示项目未实现。

### 9.3 一致性与异常的口述边界

已有记忆材料采用关系库权威记录与异步向量索引同步，向量命中后回表检查版本、状态及来源。教材更新同样需要明确版本和索引重建范围。向量删除、权威撤回和缓存失效不能彼此遗漏。

重排超时可回退到已过滤的融合排序；Milvus 暂不可用时，记忆可按用户、知识点和时间走已有结构化查询。不能通过取消用户隔离、使用别的年级或强行放宽权限来补足候选；没找到可靠教材证据，应澄清或明确证据不足。

### 9.4 两个可练习的例子

**教材例子：** 学生问“括号前面是负号，为什么里面都变号？”先确定年级和教材范围，Dense 找相近解释，BM25 补去括号法则相关词项，融合后重排选取真正解释变号原因的证据。术语被 OCR 弄错时，先修语料或查询，不能只调大索引参数。

**记忆例子：** 学生问“我以前是不是也在这种题上错过？”先确定用户和当前知识点，检索相关 L2，再回表核对任务版本和证据性质。找到了同类错误不等于今天仍未掌握，过去的任务结果不能直接改成当前 L3 的确定结论。

### 9.5 一万条范围下的查询耗时：分段口径与计算示例

本节按用户提出的“单用户 L2 或一次教材查询的相关范围约一万条”讨论，不把该范围当成全库总量，
也不覆盖前文已确认的生产规模。**仅凭条数不能确定耗时，下面的数字是计算示例，不是项目实测、行业标准或服务承诺。**

历史 L2 和教材片段已在入库时编码；一次普通检索只编码当前查询，不重新向量化一万条历史记录，
也不重新生成 L1/L2/L3。在线延迟要区分三种口径：

| 口径 | 计入什么 | 不应混入什么 |
| --- | --- | --- |
| 向量搜索调用 | 给定查询向量和过滤条件，从发起数据库请求到收到候选结果；含这次 RPC | 查询 Embedding、重写和重排；数据库内部计算时间也不能直接当成客户端调用时间 |
| L2 记忆检索 | 查询 Embedding、带用户过滤的向量搜索、批量回关系库核对；按需增加重写或重排 | 后台记忆提炼、画像归并、最终回答生成 |
| RAG 检索链路 | 按需重写、查询 Embedding、Dense/BM25 召回、融合、重排及取证 | 最终聊天模型的首 Token 或完整回答时间；若一起统计需明确改为回答端到端口径 |

向量搜索可以按毫秒级步骤理解，但不能从一万条保证某个固定毫秒数。索引、实际维度、过滤分布、
内存与冷热状态、返回字段、持续写入、并发、网络和排队都会改变结果；小数据集也可能有未索引段。
公开基准同样需要固定硬件、数据集、精度和并发条件，不能直接作为本项目数据。
参考：[Milvus 性能 FAQ](https://milvus.io/docs/performance_faq.md)、[Qdrant 基准的测试口径](https://qdrant.tech/benchmarks/)。

以下是假设短查询、较短的非思考重写、少量重排候选、同机房数据库且低负载时的一组延迟预算示例。
它只帮助计算各步骤如何叠加，不代表模型或硬件已经选定，也不是 P50/P95：

| 步骤 | 假设耗时 |
| --- | --- |
| 查询 Embedding | 100ms |
| 带过滤的向量搜索调用 | 20ms |
| L2 批量回表核对 | 10ms |
| LLM 查询重写，等待完整改写结果 | 500ms |
| BM25 召回 | 10ms |
| RRF 融合与去重 | 5ms |
| 小候选集 Rerank | 200ms |

```text
L2 记忆检索，不重写、不重排：
  100 + 20 + 10 = 130ms

RAG 重写 + Embedding + 单路向量召回：
  500 + 100 + 20 = 620ms

RAG 重写后，Dense 分支（含 Embedding）与 BM25 分支并行，再融合、重排：
  500 + max(100 + 20, 10) + 5 + 200 = 825ms
```

这是一次假设请求的关键路径计算。各阶段的 P95 不能直接相加就宣称得到端到端 P95，
端到端分位数需要从同一批完整请求单独统计。网络或模型排队、CPU 编码、长输入、深度思考及更大候选集
都可能让链路明显超过这个例子；模型输出长度和思考模式也影响总等待时间。
参考：[百炼深度思考的耗时说明](https://help.aliyun.com/zh/model-studio/deep-thinking/)。

面试时的实测口径应至少包括：全库总量与过滤后范围、模型及维度、索引和机器、Top K、
查询长度、并发/QPS、缓存冷热、是否重写/重排，以及各阶段和完整链路的 P50/P95、超时率与召回质量。
P50 表示一半请求不超过的时间，P95 表示 95% 请求不超过的时间。现在没有可核对的延迟记录，
不能把上述示例改成“我们线上就是 130ms/825ms”；这只是性能证据缺口，不表示项目未实现。

优化方向与已落地机制分开讲：查询已明确时可以评估跳过重写，重写用短输出并避免不必要思考，
独立检索分支可并行，小候选集批量重排、回表核对用批量查询。每项优化都要同时检查质量与延迟，
不能通过取消用户过滤、只取全库候选再过滤，或减少必要证据来换取更快的数字。
