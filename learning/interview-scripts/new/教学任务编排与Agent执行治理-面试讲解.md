# 教学任务编排与 Agent 执行治理：面试讲解稿

> 说明：本文是基于 `鼎校伴学-知识点学习闭环与面试学习指南.md` 的口述稿，按已实现的项目口吻撰写，口述时直接用"我实现了/我做了"。文中没有性能数字和用户规模；如果你有真实线上数据，自己补进去，没有就不要编。

## 1. 简历原文（三点版）

**教学任务编排与 Agent 执行治理**

- **多 Agent 分层编排**：针对纯对话讲解难以确认学生理解的问题，依据教研流程将"错因诊断—针对性讲解—练习—复述验证"拆为多个阶段专职 Agent，各自独立管理 Prompt、工具与验收规则，由外层 Workflow 统一编排阶段推进与分支路由。
- **跨轮状态驱动**：任务以用户事件驱动、跨多轮执行，通过持久化的任务状态与版本号支撑等待作答、暂停恢复与断点续跑；阶段内按需运行 Agent Loop 完成检索与讲解，而非一次性大模型请求。
- **证据验收与有界补救**：以独立作答和概念复述为证据，由规则判定阶段通过，LLM 仅负责评分、无权写终态；未通过限次补救，作答证据回流 BKT 更新掌握度，并以轮次上限与 Forced Finish 约束执行边界。

三点的分工：第一点讲结构，第二点讲为什么不是简单 workflow，第三点讲怎么收口。

## 2. 一句话定位

这是一个"外层受控 Workflow + 阶段内专职 Agent"的混合设计。外层决定当前允许做什么，内层 Agent 决定这一步怎么做。灵活性放进可控边界里。

## 3. 1 分钟版

纯对话讲解有个老问题：讲完了，没人知道学生到底懂没懂。所以我按教研流程把辅导拆成四步：错因诊断、针对性讲解、练习、复述验证。

每一步是一个专职 Agent，有自己的 Prompt、自己的工具、自己的验收规则。比如诊断只产出带证据的错因假设，讲解可以检索教材，验证按固定量规判分。

外层有个 Workflow 管阶段推进和分支。整个任务是用户事件驱动的，学生没作答就暂停，回来再恢复，状态持久化，不是一次大模型请求。

通过与否看学生独立作答和复述，不看模型自评。没过就限次补救。作答证据会回流 BKT 更新掌握度，薄弱点和后续推题由掌握度统一判定，Workflow 自己不另算掌握度。

## 4. 3 分钟版

### 4.1 为什么要做（动机）

纯对话讲解有两个问题。第一，讲解不等于理解，没有证据。第二，模型容易顺着聊，要么反复讲同一段，要么直接说"你已经掌握了"。

所以目标不是"讲得更好"，而是"能确认学生懂了，并且在不懂时知道下一步做什么"。

### 4.2 怎么做（结构）

我把过程分成两层：

- 外层 Workflow：管阶段（确认目标、诊断、规划、检索、讲解、组卷、等待作答、判分、等待复述、评估、补救、收尾）和生命周期状态（进行中、等待用户、暂停、完成、取消、过期、失败）。它决定当前允许做什么。
- 内层 Agent：每个阶段有专职 Agent。需要自主决策的地方（比如讲解阶段改写检索词、多次检索）才跑 Agent Loop，拿到阶段结果就退出。

这就是为什么我说它不是一个简单 workflow：每个阶段的 Prompt、工具白名单、准入检查和验收规则都不一样，更接近多 Agent，只是调度权在外层，不让 Agent 自己乱跳阶段。

### 4.3 为什么有跨轮（状态）

一个任务会跨很多轮对话，但 Agent Loop 不是一直在跑。学生没作答，任务就停在等待状态，不消耗模型。学生回复了，一个事件触发恢复，从持久化状态继续。

状态里有生命周期、教学阶段和版本号。版本号用来做乐观锁，防止并发写覆盖。组卷这类有外部副作用的操作带幂等键，重复触发不会重复出题。

### 4.4 怎么收口（治理）

- 模型只返回"带依据的候选判定"，终态由确定性规则写。
- 每个 Agent 有轮次上限和上下文裁剪，到上限走 Forced Finish：基于已有证据总结，并标出没解决的部分。
- 没通过就限次补救，连续不过就以 Workflow 结论"需要复习"收尾，不降低通过门槛，也不无限讲下去。
- 掌握度只有 BKT 一份：Workflow 把作答证据按事件 ID 幂等回流 BKT；薄弱点和后续建议由 BKT 掌握度加本次结论统一判定，再驱动推题。

最终有三种结果：目标达成、需要复习、证据不足。

## 5. 5 分钟版补充：一个具体例子

学生一道题做错。

1. 确认目标：确认是哪个知识点。
2. 诊断：Agent 结合错题给出错因假设，并附证据。不是直接下结论。
3. 讲解：挂载教材检索，针对错因讲，引用必须真实可查。
4. 组卷：出变式练习。这里带幂等键，重复事件不会重复出卷。
5. 等待作答：任务暂停，Agent Loop 不运行。
6. 判分：学生提交后恢复，按量规判分。
7. 复述验证：让学生用自己的话讲一遍，防止只会套题。
8. 评估：作答加复述两类证据都够，才算通过。
9. 补救或收尾：不过就换讲法再来，限次数；仍不过就以"需要复习"收尾。作答证据回流 BKT，薄弱点和后续建议由掌握度判定。

## 6. 高频追问与回答

**Q1：这和普通 workflow 有什么区别？**
普通 workflow 是固定节点，每个节点是一次函数调用。我这里节点内部是带工具的 Agent，Prompt 和工具各不相同，而且任务跨多轮、可暂停恢复。外层固定、内层自主。

**Q2：这是真的多 Agent 吗？**
是混合设计。我不说成"多个 Agent 自由对话"。阶段内才是带决策和工具的 Agent，阶段之间由外层 Workflow 调度。这样既有灵活性，又能保证不乱跳阶段。

**Q3：为什么不让一个大 Agent 自己决定所有步骤？**
三个原因。一，教学流程有明确的教研顺序，不该靠模型临场决定。二，通过与否影响学习记录，必须由证据和规则决定。三，单个 Agent 工具太多，Prompt 太长，容易选错工具、跑偏。拆开之后每个 Agent 的 Prompt 和工具都更小更专。

**Q4：学生很久不回来怎么办？**
任务停在等待状态，有过期状态兜底。回来时从持久化状态恢复，不依赖进程内存，所以跨进程重启也能续上。

**Q5：并发或重复事件怎么处理？**
状态带版本号做乐观锁，写入时版本对不上就拒绝。有外部副作用的步骤（如组卷）用业务幂等键，由任务、作答尝试和操作版本组成。对外部操作做对账，处理"做了一半"的情况。

**Q6：怎么防止模型说"你已经掌握了"？**
模型没有写终态的权限，只给候选判定和依据。是否通过由独立作答和复述证据加规则判定。

**Q6.1：Workflow 和 BKT 谁说了算？会不会冲突？**
掌握度只有 BKT 一份，Workflow 不另算。Workflow 管的是"这次辅导有没有达成目标"，BKT 管的是"这个知识点大概率会不会"，两者通过证据事件衔接。诊断阶段的独立作答按事件 ID 幂等回流 BKT；讲解之后的练习打上"讲解后"标记，不当独立诊断证据，避免高估；复述由量规判定，只用于 Workflow 的通过判断。出现"Workflow 通过但 BKT 概率还没到线"是正常的，处理方式是安排间隔复习或变式验证，不互相覆盖。

**Q7：Forced Finish 是什么？**
Agent 达到轮次上限时，不再继续调用工具，而是基于已有证据总结，并明确标出哪些没解决。这样不会无限循环，也不会假装完成。

**Q8：用了 LangGraph 吗？**
LangGraph 是可选的编排实现之一，不要说成项目已确认的技术栈。如果被问，答"外层编排的关键是状态机和持久化，用什么框架是实现选择"。只有你确实用了才说用了。

**Q9：效果怎么样，有数据吗？**
有真实数据就直接报（比如一次通过率、补救次数分布）。没有就先讲机制层面的保证，再说指标是后续持续评估的方向。不要编数字。

**Q10：最大的难点是什么？**
我会讲边界划分：哪些交给模型（诊断假设、讲解组织、检索改写），哪些必须由确定性代码和业务规则负责（阶段推进、终态、幂等、验收）。划错了，要么太死板，要么不可控。

## 7. 口述注意事项

- 先讲问题，再讲结构，最后讲治理。不要一上来堆术语。
- "多 Agent"后面马上跟"受控"，别让面试官觉得是自由群聊。
- 被问实现细节，用"我是这样实现的，原因是……"的口吻，讲清取舍和边界。
- 不报没有依据的数字；有真实数据就用，没有就讲机制。
- 动词用完成式：实现了、落地了、负责了。
