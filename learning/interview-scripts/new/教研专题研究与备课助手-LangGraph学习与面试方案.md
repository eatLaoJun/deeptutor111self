# 教研专题研究与备课助手：LangGraph 学习与面试方案

## 1. 定位与当前状态

这是一份待实现的业务扩展与面试学习方案，不代表当前项目已经上线该能力。目标是在现有学生辅导业务之外，补充面向教师的专题研究与备课任务，学习动态任务规划、条件编排、人工反馈和证据校验。

现有简历已经覆盖 Agent Runtime、Memory、教材 RAG 和个性化练习。新增业务应补足不同的任务形态，而不是重复增加框架关键词。面试邀约率低的原因尚未验证，不能直接归因于业务数量不足。

## 3. 为什么不是简单地写“CoT + Workflow”

更准确的技术主线是：Plan-and-Execute + 反馈修订 + 有状态编排。

- 推理：模型分析需求、识别信息缺口。
- 规划：输出系统能读取的结构化子任务，而不只是自然语言说明。
- 编排：程序安排节点执行、等待用户、合并结果和控制终止。
- 反馈：根据证据与任务完成情况决定补查、修订或结束。

结构化计划不是模型内部思维链，LangGraph 也不是让模型自动具备正确推理能力的组件。面试时优先讲可观察的任务计划、工具调用、证据和状态变化，不以展示思维链代替效果验证。

## 4. 业务场景：教研专题研究与备课助手

示例需求：

> 为人教版八年级“一次函数”准备一份专题教学方案，包含先修知识、常见误区、分层例题与课堂练习，并标注教材依据。

预期交付物：教学目标、先修知识、教学重难点、讲解提纲、例题与练习、来源引用，以及资料不足或需要教师复核的提示。

与已有辅导业务的区别：

| 维度 | 学生辅导 | 教研专题研究 |
| --- | --- | --- |
| 对象 | 学生 | 教师、教研人员 |
| 任务范围 | 一道题或一个知识点 | 一个专题的完整材料 |
| 流程特征 | 教学阶段相对固定 | 研究子任务随需求生成 |
| 交互重点 | 学生作答、理解验证 | 教师确认计划、修改材料 |
| 输出 | 讲解与反馈 | 带证据的结构化备课材料 |

## 5. 建议的任务链路

```text
需求澄清：教材版本、年级、专题、课时与输出要求
    ↓
生成结构化备课计划
    ↓
教师确认或修改 ── 修改 → 修订计划
    ↓ 确认
按计划执行研究子任务
    ├─ 教材与课标依据
    ├─ 先修知识与常见误区
    └─ 分层例题与课堂练习
    ↓
汇总证据并检查覆盖、一致性与来源支撑
    ├─ 存在缺口且未超预算 → 定向补查
    └─ 充分或预算耗尽 → 生成材料，明确剩余缺口
    ↓
教师审阅与交付
```

这张图是改造方案，不是对原项目图结构的逐节点复述。并行任务必须先确认没有前置依赖，不能把所有子任务无条件并发。

可复用的业务资产包括教材 RAG、知识点树和题库接口；接入前仍需核对实际接口、权限与元数据质量。外部搜索只用于允许的资源，并与内部教材证据区分来源。

## 6. LangGraph 的具体落点

### 6.1 状态设计

建议从最小状态开始：

| 状态字段 | 用途 |
| --- | --- |
| request_constraints | 教材版本、年级、主题、课时等约束 |
| plan / plan_version | 当前任务计划及版本 |
| teacher_feedback | 教师修改意见与确认结果 |
| task_results | 按任务标识保存研究结果 |
| evidence_refs | 来源标识、页码或链接等证据引用 |
| gaps | 尚未解决的信息缺口 |
| revision_count / limits | 补查次数及预算边界 |
| final_material | 最终材料与未解决问题 |

计划任务可包含 `task_id`、目标、依赖、检索范围、预期产物和验收条件。避免将所有原始文档无限追加到共享状态中。

### 6.2 条件路由

固定图结构负责定义允许的执行路径，模型生成的计划负责表达本次任务内容。动态任务规划不等于让模型任意修改图或调用任何工具。

重点分支：需求不完整则澄清；计划未确认则等待；证据不足且仍有预算则补查；任务完成或预算耗尽则输出结果。

### 6.3 人工确认与恢复

优先验证“教师修改计划后继续执行”这一条路径。应用需要关联同一个任务标识，保存计划与反馈，而不是一直挂着请求等待回复。

Checkpoint 的持久化后端、线程标识和恢复入口需要明确配置。进程重启后是否恢复成功必须通过测试证明，不能仅因使用了检查点就声称具备完整故障恢复。

### 6.4 结果合并与计划变更

研究结果按任务标识归档。若采用并行分支，需要明确共享字段的合并规则，避免覆盖、重复追加与顺序不确定。

教师改计划后，判断哪些任务结果仍有效，哪些必须作废；通过计划版本避免将旧计划结果混入新报告。

### 6.5 副作用与执行边界

恢复过程可能重放部分操作。发布材料、写入业务记录等有副作用的动作需要独立考虑幂等与去重，Checkpoint 不等于自动保证只执行一次。

设置最大补查轮次、超时及调用预算。证据不足时输出缺口，比反复检索或编造引用更合理。

## 7. 源码阅读与最小验证顺序

1. 阅读 `legacy.md`，确认工作流版本的输入、产物与人工反馈方式。
2. 从 `graph.py` 的图构建处反向追踪计划、反馈、检索写作和汇总节点。
3. 查看状态类型与结构化输出定义，理解节点读写哪些字段。
4. 沿调用关系阅读 Prompt，区分计划生成、内容写作与质量评估的职责。
5. 结合 notebook 跑通一个普通研究主题，再替换成一次函数备课场景。

第一轮只验证一条窄链路：生成计划 → 人工修改 → 确认 → 检索写作 → 不足补查 → 输出。

待验证清单：

- [ ] 普通主题端到端生成报告。
- [ ] 教师修改计划后，新计划真正影响后续执行。
- [ ] 检索不到材料时，流程有限终止并标出缺口。
- [ ] 使用持久化配置后，重启进程可以恢复同一任务。
- [ ] 结果引用能回到真实材料，教材版本不会混用。
- [ ] 若增加并行任务，结果不遗漏、不重复、不跨计划混合。

## 8. 面试讲解重点

### 为什么不是一次 Prompt 直接生成？

备课材料同时涉及范围约束、多源检索、教师反馈与证据校验。一次生成难以显式控制各项任务是否完成，也不便于定向补查和局部修订。

### 为什么使用 LangGraph？

目标不是替换模型能力，而是明确管理共享状态、条件分支、人工等待和执行恢复。节点内部仍可以使用已有检索工具或 Agent Loop，不必重写整套业务。

### 和现有教学 Workflow 有什么不同？

学生辅导围绕固定教学阶段推进；教研任务先生成研究计划，再按计划组织资料收集和产物生成。外层仍有固定规则，任务内容可以动态变化。

### 如何判断报告合格？

至少检查需求覆盖、教材版本一致、引用可追溯、关键结论有证据支撑以及例题答案正确。模型评分可以辅助，但不能替代确定性检查与教师抽检。
