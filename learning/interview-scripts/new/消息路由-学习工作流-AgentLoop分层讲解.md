# 消息路由、学习工作流与 Agent Loop：分层讲解

> 日期：2026-09-11。
> 定位：知识点学习 Agent 的设计理解与面试口述材料，不代表当前项目已经实现。
> 配套文档：[鼎校伴学：知识点学习闭环与面试学习指南](鼎校伴学-知识点学习闭环与面试学习指南.md)。

## 1. 先记住三个名字，不要记成五个 Agent

之前说的“外部三层”，合起来属于**消息接入与路由**；你理解的“第四层”，是**外层学习工作流**；最后才是阶段内按需运行的 **Agent Loop**。

```text
① 消息接入与路由：处理用户这次发来的消息
   ├─ 程序：校验任务关联和权限
   ├─ 模型辅助：识别回答、追问、暂停等用途
   └─ 程序：结合当前状态，校验并受理事件
                    ↓
② 外层学习工作流：管理整个学习任务的进度
   阶段、等待、分支、补救、暂停、恢复与结束
                    ↓ 按需调用
③ 内层 Agent Loop：完成当前需要灵活处理的步骤
   模型决策 → 工具调用 → 结果回填 → 继续决策
                    ↓
   阶段结果返回工作流，由程序校验和保存下一状态
```

**这是一种职责划分，不要求部署五个服务或使用五个模型。** 消息受理与状态推进可以在同一个应用服务中协调；图里的箭头也不表示每条消息必须走完所有组件。

| 模块 | 核心问题 | 类比 |
|---|---|---|
| 消息接入与路由 | 用户这句话想干什么，可以受理吗？ | 分清这次请求 |
| 外层学习工作流 | 任务进行到哪，接下来做什么？ | 管理学习进度 |
| 内层 Agent Loop | 当前这一步怎么完成，需要哪些工具？ | 执行具体步骤 |

## 2. 消息接入与路由：之前的“外部三层”

假设系统正在展示任务 T1 的诊断问题 D1：“3 应该乘括号里的哪些部分？”

前端发送：

```json
{
  "task_id": "T1",
  "reply_to": "D1",
  "message": "只乘 x"
}
```

这些字段是拟议交互示例。前端只是把当前界面关联的任务和问题带上，并没有证明内容相关，更不能替后端决定真实任务状态。

### 2.1 程序先检查关联和权限

检查 T1 是否存在、是否属于登录用户、D1 是否属于 T1，以及请求结构是否合法。

- 无权限或关联错误：拒绝，不把不该访问的任务内容发给模型。
- 没有明确关联：在授权范围内查找候选，必要时询问用户。
- 关联历史问题：可能是追问或重复提交，不能直接当成当前问题的新答案。

**这一层不是不校验，而是不负责理解自然语言。** task_id 是前端声明的关联，服务端状态才是执行依据。

### 2.2 识别消息用途

对自由文本，给模型最小必要上下文：

```text
当前阶段：等待诊断回答
当前问题：3 应该乘哪些部分？
用户消息：只乘 x
```

候选输出：

```json
{
  "message_type": "ANSWER",
  "needs_clarification": false
}
```

| 用户消息 | 可能用途 | 说明 |
|---|---|---|
| “只乘 x” | ANSWER | 在回答当前问题，但答案可能暴露误解 |
| “不知道” | ANSWER | 相关，却未必提供足够诊断证据 |
| “为什么要乘负数？” | FOLLOW_UP | 追问，不能自动按正式答案处理 |
| “先停一下” | PAUSE | 请求暂停，不是答题失败 |
| “讲一下英语” | NEW_REQUEST | 新需求，不推进原任务 |

通常一次结构化模型调用就足够，不需要在这里强行运行工具循环。可以把轻量模型作为待评估的实现选项，但不能因模型小或快就假定分类准确；具体模型选择需用任务上下文样本验证。明确的按钮 Action 可直接路由，跳过语义分类，但不能跳过权限和业务校验。

**ANSWER 只表示消息在回答问题，不等于回答正确，也不等于证据足够。** 是否支持错因假设属于后续诊断评估。

### 2.3 程序校验并受理事件

程序检查模型结果的结构、允许的类型，以及服务端最新状态：

- 任务是否已经暂停、取消或结束？
- 新答案是否对应当前等待的问题？
- 是否重复提交，是否发生并发版本变化？
- 当前事件允许触发什么业务动作？

不能只检查 JSON 是不是包含 ANSWER 或 PAUSE，就直接照做。已受理提交的重试，在鉴权后按幂等规则返回已有结果；新提交才校验当前版本并原子受理，详见主文档 Q15。

程序能够约束状态变化，但不能用格式校验证明语义判断正确。不确定就澄清，不因为输出格式合法而推进教学。

## 3. 外层学习工作流：你理解的“第四层”

它不一定是一个 Agent，也不是一个专门记录 task_id 的模型。它是整个学习任务的流程控制者。

### 3.1 task_id 是编号，状态才记录进度

```text
task_id：T1
所属用户：U1
status：WAITING_USER
stage：DIAGNOSE
等待问题：D1
已有证据：原题、错误步骤、相关历史引用
补救次数：0
```

只保存 T1 这个编号不够，还要保存它对应的目标、阶段、等待对象、题组和证据等。持久化记录存在，不代表后台有一个线程一直运行。

### 3.2 工作流负责四件事

| 职责 | 举例 |
|---|---|
| 记住进度 | 当前在等诊断答案，还是练习答案？ |
| 安排下一步 | 诊断证据足够后安排讲解，再安排练习 |
| 控制分支 | 达标总结，有明确薄弱点则在额度内补救 |
| 管理生命周期 | 暂停后保存，恢复后接着原阶段，取消后不复活 |

它依据阶段结果和既定规则推进，不是自己凭空完成诊断。比如错因评估可能调用一次模型，客观判分可能调用业务代码，复杂的检索讲解可能调用 Agent Loop。

阶段计算与最终状态提交之间仍要检查版本，避免用户已经暂停，迟到的讲解结果又推动任务继续组卷。

## 4. 内层 Agent Loop：工作流调用的一种执行方式

假设工作流允许进入“检索教材并生成针对性讲解”阶段：

```text
输入：本次目标、错因证据、必要上下文和允许的工具
   ↓
模型决定查询教材
   ↓
程序校验工具参数与权限，执行检索
   ↓
工具结果回填给模型
   ↓
模型判断依据是否足够
   ├─ 不够：在预算内调整查询，再调用工具
   └─ 足够：生成讲解和来源，结束本阶段 Loop
   ↓
阶段结果交回工作流，校验、保存并安排下一步
```

Loop 的“循环”是模型与工具之间的有限往返，不是持续询问学生是否回复。

- 限制轮次、调用次数和耗时，避免无限检索。
- 只能使用当前阶段允许的工具和权限。
- 不擅自修改通过规则，不直接把整个任务写成已掌握。
- 阶段失败返回明确失败或证据不足结果，由工作流决定重试、澄清或收尾。

**不是每个阶段都需要 Agent Loop：**

| 阶段工作 | 可以采用的执行方式 |
|---|---|
| 消息用途分类 | 一次结构化模型调用 |
| 诊断分析 | 一次模型评估，必要时由工作流发起追问 |
| 客观题判分 | 确定性代码或题库服务 |
| 教材检索与讲解 | 固定调用链，或需要灵活查询时使用 Agent Loop |
| 等待学生、保存暂停 | 状态持久化，不需要模型循环 |

### 4.1 补充：按课本讲解时，强制的是教材依据

当前方案不固定在进入讲解节点时由程序先调用 RAG。提示词明确教材证据与引用要求，模型可以先改写查询，再自主检索；已有有效片段则复用。准备结束时节点验收，不通过就反馈具体缺口，让模型在预算内补查或修改，仍失败则返回依据不足，不发布为教材支持的讲解。

检查使用后端真实工具结果及已保存的证据，不看模型是否声称“调用过 RAG”。来源和引用可做程序校验，讲解是否真正得到材料支持仍需内容核验与评测。

同一通用 Loop 可以服务多个节点：讲解节点配置教材证据检查，其他节点配置自己的规则，不需要分别重写循环。模型直接产出合格结果就是一轮退出，有必要才继续调用工具。工作流只按阶段结果安排后续处理。

完整策略与面试口述见主文档 4.8 节及 Q18。

如果题目无法可靠定位知识点，应先补全信息、缩小候选或确认转普通答疑，不进入按知识点组卷和掌握评估。定位失败是目标不明，检索失败是目标明确但课本依据缺失，不能混为同一种重试。详见主文档 4.9 节及 Q19。

## 5. 三个例子：不是每条消息都跑到 Agent Loop

### 5.1 学生说“先停一下”

```text
关联与权限校验
  → 识别 PAUSE
  → 程序检查任务允许暂停
  → 工作流保存 PAUSED 和当前进度
  → 确认暂停，结束本次处理
```

**这次不启动讲解 Agent Loop。** 暂停可由聊天触发，不需要前端一直显示暂停按钮。

### 5.2 学生回复“只乘 x”

```text
关联与权限校验
  → 识别 ANSWER
  → 程序受理当前诊断回答
  → 诊断评估：支持漏乘第二项的假设
  → 工作流允许进入讲解
  → Agent Loop 检索教材并生成讲解
  → 工作流保存结果、安排组卷并保存等待点
  → 返回练习，结束本次处理
```

如果诊断证据不足，就发一个澄清问题并等待，不必启动讲解 Loop。

### 5.3 学生提交练习答案

```text
关联与权限校验
  → 明确提交事件直接路由，或聊天输入先识别用途
  → 程序校验题组、重复提交和当前阶段
  → 工作流调用评分服务
  → 保存评分证据，生成概念解释问题
  → 保存新的等待点，结束本次处理
```

这一轮可能只用判分代码与一次问题生成调用，也不必有工具循环。部分答案的处理沿用主文档 Q16，不能收到任意答案就推进到概念验证。

## 6. 一个 Task 可以跨很多轮，但每次处理都会结束

```text
T1：诊断问题 → 等待用户
T1：收到诊断回答 → 讲解与练习 → 等待用户
T1：收到练习答案 → 理解验证 → 等待用户
T1：收到概念解释 → 总结或补救
```

Task 是学习任务；一次用户交互是处理一个消息/事件；一次模型调用是更小的执行动作；一个 Agent Loop 可以包含多次模型和工具调用。这些不是一一对应关系。

用户说“继续之前的讲解”时，在其权限范围内查找可恢复任务。明确匹配则读取状态，多个候选则询问，不能随便选一个。查任务可以由后端直接完成，也可以通过受控工具完成；模型不是查找数据库记录的必经环节。

恢复以任务状态决定从哪里继续，对话和证据补足上下文。如果停在答题却要求再讲解，应先说明和确认，而不是盲目重跑旧流程。

## 7. 最容易混淆的六句话

| 容易误解的说法 | 准确理解 |
|---|---|
| 前端传了 task_id，所以肯定是答案 | 只声明关联，后端验证权限，语义另行识别 |
| 第一层只传参数，不校验 | 第一层程序要做关联和权限校验 |
| 消息识别内部还有两层 Agent | 消息识别与学习工作流、阶段 Loop 是不同职责 |
| 模型返回 ANSWER 就进入讲解 | 受理回答后，还需要诊断证据支持 |
| 每个阶段都要用 Agent Loop | 程序、单次调用、固定工具链都可以完成阶段 |
| Task 没结束，后台 Loop 就不能停 | 等用户时保存状态并退出，下次事件再继续 |

## 8. 面试口述与学习自测

### 8.1 一分钟讲法

> 我把这个设计分为三块。第一块是消息接入与路由，内部先校验任务关联和权限，再识别用户是在回答、追问还是暂停，最后由程序结合当前状态受理事件。
>
> 第二块是学习工作流，负责整个任务的阶段、等待、补救和结束。task_id 只是编号，真正恢复依赖持久化的阶段、题组和证据。
>
> 第三块才是阶段内按需调用的 Agent Loop，比如讲解时让模型检索教材、读取工具结果再生成内容。暂停只改状态，简单判分可以直接用代码，不是每条消息都必须跑 Loop。需要学生输入时保存等待点并退出，下次再按任务状态继续。

### 8.2 三个自测问题

1. 同样带 T1 和 D1，为什么“只乘 x”和“先停一下”走不同路径？
2. 如果分类期间用户在另一端取消任务，为什么执行前还要检查最新状态？
3. 用户十分钟后才答题，这十分钟里应该保存什么，哪些执行不需要一直运行？

**最终记法：消息路由识别请求，学习工作流管理进度，Agent Loop 按需完成步骤。**
