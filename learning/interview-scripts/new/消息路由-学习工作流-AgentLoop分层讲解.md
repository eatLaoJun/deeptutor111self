# 消息路由、学习工作流与 Agent Loop：分层讲解

> 更新日期：2026-10-14。
> 定位：基于用户已确认的鼎校伴学项目，整理知识点学习 Agent 的分层理解与面试口述。字段与接口示例用于解释职责，不代表实际接口名称；新增建议与已有项目能力分别表述。
> 配套文档：[鼎校伴学：知识点学习闭环与面试学习指南](鼎校伴学-知识点学习闭环与面试学习指南.md)。

## 1. 先记住三个名字，不要记成五个 Agent

之前说的“外部三层”，合起来属于**消息接入与路由**；你理解的“第四层”，是**外层学习工作流**；最后才是阶段内按需运行的 **Agent Loop**。

```text
① 消息接入与路由：处理用户这次发来的消息
   ├─ 程序：校验任务关联和权限
   ├─ 模型辅助：识别回答、追问、暂停等用途
   └─ 程序：结合当前状态，校验并受理事件
                    ↓
② 外层学习工作流：管理整个学习任务的进度
   阶段、等待、分支、补救、暂停、恢复与结束
                    ↓ 按需调用
③ 内层 Agent Loop：完成当前需要灵活处理的步骤
   模型决策 → 工具调用 → 结果回填 → 继续决策
                    ↓
   阶段结果返回工作流，由程序校验和保存下一状态
```

**这是一种职责划分，不要求部署五个服务或使用五个模型。** 消息受理与状态推进可以在同一个应用服务中协调；图里的箭头也不表示每条消息必须走完所有组件。

| 模块 | 核心问题 | 类比 |
|---|---|---|
| 消息接入与路由 | 用户这句话想干什么，可以受理吗？ | 分清这次请求 |
| 外层学习工作流 | 任务进行到哪，接下来做什么？ | 管理学习进度 |
| 内层 Agent Loop | 当前这一步怎么完成，需要哪些工具？ | 执行具体步骤 |

## 2. 消息接入与路由：之前的“外部三层”

假设系统正在展示任务 T1 的诊断问题 D1：“3 应该乘括号里的哪些部分？”

前端发送：

```json
{
  "task_id": "T1",
  "reply_to": "D1",
  "message": "只乘 x"
}
```

这些字段是拟议交互示例。前端只是把当前界面关联的任务和问题带上，并没有证明内容相关，更不能替后端决定真实任务状态。

### 2.1 程序先检查关联和权限

检查 T1 是否存在、是否属于登录用户、D1 是否属于 T1，以及请求结构是否合法。

- 无权限或关联错误：拒绝，不把不该访问的任务内容发给模型。
- 没有明确关联：在授权范围内查找候选，必要时询问用户。
- 关联历史问题：可能是追问或重复提交，不能直接当成当前问题的新答案。

**这一层不是不校验，而是不负责理解自然语言。** task_id 是前端声明的关联，服务端状态才是执行依据。

### 2.2 识别消息用途

对自由文本，给模型最小必要上下文：

```text
当前阶段：等待诊断回答
当前问题：3 应该乘哪些部分？
用户消息：只乘 x
```

候选输出：

```json
{
  "message_type": "ANSWER",
  "needs_clarification": false
}
```

| 用户消息 | 可能用途 | 说明 |
|---|---|---|
| “只乘 x” | ANSWER | 在回答当前问题，但答案可能暴露误解 |
| “不知道” | ANSWER | 相关，却未必提供足够诊断证据 |
| “为什么要乘负数？” | FOLLOW_UP | 追问，不能自动按正式答案处理 |
| “先停一下” | PAUSE | 请求暂停，不是答题失败 |
| “讲一下英语” | NEW_REQUEST | 新需求，不推进原任务 |

通常一次结构化模型调用就足够，不需要在这里强行运行工具循环。可以把轻量模型作为待评估的实现选项，但不能因模型小或快就假定分类准确；具体模型选择需用任务上下文样本验证。明确的按钮 Action 可直接路由，跳过语义分类，但不能跳过权限和业务校验。

**ANSWER 只表示消息在回答问题，不等于回答正确，也不等于证据足够。** 是否支持错因假设属于后续诊断评估。

### 2.3 程序校验并受理事件

程序检查模型结果的结构、允许的类型，以及服务端最新状态：

- 任务是否已经暂停、取消或结束？
- 新答案是否对应当前等待的问题？
- 是否重复提交，是否发生并发版本变化？
- 当前事件允许触发什么业务动作？

不能只检查 JSON 是不是包含 ANSWER 或 PAUSE，就直接照做。已受理提交的重试，在鉴权后按幂等规则返回已有结果；新提交才校验当前版本并原子受理，详见主文档 Q15。

程序能够约束状态变化，但不能用格式校验证明语义判断正确。不确定就澄清，不因为输出格式合法而推进教学。

## 3. 外层学习工作流：你理解的“第四层”

它不一定是一个 Agent，也不是一个专门记录 task_id 的模型。它是整个学习任务的流程控制者。

### 3.1 task_id 是编号，状态才记录进度

```text
task_id：T1
所属用户：U1
status：WAITING_USER
stage：DIAGNOSE
等待问题：D1
已有证据：原题、错误步骤、相关历史引用
补救次数：0
```

只保存 T1 这个编号不够，还要保存它对应的目标、阶段、等待对象、题组和证据等。持久化记录存在，不代表后台有一个线程一直运行。

### 3.2 工作流负责四件事

| 职责 | 举例 |
|---|---|
| 记住进度 | 当前在等诊断答案，还是练习答案？ |
| 安排下一步 | 诊断证据足够后安排讲解，再安排练习 |
| 控制分支 | 达标总结，有明确薄弱点则在额度内补救 |
| 管理生命周期 | 暂停后保存，恢复后接着原阶段，取消后不复活 |

它依据阶段结果和既定规则推进，不是自己凭空完成诊断。比如错因评估可能调用一次模型，客观判分可能调用业务代码，复杂的检索讲解可能调用 Agent Loop。

阶段计算与最终状态提交之间仍要检查版本，避免用户已经暂停，迟到的讲解结果又推动任务继续组卷。

### 3.3 等待作答时，是主 Agent 还是讲解 Agent 在接管

**等待节点首先是由 Workflow 执行器维护的状态，不是必须由某个 Agent 一直运行的节点。** 保存当前题组、待回复问题与等待状态后，本次模型调用和处理请求可以结束。用户仍面对同一个聊天入口，但这不等于后台始终是同一个 Agent 在处理所有消息。

新消息到达时，先由消息接入与路由识别本次事件，再由编排层选择执行方式。自由文本可以交给通用主 Agent 或一次结构化模型调用辅助识别，明确的提交和暂停事件则不要求先启动完整 Agent Loop。

| 等待作答期间的新消息 | 处理方式 | 对原学习进度的影响 |
| --- | --- | --- |
| 正式提交当前题目答案 | 校验题组与提交关联，再调用确定性判分或必要的评估 Agent | 按提交完整性与阶段规则决定是否推进 |
| “刚才为什么要乘到第二项？” | 在教学规则允许时，临时调用讲解 Agent，带上原题、相关材料与追问 | 保留原等待点，追问结束后继续等待作答，不自动算提交 |
| “直接告诉我这道题答案” | 按辅助作答规则处理，或澄清学生是否仍要独立验证 | 记录提示或答案曝光，不能把之后的正确答案算成未经辅助的独立证据 |
| “先停一下” | 程序受理暂停并保存状态 | 不算学生答错，不增加补救次数 |
| “换成学英语” | 通用入口处理新需求，必要时确认暂停或切换原任务 | 不错误推进原数学任务，也不直接覆盖原计划 |
| 用途不明确 | 澄清本次消息，保持必要等待关联 | 不根据模糊判断强行推进 |

临时调用讲解 Agent 不一定意味着把主流程的当前阶段永久改回讲解。可以将它作为当前阶段允许的追问处理动作，保存原等待点和相关执行记录，回收结果后继续原任务。结果回来时仍要检查任务是否有效、是否已暂停或取消，以及对应状态版本。

### 3.4 什么时候切换 Agent，工具少了怎么办

这里的“切换”主要是**在下一次执行或模型请求前，选择角色并装配独立上下文**，不是模型生成到一半才发现 Workflow，然后悄悄更换 System Prompt。角色可以复用同一模型与 Runtime；阶段执行器也不必都包装成由主 Agent 创建的子 Agent。

固定 Workflow 的定义提前存在。用户进入学习流程时，程序创建或读取的是本次任务实例和状态，不是每条消息都重新生成一套流程节点。默认链路可以讲成：

```text
消息到达 / 用户明确进入学习流程
    → 校验任务关联、权限与本次意图
    → 读取或建立任务状态
    → Workflow 根据阶段、事件与规则选择执行器
    → Runtime 装配对应角色 Prompt、必要证据与允许工具
    → 执行阶段 Agent Loop 或确定性步骤
    → 节点验收，回收结果，校验并保存任务状态
    → 输出回复；需要用户输入则保存等待点并退出
```

例如，诊断证据满足条件时选择讲解 Agent；正式答案受理后选择判分或评估执行器；等待期间的合法追问则临时选择讲解角色。任务调度不需要先把完整 Workflow 传给通用主 Agent，等它运行一轮后再强制中断。

如果请求本来从通用主 Agent 的对话 Loop 进入，也可以让它通过结构化候选动作或已注册的流程入口 Tool 提出转交。程序在模型返回或 ToolCall 处理边界校验并接管调度；主 Loop 可以正常结束或受控让出执行权，不要求强制打断正在生成的模型请求。这里转入的是阶段 Agent，不是另外创建一个权限更大的“新主 Agent”。

**工具白名单更小是职责收敛，但必须覆盖角色的核心工作。** 讲解角色需要教材证据能力，却不一定需要改画像、查其他课程或处理所有通用任务；漏配本职所必需的工具确实是配置问题，应修正角色配置，而不是靠随意切换规避规则。

对于超出职责或缺少能力的请求，可按以下边界处理：

- 能用已有有效材料回答的相关概念追问，不必增加工具。
- 缺少用户信息时，返回明确缺口，由主流程澄清。
- 确实需要其他能力时，返回转交建议和原因，由编排层选择已授权的工具、其他角色或通用主 Agent。
- 没有合法能力或必要依据时，明确说明不足，不伪造结果，也不因转交到主 Agent 就绕过教学阶段与数据权限。

上述能力不足的返回字段可以按输出契约定义，不要求存在某个固定名称的转交工具。通用主 Agent 的可用工具也要经过当前任务授权与用户数据权限检查，不能假定它拥有任意权限。等待答题时给出提示，还需要记录对本次作答证据的影响。

#### 3.4.1 所需工具只有主 Agent 有，具体怎样补齐

**不是让子 Agent 不回答，而是将额外取数交给主 Agent 协助，再回填材料。** 这是本轮明确的处理方案，不声明新增接口已注册。子 Agent 暂时返回能力请求，既不伪造答案，也不将尚未完成的阶段直接写成成功或失败。

例如，讲解 Agent 只有教材相关工具，用户却追问“我之前跟这位老师学过这个知识点吗？”回答需要课程历史查询，而该能力只向通用主 Agent 开放。子 Agent 可以返回以下候选动作，字段和能力标识均为示例：

```json
{
  "type": "needs_capability",
  "required_capability": "course_history_read",
  "reason": "需要核对当前学生与同一老师的相关历史课程",
  "input_refs": ["current_student", "current_teacher", "current_topic"]
}
```

具体处理链路是：

```text
讲解 Agent 返回能力请求与已有可用材料
    → Pipeline 保存待补请求，保留原阶段与等待对象
    → 校验所需能力、任务范围、用户权限和剩余预算
    → 发起一次主 Agent 调用，只交付这个补充查询目标
    → 主 Agent 调用自己的已授权课程历史工具
    → 返回查询材料、来源引用与明确缺口
    → Pipeline 检查结果关联、任务有效性与状态版本
    → 将相关材料回填讲解 Agent 的下一次调用
    → 讲解 Agent 完成回答；原流程按业务条件继续或等待
```

身份、查询范围和参数来自服务端可信上下文或经校验的引用，不能直接照搬子 Agent 自由生成的身份信息。主 Agent 协助的是补充目标，不负责因此接管整份 Workflow、重置阶段或擅自扩大权限。Pipeline 可以重新发起主 Agent 角色的调用，不要求某个主 Loop 一直活着等子 Agent 请求。

回填时优先提供相关工具材料与可追溯引用，而不是只给一句主 Agent 的结论。主 Agent 的这次取数完成，不等于原讲解节点已经通过验收；仍由阶段 Agent 组织回答，节点与 Workflow 按原规则检查和推进。

如果用户的问题已经不属于当前学习任务，则可以由主 Agent 直接处理该问题，保留或按规则暂停原任务，不必强行回填讲解 Agent。能力协助次数和调用预算应受限，避免主子 Agent 反复转交；确实无权限、工具失败或仍无必要依据时，才澄清、给出有依据的部分回答或说明缺口，不冒充已经查到。

**口述记法：入口统一收消息，Workflow 保存等待与进度，Runtime 按事件选择角色。Agent 不必一直在线，切换不必强制中断；小工具集负责本职，超范围交回编排层。**

## 4. 内层 Agent Loop：工作流调用的一种执行方式

假设工作流允许进入“检索教材并生成针对性讲解”阶段：

```text
输入：本次目标、错因证据、必要上下文和允许的工具
   ↓
模型决定查询教材
   ↓
程序校验工具参数与权限，执行检索
   ↓
工具结果回填给模型
   ↓
模型判断依据是否足够
   ├─ 不够：在预算内调整查询，再调用工具
   └─ 足够：生成讲解和来源，结束本阶段 Loop
   ↓
阶段结果交回工作流，校验、保存并安排下一步
```

Loop 的“循环”是模型与工具之间的有限往返，不是持续询问学生是否回复。

- 限制轮次、调用次数和耗时，避免无限检索。
- 只能使用当前阶段允许的工具和权限。
- 不擅自修改通过规则，不直接把整个任务写成已掌握。
- 阶段失败返回明确失败或证据不足结果，由工作流决定重试、澄清或收尾。

**不是每个阶段都需要 Agent Loop：**

| 阶段工作 | 可以采用的执行方式 |
|---|---|
| 消息用途分类 | 一次结构化模型调用 |
| 诊断分析 | 一次模型评估，必要时由工作流发起追问 |
| 客观题判分 | 确定性代码或题库服务 |
| 教材检索与讲解 | 固定调用链，或需要灵活查询时使用 Agent Loop |
| 等待学生、保存暂停 | 状态持久化，不需要模型循环 |

### 4.1 补充：按课本讲解时，强制的是教材依据

当前方案不固定在进入讲解节点时由程序先调用 RAG。提示词明确教材证据与引用要求，模型可以先改写查询，再自主检索；已有有效片段则复用。准备结束时节点验收，不通过就反馈具体缺口，让模型在预算内补查或修改，仍失败则返回依据不足，不发布为教材支持的讲解。

检查使用后端真实工具结果及已保存的证据，不看模型是否声称“调用过 RAG”。来源和引用可做程序校验，讲解是否真正得到材料支持仍需内容核验与评测。

同一通用 Loop 可以服务多个节点：讲解节点配置教材证据检查，其他节点配置自己的规则，不需要分别重写循环。模型直接产出合格结果就是一轮退出，有必要才继续调用工具。工作流只按阶段结果安排后续处理。

完整策略与面试口述见主文档 4.8 节及 Q18。

如果题目无法可靠定位知识点，应先补全信息、缩小候选或确认转普通答疑，不进入按知识点组卷和掌握评估。定位失败是目标不明，检索失败是目标明确但课本依据缺失，不能混为同一种重试。详见主文档 4.9 节及 Q19。

### 4.2 Workflow 存成 JSON，怎样知道一个节点结束了

**JSON 负责描述与保存，Workflow 执行器负责执行与判断。** 节点除了关联 Agent 角色，还要关联输出契约、验收规则和转移规则；只保存“当前节点是谁、调用哪个 Agent”，不足以可靠推进。

以下仅为讲解节点的配置示例，不声明实际接口或新增实现：

```json
{
  "node_id": "EXPLAIN",
  "agent_role": "explanation",
  "completion_check": "textbook_explanation_check",
  "next_on_success": "PREPARE_PRACTICE"
}
```

`completion_check` 是预注册检查逻辑的标识，不是 JSON 自己会执行的函数，也不是让模型临时编写任意规则。执行器读取配置后，调用对应检查逻辑；检查所需的输出、教材范围和实际证据由本次节点上下文提供。

完成链路是：

```text
Agent 生成候选结果，准备结束本次 Loop
    → 节点检查输出是否完整、证据是否真实且适用
    → 内容与错因覆盖按教学要求进行语义核验
    → 通过：返回正式节点结果
    → Workflow 再检查任务有效性、当前阶段与状态版本
    → 可靠保存结果和新状态，安排允许的下一步
```

程序检查任务关联、字段、引用、教材版本、提交完整性等硬条件；客观题按评分规则判断。错因与复述等语义内容可由模型按预定义量规评估，返回候选分项结果、证据与不确定项，再由程序受理并执行分支规则。模型评估仍可能出错，格式合法或模型自报 `done` 都不等于判断可靠。

| 节点职责 | 可以结束本节点工作的条件 | 不能作为充分条件的信号 |
| --- | --- | --- |
| 错因诊断 | 本次目标可定位，已有足够证据支持有限范围内的错因假设，可交给讲解使用 | 模型只输出一个错因标签 |
| 针对性讲解 | 讲解覆盖目标错因，关键解释有适用的教材支持，内容通过核验 | 输出一段正文、调用过一次 RAG，或学生说“懂了” |
| 练习准备 | 合规题组、题目版本与评分信息齐备，并保存所需关联记录 | 查到几道相似题 |
| 等待作答 | 收到当前题组所需的有效提交，满足本次提交完整性规则 | 已显示题目，或只保存了答案草稿 |
| 理解评估 | 所需作答与概念解释证据齐备，按量规形成有效评估结果 | 模型凭印象说“学生掌握了” |

这里区分三件事：

- **本次 Agent 运行停止：** 输出候选结果、请求用户输入或触及执行上限，都可能停止本次运行；不保证节点成功。
- **节点成功结束：** 完成本节点负责的交付物并通过节点验收，才允许走对应成功边。
- **整个学习任务达标：** 根据有效作答与理解证据执行任务评价规则，不由讲解节点直接宣布。

尤其是评估节点，得到“未达标”的有效结论也可以正常结束，然后走补救边；不能把“评估工作完成”与“学生通过评估”合成一个布尔值。取消、超时或证据不足也有明确停止出口，但不能伪装成成功推进。

验收发现可修复的缺口时，回填具体原因，在预算内继续当前 Loop；需要学生补充时保存 `WAITING_USER` 与问题关联，结束本次处理但不完成等待节点；达到修正或调用上限时返回明确失败或缺口，由外层选择澄清、失败分支或收尾。技术修正次数与教学补救次数分开计算。

例如，针对 `3(x - 2)` 被写成 `3x - 2`，诊断先取得学生“只乘第一项”的解释，讲解再用教材依据说明每一项都要乘。讲解产物合格后可以进入练习准备，但学生是否真正理解，要等新题作答与概念解释。若把准备题组和等待作答拆成两个节点，前者可以已完成，后者仍在等待，不需要让出题 Agent 一直运行。

**口述记法：节点配验收，Agent 交结果，程序判转移；讲解完成不等于学生掌握，运行停止也不等于节点成功。**

## 5. 三个例子：不是每条消息都跑到 Agent Loop

### 5.1 学生说“先停一下”

```text
关联与权限校验
  → 识别 PAUSE
  → 程序检查任务允许暂停
  → 工作流保存 PAUSED 和当前进度
  → 确认暂停，结束本次处理
```

**这次不启动讲解 Agent Loop。** 暂停可由聊天触发，不需要前端一直显示暂停按钮。

### 5.2 学生回复“只乘 x”

```text
关联与权限校验
  → 识别 ANSWER
  → 程序受理当前诊断回答
  → 诊断评估：支持漏乘第二项的假设
  → 工作流允许进入讲解
  → Agent Loop 检索教材并生成讲解
  → 工作流保存结果、安排组卷并保存等待点
  → 返回练习，结束本次处理
```

如果诊断证据不足，就发一个澄清问题并等待，不必启动讲解 Loop。

### 5.3 学生提交练习答案

```text
关联与权限校验
  → 明确提交事件直接路由，或聊天输入先识别用途
  → 程序校验题组、重复提交和当前阶段
  → 工作流调用评分服务
  → 保存评分证据，生成概念解释问题
  → 保存新的等待点，结束本次处理
```

这一轮可能只用判分代码与一次问题生成调用，也不必有工具循环。部分答案的处理沿用主文档 Q16，不能收到任意答案就推进到概念验证。

## 6. 一个 Task 可以跨很多轮，但每次处理都会结束

```text
T1：诊断问题 → 等待用户
T1：收到诊断回答 → 讲解与练习 → 等待用户
T1：收到练习答案 → 理解验证 → 等待用户
T1：收到概念解释 → 总结或补救
```

Task 是学习任务；一次用户交互是处理一个消息/事件；一次模型调用是更小的执行动作；一个 Agent Loop 可以包含多次模型和工具调用。这些不是一一对应关系。

用户说“继续之前的讲解”时，在其权限范围内查找可恢复任务。明确匹配则读取状态，多个候选则询问，不能随便选一个。查任务可以由后端直接完成，也可以通过受控工具完成；模型不是查找数据库记录的必经环节。

恢复以任务状态决定从哪里继续，对话和证据补足上下文。如果停在答题却要求再讲解，应先说明和确认，而不是盲目重跑旧流程。

## 7. 最容易混淆的六句话

| 容易误解的说法 | 准确理解 |
|---|---|
| 前端传了 task_id，所以肯定是答案 | 只声明关联，后端验证权限，语义另行识别 |
| 第一层只传参数，不校验 | 第一层程序要做关联和权限校验 |
| 消息识别内部还有两层 Agent | 消息识别与学习工作流、阶段 Loop 是不同职责 |
| 模型返回 ANSWER 就进入讲解 | 受理回答后，还需要诊断证据支持 |
| 每个阶段都要用 Agent Loop | 程序、单次调用、固定工具链都可以完成阶段 |
| Task 没结束，后台 Loop 就不能停 | 等用户时保存状态并退出，下次事件再继续 |

## 8. 面试口述与学习自测

### 8.1 一分钟讲法

> 我把这个设计分为三块。第一块是消息接入与路由，内部先校验任务关联和权限，再识别用户是在回答、追问还是暂停，最后由程序结合当前状态受理事件。
>
> 第二块是学习工作流，负责整个任务的阶段、等待、补救和结束。task_id 只是编号，真正恢复依赖持久化的阶段、题组和证据。
>
> 第三块才是阶段内按需调用的 Agent Loop，比如讲解时让模型检索教材、读取工具结果再生成内容。暂停只改状态，简单判分可以直接用代码，不是每条消息都必须跑 Loop。需要学生输入时保存等待点并退出，下次再按任务状态继续。

### 8.2 三个自测问题

1. 同样带 T1 和 D1，为什么“只乘 x”和“先停一下”走不同路径？
2. 如果分类期间用户在另一端取消任务，为什么执行前还要检查最新状态？
3. 用户十分钟后才答题，这十分钟里应该保存什么，哪些执行不需要一直运行？

**最终记法：消息路由识别请求，学习工作流管理进度，Agent Loop 按需完成步骤。**

## 9. 从 Pi 教程补强 Agent Loop 的简历与口述

> 整理日期：2026-09-30。参考冬瓜的 `dg-ai-notes` 第 3、5、7、8 章，并对照本地 Pi
> `1b347794e` 的相关循环逻辑。本文是学习与设计材料，不证明鼎校伴学已经实现 Pi 的机制。
> 原有经历沿用简历自述口径；新增 Schema 校验、拦截钩子、输出验收及消息队列等能力，
> 未经本人确认不得写成上线经历。没有新增或迁移任何收益数字。

### 9.1 简历要突出什么

不是堆叠 Pi 的接口名，而是说明三件事：模型怎样利用反馈继续决策，程序怎样约束工具执行，
以及系统怎样控制结束边界。前两项解释为什么不是简单 Function Calling，最后一项解释
为什么不是一个无限运行的 while 循环。

对照当前材料，最值得加强的是：

| 重点 | 鼎校伴学中的具体讲法 | 表达边界 |
|---|---|---|
| 反馈驱动的多轮执行 | 教材依据不充分时，在预算内调整查询，读取真实结果后继续组织讲解 | 不是每条消息都必须检索 |
| 工具执行职责分离 | Registry 找实现，Dispatcher 调度，ToolResult 表达结果 | 不把注册表说成调度器 |
| 错误作为可处理的观察 | 参数或检索失败回填给模型，允许修正或说明限制 | 失败隔离不承诺自动恢复 |
| 结束与业务验收分开 | Loop 不再需要工具，不代表讲解有依据，更不代表学生已掌握 | 教材验收属于已有设计；掌握评估属于 Workflow |
| 执行与事件展示分离 | 模型、工具事件用于进度展示和 Trace；需要阻止执行的检查必须在执行前完成 | 新的钩子机制只能作为演进建议 |
| 上下文是每轮治理对象 | 大结果先限量，历史按相关性和摘要组织，必要时保留原始证据引用 | 摘要不是完整历史，也不是任务状态 |

### 9.2 用一个业务例子讲清循环

以下为设计示例，不代表新增功能已经实现：

```text
目标：根据当前教材解释学生漏乘括号第二项的问题

Round 1：模型提出教材查询
  -> 程序执行受控检索，回填片段及来源
Round 2：模型发现只有例题，没有足够规则解释
  -> 在预算内调整查询，回填新的证据
Round 3：模型生成讲解和引用，不再提出工具调用
  -> 若讲解阶段配置了输出验收，检查真实来源和证据缺口
     通过：返回阶段结果
     未通过：反馈具体缺口并有限继续；仍不足则明确失败
  -> 外层 Workflow 决定是否安排练习，不直接认定学生掌握
```

可以说“边执行边调整下一步”，不需要把短链路包装成完整 DAG Planner。一次模型请求
可能产生多个工具调用；独立调用可以并发，存在依赖的调用分轮完成。原简历材料中的
批内去重不等于跨轮幂等，超时未知的写操作仍要先确认是否已经生效。

### 9.3 简历候选：原有经历与新增设计分开写

**原有职责的强化候选，核对实际贡献后使用：**

> 参与 Agent Runtime 建设，基于“模型决策—工具执行—结果回填”的多轮闭环支撑动态教材
> 检索；通过 Tool Registry、Dispatcher 与 ToolResult 分离工具注册、异步调度和结果协议，
> 将普通工具异常转换为可处理反馈，结合轮次预算、上下文裁剪与收尾策略控制执行边界。

此句只重组当前材料已有职责，不因阅读 Pi 教程增加“自研框架”、安全沙箱、自动恢复等主张。
若没有参与其中某一项，就删除或改成理解方案，不能用“参与”掩盖未做过的工作。

**新增方案候选，只作为设计经历表述：**

> 设计阶段化学习 Workflow 与 Agent Loop 的协作边界，由工作流管理诊断、练习、等待和
> 理解验证；讲解阶段配置教材依据与引用检查，未满足要求时反馈具体缺口并有限补查，避免
> 将模型停止生成等同于完成教学目标。

投递时一般保留第一句的核心内容，第二句按岗位需要取舍。不要把所有机制塞进一条职责。

### 9.4 一分钟面试表达

> 我理解 Agent Loop 的重点不是多调用几次模型，而是让真实工具反馈进入下一轮决策。
> 在教材讲解场景，模型可以先查询材料，看到依据不足后调整查询，再生成带来源的讲解。
> 模型提出动作，Runtime 负责受控执行和结果回填，两者的职责是分开的。
>
> 我会分别解释工具注册、批次调度和结果协议。工具的普通失败需要回填为可处理的结果，
> 模型才有机会修正参数或降级回答；但参数错误、临时网络错误和写操作超时不能无差别重试。
> 循环还要受轮次、耗时和上下文预算约束，达到边界后明确收尾。
>
> 在进一步的教学 Workflow 设计中，我还区分了循环结束和业务完成。没有工具调用只说明
> 这一轮准备结束，讲解仍要有教材依据；学生是否掌握，则要靠后续作答和解释证据判断。
> 所以外层管学习进度，内层只完成需要动态处理的步骤。

这是模拟口述，前两段中的具体工程职责仍需按本人实际参与范围调整。

### 9.5 学教程时不能直接照搬的地方

1. **术语口径不同。** 教程的 Pi `Turn` 指一个模型调用及其工具批次；当前学习材料常把
   用户请求叫 Turn、内部模型调用叫 Round。面试先定义一次，再保持一致。
2. **运行停止不等于业务成功。** 教程里的简化停止条件适合理解机制，不能替代业务验收。
   当前 Pi 会话层也不能把低层 `agent_end` 当成全部自动处理结束；其文档区分 `agent_settled`。
3. **示意图不等于当前实现。** 教程第 3 章部分简化表述与详细规则不一致；本地版本的工具
   批次终止检查用 `every`，不是任一工具返回终止就结束。生成被 `length` 截断时，当前代码
   不直接执行该消息中的工具调用，而是生成失败结果。不要背诵教程里的行号或旧钩子名。
4. **观察者不等于控制者。** 记录日志、推送进度不能代替执行前的权限检查。拦截器必须接入
   会被执行流程等待并消费结果的位置；有扩展钩子也不代表默认具备完整权限或沙箱系统。
5. **消息追加不等于工作流恢复。** Pi 的 steering/follow-up 用于运行中补充或追加指令，
   不是知识点学习流程里的持久化等待点。当前简历不要新增这些能力；学生等待与恢复仍由外层
   任务状态管理。
