# 鼎校伴学：Planner 与 Subagent 业务扩展学习方案

> 日期：2026-09-16。
> 定位：基于现有项目叙述的演进设计和学习材料，不代表当前仓库或生产系统已经实现。
> 原则：保留已有 Workflow 和 Agent Runtime，只对确有动态规划或独立探索价值的任务扩展。
> 配套：[消息路由、学习工作流与 Agent Loop](消息路由-学习工作流-AgentLoop分层讲解.md)。

## 1. 先明确：增加的是能力，不是技术名词

现有项目已有错题和知识点讲解的业务基础，可以沿两个真实问题扩展：

1. **复杂错题诊断：** 一道题涉及多个知识点，历史错因和教材证据需要分别调查，简单的一次检索不够。
2. **阶段复习规划：** 多个知识点争夺有限学习时间，需要结合前置关系、学生证据和反馈调整安排。

建议先实现第一个，复用工具和 Runtime 的范围更大，也更容易验证完整链路。第二个适合作为后续扩展。
普通单题讲解继续走原有流程，不强制所有请求都调用 Planner 和多个 Subagent。

面试优势不是“我用了五个 Agent”，而是能解释：为什么拆、依赖怎么处理、失败怎么恢复、是否真的比简单方案好。

## 2. 五个组件各管什么？

| 组件 | 职责 | 不负责什么 |
| --- | --- | --- |
| Workflow | 管理诊断、讲解、练习、等待学生、验证等业务阶段 | 不必动态决定每次检索细节 |
| Planner | 在允许范围内生成子目标、依赖和验收条件，必要时修订计划 | 不直接执行工具，不自行批准业务状态变化 |
| Scheduler（调度器） | 校验依赖，调度就绪任务，控制并发、预算与状态 | 不凭模型生成的顺序盲目执行 |
| Subagent | 在限定上下文和工具权限内，独立完成子目标，可多轮调查 | 不获得主任务全部上下文和任意写权限 |
| Tool | 执行定义明确的操作，返回结果 | 不因包含一次模型调用就自动成为 Subagent |

```text
消息路由 → 原有学习 Workflow
                   ↓ 复杂诊断阶段按需进入
                Planner
                   ↓ 结构化计划
             校验器 + Scheduler
                 /       \
          诊断 Subagent   教材 Subagent
                 \       /
              结果校验与汇总
                   ↓
          回到原有讲解、练习和验证流程
```

Planner 可以只是一次结构化模型调用；Subagent 可以复用同一模型和同一 Runtime。
它们不必各自部署成服务，也不必使用不同框架。串并行是任务依赖关系，不是 Agent 的定义。

## 3. 场景一：复杂错题的并行诊断与教材取证

### 3.1 用户需求与拆分理由

学生上传一道带解题步骤的整式运算错题，询问：“这种题我总错，到底哪里没理解？”
可能涉及分配律、负号处理、合并同类项。一次错误不能直接证明哪个知识点薄弱。

系统需要完成两类可独立开展的调查：

- **学习诊断：** 对比当前步骤与历史作答，区分漏乘、符号错误、偶发计算错误等候选原因。
- **教材取证：** 在匹配教材范围内找到对应规则和例题，必要时补查前置知识及原文。

两者都有可能需要多次工具调用，且最终输出边界清楚，因此可以拆成 Subagent。
如果业务只需各查一次并返回，则普通工具并行已经足够，不必使用 Subagent。

### 3.2 一次端到端过程

**步骤 A：程序完成输入准备。** 有图片时执行 OCR，保留原图、题目和学生步骤的关联。
OCR 关键符号不确定时先澄清，不让两个 Agent 在错误题目上继续推理。身份、教材范围由可信业务上下文提供。

**步骤 B：Planner 生成有限计划。** 输入为题目结构、学生问题、已知知识点候选、允许角色和预算。
输出可选择：仅教材取证、仅历史诊断、两者并行，或先澄清。不要无条件生成固定的双 Agent 计划。

**步骤 C：程序校验计划并派发。** 通过后并行启动诊断和教材子任务：

| 子任务 | 必要输入 | 允许工具（示意） | 终止条件 | 返回结果 |
| --- | --- | --- | --- | --- |
| 学习诊断 | 当前题目、学生步骤、知识点候选、授权范围 | 查询历史、读取作答详情 | 候选错因有证据，或明确证据不足 | 错因候选、证据 ID、待验证问题 |
| 教材取证 | 当前题目、知识点候选、教材版本范围 | 检索教材、读取原文 | 有匹配材料，或确认当前查询仍不足 | 规则、引用 ID、适用范围、缺口 |

两者都不能直接写“学生已掌握/未掌握”到长期画像，也不直接向学生发送最终结论。

**步骤 D：主流程汇总。** 校验引用和学生归属，组织“当前错误 → 候选原因 → 支持证据 → 验证问题”。
如果历史与教材调查给出不同解释，不用多数投票；回到当前作答核对，必要时向学生发一道区分性问题。

**步骤 E：继续原有 Workflow。** 根据学生回答讲解、练习和验证，最后按业务规则沉淀证据。
等待学生时保存任务状态并释放执行资源，不让 Subagent 空转等待。

### 3.3 A 串行、B/C 并行到底怎么表示？

```text
A：OCR 与题目结构校验（固定工具步骤）
                ↓
P：Planner 生成并经程序校验的计划
           /                  \
B：学习诊断 Subagent      C：教材取证 Subagent
           \                  /
       D：证据校验、汇总与讲解准备
                ↓
        原 Workflow：澄清或讲解
```

B/C 并行的前提是二者输入已齐备。若教材任务必须先拿到诊断出的精确知识点，则应改成 B → C，
或先独立取证，再仅对诊断新增的知识点补查。不能为了宣称并行而隐藏真实依赖。

### 3.4 Planner 输出示例

以下为协议草案，不是当前代码已有接口。A 已完成，计划中的依赖只引用本计划任务。

```json
{
  "plan_version": 1,
  "tasks": [
    {
      "id": "diagnosis",
      "executor": "learning_diagnosis",
      "depends_on": [],
      "input_refs": ["current_question", "student_answer"],
      "goal": "对当前错误提出有历史证据支持的错因候选",
      "acceptance": "返回证据引用；证据不足时明确标记，不强行诊断"
    },
    {
      "id": "materials",
      "executor": "textbook_research",
      "depends_on": [],
      "input_refs": ["current_question", "textbook_scope"],
      "goal": "查找支持当前题目讲解的教材规则和例题",
      "acceptance": "返回可解析且匹配教材范围的引用"
    },
    {
      "id": "synthesis",
      "executor": "evidence_synthesis",
      "depends_on": ["diagnosis", "materials"],
      "input_refs": ["diagnosis.result", "materials.result"],
      "goal": "整理讲解依据及仍需向学生验证的问题",
      "acceptance": "事实与推断分开，不越权更新学习状态"
    }
  ]
}
```

`executor` 必须映射到服务端白名单；其中 `evidence_synthesis` 可以是普通处理函数加一次模型调用，
不必也是 Subagent。身份和权限不从模型生成的计划中取。预算由服务端分配，模型不能自行提高。

校验器至少检查：结构、任务数、ID 唯一、依赖存在、无环、角色白名单、输入引用可用、权限及总预算。
验收说明只是计划目标，不是成功证明；引用存在、范围匹配等要由程序检查，解释质量再通过评估判断。
无效计划允许有限修复；仍无效时退回原有简单流程，而不是执行部分任意节点。

### 3.5 什么情况下需要重新规划？

- 历史查询没有记录：跳过历史性结论，转为当前题目诊断或向学生追问，不反复查询同一空结果。
- 教材结果暴露输入版本不明确：暂停需要该版本的任务，先澄清。
- 学生验证否定了主要错因：基于新证据安排一次针对性补查。
- 暂时性接口超时：通常先由执行器有限重试，不必每次都重新调用 Planner。

新计划只重做受影响的未完成任务；已完成结果在输入、权限和数据版本未变化时可以复用。
修改计划要递增版本，旧计划仍在运行的任务不能把结果覆盖到新计划。总预算覆盖所有计划版本，
不能每次重规划都获得一份新预算。

## 4. 场景二：跨知识点的阶段复习规划与反馈调整

### 4.1 用户需求

“下周考试，我每天只有 20 分钟，最近去括号、整式运算和方程都容易错，帮我安排复习。”

这里的问题不只是执行工具，而是在时间约束下选择先学什么、后学什么、何时检查效果。
前置知识、证据强弱、教材范围和学生反馈会影响计划，适合有限的动态规划。
20 分钟只是本例用户约束，不是预设教学效果指标。

### 4.2 不要给每个知识点无上限创建一个 Agent

先用结构化查询得到近期作答和知识点关系，再按相关知识簇分组。最多同时启用少量诊断角色，
例如“代数运算”和“方程求解”，让各自检查当前薄弱证据和前置缺口，而不是每个 Chunk 启动一个 Agent。

```text
程序：查询近期作答、课程范围、可用学习时段
                       ↓
Planner：选择需要调查的知识簇与依赖
                /                 \
       运算诊断 Subagent      方程诊断 Subagent
                \                 /
程序校验前置关系 + Planner 整理复习安排
                       ↓
学生确认 → 按天创建原有学习 Workflow 任务
                       ↓
阶段检测结果 → 更新证据 → 有限调整剩余计划
```

若两个知识簇共用分配律的调查结果，由公共任务生成一次供双方引用，避免重复工具调用。
如果知识图谱没有可靠关系，不能让模型编造前置知识边并当成数据库事实。

### 4.3 输出什么，如何控制？

计划包含每个学习单元的目标、预计时长、依赖、教材证据、验证方式，以及暂缓内容。
程序检查总时长、时间冲突和已有前置关系；预计时长仍是估计，不能保证学生一定按时完成。
时间不够时应减少内容或说明取舍，而不是生成表面完整但不可执行的计划。

学习计划不是“掌握结果”。每天仍进入已有的讲解、练习和验证 Workflow；未验证通过的前置能力，
不能因计划表写着“已学完”就跳过。一次低分也不自动推翻整周计划，要结合题目难度、提示依赖等证据。

现有单词测评、试卷学情分析仍保持独立业务入口。可以通过 Action 引导学生进入这些业务，
再接收有授权和任务关联的完成结果；不要把 Action 展示当成业务已经执行，也不要让 Subagent
自行模拟这些业务的内部接口。

### 4.4 为什么不直接让一个模型生成七天表格？

只有日期和知识点清单时，一次模型调用或模板已经足够。只有当计划需要调查真实学习历史、
核对教材证据、处理多个独立子问题并随反馈调整时，Planner/Subagent 的额外复杂度才可能值得。
对比基线时也要保留单 Agent 完成全部调查的方案，而不是只与完全不查数据的模型比较。

## 5. 复用 Agent Runtime 的实现方式

### 5.1 子任务不是复制整段主对话

每次调用可创建一个子运行实例，传入：

```text
parent_run_id / run_id / task_id / plan_version
子目标与允许角色
最小必要输入、引用 ID 和可信权限范围
允许工具集合
截止时间、最大步数和分配预算
统一结果 Schema
```

两个 Subagent 复用 Runtime 实现，但使用独立消息列表、调用轨迹和执行状态。
共享的是受控证据和只读业务数据，不是任意互相修改的消息数组。
不要直接并发调用同一个带可变会话状态的 Agent 实例。

### 5.2 主流程伪代码

```python
async def investigate(question, trusted_context):
    plan = await planner.create(question, allowed_roles=ROLE_CATALOG)
    validated = validate_plan(plan, trusted_context)
    results = await scheduler.execute(
        validated,
        agent_factory=create_isolated_agent,
        parent_budget=trusted_context.budget,
        deadline=trusted_context.deadline,
    )
    evidence = validate_result_references(results, trusted_context)
    return await synthesize(question, evidence)
```

这是职责示意，不是可直接运行的代码。Scheduler 对无依赖或依赖已满足的任务派发；
不能简单把所有节点一次性 `gather`。B/C 同时就绪时才可使用并行异步任务。
依赖失败后，下游是阻塞、接受部分结果还是切换降级分支，必须由明确策略决定。

### 5.3 统一返回协议

```json
{
  "task_id": "diagnosis",
  "plan_version": 1,
  "status": "partial",
  "summary": "当前作答存在漏乘现象，历史证据不足以确认持续薄弱",
  "evidence_refs": ["answer:current:step2"],
  "hypotheses": ["可能未完整应用分配律"],
  "missing_information": ["缺少不依赖提示的验证作答"],
  "suggested_next_step": "提出一道验证问题"
}
```

状态可约定 `completed / partial / failed / needs_input / cancelled`，但由 Runtime 根据实际执行结果
统一封装。模型自称完成不等于任务通过验收。返回简洁结论、证据和不确定性，不要求上传完整内部推理过程。
引用只是示例，服务端必须能解析并验证其存在和归属。

## 6. 并发、失败、恢复与记忆写入

| 问题 | 设计方式 |
| --- | --- |
| 子 Agent 越来越多 | 限制角色、任务数、最大嵌套深度；首版禁止子 Agent 再创建子 Agent |
| 并行争抢模型额度 | 子任务并发限制与模型调用额度分开控制；多实例共享额度，不能只靠进程内 Semaphore |
| 超时或取消 | 子任务截止时间不超过父任务；父取消向下传播，关闭在途调用并拒绝后续派发；不能保证供应商即时停止计费 |
| 一个分支失败 | 保存其他成功分支结果；按业务要求部分降级或请求补充，不把失败当作无历史证据 |
| 重复执行 | 只读结果按用户、输入和版本复用；写操作采用业务幂等键，禁止直接重复提交 |
| 服务重启 | 持久化计划版本、任务状态、输入输出引用和重试记录；worker 通过租约与条件更新领取任务 |
| 旧 worker 晚返回 | 写结果时检查计划版本、执行尝试和领取令牌，拒绝失效执行覆盖；只设置租约到期还不够 |
| 多 Agent 结论冲突 | 对齐对象、场景、时间和原始证据；必要时追问，不通过简单投票决定事实 |
| 画像被反复修改 | Subagent 返回候选证据，由主流程校验后统一写入；区分原始事实、推断和学习状态 |

持久化领取仍不能保证外部副作用“只执行一次”，副作用接口还需要业务幂等及结果查询。
首版可以先实现单进程并发和数据库记录，再增加多 worker 恢复；不要一开始同时引入全部基础设施。

## 7. 建议按三个里程碑学习和实现

### 里程碑一：先做无 Planner 的双分支基线

- 保留原 Workflow，在复杂诊断阶段固定启动两个受限 Subagent。
- 两者独立上下文、工具白名单和步数预算，统一返回证据。
- 跑通正常、空历史、教材为空、超时、取消和引用无效的案例。
- 与原有“一次历史查询 + 一次教材检索”的简单实现对比。

这一步证明 Subagent 是否真的能解决多轮取证问题，不急于增加动态规划。

### 里程碑二：增加有限 Planner

- 只允许少量已知角色，不允许任意代码或任意工具名称。
- 支持按任务需要选择单分支、双分支、串行依赖或先澄清。
- 实现计划 Schema、依赖无环校验、预算检查及有限修复。
- 用相同测试任务对比固定编排，记录动态计划是否实际减少无用调用。

如果所有输入都生成同一个计划，Planner 没有证明额外价值，应保留固定编排。

### 里程碑三：增加反馈与恢复

- 支持部分失败、输入澄清后的恢复和有限重规划。
- 持久化计划与子任务状态，验证重启恢复不重复提交副作用。
- 加入跨知识点复习场景，复用已有学习 Workflow，不再另造一套教学执行链路。

## 8. 怎么证明做得比原来好？

至少比较三种方案：原有固定 Workflow、单 Agent 多工具调查、Planner + Subagent。
使用相同题目、相同数据快照、相同工具权限，记录各方案模型和预算差异，多次运行观察波动。

| 维度 | 观察内容 |
| --- | --- |
| 业务质量 | 错因是否有证据、教材版本是否匹配、是否提出有区分度的验证问题 |
| 规划有效性 | 计划是否合法、依赖是否正确、任务是否遗漏、是否产生无用分支 |
| 可靠性 | 空结果与失败是否区分、取消是否生效、恢复是否重复写入 |
| 效率 | 端到端 P50/P95 延迟、模型调用数、Token 与费用、重复检索率 |
| 可追溯性 | 最终结论能否定位到子任务、工具结果和原始证据 |

“多个模型都认为正确”不能作为独立真值。诊断质量可用人工标注案例和教研审查，引用及权限
用程序校验；用户满意不等于真正学会，掌握效果需要后续作答证据。
只记录真实测得的结果，不预先写“准确率提升 20%”或“延迟下降 50%”。

## 9. 面试如何讲，简历什么时候能写？

### 实现并验证后的一分钟介绍模板

我是在已有错题讲解 Workflow 上增加了复杂任务调查能力，而不是把全部流程改成多 Agent。
普通题仍走原流程；复杂题需要同时分析学习历史和查教材依据时，由 Planner 生成受限任务计划，
程序检查依赖和预算，再派发给学习诊断与教材取证两个 Subagent。

子 Agent 复用现有 Runtime，但拥有独立上下文、工具范围和运行预算，可以围绕自己的目标多轮取证。
结果带证据引用返回主流程，校验后继续讲解和理解验证，不让子 Agent 直接修改掌握状态。

工程上重点处理并发预算、部分失败、取消和计划版本，避免重复调查或旧结果覆盖。
我通过与固定 Workflow 和单 Agent 方案对比，判断哪些任务值得启用这套机制。

### 简历表述按完成程度区分

- **仅设计阶段：** 作为学习方案或面试中的演进思路，不写成已交付项目成果。
- **已完成可运行原型：** “基于现有 Agent Runtime 实现复杂错题诊断原型，支持受限任务规划、
  学习诊断与教材取证子 Agent 协作，完成依赖校验、独立上下文和预算控制。”
- **已落地并评测：** 在真实职责范围内补充上线范围、失败恢复能力与实测结果；仍不虚构数字。

能支撑简历的材料至少包括：可运行代码、一条完整 Trace、失败案例、基线对比和可解释的取舍。
比起写“熟悉 Planner、Multi-Agent”，这些证据更能体现工程深度。

## 10. 最后记住三个边界

1. **计划不等于执行：** Planner 提建议，程序校验和调度。
2. **并行不等于多 Agent：** Tool 执行指定操作，Subagent 围绕子目标独立决策。
3. **复杂不等于更好：** 不需要调查的任务继续走简单 Workflow，用评测决定是否启用扩展。
