# 鼎校伴学：知识点学习闭环与面试学习指南

> 编写日期：2026-09-10。
> 定位：业务与技术设计学习材料，不是已上线功能说明，也不是当前仓库的实现审计。
> 使用方式：先学习第一部分的业务故事，再学习第二部分的状态机制，最后用第三部分模拟追问。

## 0. 事实边界与阅读导航

### 0.1 哪些可以当作事实讲

本文依据用户提供的简历及本次讨论整理。简历自述已有 Agent Loop、工具调度、教材 RAG、题库接入和分层记忆能力；本次没有逐项核实这些能力的生产实现、数据规模及指标。

- **简历自述**：可以作为待核对的经历材料，不等于已通过代码或生产证据验证。
- **本文设计**：薄弱知识点自适应辅导、显式状态机、跨进程恢复、业务幂等、补救规则及评测方案。
- **待验证**：题库是否支持知识点和难度过滤、是否提供幂等接口、能否获取逐题答案和提示使用记录。
- **不作承诺**：当前项目已经使用 LangGraph、本文流程已上线、存在本文未给出的效果数据。

面试措辞分三个层级：

| 实际证据 | 合适口径 |
|---|---|
| 只有设计 | “我针对现有能力设计了一个演进方案……” |
| 有可复现原型 | “我在原型中验证了……，尚未覆盖生产规模。” |
| 有上线记录和评测 | “我负责实现并上线了……，在某口径下测得……” |

不要把设计中的字段名说成现有代码中的类或表。本文不使用简历中的百分比为新流程背书。

### 0.2 三份面试材料对应位置

1. **业务说明**：第一部分。回答为谁做、解决什么问题、怎样算结束。
2. **架构与状态图**：第二部分。回答系统怎样执行、暂停、恢复、分支和留证据。
3. **追问备忘与指标**：第三部分。回答为什么这样设计、异常怎么办、怎样证明有效。

# 第一部分：一页业务说明与贯穿案例

## 1. 业务方向：错题驱动的薄弱知识点辅导

### 1.1 一句话定位

围绕学生的一道错题或一个明确的薄弱知识点，完成诊断、针对性讲解、练习和理解验证，形成可以暂停恢复、可以追溯依据的短时学习任务。

### 1.2 用户、入口与痛点

- 用户：具有明确教材和年级背景的 K12 学生。
- 入口一：学生做错一道题，选择“帮我弄懂这个知识点”。
- 入口二：学生主动说“去括号我不会”，补齐必要背景后进入辅导。
- 痛点：一次性解答能够告诉学生答案，但不知道学生错在哪里，也没有验证学生能否独立解决类似问题。
- 业务价值假设：缩短从“看到答案”到“验证理解”的路径，让下一次辅导能够利用历史证据。该假设需要评测，不直接宣称提高成绩。

### 1.3 最小范围与非目标

第一版限定一个知识点、文本交互、已有题库、最多一次补救。一次补救不是一道题，而是一轮“针对性讲解、补充练习、理解验证”。

暂不覆盖全学期规划、多知识点无限递归补课、OCR 识题、自主生成正式试题和长期学习能力预测。若发现前置知识缺口超出范围，记录原因并建议另开任务，而不是悄悄扩大当前任务。

### 1.4 三种结束结果

| 结果 | 含义 | 对学生怎么说 |
|---|---|---|
| `GOAL_MET` | 本次预设验证条件满足 | “这次练习和解释达到了本次目标，之后还可以复习验证。” |
| `NEEDS_REVIEW` | 有证据表明仍薄弱，且补救预算已用完 | “你已经能完成部分步骤，但负号处理仍需巩固。” |
| `INSUFFICIENT_EVIDENCE` | 有效题目或评估依据不足，无法得出可靠结论 | “目前还不足以判断，我们先保留进度和已有记录。” |

业务流程结束不等于目标达成；目标达成不等于长期掌握。取消、过期、技术失败也不等于学习能力不足。

## 2. 贯穿案例：去括号错误

原题：`3(x - 2) = 9`。学生写成 `3x - 2 = 9`。

系统提出“可能没有把乘法分配到括号内每一项”的假设，但也保留粗心等可能性。用一个短诊断问题验证，再检索对应教材的分配律内容，解释为什么应该得到 `3x - 6 = 9`。

练习使用不同表面形式，例如 `2(x - 4) = 6`，而不是只要求学生重做原题。理解验证可以问：“为什么括号里的两项都要乘 2？”

如果学生仍认为只乘第一项，进入一次针对性补救；如果补救后仍存在同类问题，结束为待巩固，不继续无限出题。

## 3. 完整业务流程：从一道错题到一次有依据的学习结论

| 环节 | 输入与动作 | 输出及进入下一步的条件 | 对外口径与异常边界 |
|---|---|---|---|
| 目标确认 | 错题或诉求、教材版本、年级 | 明确知识点 ID 和本次范围 | “先确认你用的教材和要解决的问题。”信息不全则追问，不猜教材 |
| 读取历史 | 同知识点近期表现及来源 | 诊断线索，不直接生成最终结论 | “之前记录可用于选题，但需要看这次表现。”无历史可冷启动 |
| 诊断 | 错误步骤、短题或解释 | 错因假设和支持/反对证据 | 不把单次失误固化成用户标签；证据不足继续有限诊断 |
| 局部计划 | 目标、诊断、步骤和题量限制 | 可执行的结构化步骤 | 固定步骤叫工作流；只有动态选择子目标和顺序才称局部 Planner |
| 教材检索 | 知识点、版本、章节过滤条件 | 带来源的教材片段 | 无结果不冒充教材内容；澄清条件或结束为证据不足 |
| 针对讲解 | 教材证据和错因假设 | 围绕当前问题的解释 | 讲完不代表学会；用户可追问、暂停或换话题 |
| 题库组卷 | 知识点、难度、题量、已用题目 | 试卷 ID、题目 ID 和题目版本 | 题量不足先按获准规则调整；不得悄悄使用无关题或模型生成题替代 |
| 等待答案 | 已发布试卷及当前题组 | 关联正确任务与题组的提交 | 保存后等待，不占用一个十分钟长请求；允许明确提交部分答案 |
| 判分分析 | 答案、评分规则、提示使用情况 | 逐题结果与待确认项 | 客观题优先确定性判分；主观题低可信结果不能强行判通过 |
| 理解验证 | 针对概念的一项简短解释任务 | 按固定量规评价的解释证据 | 评价概念关系而非语言华丽；无法表达不直接等同于不会 |
| 综合评估 | 独立答题、解释、有效样本情况 | 达标、补救、待巩固或证据不足 | 路由执行预先约定的规则，模型不自行降低通过门槛 |
| 总结回流 | 评估结果及证据引用 | 任务结论、学习记录、待更新画像事件 | 保存事实成功后才展示完成；画像可以异步更新，不谎称已经更新 |




  
这一节沿用第 2 节的学生案例，重点讲清楚：**为什么进入下一步、下一步如何使用上一步的结果，以及什么情况下结束。** 以下交互和答题表现均为设计示例，不是实际学生记录，也不代表功能已经实现。

先记住业务主线：

```text
学生带着错题求助
  -> 确认这次解决什么，结合历史提出错因假设
  -> 通过短诊断判断问题在哪里，确定本轮辅导安排
  -> 根据教材围绕错因讲解
  -> 换题让学生独立作答，再解释关键概念
  -> 根据证据判断：达标收尾，或进入一次针对性补救
  -> 保存本次结论与依据，供下一次辅导参考
```

这里有两个闭环：本次任务内是“发现问题、讲解、验证、必要时补救”；跨任务是“本次证据沉淀、下次诊断参考”。不是把检索、出题、记忆几个工具依次调用一遍就算闭环。

### 3.1 学生带着错题进入，先把“帮我讲题”变成明确目标

学生在 `3(x - 2) = 9` 中写出了 `3x - 2 = 9`，点击“帮我弄懂这个知识点”。系统拿到原题和错误步骤后，不马上把完整解答发给他，而是先确认年级、教材版本，以及这次是否主要想弄懂去括号。

确认后，这次任务的范围就从宽泛的“数学不会”缩小为“能正确使用分配律去括号，尤其不遗漏括号内的第二项”。虽然原题是一元一次方程，但本轮不因此扩展成整章方程教学；后面的练习和评价也围绕去括号步骤，不把无关的移项错误直接算成分配律错误。

同时，系统读取同知识点的近期学习记录。如果以前也出现过漏乘，可以优先检查这个问题；如果没有历史，直接从本次错题开始。历史在这里决定“先问什么”，不能代替本次诊断，更不能直接给学生贴上“分配律薄弱”的永久标签。

**到这里，下一步拿到的是：明确的学习目标、教材背景，以及一个待验证的错因假设。** 背景缺失就先追问，而不是猜一个教材版本继续。

### 3.2 用一次短诊断区分错因，再决定怎么讲

接着系统问学生：“你从 `3(x - 2)` 写到 `3x - 2` 时，是怎么处理前面的 3 的？”

假设学生回答：“3 只要乘 x，后面的 -2 不变。”这条解释就支持“没有理解括号外的数要乘到每一项”的假设。系统据此安排本轮辅导：先解释分配律，再用新的题目检查是否还会漏乘，最后让学生说明理由。

如果学生反而回答：“两项都应该乘 3，我刚才漏写了”，就不能坚持原先的诊断；可以追加一个短诊断项，检查是偶发失误还是稳定误解。诊断有次数限制，信息始终不足时保留不确定性，不无限追问。

系统也会用学生能理解的话说明安排：“我们先看为什么两项都要乘，再试两道不同的题，最后看看你能不能说清楚原因。”

**诊断的结果不是一句评价，而是带依据的教学选择：本轮重点讲什么、用什么练习验证。** 主流程固定时称为工作流即可；只有确实动态选择子目标和顺序，才需要称为局部 Planner。无论怎么选择内容，都不能临时降低通过门槛。

### 3.3 带着已定位的问题找教材，而不是检索完再泛泛讲一遍

有了“漏乘第二项”这个具体问题，系统按已确认的教材版本、章节和知识点检索分配律内容，取得带来源的片段，再围绕学生刚才的推理组织讲解。

讲解可以从原题展开：

> `3(x - 2)` 表示整个 `x - 2` 乘 3，不是只有 x 乘 3。拆开后是 `3 × x + 3 × (-2)`，所以得到 `3x - 6`。你刚才保留了 -2，实际上漏掉了第二项也要乘 3 这一步。

这里教材提供讲解依据，学生的错误决定讲解重点。系统不是完整背诵一遍章节，也不是只报出原题答案。如果找不到匹配的教材依据，先核对检索条件或澄清背景；仍无法取得必要依据，就按证据不足收尾，不虚构引用。

学生可以继续追问。但即使他说“懂了”，也只表示讲解可以告一段落，不能据此判定目标达成。**下一步必须把“听懂的自述”转换成“独立作答的证据”。**

### 3.4 换题验证，让学生的表现而不是系统的讲解决定结果

讲解结束后，系统从题库选择同知识点、难度合适、尚未使用的题目，避免只让学生背着答案重做原题。例如用下面两种题面检查去括号步骤：

| 示例题面 | 要求学生完成的任务 | 观察重点 |
|---|---|---|
| `2(x - 4) = 6` | 只写出去括号后的一步 | 是否把 2 同时乘到 x 和 -4 |
| `5(3 - x)` | 展开这个式子 | 项的位置变化后，是否仍能逐项相乘并正确处理符号 |

上述题面用于说明选题意图，实际任务须使用经校验的题库题目及评分信息，不能默认题库已有这两题。系统保存题组、题目版本和当前等待点，再把题目交给学生；如果题量不足，不能悄悄换成无关题或模型生成题，也不能降低验证条件后宣告通过。

学生做题期间，系统等待提交，不持续占用一个长请求。假设学生中途说“先不学了”，就保留这组题和当前进度；在任务仍可恢复的前提下，下次继续同一轮，而不是重新诊断、重新组卷。

假设这次学生独立写出 `2x - 8 = 6` 和 `15 - 5x`。系统将答案关联到当前任务与题组，按评分规则检查去括号结果，记录是否使用提示。客观结果优先用确定性规则判分，有歧义的结果保留待确认；明确提交的部分答案可以保存，但缺答项不算已经取得验证证据。

此时还不立刻宣布通过，而是继续问：“为什么括号里的两项都要乘外面的数？减号应该怎么处理？”学生需要表达出“整个括号参与乘法，每一项都要乘，第二项的符号也要保留在运算中”这样的概念关系，不要求措辞漂亮。

**到这里，评估拿到的是两类互补证据：学生能不能独立做对，以及是否存在关键概念误解。** 提示后答对、重做原题答对和首次独立答对必须区分，不能混在一起。

### 3.5 根据同一套规则分流：达标就结束，仍有问题才补救

系统把本轮有效作答和概念解释放在一起，执行任务开始时确定的评价规则，而不是让模型凭一句“看起来懂了”自由决定结果。

沿着前面的成功路径，如果学生两道新题都首次独立做对，解释也满足量规，本次任务就进入达标收尾。这里的结论只是“满足本次目标”，不是“以后都不会再错”。

如果把案例换成另一条分支：学生仍写出 `2x - 4 = 6`，解释中也坚持“只乘第一项”，这才有依据进入补救。补救不是把刚才的话原样重复一遍，而是围绕仍然存在的误解换一种讲法。例如把 `3(x - 2)` 写成三个 `(x - 2)` 相加，让学生看到三个 x 对应三个 -2，再回到逐项相乘的写法。

补救后换一组有效新题，重新进行独立作答与理解验证，不用已经讲过答案的题目证明通过。新一轮证据达标，可以结束为 `GOAL_MET`，但保留首轮失败和补救经过，不能把它改写成“首轮就会了”。

第一版最多补救一轮。补救后仍有明确的同类错误，就结束为 `NEEDS_REVIEW`，说明具体还需巩固什么；若题目不足、评分不明确或缺少必要回答，导致无法完成可靠判断，则记录为 `INSUFFICIENT_EVIDENCE`，不能把“没证据”当成“学生不会”。

学生不愿继续时，也不强迫补救或解释：可以暂停、取消，或按其意愿以证据不足收尾。遇到超出本轮范围的前置知识问题，记录并建议另开任务，不无限扩大学习范围。

**这一环节决定了闭环的边界：成功有条件，补救有上限，无法判断也有明确出口。**

### 3.6 收尾不是一句“你学会了”，而是保存可供下次使用的结果

回到首次验证就达标的示例，系统先保存题目、原始答案、提示使用情况、解释评价及任务结论，再向学生展示：

> 这次你在两道新题中都完成了逐项相乘，也说明了每一项都要参与运算，达到了本次去括号练习的目标。之后还可以通过复习检查是否保持。

如果补救后仍未达标，总结就应改成具体薄弱点，例如“本轮仍出现漏乘第二项，建议继续巩固分配律”，而不是笼统地说“数学能力差”。如果结果保存失败，则不能先展示“本次已完成”。

保存后的学习记录才进入后续记忆回流：原始答案是证据，“本次在哪些题上表现如何”是学习事实，“近期建议复习什么”是聚合画像。画像可以异步更新；本次结果已保存但画像尚未同步时，明确区分这两件事。

下次学生再来学习分配律，系统可以据此选择更合适的诊断问题，但仍要看新的表现，而不是永远沿用旧判断。**这样，本次结果成为下一次辅导的输入，业务才从单次答疑延伸为可追溯的学习闭环。**

### 3.7 面试时，把上面的流程连成一段讲

以下是业务口播示例，按设计方案介绍，不代替个人实现经历：

> 我设计的场景是：学生做错题后，不只是想知道答案，而是想弄懂背后的知识点。例如他把 `3(x - 2)` 写成了 `3x - 2`。系统先确认教材和本次学习范围，结合历史记录提出错因假设，再问他这一步是怎么想的。如果他认为 3 只乘 x，就围绕“没有逐项相乘”来安排讲解，而不是直接把整道方程解给他看。
>
> 接下来，系统检索对应教材的分配律内容，结合这个错误解释为什么第二项也要乘 3。讲完不会因为学生说懂了就结束，而是从题库换两道没做过的题，让他独立完成去括号，再解释为什么每一项都要参与运算。这样同时看操作结果和概念理解，而不是只看原题有没有改对。
>
> 如果这些证据满足事先设定的规则，就记录本次目标达成；如果仍然漏乘，就针对同一个误解换种方式讲，再用新题验证，最多补救一轮。补救后仍有问题就明确标记待巩固，证据不够则保留不确定结论，不无限出题，也不强行判通过。
>
> 最后保存本轮答题、提示使用和解释依据，形成学习记录，供下次诊断参考。学生中途暂停也应保留当前题组和阶段，回来继续。所以这个方案的重点不是“让模型把题讲得更长”，而是让诊断决定讲解、验证决定下一步，并把结果带入后续学习。

面试官进一步问“怎么实现”时，先用 4.2 节的话术转入技术，再用 4.3 节沿同一任务讲输入、处理和输出。追问状态、暂停、异常和幂等时，分别展开 5.5、6.7、7.1 和 8.4 节。不要把所有机制一次性背完。

### 3.8 教学规则的示例口径

学习原型可以暂设“两道有效迁移题首次独立作答正确，并通过一次关键概念解释”为本次通过条件。这只是演示规则，需要教研校准，不是科学证明的掌握标准。

解释量规至少区分：能否指出括号内每项都参与运算、能否说明符号处理、是否存在关键误解。模型输出必须包含证据和量规项；自然语言“看起来理解了”不能单独触发通过。

题目错误、题目泄露答案、提示后答对、反复做同一题，应单独标记，不能混入首次独立正确率。主观解释疑似误判时允许澄清一次；仍不明确则记录证据不足。

# 第二部分：架构、状态与异常闭环

## 4. 双层执行架构

```text
用户/前端
   |
任务 API：鉴权、事件关联、重复提交检查
   |
外层学习工作流：阶段、分支、暂停、恢复、终止
   |                           |
阶段内 Agent Loop             确定性业务服务
教材查询/组织讲解              题库组卷/客观判分/状态提交
   |                           |
工具执行层：超时、结果格式、追踪、错误分类
   |
教材检索库 | 题库 | 任务存储 | 学习证据与画像存储
```

外层决定“当前允许做什么”，内层解决“这一步怎样完成”。不能让阶段内 Loop 自行跳过答题验证、改变学习结果或无限扩大知识点范围。

LangGraph 是可选的编排实现，不是业务正确性的来源。也可自建状态机和数据库；无论使用何种实现，都要自己设计授权、事务边界、幂等键和业务规则。本文是概念设计，不提供未经验证的框架 API 用法。

### 4.1 确定性代码和模型各做什么

| 交给模型 | 交给程序与业务规则 |
|---|---|
| 提出错因假设、组织讲解、提议局部计划 | 校验知识点和计划结构、限制步骤和预算 |
| 主观解释的量规评价及依据 | 检查必需证据、执行通过/补救路由 |
| 工具参数候选和检索查询 | 鉴权、教材过滤、业务幂等、超时和持久化 |
| 面向学生的总结草稿 | 核对草稿与已保存结果一致，禁止夸大掌握结论 |

### 4.2 从业务切到技术：先讲约束，再讲分层

**面试官问：“这个流程具体怎么实现？”**

> 我会把它设计成一个由用户事件推动的学习任务，而不是一次从头运行到尾的大模型请求。原因是诊断要等学生回答，练习也要等提交，学生还可能中途暂停，所以系统必须明确知道现在执行到了哪一步。
>
> 外层工作流负责保存阶段、判断允许接收的事件，以及决定继续、等待还是结束；阶段内的 Agent 负责需要语言理解和内容组织的部分，比如根据学生解释提出错因假设、检索教材并组织讲解。模型返回的是带依据的阶段结果，不能直接修改最终学习结论。
>
> 比如同样收到一句“我懂了”，如果当前是讲解阶段，可以据此准备练习；如果当前还在等答案，就不能把它当成答题通过。下面我可以沿刚才的去括号案例，讲一次任务从创建到评估的数据怎么流转。

这段回答的落点是“控制权在哪里”，不是先罗列框架。下面的字段、事件和对象都是**拟议契约示例**，不是当前仓库已有接口；示例只展示关键字段，不是完整 API 规范。

### 4.3 技术主链：同一任务的输入如何变成下一步输出

**第一段：创建任务，把自然语言诉求转换成明确状态。**

客户端提交错题、错误步骤和已确认的教材背景。服务端从认证上下文取得用户身份，检查目标信息；缺什么就返回澄清问题，信息齐全后建立学习任务。本例用 `T1` 表示任务，用 `A1` 表示首轮练习，用 `P1` 表示随后生成的题组。这些标识均由服务端分配或校验。

```text
客户端输入：
  原题 = 3(x - 2) = 9
  学生步骤 = 3x - 2 = 9
  年级、教材版本 = 已确认值

服务端处理：
  校验身份和背景 -> 建立 T1 -> 关联知识点与评价规则版本
  -> 读取相关历史 -> 生成并保存本次诊断问题

持久化输出：
  task_id = T1
  status = WAITING_USER
  stage = DIAGNOSE
  待回答对象 = 本次诊断问题

给学生的输出：
  “你觉得括号外的 3 应该乘哪些部分？”
```

这里创建任务的输出，就是下一次回答的上下文。不是发完问题后只在聊天记录里留一句话，下一轮再让模型猜刚才问了什么。

**第二段：接收诊断回答，模型给分析，程序决定是否进入讲解。**

学生回答“只乘 x”。服务端先确认这是 T1 正在等待的诊断回答，再保存原话和证据引用。交给模型的是当前目标、原题、学生解释和相关历史线索，而不是无筛选地塞入全部历史会话。

```text
模型输入：
  本次目标 + 错误步骤 + 本次诊断回答 + 有来源的历史线索

模型候选输出：
  错因假设 = 漏乘括号内第二项
  支持证据 = 本次回答的引用
  待澄清项 = 无
  建议讲解重点 = 每一项都参与乘法

程序处理：
  校验结构、证据引用和目标范围
  -> 形成受限计划 -> 推进至教材检索
```

程序可以检查格式、引用是否存在和步骤是否越界，但这不等于已经证明模型的教学判断正确；语义质量仍需量规和评测。如果证据不足，则在预算内继续诊断，不因模型返回了合法结构就强行推进。

**第三段：检索与讲解完成后，把练习发布成一个可恢复的等待点。**

检索工具接收知识点、教材版本和章节条件，返回教材片段及来源。模型基于这些片段和错因组织讲解。讲解阶段结束后，外层调用题库服务，传入知识点、难度、题量和排除题目，得到经过校验的题目、版本以及服务端评分信息。

```text
组卷输入：
  task_id = T1，attempt_id = A1
  知识点 = 本次分配律目标
  题量 = 2，排除题目 = 已讲解或已使用的题目
  业务操作键 = 本轮稳定的组卷标识

组卷成功并提交后的状态：
  paper_id = P1
  status = WAITING_USER
  stage = WAIT_ANSWER
  question_ids = [Q1, Q2]
  state_version = 7

给客户端的输出：
  T1、A1、P1、版本 7、题目展示内容、允许的下一步动作
```

版本 7 仅用于后面的并发示例，不表示前面恰好发生了六次更新。评分答案留在服务端，不放进学生可见的题目响应。先保存题组和等待点，再通知学生；即使通知丢失，也可以通过读取任务恢复展示。此时本次处理结束，等待下一次事件，不让 Agent 在后台不断询问“学生答了吗”。

**第四段：提交答案，先产生评分证据，再发起理解验证。**

```json
{
  "event": "SUBMIT_ANSWERS",
  "task_id": "T1",
  "attempt_id": "A1",
  "paper_id": "P1",
  "submission_id": "S1",
  "expected_state_version": 7,
  "answers": [
    {"question_id": "Q1", "answer": "2x - 8 = 6"},
    {"question_id": "Q2", "answer": "15 - 5x"}
  ]
}
```

这是客户端输入，不是可信结论。服务端核对任务归属、题组、轮次、允许的阶段及提交是否重复，评分规则和提示使用情况从服务端记录读取，不接受客户端自报“独立作答”“已通过”。

受理后先保存唯一提交，进入评分处理。处理尚未完成时返回“已受理/处理中”，不能冒充已评分；完成后保存逐题证据，并生成概念解释问题，推进到 `WAIT_EXPLANATION`、`WAITING_USER`，再通知客户端。客户端也可主动读取最新状态。

**第五段：解释提交后，规则评估产生分支，收尾才产生最终结论。**

学生的概念解释同样关联到 T1 当前等待的问题。模型按量规返回各项判断及原话依据；程序结合有效题数、首次独立作答结果和解释评价，执行保存的规则版本。

```text
评估输入：
  本轮逐题评分 + 提示记录 + 概念解释量规结果 + 补救次数

规则输出：
  满足本次条件 -> FINALIZE，准备保存 GOAL_MET
  明确仍薄弱且剩余一次补救 -> 创建 A2，进入针对性补救
  补救已用完且仍薄弱 -> FINALIZE，准备保存 NEEDS_REVIEW
  必要证据不足且无法继续有效验证 -> FINALIZE，准备保存 INSUFFICIENT_EVIDENCE

收尾提交成功后给客户端：
  已保存的 outcome、原因、可展示的证据摘要、后续建议
```

创建补救轮次时保留 A1 的历史，不覆盖旧答案。最终结果与待发送的画像更新事件一起可靠保存，画像异步消费；外层状态提交成功后才允许对学生宣布完成。

**面试时这条技术主链可以收成一句话：**

> 每次交互都会接收一个有关联的事件，读取当前任务状态，校验这次允许做什么，调用必要的模型或服务，再保存阶段结果并返回新的等待点或最终结论。下一次不是从聊天摘要重新开始，而是接着这个已保存状态继续。

### 4.4 追问：“你给模型什么，它具体返回什么？”

> 我会按阶段提供最小必要上下文。诊断阶段给目标、错题、学生解释和相关历史证据，要求返回错因假设、支持依据和待澄清项；讲解阶段再加入检索到的教材片段，返回讲解内容及来源引用；理解验证阶段给学生原话和固定量规，返回每项判断及依据。程序负责校验这些候选结果，模型没有直接写任务终态或修改通过规则的权限。

以理解验证为例，模型输出可以约定为：

```json
{
  "rubric_version": "concept-v1",
  "items": [
    {
      "criterion": "all_terms_multiplied",
      "judgment": "supported",
      "evidence_quote": "括号里的每一项都要乘外面的数"
    },
    {
      "criterion": "sign_handling",
      "judgment": "unclear",
      "evidence_quote": null
    }
  ],
  "needs_clarification": true
}
```

这是虚构的契约样例：`supported`、`contradicted`、`unclear` 分别表示支持、反对和证据不清楚。程序核对量规版本、必需项、枚举和引文是否对应本次回答，再按规则澄清或评估；不会因为第一项满足就忽略第二项。这个模型输出刻意不包含最终 `GOAL_MET`，以避免把教学终态控制权交给模型。

## 5. 状态不是一段聊天摘要

### 5.1 将生命周期和教学阶段分开

**生命周期 `status`**：

- `ACTIVE`：系统可执行当前阶段。
- `WAITING_USER`：正常等待答案、复述或必要信息，不算异常。
- `PAUSED`：用户明确暂停或系统因预算保护挂起，记录原因。
- `COMPLETED`：流程正常收尾，必须有业务结果。
- `CANCELLED`：用户明确取消，不再自动恢复。
- `EXPIRED`：超过已配置的保留/恢复期限，不能直接继续旧状态。
- `FAILED`：不可恢复的技术故障或恢复手段耗尽，无学习结论。

**教学阶段 `stage`**：`CONFIRM_TARGET`、`DIAGNOSE`、`PLAN`、`RETRIEVE`、`EXPLAIN`、`ASSEMBLE`、`WAIT_ANSWER`、`GRADE`、`WAIT_EXPLANATION`、`ASSESS`、`REMEDIATE`、`FINALIZE`。

补救是教学阶段，不是用户暂停；等待输入不是程序失败；技术重试不是教学补救。

### 5.2 最小状态字段

| 字段 | 用途 |
|---|---|
| `task_id`, `user_id` | 稳定任务标识和所属用户，防止跨用户恢复 |
| `session_id`, `turn_id` | 关联会话和本次交互，不代替任务 ID |
| `status`, `stage`, `state_version` | 生命周期、阶段、乐观锁版本 |
| `target`, `plan`, `plan_version` | 教材/知识点目标和已校验计划 |
| `learner_context_snapshot`, `resource_refs` | 学生背景快照与实际资源来源分开保存；教材过滤使用本次确认的 target，不永久绑定学生资料 |
| `assessment_policy_version` | 固定本任务的通过条件与补救规则版本 |
| `paper_id`, `question_ids`, `attempt_id` | 试卷、题目及当前作答轮次 |
| `submission_id`, `submission_version` | 去重并区分修改答案和重复发送 |
| `evidence_refs` | 原始答案、量规、教材来源等引用，不把大对象全塞入状态 |
| `remediation_count`, `tool_retry_count` | 教学补救与技术重试分别计数 |
| `pause_reason`, `resume_stage`, `pending_action` | 暂停原因、返回阶段、待确认外部操作 |
| `outcome`, `outcome_reason` | 正常收尾的学习结果和原因 |
| `created_at`, `updated_at`, `expires_at` | 时效与恢复期限，期限值由产品规则决定 |

### 5.3 正常教学状态图

```text
CONFIRM_TARGET -> DIAGNOSE -> PLAN -> RETRIEVE -> EXPLAIN
                                                     |
                                                  ASSEMBLE
                                                     |
                                    WAIT_ANSWER [WAITING_USER]
                                                     |
                                                   GRADE
                                                     |
                               WAIT_EXPLANATION [WAITING_USER]
                                                     |
                                                   ASSESS
                       +-----------------------------+--------------------+
                       |                             |                    |
                    证据达标                   薄弱且尚可补救        无法继续有效验证
                       |                             |                    |
                    FINALIZE                    REMEDIATE              FINALIZE
                       |                             |                    |
             COMPLETED / GOAL_MET          EXPLAIN -> ASSEMBLE    COMPLETED / 对应结果
```

补救再次回到答题和解释验证，使用新的 `attempt_id`。补救预算耗尽且仍薄弱，结果为 `NEEDS_REVIEW`；有效证据不足则为 `INSUFFICIENT_EVIDENCE`。

### 5.4 生命周期转移规则

| 当前状态/事件 | 条件与动作 | 新状态 |
|---|---|---|
| ACTIVE / 已发布题目或解释问题 | 先保存业务对象和等待点，再通知用户 | WAITING_USER |
| WAITING_USER / 合法提交 | 所属用户、任务、题组和版本都匹配，提交未处理 | ACTIVE，进入相应评估阶段 |
| ACTIVE 或 WAITING_USER / 暂停 | 保存进度和安全恢复点，停止后续调度 | PAUSED |
| PAUSED / 继续 | 重新鉴权、核对版本、时效和未决操作 | ACTIVE 或 WAITING_USER，回到保存阶段 |
| 非终态 / 明确取消 | 记录取消，禁止后续业务推进 | CANCELLED |
| 非终态 / 到期 | 依据配置过期，晚到事件不能复活任务 | EXPIRED |
| ACTIVE / 正常收尾持久化成功 | 保存学习结果，排队发送画像更新事件 | COMPLETED |
| ACTIVE / 不可恢复技术故障 | 记录错误与已有证据，不产生掌握结论 | FAILED |
| 任意终态 / 新提交或继续 | 返回终态结果或询问是否新建任务 | 原状态不变 |

终态不可被迟到的工具回调或学生提交重新激活。重开任务使用新 ID，并显式引用旧证据。

### 5.5 面试表达：不要背字段，拿一条状态解释它们

**面试官问：“你到底保存什么状态，为什么不能只用聊天历史？”**

> 我会区分“任务是否能继续”和“教学走到了哪里”。比如刚才发布题目后，任务是等待用户，教学阶段是等待答案；学生暂停后，生命周期改成暂停，但题组和教学位置不能丢掉。所以状态中至少要有任务归属、生命周期、阶段、当前轮次和题组、规则版本、并发版本，以及证据引用。
>
> 聊天摘要可以告诉我“正在学分配律”，却不能可靠回答“这份答案属于哪组题、是否已经处理、补救额度是否用过”。这些决定业务是否可以推进，我会用结构化持久化状态作为权威来源，而不是从文本推断。

结合 4.3 节的同一题组，可以在白板上写：

```text
输入：T1 / A1 / P1，WAITING_USER + WAIT_ANSWER，版本 7
事件：收到唯一提交 S1
处理：校验归属与关联，保存提交，条件更新状态
输出：ACTIVE + GRADE，版本 8；S1 已受理，尚未承诺完成判分
后续：评分提交成功 -> 保存理解问题 -> WAITING_USER + WAIT_EXPLANATION
```

**追问：“两个请求同时读到版本 7 怎么办？”**

> 我会在数据库提交时要求版本仍为 7，并且阶段允许这个动作；只有一个请求能成功推进。另一个请求不能拿旧状态覆盖新状态，而是重新读取。若是同一个提交，返回已有处理状态或结果；若是不同提交，就提示冲突或按明确的修改答案规则处理。单纯先读一次版本再无条件写入，不构成并发保护。

## 6. 暂停、恢复、补救：逐场景说明

### 6.1 用户说“先不学了”

这句话可能是暂停，也可能是取消。默认采用可逆的暂停，并提示：“已保留本次进度，之后可以继续；如果想结束本次任务，也可以取消。”明确“取消这个任务”才进入取消状态。

如果正在调用题库，暂停不能撤销已经发生的外部操作。记录未决调用；回包后可以保存试卷 ID，但不能继续向学生发布新题或推进教学。恢复时先确认调用结果，避免重复组卷。

### 6.2 用户断线或关闭页面

断线只是传输事件，不自动等同于用户暂停或任务失败。已经等待答题的任务保持 `WAITING_USER`；正在执行的短任务可以完成到下一个持久化安全点。

前端重连先读取服务端权威任务状态，不能只凭本地聊天消息猜测该从哪里继续。进程重启能否恢复取决于持久化实现，内存里的等待对象不能作为跨进程恢复保证。

### 6.3 用户在补救中暂停

保存 `stage=REMEDIATE` 或实际进入的补救子阶段，并保存当前 `attempt_id`、已用补救次数、试卷和已提交证据。恢复继续同一轮，不重新消耗一次补救额度，也不跳到最初诊断。

补救计数在“批准创建新补救轮次”时原子增加；技术重试、重复提交和恢复同一轮均不增加。

### 6.4 用户换话题或要求换知识点

普通插问不自动记为答案。明显无关的话题可独立响应，原学习任务保持等待；想切换学习目标则确认暂停当前任务并新建任务。不能把“帮我看下一章”当成修改旧任务目标，从而污染原证据。

提交端最好携带任务和题组 ID。纯聊天提交缺乏关联且可能歧义时，追问确认，而不是让模型猜后直接判分。

跨年级、跨教材不一定意味着换知识点，先按 6.8 节识别范围和澄清意图，再决定继续原任务、另开任务还是独立答疑。

### 6.5 用户直接要答案或拒绝复述

可以提供帮助，但记录 `assisted=true`，不计为首次独立通过。拒绝复述不贴“不配合”或“不会”的画像标签；可以提供预先批准的等价理解题，仍拒绝则暂停，或按用户意愿以证据不足收尾。

### 6.6 长时间后继续

恢复前检查题目是否仍有效、任务是否过期、通过规则版本是否仍可执行。未过期时沿用任务保存的规则，不能无声换标准；必要变更须说明并显式迁移或新建任务。

旧成绩仍是历史事实，但不能被当作当前掌握水平。根据间隔安排新诊断属于新评估，而不是改写旧成绩。

### 6.7 面试表达：沿“补救中暂停再继续”讲一遍

**面试官问：“如果学生在补救过程中暂停，回来怎么继续？”**

> 假设首轮没有达标，我批准了一轮补救，此时轮次是 A2，补救次数已经加到 1，并且补救题组 P2 已经发布。学生暂停时，我会保存当前等待阶段和题组，把生命周期改成暂停，不清空 A2，也不把补救次数重置。
>
> 他回来后，我会先校验身份、任务有效期、题目和规则是否仍可用，再读取持久化的恢复点。如果原来在等 P2 的答案，就恢复等待这组答案，不从最初诊断重新执行。只有批准一轮新的教学补救才扣次数，暂停、恢复和工具重试都不是新的一轮。

```text
暂停前输入状态：
  T1 / A2 / P2，remediation_count = 1
  status = WAITING_USER，stage = WAIT_ANSWER

暂停事件处理：
  检查归属和版本 -> 保存恢复点 -> status = PAUSED
  输出：“已保留补救练习进度。”

继续事件处理：
  检查归属、时效、版本和未决操作
  -> status = WAITING_USER，stage = WAIT_ANSWER
  输出：同一个 A2、P2 和已保存答案；remediation_count 仍为 1
```

**追问：“服务进程已经重启呢？”**

> 这个设计不依赖原进程还活着。新进程应该能从持久化状态、题组和提交记录恢复等待点。如果当时不是等待答案，而是有未完成的外部调用，就先检查操作记录、做结果对账，不能直接重跑。要声称跨进程恢复已经实现，我还需要用进程终止后的恢复测试证明；目前这里讲的是设计契约。

### 6.8 学生问了其他年级或教材的内容怎么办

这是业务范围分支，不必然是技术异常，也不说明学生能力不足。设计原则是：**不因学生资料不匹配而直接拒绝，不擅自换教材，不让跨范围问题污染原任务的评价。** 以下交互、字段和分支仍属于设计示例。

**先把三种范围分开。**

| 信息 | 表示什么 | 如何使用 |
|---|---|---|
| 学生背景 | 资料中的年级、教材及确认时间 | 用于选择合适的表达和提出澄清，不作为永远不能跨越的限制 |
| 本次任务目标 | 学生确认要学的知识点、范围与教材背景 | 决定本轮检索、组卷和评价；已有证据后不能静默替换 |
| 实际资源来源 | 真正使用的教材版本、章节、片段和题目版本 | 用于引用、追溯和兼容性校验，不能因学生使用甲版就把乙版资源标成甲版 |

例如学生资料写的是“七年级、甲版教材”，但提交的问题疑似来自其他学习范围。系统先识别候选知识点，再结合可用教材目录或经核验的知识点映射判断差异。模型可以提出候选，不能仅凭记忆就认定“这一定是某年级内容”。检索为空也不能直接判定超纲，可能是资源缺失或检索条件不准确。

**第一步：问清意图，而不是马上切换。**

> “这道题涉及的内容可能不在你当前教材的学习范围内。你是在提前预习，还是这次使用了其他教材？可以补充一下题目来源或章节，我再安排讲解。”

只询问当前决策需要的信息；问题明确、来源齐全时不重复追问。随后按下列分支处理：

| 确认后的情况 | 处理与进入下一步的条件 |
|---|---|
| 同一知识点，只是名称或章节不同 | 核验概念、讲解方法和难度是否适合本次目标；兼容时继续原任务，标注真实来源，不因名称相似就自动认定等价 |
| 主动预习高年级内容 | 确认新目标，检查必要前置知识及教材、题库支持；具备条件后创建独立任务，不因资料年级较低直接拒绝 |
| 需要回顾低年级基础 | 只为当前讲解服务的简短回顾可留在原任务，但记录提示；需要完整诊断和练习则另开前置知识任务，不无限递归补课 |
| 资料过时或本次更换教材 | 首次目标确认时采用本次确认信息；若已有任务证据且范围或标准需要改变，保留旧任务并新建任务。长期资料是否修改单独确认 |
| 仍不能确定范围 | 有限追问题目来源、章节或完整题干；无法确认就说明不确定，不猜版本后强行推进 |
| 缺少匹配教材或合格练习资源 | 说明缺口；可提供补充资料、暂停，或独立通用答疑等选择，不放宽原任务通过门槛 |

**第二步：只支持解释时，明确区分“答疑完成”和“学习达标”。**

如果系统能够提供可靠的通用概念解释，但没有本次教材依据，可以说明：

> “我可以先做通用概念解释，但目前没有你这版教材的对应资料，不能保证章节和教学顺序一致。你想先了解概念，还是补充教材信息后继续？”

经学生确认后，通用答疑作为独立交互处理，标明不属于教材验证闭环。解释缺乏可靠依据时仍须承认不确定，不能用“通用”作为自由编造的理由。原学习任务按用户意愿暂停，或在无法继续有效验证时以 `INSUFFICIENT_EVIDENCE` 收尾；用户明确取消则取消。不能把原任务悄悄改成答疑后标记 `GOAL_MET`。

如果通用答疑展示了原任务待验证题的答案或关键提示，也要记录辅助情况，后续不能再把这些题算作首次独立作答。换一种交互模式不意味着清空证据约束。

**第三步：技术上把范围确认作为显式输入，不靠模型自行放宽过滤。**

```text
输入：
  学生背景 = 七年级、甲版教材
  原任务 T1 = 当前已确认知识点、规则版本及等待点
  新问题 = 疑似其他教材或学习范围的题目

识别与澄清：
  提取候选知识点 -> 核对目录、映射和来源
  -> 保存待确认的范围问题 -> 接收学生确认意图
  -> 检查资源覆盖与必要前置知识

确认后的输出：
  同目标且资源兼容 -> 保留 T1 目标和规则，记录真实来源后继续
  明确换目标且可支持 -> 确认暂停 T1，创建 T2 并关联来源任务
  仅可做概念解释 -> 独立答疑，T1 按确认结果暂停或收尾
  仍不明确或无法支持 -> 说明缺失信息和可选动作，不自动判通过
```

首次进入时，范围澄清可留在 `CONFIRM_TARGET`、`WAITING_USER`；已有任务中的插问则独立保存澄清交互及其关联，不把它塞进当前题组答案，也不擅自将原任务退回目标确认。确认切换时按当前状态和版本保存原进度，再创建新任务；重复确认不能重复创建 T2，需要稳定确认事件标识和可恢复的切换记录。题库、检索调用只有在新目标经校验后，才使用新的过滤条件。

这里的 `learner_context_snapshot` 对应学生背景快照，`target` 对应本次目标，`resource_refs` 对应实际来源。候选范围、确认问题和确认事件可作为独立交互记录保存，不等于已经修改了 `target`。新任务的答题证据归新任务；旧任务恢复后仍沿用自己的目标、轮次和评价规则。

**面试官问：“如果学生问的不是这个年级、不是这版教材，怎么办？”**

> 我会区分学生资料、本次学习目标和实际资源来源，不把资料中的年级当成不能跨越的限制。遇到疑似跨范围问题，先确认是预习、补基础，还是换了教材；同一知识点可以在核验兼容性后继续讲，但引用必须保留真实来源。如果确实换目标，就保留原任务并创建新任务，不混用两边的答案和评价规则。
>
> 技术上，模型只提出候选知识点和澄清建议，程序根据确认结果和资源覆盖决定路由。检索过滤使用本次确认的任务范围，不因检索为空就自动取消教材限制。如果只有通用解释能力，没有对应教材和练习验证能力，我会经确认提供独立答疑，但不会把原学习任务标成达标。这样既允许合理的跨范围学习，也保护了原任务的评价口径。

## 7. 异常处理矩阵

下列次数属于原型策略示例：工具调用最多重试两次，即首次调用加最多两次重试；教学补救最多一轮。生产值应配置化并通过测试确定。

| 异常 | 系统处理 | 用户口径 | 数据与状态保护 |
|---|---|---|---|
| 教材检索为空 | 检查过滤条件，有限改写或询问背景 | “没找到对应教材依据，需要确认版本。” | 不拿其他版本冒充，不虚构引用 |
| 问题疑似跨年级或跨教材 | 按 6.8 澄清意图，核验范围映射与资源覆盖 | “是在预习、补基础，还是这次用了其他教材？” | 不自动改目标或长期资料，不将检索为空等同超纲 |
| 仅支持通用解释、不支持教材闭环 | 经确认独立答疑，原任务暂停或按规则收尾 | “可以先解释概念，但不能据此完成本次教材学习验证。” | 不伪造来源，不判原任务达标，记录相关答案曝光与提示 |
| 题库题量不足 | 按已批准策略减少题量或询问调整 | “可用题目不足，是否调整本次练习？” | 调整后若不满足验证条件，不判通过 |
| 模型输出格式错误 | 校验结构，有限修复重试 | “分析暂未完成，正在重试。” | 无合法结构不能推动业务状态 |
| 主观判分有歧义 | 澄清、人工复核入口或记录未知 | “这段解释还需要确认。” | 未知不是错误，也不是通过 |
| 工具超时/限流 | 可重试错误退避重试，检查剩余预算 | “服务暂时繁忙，进度已保留。” | 外部写操作先对账，不能盲目重做 |
| 永久参数错误/无权限 | 停止调用，修正输入或结束技术失败 | “当前请求无法执行，需要调整信息。” | 不自动放宽权限或越权换数据 |
| 重复提交 | 根据 submission_id 返回已有结果 | “这份答案已收到。” | 不重复判分、计数或写记忆 |
| 两端同时继续 | state_version 条件更新，只接受一次推进 | “任务已在另一端更新，已刷新进度。” | 失败方读取最新状态而非覆盖 |
| 旧题组答案晚到 | 拒绝用于当前轮，保留审计信息 | “这是上一轮题目，请确认当前练习。” | 不覆盖当前 attempt 的结果 |
| 暂停后工具返回 | 保存外部结果，停止教学推进 | 通常无需主动打扰 | 回调检查状态和版本，不复活任务 |
| 学生拒绝继续 | 明确暂停、取消或证据不足收尾 | 尊重停止，不反复劝做题 | 不能记为能力不足 |
| 系统预算耗尽 | 安全点挂起，或不可恢复时技术失败 | “本次分析资源达到上限，已保存进度。” | 不伪装成教学通过或补救耗尽 |
| 画像服务不可用 | 重试事件，任务保留已保存学习结论 | “本次结果已保存，历史概览稍后同步。” | 画像更新具有幂等事件 ID |
| 任务结果持久化失败 | 不宣布完成，重试或故障收尾 | “结果保存尚未完成。” | 不先展示完成后丢失事实 |

### 7.1 面试表达：异常不是统一“重试三次”

**面试官问：“模型或者工具出错，你怎么兜底？”**

> 我会先区分技术失败、业务证据不足和外部结果未知。比如教材查询成功但没有匹配内容，这是证据不足，可以有限澄清或调整检索条件；模型返回了错误结构，可以在预算内修复，但不能直接推进阶段；组卷请求超时则更特殊，它可能已经在题库创建了试卷，不能当成确定失败直接重做。
>
> 所以我会记录错误类别、操作标识和当前状态，只对适合重试的错误执行有界重试。对结果未知的外部写操作先对账，对证据不足不判通过，对不可恢复的技术故障不生成“学生不会”的结论。兜底的目标首先是保持事实和状态正确，不是任何异常都必须给出一个学习成绩。

同样是“没有拿到需要的结果”，输入和输出必须区分：

| 输入事件 | 拟议处理 | 对外输出与禁止事项 |
|---|---|---|
| 检索成功但匹配片段为空 | 校对背景、有限改写；仍无依据则收尾 | 说明缺少教材依据，不虚构引用 |
| 解释评价缺少必需量规项 | 保留原回答，在预算内修复评价 | 仍未完成评价，不跳到通过 |
| 组卷超时、外部是否创建未知 | 保存未决操作，按稳定键查询或幂等重试 | 显示处理中或保留进度，不盲目新建 |
| 最终结果已保存、画像同步失败 | 重试待发送事件，消费者去重 | 本次结果可展示，画像尚未同步 |

具体的“组卷超时后又暂停”用 8.4 节展开，不必在开场同时解释全部异常。

## 8. 幂等、事务与恢复如何讲清楚

### 8.1 业务幂等不是工具去重

工具去重可阻止同一轮重复参数调用，但不能保证超时后、重启后或两个并发请求之间不重复产生试卷。

组卷幂等键可以设计为 `task_id + attempt_id + assemble_operation_version`，数据库设唯一约束。不要只用知识点 ID，因为同知识点可以合法出现多次练习。

外部题库支持幂等时传入稳定键；不支持但可按业务请求号查询时，超时后先查再决定是否重试。如果两者都不支持，就不能宣称严格一次执行，应将结果未知的操作挂起对账，或说明只能尽力去重。

### 8.2 一次答案提交的提交边界

```text
鉴权及事件关联
  -> 保存唯一提交事件
  -> 执行可重试的判分计算
  -> 同一事务内保存判分结果、推进任务版本、写待发送事件
  -> 事务成功后通知用户
  -> 异步消费事件更新画像
```

执行失败后从已提交的边界恢复，不从聊天摘要推断。外部调用与本地数据库通常不能组成一个普通本地事务，因此使用业务请求号、状态记录和结果对账处理不确定性。

### 8.3 至少需要观察什么

追踪关联 `task_id`、`turn_id`、`attempt_id`、操作 ID、状态前后版本、规则版本、错误类别、重试次数、系统耗时和用量。日志不默认记录完整学生隐私；必要证据按访问权限保存。

### 8.4 面试表达：把幂等讲成一次真实可能发生的故障

**面试官问：“组卷已经成功，但响应丢了，这时候学生又暂停怎么办？”**

> 我会在请求题库之前，先为当前任务和练习轮次保存一个稳定的组卷操作标识。例如 T1 的 A2 只有一个当前组卷操作，重试不能临时换一个新标识。请求超时后，我只能确定本地没收到结果，不能确定题库没有创建试卷，所以先把这个操作记为结果未知。
>
> 如果这时学生暂停，我会停止后续教学推进，但保留这个未决操作。题库支持按业务标识查询时，就查询并关联原试卷；支持幂等创建时，则可使用同一个键重试。即使查到了试卷，也只保存结果，不在暂停状态下突然发题。
>
> 恢复时先解决这笔未决操作，再决定发布已有试卷还是继续等待对账，不能直接重新组卷。如果题库既不支持幂等也不能查，我就不能保证严格一次创建，需要挂起处理或明确只能尽力去重。这也是持久化检查点和业务幂等必须分开设计的原因。

把这段口播还原成输入、处理和输出：

```text
1. 输入：T1 / A2 的组卷需求
   处理：保存唯一操作 K2 -> 携带 K2 调用题库
   外部：创建 P2，但响应丢失

2. 输入：超时事件
   处理：记录 K2 的结果未知，不创建 K3
   输出：保留未决操作，尚无可承诺的题组结果

3. 输入：学生暂停
   处理：提交 PAUSED，保留 K2
   输出：已保存暂停状态，不继续发布题目

4. 输入：通过查询或幂等重试得到 K2 对应的 P2
   处理：保存 K2 -> P2，重新检查任务状态和版本
   输出：任务仍为 PAUSED，只关联结果，不推进教学

5. 输入：学生继续，任务与题目仍有效
   处理：确认 K2 已解决 -> 使用 P2 -> 提交等待点
   输出：WAITING_USER + WAIT_ANSWER，发布原 P2
```

步骤 4 与暂停可能并发发生，不能只检查调用发出时的状态。提交教学推进时还要检查当前状态和版本；外部结果可以独立留档，但不能借回调复活暂停或终态任务。

**追问：“答案重复提交，或者写数据库只成功一半呢？”**

> 对答案提交，我会先保存唯一提交标识和内容摘要。同一个标识、相同内容重发，就返回已有状态或结果；同一个标识却换了答案，应拒绝冲突，修改答案需要显式版本规则。判分计算可以重试，但判分结果、任务推进和待发送事件需要在同一个本地事务里提交，避免成绩写了、阶段没变，或者任务结束了、更新事件丢了。
>
> 如果提交已保存但计算前进程崩溃，恢复处理应能找到未完成提交继续计算；如果结果已提交但响应丢失，客户端重试就读取已有结果。异步画像更新也按稳定事件标识去重。这里保证的是重复请求不重复产生业务结果，不是说底层模型永远只调用一次。

需要验证的输出不是“接口没有报错”，而是：同一业务操作没有重复试卷，同一提交没有重复记分，暂停状态未被回调推进，且任务结果与证据、待发送事件保持一致。这些应通过故障注入和并发测试检查，目前不宣称已通过测试。

## 9. 记忆回流：状态、事实、画像分开

| 层次 | 保存内容 | 谁是真实来源 |
|---|---|---|
| 执行状态 | 当前阶段、等待对象、试卷 ID、恢复点 | 任务状态存储 |
| L1 原始证据 | 答案、题目版本、提示使用、复述、判分记录 | 原始业务记录及引用 |
| L2 学习事实 | 某次任务中哪些知识点表现如何 | 可回溯到 L1 的结构化事实 |
| L3 聚合画像 | 近期待巩固项、讲解偏好和变化趋势 | 多次证据聚合，不是模型自由总结 |

本例 L2 可表述：“在本次两道相关练习中出现分配律应用错误。”L3 可以是“近期建议复习分配律”，而不是“数学能力差”。事实需记录时间、知识点、证据引用和提取规则版本。

新证据与旧结论冲突时，保留历史成绩，更新聚合判断的时效和依据。用户明确纠正偏好可以覆盖旧偏好；用户说“我已经会了”属于自述，不直接覆盖答题证据。

恢复执行读取任务状态；后续个性化读取学习事实和画像。成绩和阶段等结构化事实适合关系存储，语义检索可以用于找相关历史片段。向量相似度不能充当掌握程度或事实可信度。

权限按用户隔离；删除学习记录时，派生画像和检索索引也要有对应清理机制。不要无限保存原始学生内容。

# 第三部分：面试口径、指标与追问

## 10. 指标口径：先有定义，再谈数字

以下是待执行的评估方案，没有实测结果。简历既有的 71% 完成率、37% Token 降低及其他数字不能自动迁移到此业务。

| 指标 | 分子/分母或定义 | 采集与排除口径 |
|---|---|---|
| 辅导启动率 | 已确认目标并创建任务数 / 去重后的有效入口曝光数 | 明确按用户还是曝光计数，内部测试与重复事件排除 |
| 验证流程完成率 | 有有效练习和理解验证、且已正常收尾的任务数 / 同批启动任务数 | 以固定观察窗口统计；未到窗口的队列单列；暂停、取消、失败不能偷偷删除 |
| 本次目标达成率 | GOAL_MET 任务数 / 同批启动任务数 | 同时报达标数/有效完成任务数，避免只看完成者的幸存偏差 |
| 首次独立正确率 | 未获提示的首次有效作答正确数 / 对应有效首次作答数 | 同题重做、答案曝光、无效试题单列，不混入独立作答 |
| 辅导前后表现变化 | 配对学生在难度与知识点匹配但不同题组上的正确率差 | 记录样本量、流失、题目匹配；无对照不能声称因果提升 |
| 恢复成功率 | 故障注入后恢复到预期阶段且无重复副作用的用例数 / 有效恢复用例数 | 分断线、重启、并发、晚到回包报告；保存预期状态断言 |
| 重复副作用率 | 产生重复试卷/重复记分的业务操作数 / 去重后的逻辑业务操作数 | 同一幂等键下多次传输只算一个逻辑操作 |
| 单任务模型成本 | 完成任务关联调用的实际计费用量或金额 | 失败调用、重试也计入；同时报告所有启动任务总成本/完成数 |
| 系统处理耗时 | 服务端处理区间总和及端到端墙钟时间 | 单列等待学生时间，报告 P50/P95，不用十分钟思考时间解释模型延迟 |
| 学习事实可追溯率 | 能解析到有效原始证据的事实数 / 被审计事实数 | 区分“有引用”与“引用确实支持结论”，后者需内容审核 |

### 10.1 评测怎样避免“看起来提升”

- 业务基线：一次性讲解或现有问答流程，而不是人为做弱的对照。
- 教学条件：尽量控制题目难度、学习时长、模型版本与教材来源。
- 工程条件：用同一组故障注入用例比较恢复行为，不比较主观流畅感。
- 成本比较：保证任务质量标准相近，不能靠跳过理解验证换取 Token 降低。
- 所有百分比都保留分子、分母、窗口、版本和排除规则；小样本不泛化为全体用户表现。
- 没有上线实验时说“我设计了这些验收口径”，不要说“提升了多少”。

## 11. 面试表达模板

### 11.1 30 秒业务版：当前仅设计时使用

> 我围绕现有的教材检索、题库和 Agent 工具执行能力，设计了一个错题驱动的知识点辅导方案。它不是讲完答案就结束，而是先验证错因，再针对性讲解，通过新的练习和概念解释检查本次目标。工程重点是跨多轮状态、暂停恢复、有界补救和可追溯学习记录，目前这部分应按设计方案介绍。

### 11.2 两分钟技术版：按实际完成范围替换动词

> 这个场景最重要的约束是学生不一定连续完成任务，模型也不能自由跳过验证。因此我把设计分为两层：外层显式控制诊断、讲解、答题和评估阶段，内层用 Agent Loop 做检索和内容组织。
>
> 学生做题时保存试卷和等待点，提交通过任务 ID 和题组版本恢复，不靠聊天摘要猜进度。恢复可能导致重复调用，所以组卷和判分需要业务幂等；外部调用超时时还要区分失败和结果未知。
>
> 学习效果方面，我区分首次独立作答、提示后答对和概念解释。未达标只做有界补救，证据不足则明确保留不确定结论。最后把原始答题证据、学习事实和聚合画像分开，下一次用历史证据选诊断题，而不是永久贴薄弱标签。
>
> 如果采用 LangGraph，它负责流程编排，但业务状态、授权和幂等仍需要应用侧设计。评估会同时看教学验证、恢复可靠性和成本，目前没有实测的部分不报收益数字。

### 11.3 实现后可考虑的简历句式

> 构建知识点辅导工作流，编排教材检索、针对性讲解、题库练习和理解验证；通过持久化任务状态、业务幂等及有界补救支撑多轮交互，并将学习证据回流至跨会话个性化服务。

只有实际完成相应部分才能使用“构建”“支撑”等完成性表述。未做动态规划就不写 Planner；未采用 LangGraph 就不把它列为本项目技术栈。

## 12. 高频追问备忘

### Q1：为什么不用一个大 Prompt？

Prompt 能表达建议流程，但不能替代事务、状态持久化和业务规则。学生尚未提交、工具结果未知、进程重启等问题需要应用层控制。

### Q2：这到底是 Agent 还是工作流？

外层是受控工作流，阶段内有模型决策和工具调用。没有必要把全部业务控制权交给模型，混合设计是为了把灵活性放在可控范围内。

### Q3：Planner 的输出是什么？

是经过校验的有限步骤、目标和练习策略，而不是一段自由文本。完成条件由既定规则控制。若计划固定，就直接承认没有动态 Planner。

### Q4：为什么不是 DAG？

存在评估后返回讲解的补救边，因此整个执行图可以有环。强调显式状态和有界循环，不为使用 DAG 一词强行消除业务回路。

### Q5：暂停和补救分别是什么？

暂停改变任务生命周期，保留当前教学阶段；补救改变教学路径，仍然可能运行或等待学生。补救中暂停后恢复同一轮，不额外扣一次补救预算。

### Q6：跨 Session 怎么继续？

先鉴权，再按用户所属 task_id 查询权威状态和等待对象。会话消息用于展示，任务状态用于执行，长期画像用于个性化，三者不互相替代。

### Q7：用了 checkpoint 就不会重复组卷了吗？

不会。恢复可能重新执行尚未提交完成的操作，必须依靠稳定业务键、外部幂等或对账。持久化执行进度不等于外部副作用恰好一次。

### Q8：两次答对就真的掌握了吗？

只能说明满足本次验证规则，不能代表长期掌握。要证明保持和迁移还需要后续复测与有效评测设计。

### Q9：学生一直答错怎么办？

在预算内做针对性补救；用完后总结具体薄弱点并结束为待巩固。超范围前置知识另开任务，不无限递归。

### Q10：记忆错了怎么办？

区分原始事实、提炼结论和画像。事实保留证据，派生结论可以修正和失效；新证据更新当前判断，但不篡改历史成绩。

### Q11：题库和 RAG 有什么区别？

RAG 提供讲解依据，题库提供可追溯的练习与评分信息。检索到相似文本不等于得到合格试题，不能随意互相替代。

### Q12：用户只想要答案，为什么逼他复述？

不强迫。允许获得答案或退出，但改变评估口径：辅助后正确不能算独立掌握，拒绝验证时保留证据不足。

### Q13：你实际做了什么，哪些只是设计？

按 0.1 节逐项回答，展示已有接口、原型测试或上线证据。技术设计能讲完整，不需要虚构所有能力都已上线。

| 同知识点跨教材且资源兼容 | 保留原目标与规则，标记真实来源，不冒充学生教材 |
| 确认预习或完整补基础 | 原任务进度保留，新任务目标与证据独立，重复确认不重复建任务 |
| 检索为空但未确认跨范围 | 不直接判定超纲，不自动取消教材过滤 |
| 仅提供通用答疑 | 不将原任务判为 GOAL_MET，相关答案曝光计入提示记录 |
| 本次临时换教材 | 不自动覆盖长期资料，旧任务评价口径不变 |
| 画像更新失败 | 已保存任务结果不丢失，事件可幂等重试 |
