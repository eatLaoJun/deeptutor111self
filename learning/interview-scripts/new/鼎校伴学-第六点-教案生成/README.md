## 1. 定位与当前状态

本次将原 KingSchool 教练端的专题研究与教案生成材料归入鼎校伴学，作为同一项目下与学生辅导并列的业务能力，不再单独增加 Agent Harness 简历项目。主线改为：教练提出备课需求，主 Agent 生成计划并委派子任务，汇总证据后生成供教练审阅的教案。

鼎校伴学已有的知识点学习闭环、双层编排、三层记忆、RAG 与教练端业务，按用户确认的已实现项目讲述。第六点在此基础上补充规划与子 Agent 扩展；本轮新增“学情与学习习惯分析”角色，复用已有的课程项目查询 Tool。下文接口字段、任务标识和案例记录用于解释方案，不新增用户未提供的效果指标。

学生端“错因诊断—针对性讲解—练习—复述与理解验证”Workflow 保持不变。教练端补足规划式任务、子 Agent 委派和人工审阅的任务形态，不把复杂备课流程塞进每次学生问答，也不重复建设另一套 Runtime。

本轮进一步明确：Plan-and-Execute 是执行策略，子 Agent 委派是任务组织方式，两者均不绑定 LangGraph。简历重点写业务拆分、独立上下文、受限工具与证据汇总，不为了增加框架关键词改变已有架构。

## 3. 为什么不是简单地写“CoT + Workflow”

更准确的技术主线是：Plan-and-Execute + 反馈修订 + 有状态编排。

- 推理：模型分析需求、识别信息缺口。
- 规划：输出系统能读取的结构化子任务，而不只是自然语言说明。
- 编排：程序安排节点执行、等待用户、合并结果和控制终止。
- 反馈：根据证据与任务完成情况决定补查、修订或结束。

结构化计划不是模型内部思维链，也不依赖特定编排框架。面试时优先讲可观察的任务计划、工具调用、证据和状态变化，不以展示思维链代替效果验证。

## 4. 业务场景：教练端专题备课与教案生成

示例需求：

> 为人教版八年级“一次函数”准备一份专题教学方案，包含先修知识、常见误区、分层例题与课堂练习，并标注教材依据。

业务交付物：教学目标、先修知识、教学重难点、讲解提纲、例题与练习、来源引用，以及资料不足或需要教师复核的提示。

个性化备课时还可以指定学生与当前授课老师。例如，为之前跟同一老师上过背单词课的学生准备下一节英语课：先查历史课程、已学词表、复习表现与有效学习偏好，再决定本节复习重点、新内容范围和课堂安排。通用专题备课不需要查询具体学生的历史。

与已有辅导业务的区别：

| 维度 | 学生辅导 | 教研专题研究 |
| --- | --- | --- |
| 对象 | 学生 | 教练、教师或教研人员 |
| 任务范围 | 一道题或一个知识点 | 一个专题的完整材料 |
| 流程特征 | 教学阶段相对固定 | 研究子任务随需求生成 |
| 交互重点 | 学生作答、理解验证 | 教练确认计划、审阅与修改材料 |
| 输出 | 讲解与反馈 | 带证据的结构化备课材料 |

## 5. 备课任务链路

```text
需求澄清：教材版本、年级、专题、课时与输出要求；个性化备课时指定学生与授课老师
    ↓
主 Agent 生成结构化备课计划，程序校验范围、依赖与预算
    ↓
教练确认或修改 ── 修改 → 修订计划
    ↓ 确认
执行层按依赖派发受限子 Agent
    ├─ 学情与学习习惯分析 Agent（按需，查询同一老师的历史课程）
    ├─ 教材与教学目标 Agent
    ├─ 先修知识与误区 Agent
    └─ 例题与课堂练习 Agent
    ↓
主 Agent 汇总结果，检查覆盖、一致性与来源支撑
    ├─ 存在缺口且未超预算 → 定向补查
    └─ 充分或预算耗尽 → 生成材料，明确剩余缺口
    ↓
教练审阅 → 保存或导出，不自动发布
```

这张图用于讲解委派链路，不是源码执行图。任务有前置依赖时顺序执行，确认独立后才考虑受控并行；有多个角色不等于每次全部调用，也不等于全部并行。个性化例题或课堂安排依赖历史学情时，先获得学情子任务结果再执行这些任务。

可复用的业务资产包括教材 RAG、知识点树、题库接口和已有的课程项目查询 Tool；个性化备课按当前老师与学生的授权范围读取历史。外部搜索只用于允许的资源，并与内部教材证据区分来源。

### 5.1 Plan：输出可执行的任务计划

以“两课时一次函数教案”为例，计划可以包含以下子任务。任务标识与字段为设计示例，不是已有接口。

| 子任务 | 目标与产物 | 依赖示例 |
| --- | --- | --- |
| C0：学情与学习习惯分析（按需） | 整理同一老师的历史授课、已学内容、练习表现与有依据的学习偏好，给出备课建议与缺口 | 已确认的学生、老师、课程类型及授权查询范围 |
| C1：教材与教学目标 | 确认教学范围，整理概念、图像性质及教材依据 | 已确认教材版本与专题 |
| C2：先修知识与误区 | 整理相关前置关系、典型误区及来源；具体学生的薄弱点须有学情证据支持 | 已明确的教学范围；若依赖 C1 或 C0 的结果，则等待对应任务 |
| C3：例题与课堂练习 | 从题库整理符合范围与梯度的候选题，保留题目及答案来源 | 经确认的教学目标与误区重点；个性化练习还依赖 C0 的相关结果 |

计划还需明确课时安排、任务范围、允许的资料、预期产物和验收条件。模型提出计划，程序核对依赖、任务数量与授权范围，教练确认教学安排。主 Agent 可以承担 Planner 角色，不必再增加一个独立 Planner Agent。

动态的是本次要研究哪些内容，以及哪些任务需要补查；权限、预算和允许的执行路径不能由模型任意扩大。

### 5.2 Execute：怎样委派子 Agent

本方案进一步明确为“预定义角色 + 动态子任务 + 按任务创建独立子运行”。这是材料中的默认设计，不是已经核验的实现事实。

**提前定义的是角色配置，不是常驻的多个 Agent 进程。** 每个角色声明角色 Prompt 模板、可用工具白名单、输出契约和预算边界。例如：

| 角色标识示例 | 预置角色职责 | 工具范围示例 |
| --- | --- | --- |
| learner_history | 回顾当前学生与同一老师的历史课程，区分已学事实、明确偏好与待验证判断，输出备课建议 | 已有课程项目查询 Tool、已授权的课程详情或学习记录查询、只读学习记忆查询 |
| textbook_evidence | 围绕已确认教材整理教学目标，要求引用来源 | 教材检索、原文读取 |
| prerequisites_and_misconceptions | 整理先修关系与典型误区，区分依据和推断 | 教材检索、已授权的知识点关系查询 |
| examples_and_exercises | 按教学范围整理例题与练习，核对题目来源 | 题库查询、题目详情读取 |

标识和工具名称仅用于解释设计，可用接口仍以实际业务能力为准。角色可以只是配置，复用同一套 Agent Loop，不必为每个角色开发一套执行引擎。

**主 Agent 动态决定的是选哪个角色、完成什么子目标、交付什么材料，以及任务依赖。** 它可以编写本次子任务指令，但默认不临时改写角色的系统 Prompt、发明新工具或扩大权限。角色指令与工具定义由预置配置和 Tool Registry 提供。

执行过程可以讲成：

```text
主 Agent：选择 role_id，提出子目标、输入引用和依赖
    → 执行层：核对角色目录、任务范围、权限与预算
    → Runtime：装配预置角色 Prompt + 本次任务指令 + 必要证据
    → 为本次子任务创建独立上下文，挂载允许的工具
    → Agent Loop 执行并返回结构化结果
```

实际工具集合不能超过“角色工具白名单、当前任务授权、用户数据权限”的共同允许范围。主 Agent 即使提出额外工具，也必须由执行层校验；模型生成的文本不产生新权限。

委派不是复制完整主对话，也不是只给工具换个名字。每个子 Agent 获得：

- 主任务标识、子任务标识与计划版本。
- 单一子目标、教材与课时约束、已有相关证据。
- 从预定义角色装配的 Prompt、经执行层校验的工具与数据范围。
- 执行预算、输出格式和结束条件。

子 Agent 可以复用相同模型与 Agent Loop，但维护独立消息列表和调用轨迹。比如教材 Agent 可以改写查询、比较片段并补查缺口；例题 Agent 可以查询候选题、排除不匹配题目并核对题目版本。若只需一次固定查询，用普通工具即可，不强行创建子 Agent。

学情 Agent 可以先查询同一老师的相关课程，再下钻背词等项目的学习记录，并与有效学习偏好核对；它自己决定缺哪类证据、是否需要有限补查，主 Agent 只回收与本次备课有关的摘要，不接收全部历史流水。

子 Agent 返回的是“结论或材料片段 + 来源引用 + 信息缺口 + 执行状态”，不是自行生成并发布最终教案。它不能修改主计划、提高预算、更新学生画像或对教练宣布主任务完成。

### 5.3 主 Agent 如何回收与整合

执行层校验结果格式、任务关联和计划版本；主 Agent 整合材料并提出覆盖缺口，程序检查引用是否存在、版本是否匹配以及必要项是否齐全。教学内容是否正确，还需要语义评价与教练复核，结构合法不等于教案合格。

有缺口时只委派需要补充的任务，不重新运行整份计划。某个子任务失败时，保留其他有效结果；达到预算上限则输出部分教案并标明缺口，不能把未查到的结论伪装成教材内容。

### 5.4 教练反馈如何影响执行

例如教练把“加入拓展应用”改为“只覆盖基础图像与解析式”。主 Agent 据此修订计划，程序核对新的范围；涉及教学目标或课时等关键变化时重新确认。

仍符合新约束的教材证据可以复用，超范围的例题任务需要作废或重做。旧版本晚到的结果可以保留为历史记录，但不能直接并入当前教案。任务状态由外部编排维护，子 Agent 只返回阶段结果。

若更换学生、授课老师或历史查询范围，原学情摘要也要重新校验，不能只因教学专题相同就继续复用；仍适用的教材材料可以保留，依赖学情的课堂安排与练习则按影响范围更新。

### 5.5 一次委派的输入与输出

下面是契约示例，字段、工具名、标识与数字均用于解释设计，不代表现有接口或生产配置。

**交给教材子 Agent 的输入：**

```json
{
  "task_id": "P1",
  "subtask_id": "C1",
  "plan_version": 1,
  "role_id": "textbook_evidence",
  "goal": "整理一次函数的教学目标与教材依据",
  "constraints": {
    "textbook_version": "已确认版本",
    "topic": "一次函数",
    "lesson_count": 2
  },
  "allowed_tools": ["textbook_search", "read_source"],
  "limits": {"max_steps": 4}
}
```

上面展示的是服务端装配后的执行输入。主 Agent 可以选择候选 `role_id`、提出子目标与检索建议；任务标识、角色是否可用、可信资料范围、工具权限和预算由服务端分配或校验，不能直接相信模型生成的权限字段。实际执行还要携带本次执行尝试的关联记录，便于区分重试结果。

**回收的阶段结果：**

```json
{
  "task_id": "P1",
  "subtask_id": "C1",
  "plan_version": 1,
  "status": "partial",
  "summary": "已整理概念与图像性质，增减性的教材依据仍有缺口",
  "evidence_refs": ["E1", "E2"],
  "gaps": ["尚缺当前教材版本对增减性的解释片段"]
}
```

`E1`、`E2` 只是示例，实际引用必须能解析到真实工具返回的来源。执行层核对关联与执行状态，主 Agent 根据材料和缺口决定补查或生成标明不足的草稿；模型自报完成，不等于子任务通过验收，更不等于整份教案合格。

### 5.6 共享业务事实，不共享可变对话

各子 Agent 可以使用同一模型和同一套 Runtime，但每次子运行维护独立消息列表与调用轨迹。它们共享的是主任务约束和受控证据引用，不是任意互相修改的聊天数组。

派发时按当前计划装配上下文快照，回收时再核对计划版本。不要把同一个带可变会话状态的 Agent 实例交给多个并发子任务，否则不同任务的工具反馈与消息可能混入同一上下文。

### 5.7 学情与学习习惯分析：同一老师的历史课怎么用于备课

这是本轮新增的子 Agent 扩展。用户已经具备查询对应课程项目的 Tool，新增角色复用这一业务能力，负责把历史记录整理成“这节课应该参考什么”，而不是重新建设课程系统或替代已有的三层记忆。

**委派目标：** 回顾当前学生与当前老师的相关历史课程，整理已学内容、近期薄弱点及有记录支撑的学习偏好，为主 Agent 提供复习重点、教学节奏和练习安排建议。

**输入与工具边界：**

- 输入包含当前学生、授课老师、本次课程类型与主题、历史查询范围，以及任务与计划版本。学生和老师的关联由服务端核对，不让模型随意填写身份扩大查询范围。
- 优先使用已有课程项目查询 Tool，按当前学生与同一老师筛选相关课程；需要细节时，再调用白名单内的项目详情或学习记录工具。
- 若相应记录提供已学词表、作答、复习或作业反馈，则结合这些字段分析；未返回的字段不能假设存在，工具查不到也不等于学生没学过。
- 需要核对学习偏好时，只读当前学生的有效记忆，保留时间、来源与适用范围。子 Agent 不直接改写长期画像，也不读取其他学生或无授权老师的记录。

**返回契约：** 继续使用第 5.5 节的任务标识、计划版本、执行状态、来源引用与缺口字段，材料内容进一步区分：

| 内容 | 应该如何表达 |
| --- | --- |
| 已学事实 | 上过哪些相关课程、覆盖哪些内容、记录到什么练习结果，保留课程或学习记录引用 |
| 明确偏好 | 学生明确表达或有效画像中已有的偏好，说明适用课程及时间，不把单次要求当成永久偏好 |
| 近期观察 | 反复出现的错误或复习表现，与长期习惯分开；没有足够记录时标为待验证判断 |
| 教学建议 | 建议先复习什么、怎样组织讲解与练习，关联支持依据；建议不是已经验证的效果结论 |
| 信息缺口 | 没有相关历史、记录过旧、缺少复习反馈或存在矛盾，供主 Agent 决定澄清或采用通用教案 |

**一条窄链路示例：**

> 当前老师要为学生准备“单词复习 + 新词学习”课程。以下内容是假设工具返回的讲解示例，不代表真实学生记录。

1. 主 Agent 委派 `learner_history`：查询这个学生之前跟当前老师上过的英语课，重点看背词课程。
2. 子 Agent 先查课程项目，定位相关历史课，再按需读取已学词表和复习反馈。若记录表明部分词在后续练习中再次答错，只归纳这些词需要复查，不概括为“学生记忆力差”。
3. 若有效记忆中有学生明确提出“希望通过例句记词”，将它作为英语词汇课的表达偏好；没有记录就不补造这一偏好。
4. 子 Agent 返回已学内容、需要复查的词、可用偏好、来源与缺口。例如缺少课后复习记录时，不能推断学生“不爱复习”。
5. 主 Agent 据此安排先复习相关错词，再组织新词的例句练习，并由教练审阅；只有依赖这些学情的任务需要等待，教材取证不必全部停下来。

历史结果用于细化已有计划；若导致教学目标或课时等关键变化，按第 5.4、6.3 节修订计划并重新确认。未指定学生的通用备课可以跳过该角色；背词表现不能直接证明学生的数学掌握情况，跨学科复用学习偏好也要检查适用范围。

若只是按固定参数查一条历史课程，直接调用 Tool 即可。子 Agent 的价值在于围绕独立子目标进行多步检索、关联记录、核对冲突和有限补查，而不是给查询工具换个名字。

**不是所有历史查询都升级为子 Agent：**

| 实际任务 | 优先方案 | 判断理由 |
| --- | --- | --- |
| 固定参数查一条课程或一份背词记录 | 直接调用 Tool | 输入输出明确，不需要独立分析循环 |
| 固定顺序查询多份记录并按规则汇总 | 固定流程或工具组合 | 工具数量多不代表需要模型自主决策 |
| 根据结果动态补查，但材料少、主任务简单 | 主 Agent 调用 Tools | 主 Agent 自己也能选择工具并循环，不必额外委派 |
| 可独立验收的学情分析，需要多轮取证且会产生较多中间材料 | 按需委派学情子 Agent | 子目标、证据上下文和结果契约可以独立，主 Agent 专注教案规划与整合 |

例如，课程列表只说明上过背词课，未说明具体词表与复习情况。学情 Agent 根据这个缺口决定下钻对应项目；若复习记录与已有偏好或旧学情结论不一致，再按时间和来源核对，必要时有限补查。证据充分则返回摘要，不充分则标明缺口。这是“观察结果后决定下一步”，而不是预设所有工具每次都执行一遍。

上下文隔离的目的，是不让完整历史记录、检索中间结果与失败轨迹挤占主 Agent 的备课上下文；只回传相关结论和可追溯证据。它不自动保证结论正确，也不自动降低总 Token、延迟或成本；委派本身增加模型调用和交接开销，因此简单场景仍优先用 Tool 或主 Agent 直接处理。

## 6. 编排与状态管理：复用 Runtime，不强制 LangGraph

默认设计是“外部任务编排 + 持久化任务记录 + 复用 Agent Runtime”，不新建独立 Harness，也不要求引入 LangGraph。

- 主 Agent 提出计划、整合证据与修订建议。
- 编排与执行层核对授权、依赖、确认版本和预算，派发子任务并提交状态。
- 子 Agent 复用 Agent Loop 完成限定目标，返回结果，不直接控制主任务终态。

任务编排可以采用轻量状态机和业务存储。已有 Runtime 负责模型与工具循环，不等于已经自动具备计划确认、持久化或恢复能力；这些仍需明确设计。以下字段是讲解契约，不是已核验的数据库表或接口。

### 6.1 状态设计

面试时按以下状态职责解释；字段名为讲解示意，不作为已核验的源码符号：

| 状态字段 | 用途 |
| --- | --- |
| request_constraints | 教材版本、年级、主题、课时等约束；个性化备课还包含经校验的学生、老师及历史查询范围 |
| plan / plan_version | 当前任务计划及版本 |
| teacher_feedback | 教练修改意见与确认结果 |
| task_results | 按子任务标识与计划版本保存研究结果 |
| evidence_refs | 来源标识、页码或链接等证据引用 |
| gaps | 尚未解决的信息缺口 |
| revision_count / limits | 补查次数及预算边界 |
| final_material | 最终材料与未解决问题 |

计划任务可包含 `task_id`、目标、依赖、检索范围、预期产物和验收条件。避免将所有原始文档无限追加到共享状态中。

### 6.2 条件路由

程序定义允许的状态和事件，模型生成的计划表达本次任务内容。动态任务规划不等于让模型任意跳转状态或调用任何工具。

重点分支：需求不完整则澄清；计划未确认则等待；证据不足且仍有预算则补查；任务完成或预算耗尽则输出结果。

### 6.3 人工确认与恢复

讲解“教练修改计划后继续执行”这一条路径时，应用需要关联同一个任务标识，保存计划与反馈，而不是一直挂着请求等待回复。人工确认绑定计划版本，不能用旧确认推进新计划。

保存当前阶段、待确认计划版本、子任务状态与已有结果，后续事件根据任务标识续接，而不是让模型从聊天摘要猜进度。若需要跨进程恢复，还需明确持久化与重新派发方式；能保存记录不等于已经验证重启恢复。

### 6.4 结果合并与计划变更

研究结果按任务标识归档。若采用并行分支，需要明确共享字段的合并规则，避免覆盖、重复追加与顺序不确定。

教练改计划后，判断哪些任务结果仍有效，哪些必须作废；通过计划版本避免将旧计划结果混入新教案。

### 6.5 副作用与执行边界

重试或恢复可能重放部分操作。保存、导出以及后续可能增加的发布动作，需要按业务操作标识处理幂等与去重；任务状态持久化不等于自动保证只执行一次。

设置最大补查轮次、超时及调用预算。证据不足时输出缺口，比反复检索或编造引用更合理。

### 6.6 LangGraph 只是可选实现

当前业务流程没有必须使用 LangGraph 的要求。若后续任务出现大量依赖分支、多次人工中断或复杂恢复需求，再评估现有编排维护成本与引入框架的收益。可选框架仍可以调用已有 Agent Loop，不必替换 Runtime。

这里只保留选型边界，不将 LangGraph、checkpoint 后端或框架 API 作为本条简历的必讲内容，也不因不用框架就省略状态、授权、幂等和预算设计。

### 6.7 并发、失败与结果回收

下表是本点需要掌握的设计边界，不表示这些场景已经完成实现或验证。

| 情况 | 处理原则 |
| --- | --- |
| 任务间存在依赖 | 只派发前置结果已满足的任务；例如例题整理依赖教学目标时，先拿到目标，不将全部任务无条件并发 |
| 子任务数量或调用不断增加 | 限制任务数、并发数、单个子任务轮次和父任务总预算；初版不允许子 Agent 再创建子 Agent |
| 一个子任务失败或超时 | 保留其他有效结果，按错误类型决定有限修正、重试或标记缺口；必需材料缺失时不能声称生成了完整可用教案 |
| 教练取消主任务 | 拒绝继续派发；晚到结果可记录，但不能推进任务或自动发布教案 |
| 计划修改或旧执行晚到 | 核对任务、子任务、计划版本与执行尝试，拒绝失效结果覆盖当前材料 |
| 重复回调或重复提交 | 核对已有受理记录；保存与导出另用业务操作标识控制幂等，不能仅凭执行状态保证只执行一次 |
| 子 Agent 结论冲突 | 回到相同教材版本、教学范围与原始证据核对；无法消除的冲突交教练复核，不用多数投票判定事实 |

初版先讲清有限任务与结果记录，不默认引入多 worker、租约或复杂调度基础设施。若只保存子任务级进度，恢复时可能需要重新执行未完成的取证任务；不能把任务级恢复说成模型循环内每一步都可续跑。

## 7. 实际经历与验证记录准备

本节用于区分已有经历、设计细节与尚未提供的验证记录，不要求读取源码、运行测试或补做实现。

1. 明确个人负责的是规划、委派、检索、证据检查还是编排，不把项目整体都写成个人贡献。
2. 准备一份真实的备课需求、任务计划与最终教案；没有真实产物时，示例必须注明设计性质。
3. 说明子 Agent 是否维护独立上下文、是否多轮决策；若只是固定工具调用，不称为已实现子 Agent。
4. 若已有记录，展示教练修改计划前后的任务与产物变化。
5. 串行、并行、持久化、重启恢复分别说明完成和验证范围，不打包承诺。

口述只需先讲清一条窄链路：需求 → 计划 → 教练确认 → 子任务执行 → 汇总补查 → 教案审阅。

待整理的验证记录：

- [ ] 真实备课主题、计划与教案产物的对应关系。
- [ ] 子 Agent 的输入、工具轨迹、结构化返回及主 Agent 汇总结果。
- [ ] 教练修改计划后，新计划真正影响后续执行。
- [ ] 检索不到材料时，流程有限终止并标出缺口。
- [ ] 使用持久化配置后，重启进程可以恢复同一任务。
- [ ] 结果引用能回到真实材料，教材版本不会混用。
- [ ] 若增加并行任务，结果不遗漏、不重复、不跨计划混合。

以上勾选状态表示本文尚未收录记录。旧材料确认的业务实现状态与本次新增委派设计应分别说明，不据勾选状态推断整个业务已经或尚未实现。

## 8. 面试讲解重点

### 为什么不是一次 Prompt 直接生成？

备课材料同时涉及范围约束、多源检索、教师反馈与证据校验。一次生成难以显式控制各项任务是否完成，也不便于定向补查和局部修订。

### 为什么不用 LangGraph？不使用框架怎么管理任务？

Plan-and-Execute 与子 Agent 委派不绑定框架。在这份设计里，复用已有 Runtime 处理模型与工具循环，用外部任务编排管理计划、依赖和确认，持久化任务状态与子任务结果，避免为有限的业务流程再引入一套框架。

不使用 LangGraph 并不意味着只写几个函数顺序调用就结束：等待教练、版本冲突、超时、取消和重复提交仍要有明确规则。是否引入框架取决于编排复杂度，而不是简历是否需要关键词。

### 和现有教学 Workflow 有什么不同？

学生辅导围绕固定教学阶段推进；教研任务先生成研究计划，再按计划组织资料收集和产物生成。外层仍有固定规则，任务内容可以动态变化。

### 为什么需要子 Agent，而不是多调用几个工具？

先承认边界：如果只是根据学生和老师查询一次课程，Tool 更合适；即使需要调用多个工具，也不必然需要子 Agent。主 Agent 本身就可以多工具选择和循环，不能把这些能力当成必须委派的理由。

这里把“围绕本次备课回顾学情并提出有依据的建议”作为可独立验收的子目标。当它需要多轮取证、比较历史与近期记录、检查缺口，并产生较多中间材料时，才有委派价值：独立上下文承载取证过程，角色 Prompt 约束分析任务，受限工具与预算控制执行，结构化结果让主 Agent 专注教学规划与整合。

面试中可以从三个特性展开，但每个特性都要对应业务问题：

- **上下文隔离：** 历史课程与背词记录留在子任务上下文，主 Agent 只接收与教案有关的摘要、引用和缺口，避免取证流水干扰规划。隔离不是自动的正确性或权限保证，授权仍由执行层和 Tool 校验。
- **按反馈选择工具：** 先看相关课程，再判断是否需要查词表、复习记录或有效偏好。关键是调用路径随证据变化，不是注册了更多工具。
- **受限自主 Loop：** 子 Agent 在自己的目标下判断是否补查、核对冲突或结束；轮次和总预算受控。关键是有独立判断与交付，不是固定脚本外面加一个 while 循环。

**可直接口述：**

> 如果只是查一次历史课程，我会直接用 Tool，不会为了多 Agent 而增加一层。学情子 Agent 的职责不是取数，而是围绕这次备课，把同一老师的历史课程、背词表现和有效偏好整理成有依据的建议。它根据工具返回决定是否下钻项目、核对近期记录或补查，证据充分就结束，不足就返回缺口。主 Agent 也能做这些事；当这条分析链路较独立、材料较多时，我才把它拆出来，用独立上下文和受限 Loop 承载过程，主 Agent 负责教案规划与整合。简单场景仍直接调用 Tool，因为委派也会增加延迟、调用成本和结果交接成本。

上面的复杂链路应对应实际子任务行为。如果实际只是一次固定查询，按 Tool 能力讲更准确；如果固定多步就能完成，用固定流程也成立，不靠上下文隔离、工具数量或 Agent 名称证明业务必要性。

### 不同 Prompt 就等于子 Agent 委派吗？

不一定。这里的子 Agent 接收独立子目标，在自己的上下文、工具与预算边界内执行，再按结果契约回到主任务。若只是主 Agent 在连续几次调用中更换 Prompt，没有独立子任务执行与结果交接，称为分阶段处理更准确。

### 是主 Agent 临时写 Prompt 和工具，还是提前定义子 Agent？

本方案选用预定义角色：提前准备角色 Prompt、工具白名单和输出契约；主 Agent 只按计划选择角色并编写本次子任务指令，执行层校验后创建独立运行实例。固定的是角色边界，动态的是任务内容和调用次数。

也可以设计动态生成角色指令的方案，但工具仍必须来自已注册、已授权的能力。对于范围明确的教练备课任务，先采用预定义角色更便于控制职责、比较输出和排查问题，不需要为了委派而允许主 Agent 任意创建新角色。

### 每次都固定调用这些角色，为什么还需要规划？

角色目录不等于每次固定的任务清单。通用专题备课不需要学情 Agent；指定学生且需要沿用同一老师的授课进度时，才增加历史学情任务。教练只要基础概念提纲时，可以减少例题任务；要求分层练习时，才增加对应取证与整理。若所有需求都生成相同任务与顺序，固定流程或单 Agent 可能更简单。

### 学情子 Agent 和查历史工具、三层记忆有什么区别？

课程查询 Tool 返回具体记录，三层记忆保存和召回已有学习事实与偏好；学情子 Agent 围绕本次备课目标选择、关联这些证据，核对缺口并输出教学建议。三者分别承担取数、存储召回和任务分析，不重复维护另一份长期画像。

这个角色默认只读，不能凭一次答错给学生贴长期标签。查不到记录时返回缺口，主 Agent 可以请教练补充情况，或保留通用教案并标明未完成个性化，不把“未知”当成“没有”。

### 子任务是否都要并行？

不需要。并行是调度优化，不是多 Agent 的定义。先检查依赖，再在额度内派发就绪任务；没有并行也可以体现主 Agent 委派、独立执行和结果汇总。

### 如何判断报告合格？

至少检查需求覆盖、教材版本一致、引用可追溯、关键结论有证据支撑以及例题答案正确。模型评分可以辅助，但不能替代确定性检查与教师抽检。

### 怎么证明多 Agent 比单 Agent 更合适？

可以设计“单次生成、单 Agent 多工具、多 Agent 委派”三种对照，比较同一备课要求下的证据覆盖、错误与缺口、教练修改量、耗时和调用成本。没有对照记录就不声称提升了效率或质量，只解释为什么选择该设计以及它增加的交接与调度成本。

- **规划与确认：** 面向教练专题备课需求设计 Plan-and-Execute，将教材版本、教学目标与课时要求转为包含子任务、依赖和验收条件的结构化计划，经程序校验与教练确认后执行。
- **受限委派：** 预定义学情与习惯分析、教材取证、误区分析及例题整理等子 Agent 角色、Prompt 和工具白名单；主 Agent 按计划下发子目标，经执行层校验后复用 Runtime 在独立上下文中执行，回收带来源与信息缺口的结构化结果。
- **汇总与收敛：** 主 Agent 按任务与计划版本整合结果，结合历史学情调整教学节奏与练习，检查需求覆盖和引用依据，在预算内定向补查，生成供教练审阅的教案；计划修改后复用有效结果或重做受影响任务，避免新旧材料混用。

#### 版面紧张时用这一条

> **规划式教案生成与子 Agent 委派：** 复用现有 Agent Runtime，设计 Plan-and-Execute 备课流程；主 Agent 生成经教练确认的计划，按需委派预定义角色，在独立上下文与工具白名单约束下完成学情分析、教材取证、误区分析及例题整理，汇总证据并有限补查，生成供教练审阅的教案。

以上先采用设计口径。明确实现和个人职责后，只调整有依据的部分；业务实现不等于个人独立完成全部模块，性能、质量提升、部署规模与用户规模不补未经验证的数字。

### 面试口述

> 鼎校伴学里，学生端主要解决错题辅导与理解验证；我把教练端教案生成作为另一项业务能力来设计。备课需要同时满足教材版本、教学目标和课时要求，所以采用 Plan-and-Execute，而不是一次 Prompt 直接生成整份教案。
>
> 主 Agent 先提出结构化计划，由程序检查范围和依赖，教练确认后，选择预定义的教材取证、误区分析和例题整理角色，下发本次子目标。执行层核对权限，再用预置角色 Prompt、任务指令与必要证据装配独立子运行；子 Agent 复用同一套执行循环，返回带来源与缺口的结果，而不是由主 Agent 临时发明角色和工具。
>
> 针对具体学生的备课，我进一步补充了学情与学习习惯分析角色，复用已有的课程项目查询工具，回顾该学生之前跟同一老师上课的情况。例如背词课会看已学内容和复习反馈，再结合有依据的学习偏好，给出本节课的复习重点与练习建议。子 Agent 返回的是带来源的学情摘要，不是把所有历史记录直接塞进主对话。
>
> 主 Agent 汇总证据，缺什么就有限补查什么，最后生成供教练审阅的教案。外部编排维护计划版本、任务状态和预算，子 Agent 不能自行修改主计划或发布材料。这个方案复用现有 Runtime，不要求使用 LangGraph；重点是动态任务规划与委派，而不是把学生端固定教学流程再讲一遍。

口述结构：业务需求 → 为什么拆分任务 → 状态与路由设计 → 教练反馈如何影响执行 → 检索不足如何终止 → 实际验证结果与局限。

## 10. 学习与面试准备顺序

先用第 4、5 节解释业务需求与一次委派过程，再用第 6 节画出计划确认、子任务执行、补查与审阅的状态流转。最后准备第 7 节中的实际职责和产物记录。

完成这一点的学习，不以“读完”为标准，而是能只靠本文做到：

1. 用一分钟说明教练备课的需求、交付物，以及为什么不能只靠一次生成。
2. 画出主 Agent、受限子 Agent、执行层与教练确认之间的关系。
3. 解释一次委派传入什么、返回什么，以及共享事实与隔离上下文的区别。
4. 讲清一个超时、计划修改或证据不足的例子，说明如何有限收敛。
5. 区分设计方案、实际个人职责与已经提供的验证记录。
6. 用同一老师的背词课案例，解释学情 Agent 如何取数、返回依据与建议，以及为什么不直接改写长期画像。

无需为了本点再去其他目录阅读 Planner、旧 Harness 或 LangGraph 材料。只有准备整个项目、其他简历条目或主动深入备选方案时，才使用第 2 节的可选链接。

口述重点是“为什么拆、交付什么、怎么汇总、失败怎么办”，不以框架名或 Agent 数量作为亮点。本次只维护学习材料，不读取实现代码，不安装依赖，也不运行服务或测试。
