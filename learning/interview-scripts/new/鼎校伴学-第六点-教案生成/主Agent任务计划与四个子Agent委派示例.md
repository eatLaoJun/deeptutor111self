# 主 Agent 任务计划与四个子 Agent 委派示例

更新日期：2026-10-17

> 本文集中展示“主 Agent 输出计划 → 执行层装配委派输入 → 四个子 Agent 按依赖执行 → 主 Agent 汇总”的完整案例。字段、身份、工具名和数字均为讲解示例。
> 项目背景、角色边界与面试口述见 [第六点学习总览](README.md)。

## 1. 主 Agent 生成的任务是什么形式

主 Agent 输出的是一份**结构化任务计划**，不是仅写一段“请四个 Agent 帮我备课”的话。可以用 JSON 表达，也可以通过模型的结构化输出或提交计划工具的参数返回；关键是程序能够解析和校验。

可以理解为：**一个主目标 + 多个子任务 + 子任务依赖 + 交付要求**。每个子任务内部的 `instruction` 是自然语言，但角色、依赖和预期产物有明确字段。

下面用“同一老师的英语词汇课”串起四个角色。示例需求是：为当前学生准备一节 45 分钟的“单词复习 + 新词学习”课程，教材版本和目标词表已经确认，并参考此前跟当前老师上课的情况。45 分钟、字段名与标识均为讲解示例；学生和老师身份来自服务端已校验的上下文，不由模型任意指定。

## 2. 主 Agent 生成的完整计划

```json
{
  "goal": "为当前学生生成供当前老师审阅的英语词汇课教案",
  "constraints": {
    "topic": "单词复习与新词学习",
    "lesson_minutes": 45,
    "textbook_scope": "已确认教材版本与目标词表"
  },
  "tasks": [
    {
      "id": "C0",
      "role_id": "learner_history",
      "instruction": "回顾当前学生与当前老师的相关历史课程，整理已学词汇、近期复习表现和有依据的学习偏好，给出本节复习建议，标明来源与信息缺口。",
      "depends_on": [],
      "expected_output": ["已学内容", "近期薄弱点", "有效学习偏好", "复习建议", "来源与缺口"]
    },
    {
      "id": "C1",
      "role_id": "textbook_evidence",
      "instruction": "依据已确认教材版本与目标词表，整理本节新词范围、教学目标和教材依据，不自行扩大教学范围。",
      "depends_on": [],
      "expected_output": ["目标词表", "教学目标", "教材来源与缺口"]
    },
    {
      "id": "C2",
      "role_id": "prerequisites_and_misconceptions",
      "instruction": "结合 C0 的学情结果和 C1 的教学范围，整理需要复习的前置内容与易错点，区分有记录支持的学生问题和待验证的常见误区。",
      "depends_on": ["C0", "C1"],
      "expected_output": ["前置复习内容", "易错点及依据", "待验证项与缺口"]
    },
    {
      "id": "C3",
      "role_id": "examples_and_exercises",
      "instruction": "结合 C0、C1、C2 的可用结果，从已授权题库整理符合教学范围和难度的例句练习与课堂检测题，核对答案来源，说明对应的教学目标或易错点。",
      "depends_on": ["C0", "C1", "C2"],
      "expected_output": ["候选例句与练习", "答案依据", "目标对应关系", "来源与缺口"]
    }
  ],
  "final_output": ["教学目标", "复习与新词环节安排", "课堂练习", "引用与待确认项"],
  "acceptance_criteria": ["覆盖已确认的教学要求", "关键材料有可追溯来源", "缺失或未确认内容明确标注"]
}
```

字段含义：

- `goal`：整份教案要解决什么问题，由主 Agent 最终整合完成。
- `tasks`：本次要执行的子任务，不是四份完整教案。
- `id`：计划内部的逻辑任务标识，用于表达依赖；程序校验后关联到正式任务记录。
- `role_id`：选择已预定义的角色，不是临时生成新的系统 Prompt 或工具。
- `instruction`：本次委派的具体目标与要求，是动态生成的自然语言。
- `depends_on`：需要哪些前置任务的可用结果，由执行层据此安排派发。
- `expected_output`：本次需要的材料项；预定义输出契约仍负责统一任务关联、执行状态、引用与缺口等结构。
- `final_output`、`acceptance_criteria`：最终教案的交付项与验收要求，不代表模型自报完成即可通过。

`constraints` 应与教练已确认的要求一致，不能由模型擅自改成另一版本教材或另一课时。程序还要检查字段合法、角色在目录内、依赖存在且无环、引用范围与预算合规，再交教练确认。计划有合法结构，不等于已经允许执行。

## 3. 每个子 Agent 实际收到什么

以 C0 为例，程序不会把整份计划和全部主对话原样塞给它，而是提取 C0 的指令，结合已授权的学生与老师、角色配置、预算和必要上下文，装配成单个任务：

```json
{
  "task_id": "P2",
  "subtask_id": "C0",
  "plan_version": 1,
  "execution_id": "E_C0_1",
  "role_id": "learner_history",
  "goal": "回顾当前学生与当前老师的相关历史课程，整理已学词汇、近期复习表现和有依据的学习偏好，给出本节复习建议，标明来源与信息缺口。",
  "inputs": {
    "student_id": "S1",
    "teacher_id": "T1",
    "course_type": "英语词汇课",
    "history_scope": "当前老师与当前学生的相关历史课程",
    "current_topic": "单词复习与新词学习"
  },
  "allowed_tools": ["course_project_query", "learning_record_query", "read_memory"],
  "limits": {"max_steps": 4}
}
```

这里的身份、正式任务关联、计划版本、执行尝试、工具权限和预算由服务端分配或校验。工具名、身份标识和预算值均为示例，不代表现有接口名称或生产配置；`allowed_tools` 只能来自角色白名单与实际授权的共同允许范围。

Runtime 再用“预置角色 Prompt + 本次 `goal` + 必要输入与证据”创建独立子运行。C0 自己在白名单内选择工具并执行受限 Loop，返回学情材料；它不负责制定整节课的最终安排。C2 派发时会按需加入 C0、C1 的可用结果，其他子任务也是同样的装配方式。

## 4. 四个子 Agent 如何执行与汇总

**角色可以预定义，但每次选择哪些角色、下发什么任务，以及何时追加委派，不必写死。执行层按当前有效计划的依赖调度，不按 C0、C1、C2、C3 的数字顺序调度。** 以下先展示第 2 节这份计划，再说明另一种按结果追加任务的方式。

### 4.1 第 2 节计划的执行顺序

```text
主 Agent 输出计划 → 程序校验 → 教练确认
    ↓
C0 学情回顾 + C1 教材取证（无相互依赖，可分别执行；不要求并行）
    ↓ 获得可用前置结果
C2 前置内容与误区分析
    ↓ 获得可用前置结果
C3 例题与课堂练习整理
    ↓
主 Agent 回收四份材料，检查覆盖与来源，整合成教案
```

前置任务仅“结束”不代表依赖满足：结果缺少下一任务必需材料时，应有限补查、澄清或标明部分完成，不能假装已经拿到完整输入。这个案例使用四个角色只是为了展示结构，不代表每份教案都要运行四个子 Agent。

这份计划里 C3 明确依赖 C0、C1、C2，因此不能一开始就把 C0、C1、C3 并行派发。顺序来自本次任务所需的输入，不是 `examples_and_exercises` 这个角色永远只能最后执行。

#### 4.1.1 先并行再串行时，谁检查前置任务是否完成

**下一个子 Agent 不负责查询上一个子 Agent 的运行状态，依赖检查由执行层统一完成。** 依赖不满足时，通常只有待执行任务记录，还没有创建下游子 Agent 的运行实例，因此不会让一个模型空转等待另一个模型。

执行层根据当前有效计划读取 `depends_on`，并维护各任务的状态、执行尝试与结果引用。下面的状态标签仅为讲解示例，假设并发额度允许 C0、C1 同时执行：

| 时点 | C0 学情 | C1 教材 | C2 误区 | C3 练习 |
| --- | --- | --- | --- | --- |
| 开始执行 | 运行中 | 运行中 | 等待依赖 | 等待依赖 |
| C0 返回并取得可用结果 | 结果可用 | 运行中 | 仍等 C1 | 等待依赖 |
| C1 返回并取得可用结果 | 结果可用 | 结果可用 | 可以进入派发 | 仍等 C2 |
| C2 返回并取得可用结果 | 结果可用 | 结果可用 | 结果可用 | 可以进入派发 |

每次子运行返回，执行层按以下顺序处理：

1. 核对子任务、计划版本、执行尝试与当前状态，校验并保存结果，更新任务记录。
2. 找到依赖该任务的待执行任务，检查它们所需的全部前置结果是否可用，而不只是检查前置运行是否停止。
3. 依赖满足后，再检查主任务仍有效、计划已确认、权限与预算允许、并发名额可用；满足这些条件才受理派发。依赖满足不等于已经开始执行，缺少名额时仍要排队。
4. 创建下游独立上下文，加入本次指令、必要的前置结果摘要与可解析的引用，再调用 Runtime；下游获得的是输入材料，不需要自己去询问前置 Agent。

前置任务失败、超时，或者虽然返回但缺少下游必需材料时，不能直接放行。先按规则补查、有限重试、澄清或修订计划；部分结果只有在满足该下游明确的输入要求时才可采用。结果可用性判断包括确定性检查，必要的内容判断仍需主 Agent 或教练介入，不能由一个成功状态代替。

这不是“每批全部结束再启动下一批”的固定屏障。若另有 C4 只依赖 C0，那么 C0 的结果可用且其他派发条件满足时，C4 就可运行，不需要等待无关的 C1。只是在本例中，C2 明确依赖 C0、C1，所以要等两者都提供可用输入。

同进程短任务可在异步返回后直接触发上述检查；长任务则在受理完成事件后检查，任务记录用于关联和恢复。已有依赖满足后不必再调用主模型决定启动顺序；只有需要补查决策或修订计划时才进入相应评价节点。多个完成事件同时到达时，可通过串行化调度或原子领取与去重，避免同一下游被重复派发；这不意味着必须引入通用 DAG 框架或消息队列。

### 4.2 可以先执行 C0、C1、C3，再根据结果追加 C4 吗

可以，但要使用相应的任务定义和依赖。另一份示例计划可以这样安排：

```text
第一批：
  C0 / learner_history：整理相关学情证据
  C1 / textbook_evidence：核对教材范围和教学依据
  C3 / examples_and_exercises：按已确认目标词表收集通用候选题
      三项此时不相互依赖，可按并发预算分别执行
    ↓ 必要结果可用
主 Agent 评价：候选题已取得，但还需要围绕有依据的薄弱点组织讲解
    ↓ 提出 C4，修订计划，经执行层校验与必要确认
C4 / examples_and_exercises：匹配薄弱点、筛选候选题并生成针对性讲解
      depends_on = [C0, C1, C3]
      可使用“基于学情的分层讲解”Skill，按需核对材料
    ↓
主 Agent 评价并汇总；满足要求就结束，否则在预算内定向补查或修订
```

这里有三个重要区别：

- **C3 的任务目标不同。** 本例第一批只收集通用候选题，不声称已按学生掌握程度完成选题；它不需要尚未返回的学情。第 2 节的 C3 则要结合 C0、C1、C2 做针对性整理，不能直接挪到第一批。
- **C4 是任务标识，不等于新增角色。** 它可以复用已有 `examples_and_exercises` 角色，以新目标和独立子运行继续处理。角色 Prompt、工具白名单和输出契约仍受预定义配置约束；任务编号不要求连续，也不代表固定执行次序。
- **追加委派要受治理。** 主 Agent 根据结果提出新增任务或调整依赖，执行层更新计划版本并检查角色、输入、依赖、授权和剩余预算；本教案流程仍遵守计划确认门槛，不能借“动态追加”绕过确认。关键目标、范围或交付要求改变时需要重新取得教练确认，普通补查则按第 8.3 节处理。旧版本的有效结果经过兼容性校验后可以显式复用，不因追加 C4 就重跑全部任务。

这可以概括为 **Plan → 执行一批就绪任务 → 评价结果 → 按需修订 Plan → 继续执行**。初始计划不必穷尽所有后续任务，但已经明确的依赖可以由执行层直接推进，不需要每完成一个任务都调用主模型。下一批只需等待它实际依赖的可用结果，不必等待所有无关任务结束；追加任务和修订次数也受父任务总预算限制。

### 4.3 外层骨架与开源项目的对应关系

外层骨架不是把 C0、C1、C2、C3 的顺序写死。这里要区分三层：教案业务流程管理规划、确认、执行、评价和结束；任务调度读取当前计划的依赖；Agent Runtime 管模型调用、工具反馈、预算和中断。它们可以在同一服务内实现，不要求三个独立框架或额外 Agent。

以下是截至 2026-10-09 查阅官方资料后的对比，不表示鼎校伴学使用了这些框架，也不把不同项目的机制都称为同一套 Workflow。RAGFlow 按 1.0.0-rc1 文档，CrewAI 按官方当前指向的 v1.15.26 文档；Hermes 与 LangGraph 按当前官方文档及相关示例。

| 项目 | 由程序或配置确定的部分 | 动态部分及与本方案的关系 |
| --- | --- | --- |
| Hermes Agent（NousResearch） | `AIAgent` 的调用循环、工具执行、迭代限制，以及子运行创建与能力约束 | 主模型通过 `delegate_task` 提出目标和上下文，由执行层创建独立子运行。类似受控 Runtime 与动态委派，但核心 Loop 本身不是教案的计划确认状态机。见 [Agent Loop](https://hermes-agent.nousresearch.com/docs/developer-guide/agent-loop/) 和 [子 Agent 委派](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation/)。 |
| RAGFlow | Canvas 上配置组件与连线；`Switch` 管规则分支，`Await Response` 管等待补充或确认，`Loop` 配置终止条件与次数限制 | Agent 组件内部决定何时调用已配置的工具或子 Agent，是“显式外层流程 + 节点内动态决策”的例子；不等于模型自由创建未配置角色。见 [Agent 组件](https://ragflow.io/docs/v1.0.0-rc1/basic_component)、[流程组件](https://ragflow.io/docs/v1.0.0-rc1/flow_components) 和 [等待响应](https://ragflow.io/docs/v1.0.0-rc1/dialogue_component)。 |
| LangGraph | 预定义节点函数、状态与路由；通过 checkpoint 和 `interrupt()` 实现暂停与恢复 | Orchestrator-worker 示例中，模型生成子任务列表，再用 `Send` 向已定义的 worker 节点动态派发调用；不是模型临时发明可执行节点代码。见 [动态 Worker 示例](https://docs.langchain.com/oss/python/langgraph/workflows-agents#orchestrator-worker) 和 [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)。 |
| CrewAI | `Flow` 用 `@start`、`@listen`、`@router` 定义入口、事件依赖和条件路由，维护流程状态；支持人工反馈门槛 | Flow 的方法中可以调用 Agent 或 Crew，把模型任务放进显式业务流程。路由可以依赖模型结果，但合法分支由程序声明。见 [Flows](https://docs.crewai.com/v1.15.26/en/concepts/flows)。 |

Hermes 当前源码的 `agent/conversation_loop.py` 在受预算限制的循环中执行预检、模型调用和响应处理，并根据是否有 ToolCall 进入工具轮或文本结束分支；`tools/delegate_tool.py` 的 `_build_child_agent()` 装配子运行和能力范围。这支持“固定运行规则、动态选择任务”的解释，不代表它已经替业务实现了教练确认、教材授权和教案验收。源码入口见 [conversation_loop.py](https://github.com/NousResearch/hermes-agent/blob/main/agent/conversation_loop.py) 与 [delegate_tool.py](https://github.com/NousResearch/hermes-agent/blob/main/tools/delegate_tool.py)。

对当前教案方案的取舍：借鉴上述分工即可，不必为了对应某个框架而迁移。用轻量业务状态机管理确认与结束，按计划依赖通用调度，并继续复用既有 Agent Runtime；选择哪些子任务、是否追加 C4，由主 Agent 提议，执行层校验后执行。引用中的默认限制和异步交付细节可能随版本变化，不把它们照抄为本项目的生产配置。

#### 4.3.1 是不是在 ChatPipeline 里增加一个 Plan 循环

**按状态与依赖循环推进的理解成立，但要把任务编排循环与 Agent Loop 分开。** 如果用“聊天 Pipeline”泛指整条业务处理链，可以说它接入了 Plan 编排；如果指当前材料中的具体 `ChatPipeline` 组件，则它主要负责装配一次 Agent 运行的输入，不负责把跨轮备课进度保存在一个常驻循环中。

职责关系可以这样理解，不表示每条聊天消息都必须经过全部模块：

```text
消息受理 / 教案任务恢复
    -> 教案任务编排：管理 Plan、依赖、任务状态、等待与结果
    -> 按需调用现有 Agent Runtime
         TurnOrchestrator -> ChatPipeline -> Agent Loop
    -> 结果回到任务编排层，经校验后推进下一步
```

任务编排循环决定“哪些任务现在可以运行”；`ChatPipeline` 准备角色指令、相关证据、工具与预算；Agent Loop 决定“当前子任务要调用什么工具、是否继续取证或交付结果”。编排器可以与 Pipeline 在同一服务中，也可以通过内部入口被它调用或由对话 Tool 转交，但职责不应混在一个模型与工具循环里。

这里的“循环”不是持续轮询所有 Agent 或反复请求模型。典型推进过程是：找出就绪任务并受控派发 -> 异步等待返回或事件 -> 校验并保存结果、更新任务状态 -> 再检查依赖。执行层依据有效结果提交状态，不让子模型直接修改共享主任务状态；新就绪任务还须检查预算、名额和取消情况，也不一定只有一个“下一级”。没有在途任务且依赖仍无法满足时，要进入失败、补查或澄清分支，不能空转；需要用户确认或反馈时保存等待点并退出，收到新事件再恢复。

**与 LangGraph 的关系是思路可对照，不是已经复刻其实现。** 状态、依赖、并行与汇合是通用编排概念；LangGraph 的 Orchestrator-worker 示例也支持模型生成子任务，再通过 `Send` 派发 worker。其底层 Pregel 则按 superstep 执行“选择本步节点 -> 本步并行执行 -> 更新 channels”，本步写入到下一步才对执行节点可见，并非任意节点一返回就立即启动下游。因此，本文第 4.1.1 节按完成事件检查依赖的方式，不能直接称为 LangGraph 原样调度。这里 Pregel 的 Plan 阶段指程序选择本步执行节点，不等同于 LLM 生成业务计划。以上区别于 2026-10-17 对照官方 [Orchestrator-worker](https://docs.langchain.com/oss/python/langgraph/workflows-agents#orchestrator-worker) 与 [Runtime](https://docs.langchain.com/oss/python/langgraph/pregel) 说明整理。

#### 4.3.2 与 ForgePilot 的上层编排类比，Workflow 与 Plan 状态放哪里

可以借助 `learning/forgePilot` 的 [总架构图](../../../forgePilot/3架构图1.png) 和 [编排层说明](../../../forgePilot/5架构图3.png) 理解“上层管理任务，下层执行 Agent Loop”。图中第 3 层包含任务理解、上下文装配、路由与运行管理，第 4 层包含 Agent Loop、模型适配、检索与工具执行；它们是分工参考，不是两个项目的组件与能力完全相同的证据。尤其是上下文装配，在本材料中还对应 `ChatPipeline` 的运行准备职责，不能把 ForgePilot 第 3 层全部等同于单一的任务调度器，也不能据此推断图中已有完整的多 Agent 依赖调度。

**外层任务编排在逻辑上独立于单次 Agent 运行；固定 Workflow 与动态 Plan 都需要这一职责，但状态模型和推进规则不同。** 对鼎校伴学可以画成：

```text
消息接入与路由
    -> 业务任务编排
         学生辅导 Workflow：既定阶段、分支、等待作答、验收
         教案任务 Plan：本次子目标、依赖、派发、汇总与修订
    -> 按需调用现有 Agent Runtime
         TurnOrchestrator -> ChatPipeline -> Agent Loop
    -> 编排层验收结果、提交业务进度，再决定下一步
```

“状态放在上面”准确说是“由编排层负责管理业务进度与调度状态”，不等于把所有数据和所有循环塞进同一个对象：

| 状态类别 | 管理职责与内容示例 |
| --- | --- |
| 业务任务状态 | 外层编排管理主任务生命周期、等待对象、确认版本、取消与预算；Workflow 保存当前阶段和验收进度，Plan 保存有效计划、依赖、子任务状态和结果引用 |
| 单次 Agent 运行状态 | Runtime 管理本次独立消息列表、工具调用与反馈、循环轮次和运行预算；必要时单独记录轨迹，不把全部流水当成主任务进度 |
| 业务事实与长期记忆 | 业务服务和记忆模块保存原始学习记录、证据与有效偏好；编排层按授权读取或引用，不因统一编排就替代这些数据源 |

两类业务可以复用任务记录、事件受理、取消、预算、版本校验与运行入口，但不意味着已经共用同一数据库、同一调度器或统一部署，也不要求把 Workflow 与 Plan 的全部字段做成一个巨大的共享 State。任务实例按标识和业务类型隔离，分别保留阶段规则或依赖规则；Workflow 的步骤也可以是确定性业务代码，不必全部包装成 Agent。

状态“由哪层管理”与“物理存在哪里”是两回事。需要跨轮恢复的进度应可靠保存到任务存储，不是让编排层一直在内存里运行；保存历史会话也不自动等于恢复正在执行的任务。面试时可以概括为：**我用外层编排管理业务进度，固定流程按阶段推进，动态计划按依赖推进；两者按需调用同一套 Runtime，单次模型与工具循环仍由 Runtime 负责。**

### 4.4 生成草稿后征求反馈：由本次 Plan 决定

本方案采用“Plan 安排本次要不要收反馈”，而不是每份教案生成后都进入固定的审阅节点。这与执行前的计划确认不同：原有确认门槛继续保留，调整的是草稿之后的交互方式。

主 Agent 可以在初始计划中安排反馈，也可以拿到子任务结果、生成草稿后补充交互步骤。需要共同打磨或澄清教学取舍时，明确询问目的、草稿版本和希望获得的信息；需求清楚、材料充分且只要求直接交付时，可以不主动征求意见。明确的人工确认要求与关键疑点不能借“不需要反馈”绕过。

```text
本次需求：先生成一版词汇课教案，再一起调整
    ↓
主 Agent 的 Plan：
  取证与整理 → 生成草稿
  → 征求教练对复习时间和练习难度的意见
  → 根据回复局部修订，必要时定向补查

另一份需求：按已确认要求直接给教案草稿
    ↓
主 Agent 的 Plan：取证与整理 → 生成草稿与缺口 → 交付
```

第 2 节的 `tasks` 示例列的是子 Agent 取证任务，不表示每个业务步骤都要有一个 `role_id`。反馈属于主任务的用户交互步骤，不是再委派一个反馈子 Agent；如果在结构化计划里表达，应区分委派、生成材料和请求用户输入等步骤类型，以上文字用于说明选择，不声明新接口。

各层分工：

- **Plan 决定是否安排交互。** 主 Agent 提出何时问、为什么问、需要什么反馈，并在结果变化时修订计划。
- **Prompt 指导规划和提问。** 它可以要求模型在需要共同打磨时安排反馈，但不写成“生成后永远问一次”。仅在结尾自然加一句意见询问，而没有计划步骤与目的，不足以说明是 Plan 驱动。
- **执行层实现通用交互。** 按已授权能力发送问题、接收回复并关联主任务与草稿版本；可以封装成用户交互工具，也可以由正常消息入口承接。若使用工具，工具名以实际注册能力为准。询问后主模型结束当前调用，等待时不忙等，回复到达后再恢复决策。

收到反馈后，主 Agent 使用当前计划、适用草稿、反馈和相关证据判断下一步：只是措辞或排版就局部修订；材料缺口则补查；教学目标或范围变化则按第 8.3 节修订并确认。不能把回复套到错误的草稿版本，也不能把未回复当作默认认可、自动结束待反馈步骤或自动发布；等待按交互截止与取消规则处理，追加任务仍受原权限和预算约束。

面试可以概括为：**主 Agent 按任务需求把征求反馈纳入当次计划，收到回复后决定局部修订还是补查；执行层只提供受控的等待与恢复，不把反馈写成所有教案必经的固定 Workflow 节点。**


## 5. 主 Agent 委派后，是不是只需要等待？

可以理解为“委派后等待可用结果，再继续决策”，但要区分模型与执行层：**等待、依赖调度和结果关联由编排层 / Runtime 管理，不是让主模型一直生成内容或反复询问任务有没有结束。**

这个案例中的过程是：

1. 主 Agent 完成一次模型调用，输出候选计划；程序校验并取得教练确认后，保存当前计划与任务关联。
2. 执行层派发就绪的 C0、C1，并记录执行状态。主 Agent 的模型此时不必持续运行。
3. C0、C1 返回后，执行层核对任务、计划版本、执行尝试、结果格式与来源关联，保存可用结果；前置条件满足时继续派发 C2，再按依赖派发 C3。已明确的依赖推进不需要每一步都重新询问主模型。
4. 到汇总或计划评价节点时，执行层将已确认计划、可用子任务结果、引用、缺口和剩余预算装配进主 Agent 上下文，再进行一次模型调用。这仍是同一个主任务的继续，不是另起一份没有关联的教案；按结果追加任务的情况见第 4.2 节。
5. 主 Agent 检查需求覆盖和内容一致性：材料充分则生成教案草稿，按本次 Plan 决定是否征求反馈；缺口可补且预算允许则提出定向补查，或按计划修订规则提出新的子任务；预算耗尽或关键材料缺失则标明未解决部分，由执行层校验并推进相应分支。草稿后的按需反馈见第 4.4 节。

因此，主 Agent 不负责忙等，也不是发完任务就结束职责。它仍负责规划、结果评价、必要的修订与最终整合；执行层负责什么时候继续、哪些结果能采用，以及超时、取消和旧结果的处理。

短任务可以由执行层异步等待子运行返回；长任务可以保存待执行状态，释放当前请求，后续由完成事件推进。两者都不要求主模型在等待期间持续推理，也不等于必须引入消息队列或某个编排框架。子任务超时或失败时返回明确状态，不能永远等待，也不能把缺少材料伪装成完成。

### 5.1 程序怎么知道子 Agent 已经结束

**执行层知道结束，是因为它掌握子运行的调用与返回，不是因为主模型不断询问，也不是从自然语言里搜索“我完成了”。** 要分清三个层次：

| 层次 | 结束或完成的含义 |
| --- | --- |
| 一次模型请求结束 | 只表示本次响应结束；如果返回 ToolCall，Runtime 还要执行工具、回填结果并继续调用模型，子运行尚未结束 |
| 一次子运行结束 | Runtime 收到符合输出契约的最终结果并退出 Loop，或者进入异常、超时、取消等终止分支；执行层收到返回值或异常，再归档本次尝试 |
| 子任务可用或主任务完成 | 执行层校验结果关联、格式与来源，检查下游必需输入；主 Agent 再评价需求覆盖与内容，不能把子运行停止等同于任务成功 |

模型提供的是候选最终结果，程序控制的是退出与受理。没有 ToolCall 也不自动代表成功：模型输出被截断、格式不合法或缺少必要材料时，应按规则有限修复、返回部分结果或失败，不能仅凭连接关闭就写成功状态。部分完成可以结束本次尝试，但不保证满足下游依赖；是否补查或重试另行决定。

同进程短任务可以用一次异步函数调用理解，下面只是正常返回路径的伪代码，函数名不是已有接口声明：

```python
result = await run_child_agent(delegation)
accepted = validate_and_save_result(result, current_task)
```

`run_child_agent` 内部承载独立上下文和工具循环；它正常 `return` 时，调用方获得结果并继续执行。`await` 等的是程序任务，不是让主模型持续推理；异常、超时与取消还要走第 7 节的分支，不保证一定拿到正常返回值。异步等待与任务返回的机制可参考 [Python 官方说明](https://docs.python.org/3/library/asyncio-task.html#awaitables)。

结果保存后，执行层按当前计划推进依赖，或在汇总节点把可用结果装配进主 Agent 的下一次模型请求。**结果先回到程序，再作为下一次模型调用的输入交给主 Agent；不是模型之间自动共享消息。** 若改用第 10.2 节的委派 Tool，则由工具处理函数把结果包装成 ToolResult 回填；不能把这种可选入口当成本文默认接口。

## 6. 多 Agent 之间的信息如何传输？

这个案例采用**执行层中转结构化任务与结果**，不是让几个 Agent 默认共享一份可变聊天记录，也不要求它们互相自由发消息。

```text
主 Agent 输出结构化计划
    ↓
执行层校验、保存任务，装配单个子任务的输入
    ↓
子 Agent 在独立上下文中调用工具并返回结构化结果
    ↓
执行层校验结果并保存，按依赖提供给后续子 Agent
    ↓
执行层把相关结果装配到主 Agent 上下文
    ↓
主 Agent 继续检查、补查或生成教案
```

### 6.1 子 Agent 返回什么

输入见第 3 节。下面是 C0 的返回示例，历史记录与建议均是假设内容，不代表真实学生数据：

```json
{
  "task_id": "P2",
  "subtask_id": "C0",
  "plan_version": 1,
  "execution_id": "E_C0_1",
  "status": "partial",
  "summary": "已整理同一老师的词汇课记录，部分历史错词需要复查。",
  "teaching_suggestions": ["本节开头先检查历史反复错词的掌握情况。"],
  "evidence_refs": ["H1", "H2"],
  "gaps": ["缺少近期课后复习反馈。"]
}
```

任务、版本和执行尝试等关联字段由 Runtime 封装或执行层核对，不由子模型随意认领。`H1`、`H2` 必须能解析到当前授权范围内的真实记录，不能只接受模型生成的来源名称；结构合法与来源存在，也不等于所有教学判断都正确。

### 6.2 C0 的结果如何交给 C2，或回到主 Agent

- C0 的结果先交给执行层，关联到当前主任务的子任务结果记录，不直接修改主对话或 C2 的消息列表。
- 执行层检查 C0、C1 是否提供了 C2 所需的可用材料，再创建 C2 的上下文，加入相关学情摘要、教学范围与引用。结果引用需要解析成必要材料，或通过已授权的读取能力获取，不是只给模型一个无法访问的标识。
- C2、C3 使用同样的方式返回结果。到汇总节点，执行层把必要结果装配进主 Agent 的下一次调用；主 Agent 不会自动看到子 Agent 的所有工具反馈和聊天流水。
- 主 Agent 如需核对细节，可按引用回查或提出受限补查，不把所有子任务原始材料无限追加到主上下文。

所以，“共享业务状态与证据”不等于“共享可变对话”。每次子运行的消息与工具轨迹仍然独立，结果只通过受控交接进入下一阶段。

### 6.3 传输一定要用网络或消息队列吗

不需要。主 Agent 和子 Agent 是逻辑角色，可以在同一个服务进程中复用 Runtime，以函数参数、结构化对象和异步返回完成任务交接；任务记录仍可以按业务需要持久化。只有扩展到不同进程或 worker 时，才需要进一步考虑 HTTP / RPC、消息队列等传输方式，以及回调、重试与去重规则。

面试时可以概括为：**主 Agent 产生计划，执行层派发与等待，子 Agent 返回带关联标识的结构化结果，执行层校验后按依赖传递材料，再唤起主 Agent 做评价与整合。**

## 7. 子 Agent 不结束，以及其他边界异常怎么办

核心原则：**不能把结束责任完全交给模型。执行层限制等待和执行预算，异常时主动生成明确结果，让主任务有下一步。** 以下字段和案例用于说明治理规则，不代表实际配置值或效果指标。

### 7.1 分层限制，而不是只设置循环次数

| 层级 | 需要限制什么 | 为什么不能省略 |
| --- | --- | --- |
| 单次调用 | 模型请求与工具调用的超时 | 卡在一次请求里时，循环次数不会增长，轮次上限不能解除等待 |
| 子运行 | 轮次、工具调用或 Token 预算，以及整个子任务的绝对截止时间 | 防止模型反复检索，也防止每次调用都没超时但整轮持续过久；有进度也不能无限顺延截止时间 |
| 主任务 | 总耗时、总调用预算、重试与补查次数、并发数 | 避免每个子任务都有限，但多个子任务和重试累加后仍无法收敛；为最终汇总预留预算 |

达到轮次或调用预算时，若仍有时间且模型可响应，可以 Forced Finish，基于已有证据总结并标出缺口。但若模型或工具本身卡住，不能继续等它主动总结；执行层应利用已保存的可用材料生成失败或超时结果，没有材料就明确返回缺口。

### 7.2 子 Agent 一直没有返回时的处理链路

1. 执行层发现子运行超过截止时间，将当前执行尝试标记为 `timed_out`，停止等待它作为正常完成结果。
2. 请求取消未结束的模型或工具调用，并停止该尝试继续派发新工具。取消是否实际生效取决于底层能力，超时不等于远端请求已经停止；仍要控制重试并发并处理晚到结果。
3. 执行层整理已保存、仍有效的部分结果与缺口，主动生成结构化超时结果。不依赖子 Agent 再回调一次“我失败了”。
4. 依据错误类型、任务重要性和剩余预算，选择有限重试、允许的替代查询、请教练补充材料，或输出部分结果。重试创建新的执行尝试，不能重置父任务总预算或无限延长截止时间。
5. 老尝试之后返回时，核对任务、计划版本、执行尝试与当前状态，不允许覆盖新尝试结果或已结束的主任务。完成事件和超时事件竞争时，状态提交也要校验并保证只接受一次合法变更。

**由执行层生成的超时结果示例：**

```json
{
  "task_id": "P2",
  "subtask_id": "C0",
  "plan_version": 1,
  "execution_id": "E_C0_1",
  "status": "timed_out",
  "error": {
    "code": "SUBTASK_TIMEOUT",
    "message": "未在截止时间内产生完整可用结果。"
  },
  "partial_result": {
    "summary": "已查到当前老师的相关词汇课，尚未获得近期复习记录。",
    "evidence_refs": ["H1"]
  },
  "gaps": ["缺少近期复习表现，无法完成个性化复习建议。"]
}
```

部分材料是假设示例，只有确已保存并通过来源核对的内容才能回收。这个结果表示一次执行尝试超时；是否继续重试、是否结束整个子任务，由执行层按规则决定，不由模型通过修改 `status` 自行恢复旧尝试。

### 7.3 常见异常怎样分开处理

| 异常 | 处理规则 |
| --- | --- |
| 单次工具超时或异常 | 转为结构化 ToolResult 回填子 Agent；允许它在白名单和预算内调整参数或换工具，不立刻丢弃其他有效材料 |
| 子 Agent 反复检索、不肯给结论 | 限制轮次与调用预算；有条件时 Forced Finish，否则返回已知材料与未解决项，不无限循环 |
| 子运行没有返回、连接断开或执行中断 | 由执行层截止时间结束等待，生成超时或失败结果；长任务不能仅靠原请求一直挂着 |
| 临时服务错误 | 在父任务剩余预算内有限重试，必要时退避；权限不足不靠反复重试解决，不能让模型自行扩大授权 |
| 查不到课程、没有复习记录或资料不足 | 当作信息缺口，而不是断言学生没学过或不复习；可澄清、定向补查或降级，不机械重复同一查询 |
| 返回 JSON 不合法、缺少必要项或引用无效 | 验收不通过，允许有限修复或补查；不能把坏格式修成好格式就视为内容正确，也不能补造来源 |
| 一个子任务失败，其他任务成功 | 保留其他有效结果；受影响的下游不能自动当作依赖已满足，要补足输入、修订计划或标记无法完成 |
| 教练修改计划或更换学生、老师 | 重新判断兼容性和影响范围；失效结果不直接参加当前汇总，有效材料经过校验后才可复用 |
| 主任务取消或超出总预算 | 停止派发，尽力取消在途调用，拒绝晚到结果继续推进任务；取消不是成功完成，不自动保存为最终教案或发布 |
| 重复回调、重试的旧结果晚到 | 按任务与执行尝试幂等受理，核对有效版本与状态；保存、导出等副作用还需独立的业务幂等标识 |
| 子 Agent 结论冲突 | 核对相同教学范围、时间与原始来源；无法消除的冲突标明并交教练复核，不通过多数投票认定事实 |

初版角色以只读取证为主。以后若工具包含写入或发布动作，超时可能表示“请求结果未知”，不能认定操作没发生后直接重试；应先核对操作结果并结合业务幂等控制，避免重复副作用。

### 7.4 C0 学情 Agent 超时，会怎样影响本次教案

假设 C0 读取历史背词课时超时，C1 已经取得教材和目标词表：

```text
C0 超时 → 保存已知材料与缺口 → 判断是否有限补查或请教练补充
C1 成功 → 保留教材结果，不因 C0 失败而全部重做
    ↓
个性化 C2、C3 的前置学情仍不足，不能直接照原计划推进
    ├─ 学情补足 → 继续个性化任务
    ├─ 教练同意通用备课 → 修订并确认计划，复用适用教材结果，生成通用练习
    └─ 个性化是硬要求且无法补足 → 输出部分材料与缺口，不声称完整满足需求
```

因此，降级不是“忽略错误然后假装完成”。它需要明确哪些需求未满足；改变关键目标或范围时按计划变更流程确认，不能偷偷删除依赖，把通用教案标成个性化教案。

### 7.5 面试可以怎样概括

> 我不依赖子 Agent 自己声明完成，而是在执行层设置单次调用超时、子任务截止时间以及父任务总预算。工具失败先结构化回填，让子 Agent 有限调整；子运行超时则由执行层收回等待控制权，回收有效材料并生成明确失败结果。之后按错误类型和剩余预算决定重试、补查或降级，保留其他有效结果，但不会让缺少输入的下游继续假装完成。结果回收还会核对计划版本、执行尝试和当前状态，防止取消后、重试前或旧计划的晚到结果污染当前教案。

## 8. Plan 如何触发，什么时候重新规划

当前支持按钮和对话两种备课入口：按钮由程序直接触发，对话由主 Agent 识别需求后通过 Tool 触发。**执行层受理并校验规划请求，主 Agent 负责生成计划内容**。不是每次对话都先规划，也不是主模型输出一句“我要做计划”就自动获得执行权限。

### 8.1 什么请求进入规划

| 用户请求或入口 | 处理方式 |
| --- | --- |
| 教练在教案业务入口点击“生成教案” | 进入备课流程，核对需求后调用主 Agent 的规划阶段 |
| 自然语言要求“结合这个学生以前跟我上课的情况，准备下一节英语课” | 通用主 Agent 识别为备课需求，通过规划 Tool 发起请求，程序校验后进入相同规划流程 |
| “查一下上次背词课学了什么” | 直接查询相关 Tool，不为一次取数额外生成多 Agent 计划 |
| 简短讲解或普通问答 | 使用正常对话或 Agent Loop，不强制走 Plan-and-Execute |

对话入口由主 Agent 判断是否需要备课，ToolCall 仍需程序校验；不额外强制增加一层独立路由模型。意图不明确时先澄清，例如区分“查看历史课程”与“生成下一节教案”，不是只要出现“背词”或“历史”就触发规划。按钮入口已经声明业务类型，但仍要核对必要约束。

先核对的是教学专题、教材版本、课时、输出要求等业务约束；个性化备课还要关联已授权的学生与老师。缺少关键约束时先澄清。历史复习表现、教材片段和题库候选属于待查证据，可以作为计划中的子任务，不需要在生成计划之前全部查完。

### 8.2 程序怎样让主 Agent 生成 Plan

下面展示两个入口汇合后的共同链路。对话入口先由主 Agent 发起规划 ToolCall，按钮入口由程序直接进入；两种入口的具体顺序见第 8.2.2 节。以下阶段名称是讲解示意，不代表实际数据库枚举或框架 API：

```text
按钮入口 / 对话产生的规划 ToolCall
    ↓
执行层受理与需求核对，必要时澄清
    ↓
进入 PLANNING 阶段
    ↓
调用主 Agent：规划 Prompt + 用户需求与已确认约束 + 角色目录 + 输出契约
    ↓
主 Agent 输出第 2 节的候选计划 JSON
    ↓
程序校验角色、依赖、范围与预算
    ↓
等待教练确认当前计划版本
    ↓
确认后进入执行阶段，派发就绪的子任务
```

调用主 Agent 时，可以把任务要求组织成下面这样的输入；课时仍沿用前文示例：

```text
当前阶段：PLANNING，由执行层设置。
用户需求：为当前学生准备一节 45 分钟的单词复习与新词学习课程，参考此前跟当前老师上课的情况。
已确认约束：教材版本、目标词表、课时和输出要求；学生与老师的授权关联由程序提供。
可选角色：learner_history、textbook_evidence、prerequisites_and_misconceptions、examples_and_exercises。
输出要求：只输出候选计划 JSON，包含主目标、约束、子任务、角色、指令、依赖、预期产物与验收要求；若本次需要共同打磨，明确反馈步骤、询问目的和所需信息，不要求每份教案都有反馈。
执行边界：此阶段不派发子 Agent，不执行取证任务；不得发明角色或扩大权限，不得把待查资料写成已确认事实。
```

这份阶段 Prompt 可以预定义，由 Runtime 结合本次需求装配；主 Agent 不必再委派一个 Planner 才能规划。计划可以通过结构化输出或提交计划工具的参数返回，关键是程序能校验，不要求必须存在一个叫 `plan` 的工具。

生成计划和执行计划是两个门槛。输出 JSON 后仍需校验与确认；若用户只要求查看计划草稿，就停留在计划产物，不自动启动子运行。计划格式不合格时允许有限修复，不无限重新生成。

#### 8.2.1 规划 Prompt 怎么加载，什么时候交给模型

**“加载 Prompt”首先是程序准备模型输入，不是模型必须先调用工具读取文件。** 用户发来消息后，后端先收到请求，再决定用什么指令调用模型；如果用户点的是“生成教案”，程序在模型理解需求之前就已知道业务类型。

要区分两件事，以下不声明现有配置路径或源码符号：

1. **程序读模板。** 基础 Prompt 和规划模板可以来自配置或文件，启动时缓存或按需读取。此时内容在后端，模型还没看到。
2. **程序把内容交给模型。** 调用规划模型时，把可信指令、本次需求、已确认约束、允许的角色摘要和 Plan 输出格式放进本次请求。通过工具按需加载时，也可以把规划方法作为 ToolResult 回填，下一轮模型调用再使用。

```text
程序发出的本次规划请求：
可信指令：主 Agent 职责 + 本轮规划要求
任务数据：用户需求 + 已确认约束 + 允许的角色摘要 + 必要上下文
输出格式：服务端预定义的 Plan 结构
    ↓
模型根据收到的内容生成候选 Plan
```

基础 Prompt 规定通用职责，规划指令说明“这次先输出计划，不执行取证”。用户原话、历史记录与检索材料仍是任务数据，不因出现指令性文字就成为系统规则。角色目录只需提供职责与输出摘要，不必复制所有子 Agent 的完整 Prompt。

Prompt 是否仍然有效，取决于它是否出现在当前模型请求的上下文中；既不是天然只生效一个对话轮次，也不是加载一次就永久生效。教案任务跨轮继续时，由程序根据任务状态重新装配所需指令，见第 8.2.3 节。

**不存在模型生成到一半，程序悄悄替换它的 System Prompt 的过程。** 程序先准备请求再调用模型；若前一次返回了 ToolCall，就先处理工具，再发起下一次模型调用。同一个逻辑主 Agent 可以经历多次模型调用，不必新增独立 Planner Agent，也不必使用 Skill。

#### 8.2.2 当前两个入口：按钮直接触发，对话通过 Tool 触发

**当前保留两种入口，并共用后续规划与执行。** 区别是按钮已经声明业务类型，对话则先由主 Agent 判断备课意图，再通过 Tool 通知程序；不是每个请求都先跑一遍分类，再跑一遍工具判断。

**入口一：用户点击“生成教案”，程序直接装配。**

用户点击按钮或从专用备课接口进入，程序已经知道目标，不需要再调用模型识别同一意图，也不要求模型先产生一个加载 Prompt 的 ToolCall：

```text
点击“生成教案” → 后端收到明确的备课请求
    ↓
核对必要约束 → 选择规划模板，装配角色目录与输出格式
    ↓
调用主 Agent → 生成候选 Plan
```

**入口二：用户通过对话提出需求，主 Agent 通过 Tool 触发。**

这里先由通用主 Agent 理解自然语言需求，再通过已注册的规划入口 Tool 请求规划方法与上下文。工具须提前提供用途说明；规划方法不一定包装成 Skill，以下 `load_skill("lesson_planning")` 仅用于说明加载机制，不声明项目的实际接口名称：

```text
调用 1：基础 Prompt + 用户需求 + 可用方法摘要与工具定义 → 主 Agent
    ↓
主 Agent 判断需要备课规划，返回 load_skill("lesson_planning") ToolCall
    ↓
程序校验并受理请求，核对必要约束，提供预定义规划方法与上下文 → ToolResult
    ↓
调用 2：主 Agent 看到规划方法与本次任务上下文 → 生成候选 Plan
```

最简单的实现是工具返回规划方法，模型在下一轮沿用基础 Prompt 并使用该方法；**加载方法不等于替换 System Prompt，也不等于工具生成了 Plan。** 如果还要切换阶段指令，则由执行层校验后设置允许的阶段，在下一次请求中装配，而不是由模型任意改写系统规则。工具也不能因方法内容要求而扩大角色、资料或工具权限。

按钮请求或对话中的规划 ToolCall 被受理时，执行层就建立或关联当前教案任务，并记录所用指令配置。即使因为缺信息而尚未生成 Plan，下一轮也能关联原任务；不只把规划方法留在一条可能被裁剪的 ToolResult 中。

**两种入口到候选 Plan 后完全汇合：** 程序校验计划 → 教练确认 → 按依赖派发子 Agent → 汇总与按需反馈。对话里的规划 Tool 不是第 10 节的子 Agent 委派 Tool；触发规划不等于直接开始取证或执行四个子任务。

**还有一种方式：规划规则常驻。** 若主 Agent 本来就专门负责备课，简短的规划规则可以一开始就在其 Prompt 中。模型收到需求后直接按规则输出候选 Plan，没有单独的“加载规划 Prompt”动作；不必为了规划额外造一个 Tool 或 Skill。

其他框架也可以让一个路由模型先返回受限分类，再由程序选择下游规划节点。此时“先路由再调用模型”指先确定业务、再调用负责规划的模型，路由本身也可能是一次模型调用。这是架构对照，不是当前对话入口还必须叠加的一层。

**官方方案对照（资料查阅日期：2026-10-10）：**

| 项目 / 模式 | 实际展示的机制 |
| --- | --- |
| LangGraph Routing / Orchestrator-worker | 路由示例先由模型输出结构化分类，程序选下游节点；规划示例由节点直接带规划指令调用模型，不要求模型先调用加载 Prompt 的工具。[官方示例](https://docs.langchain.com/oss/python/langgraph/workflows-agents) |
| LangChain Skills | 主 Agent 先看到能力摘要，再调用 `load_skill`，由工具从文件或数据库读取方法和上下文，对应上面的对话按需加载机制。[官方说明](https://docs.langchain.com/oss/python/langchain/multi-agent/skills) |
| Hermes | 基础指令与技能目录由程序装配；模型可通过 `skill_view` 按需读取完整方法，也支持用户用 `/skill-name` 显式加载。同一项目可以兼容两种入口。[Prompt 装配](https://hermes-agent.nousresearch.com/docs/developer-guide/prompt-assembly)、[Skills](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills/) |
| RAGFlow 1.0.0-rc1 | Canvas 的 Categorize 用模型分类后分支，Switch 按规则分支；Agent 节点有配置好的 Prompt，也能动态选择工具和子 Agent。[流程组件](https://ragflow.io/docs/v1.0.0-rc1/flow_components)、[Agent 组件](https://ragflow.io/docs/v1.0.0-rc1/basic_component) |

这些说明两类入口都存在，不表示所有框架默认采用同一条路径，也不要求本文引入这些框架。Function Calling 是模型提出程序动作的一种结构化接口；模型也可以返回供程序解析的受限分类或计划数据。程序主动准备下一次模型请求，更不需要先获得一个 ToolCall。

**本教案方案明确支持：按钮由程序直接触发，对话由主 Agent 识别需求并通过 Tool 触发；两者复用相同 Plan 结构、Agent Runtime 与执行治理。** 程序都要核对必要约束，缺教材范围、课时等必要信息先澄清；个性化备课仍需核对学生与老师的授权关联。候选 Plan 仍须校验格式、角色、范围、依赖与预算，经教练确认后才派发子 Agent。

入口决定“现在是否备课”，不决定“固定运行哪四个角色”。具体任务、依赖与反馈安排仍由主 Agent 生成；只查看历史可以走普通 Tool，修改措辞或排版可以直接修订草稿，不强制重规划。任务结构或关键范围变化时，再带当前 Plan、有效结果或反馈与剩余预算进入修订，见第 8.3 节。

#### 8.2.3 信息不完整时，下一轮怎样继续加载 Prompt

**不是让上一轮的 Prompt 自动一直生效，而是让程序记住“当前还在处理这个教案任务”，每次续接时再提供相应指令。** 要区分三个范围：一次模型调用只处理本次输入；一个用户对话轮次可能包含多次模型与工具调用；一个教案任务可以跨多个用户轮次完成。

以下沿用词汇课场景，假设教材、目标词表及学生与老师的授权关联已经确认，只缺课时。字段和 45 分钟仍是讲解示例，不声明实际存储结构：

```text
第 1 个用户轮次：点击“生成教案”，或在对话中提出词汇课备课需求
    ↓
受理教案任务，核对后发现缺课时
    ↓
询问：“这节课计划多长？”并记录待回复状态

任务记录示意：
task_id: P1
task_type: lesson_planning
phase: waiting_input
resume_phase: planning
prompt_profile: lesson_planning
request_constraints: 已确认的教材、目标词表、学生与老师
pending_fields: lesson_minutes
plan: 尚未生成

第 2 个用户轮次：用户回复“45 分钟”
    ↓
程序关联 P1 的待回复问题，补入并校验课时
    ↓
条件齐全，恢复 planning 阶段
    ↓
装配基础 Prompt + 规划要求 + 合并后的约束 + 角色目录 + Plan 输出格式
    ↓
调用主 Agent 生成候选 Plan，再进入校验与确认
```

对话入口的规划 Tool 是首次触发方式，不是每个续接轮次都必须重复调用。程序已经有当前任务记录，就能在下一轮直接装配所需规划上下文；模板可以从已缓存配置取出，不必每次重新读文件。任务状态保存在会话或任务记录中，不是靠学生长期画像或主模型的隐含记忆承接。

**“记录待回复状态”是程序的保存动作，不是模型输出一句提问就自动完成。** 必填规则或模型提出信息缺口后，执行层校验并写入已有约束、待补字段与问题；下一轮按任务关联读取。字段示例、实际存储机制与 RAGFlow、LangGraph、Hermes 的源码入口，单独见 [跨轮状态保存与开源框架源码对照](跨轮状态保存与开源框架源码对照.md)。

**按阶段装配，不是每一轮都机械要求完整 Plan JSON：**

- 缺必要条件时，提供基础职责、教案任务规则、已有约束与待补信息，让主 Agent 澄清；此时不强制生成完整计划，更不执行取证。
- 条件齐全时，提供规划指令、角色目录与 Plan 输出契约，生成候选计划。
- 等待计划确认或草稿反馈时，提供对应计划或草稿版本、提问目的和本轮回复，恢复该阶段；不因出现新消息就重建整个计划。

历史对话或 ToolResult 还在上下文中时，模型可能继续利用它，但不能把“模型大概还记得”当作可靠恢复机制。历史被裁剪后，程序仍要能从任务记录恢复当前约束、待回复问题和预定义指令配置。用户输入作为数据合并，不能覆盖可信指令或授权范围。

先判断新消息是否在回答当前任务的问题；明显是新需求或明确要求换任务时，走相应入口，归属不清则澄清，不把所有后续消息都当作课时答案。任务完成、取消或明确切换业务后解除当前任务关联，保留必要历史，而不是永久套用教案 Prompt。

面试可以说：**我把教案规划按任务而不是单个对话轮次管理。信息不足时保存约束和待补字段，用户下一轮回复后关联原任务，合并校验输入，再按当前阶段重新装配 Prompt。这样跨轮续接不依赖模型记忆，也不用用户重新触发备课。**

### 8.3 什么情况下重新触发 Plan

- 教练改变教学目标、课时、学生或老师等关键条件时，主 Agent 生成修订计划，程序校验、更新计划版本，并按影响范围复用或作废材料。
- 现有计划无法满足要求，需要调整任务内容、依赖或关键范围时，进入修订；例如 C0 学情不可用，教练同意改为通用备课，就要修改目标与依赖并确认。
- 只是一个查询缺口，可以在既有计划和预算内定向补查；单次工具暂时失败可以有限重试，不因此把四个任务全部重新规划。
- 草稿后收到教练反馈时，先判断影响范围：措辞或排版调整只修订草稿，不重跑取证；若需新增交互或补查步骤则更新相应计划，关键教学目标或范围变化仍需确认。征求反馈是否出现在本次计划中，见第 4.4 节。
- 主任务已取消或预算耗尽时，结束或输出缺口，不继续用“重新规划”绕过执行边界。

面试可以说：**我支持按钮和对话两种备课入口：按钮由程序直接触发规划，对话由主 Agent 识别需求并通过 Tool 触发。两者共用规划与执行链路，主 Agent 输出结构化计划，程序校验并由教练确认后才委派；只有需求或任务结构变化时重新规划，普通取数和局部失败不重跑整份计划。**

## 9. 怎样判断要不要调用子 Agent

**触发 Plan 不等于必须调用子 Agent。** 在本方案中，主 Agent 根据需求与已有上下文提出处理方式，执行层按业务规则校验后才派发。第 2 节的四角色计划用于展示完整委派结构，不要求每次备课都调用四个角色。

### 9.1 谁负责判断

- **主 Agent 做任务层面的选择：** 根据用户目标、已有材料、工具描述和角色目录，判断自己处理、调用 Tool、使用固定流程，还是提出独立子目标并委派预定义角色。
- **执行层做硬约束校验：** 当前业务是否允许委派，角色是否存在，数据与工具权限是否合规，计划版本是否已确认，依赖是否满足，是否还有并发名额和父子执行预算，任务是否已取消。
- 模型提出委派不等于获得执行权限。校验不通过则反馈限制、调整方案或结束，不让模型扩大授权。这个判断可以包含在同一次规划调用中，不必额外创建一个专门判断“要不要委派”的 Agent。

在第 2 节的计划里，`role_id` 表示主 Agent 选择的委派角色；执行层读取已确认计划中的任务项，条件满足时才创建子运行。角色目录是可选能力，不是每次必须运行的清单。

### 9.2 用什么判断规则

优先选择足够简单的执行方式：

| 任务情况 | 优先选择 | 背词课示例 |
| --- | --- | --- |
| 单次查询，输入输出明确 | Tool | 查询上次背词课的已学词表 |
| 多个查询但顺序和汇总规则固定 | 固定流程或工具组合 | 按确定的课程标识依次读取词表与作答，按规则合并 |
| 需要动态选择工具，但任务短、材料少或与主任务紧密关联 | 主 Agent 的 Agent Loop | 核对一个词的历史作答后，直接调整当前练习 |
| 有独立交付物，需要多轮取证或核对，拆分上下文有实际收益 | 子 Agent | 关联同一老师的历史课程、近期复习和有效偏好，整理带依据的学情分析与备课建议 |

主 Agent 可围绕三个问题做业务判断：

1. **能否形成独立子目标与可验收结果？** “形成带来源的学情摘要”是子目标，“调用一下查询接口”只是操作。
2. **是否需要根据中间结果自主选择下一步？** 如决定下钻哪个项目、核对什么冲突、何时补查或结束；若步骤完全固定，固定流程可能更合适。
3. **分拆是否值得交接开销？** 历史材料和取证过程较多、角色职责可独立时，隔离上下文有价值；简单任务由主 Agent 处理更直接。

这些是业务选型依据，不是一个自动准确的“复杂度分数”。工具数量、多轮调用、不同 Prompt 或能并行，都不能单独证明必须委派；主 Agent 同样具备工具选择与循环能力。

### 9.3 如何把选择传给执行层

下面是候选决策的简化示例。字段用于解释路由，不代表现有接口；也不要求在完整计划之外单独调用一次模型生成它：

```json
{
  "execution_mode": "subagent",
  "role_id": "learner_history",
  "instruction": "关联当前学生与同一老师的历史词汇课程、近期复习和有效偏好，核对相关性与冲突，形成有依据的备课建议。",
  "expected_output": ["已学内容与近期观察", "有效偏好及范围", "复习建议", "来源与信息缺口"],
  "routing_reason": "这是可独立验收的学情分析，需要按返回结果取证和核对，适合与教案规划分开管理上下文。"
}
```

接受这种委派选择时，将目标、角色和交付要求纳入计划任务项，并明确依赖与输入；通过第 9.1 节的校验后，按第 3 节装配子运行。若只是查看一次历史词表，则选择 Tool 路径，不为了展示多 Agent 把同一查询再包一层。

### 9.4 信息不够，怎么知道任务是否复杂

不需要先读取全部历史，再才能判断是否委派。首先根据明确的业务要求和已有摘要或元数据预判；用户只要记录还是需要分析，本身已经提供了重要区别。

若仍无法判断，可以在允许的流程里先做轻量查询，再根据返回内容选择继续由主 Agent 处理或提出更深入的委派。在本教案方案中，规划阶段本身不执行取证；轻量查询应作为经确认后执行的步骤，不能借复杂度判断绕过确认。若后续需要改变任务结构或关键范围，按计划修订规则处理。

也可能委派后只需一次工具调用就发现证据充分并结束。不能用实际调用次数反推 Agent 身份，关键是它是否具备独立目标、选择下一步与结束的能力；但如果业务始终只有固定查询，就应按 Tool 或固定流程讲，不强行包装成子 Agent。

### 9.5 面试口述

> 我把是否委派分成模型选择和程序校验两层。简单取数直接用 Tool，固定多步用流程，短的动态任务由主 Agent 自己执行 Loop；只有能形成独立交付物、需要多轮取证，且拆分上下文确有收益时，才选择预定义子 Agent。主 Agent 提出角色、目标和输出要求，执行层再检查计划确认、权限、依赖和预算，通过后才派发。因此进入规划不等于四个 Agent 全部启动，也不是模型说要委派就直接执行。

## 10. 子 Agent 到底通过什么接口调用，是不是 Tool

**两种入口都成立：编排层直接调用，或把委派入口封装成 Tool。本文的默认方案是前者。** 主 Agent 提出任务，不等于模型直接调用了另一个模型；真正创建子运行的是程序。

### 10.1 本文默认：编排层直接调用 Runtime

```text
主 Agent 输出计划 JSON，任务项包含 role_id
    ↓
程序校验 → 教练确认 → 按依赖选择就绪任务
    ↓
外层编排调用后端的子运行入口
    ↓
读取预定义角色配置，装配独立上下文与工具白名单
    ↓
复用 Agent Runtime 执行子 Agent Loop
    ↓
结构化结果交回执行层，再供主 Agent 或后续子任务使用
```

这里的子运行入口可以是普通后端函数或内部服务方法，不必注册为主模型可见的 Tool。主模型负责输出计划，外层程序负责执行它。第 8 节提到的“提交计划工具”只是接收候选计划，也不等于已经派发子 Agent。

### 10.2 可选入口：主 Agent 通过委派 Tool 调用

可以定义一个主 Agent 可见的委派工具，例如 `delegate_subtask`，接受预定义角色和本次目标。下面是工具调用的通用示意，工具名与字段不是现有接口声明：

```json
{
  "tool_name": "delegate_subtask",
  "arguments": {
    "subtask_id": "C0",
    "role_id": "learner_history",
    "goal": "分析当前学生与同一老师的历史词汇课程，形成带依据的复习建议。"
  }
}
```

```text
主模型产生委派 ToolCall
    ↓
执行层执行该工具的处理函数，校验角色、任务、权限与预算
    ↓
处理函数调用相同的 Runtime 子运行入口
    ↓
子 Agent 在独立上下文中执行自己的 Agent Loop
    ↓
处理函数把子任务结果包装成 ToolResult
    ↓
结果回填主 Agent，继续下一轮决策
```

此时从主 Agent 视角看，委派是一次工具调用；从执行层看，工具内部启动了一个独立 Agent 运行。可以用一个通用委派工具配合 `role_id`，不要求每个角色都定义一个新的工具。

正式主任务、计划版本和身份权限由执行层从当前任务上下文装配，校验 `subtask_id` 是否属于允许执行的计划任务，再创建本次执行尝试；模型传入的目标文本不产生新的授权。

如果在本教案流程中采用这个入口，仍要保留计划确认门槛：规划阶段不能借委派 Tool 提前执行取证；执行阶段也只能运行已允许的子目标、角色和数据范围，不能绕过第 7 节的截止时间与预算规则。

### 10.3 两种入口的共同底层

```text
编排层直接调用 ───┐
                  ├→ 受控子运行入口 → Agent Runtime → 独立子 Agent Loop
委派 Tool 处理函数 ┘
```

**Tool 是调用接口，子 Agent 是执行单元，两者不是互斥概念。** 判断是否真有子 Agent，要看内部是否存在独立目标、上下文、工具选择循环和结果交接，而不是入口是否叫 Tool。如果工具内部只是固定查询一次课程，那仍是普通查询工具，不因名称带 Agent 就变成委派。

本文继续以“已确认计划 → 外层编排 → Runtime 子运行”为默认讲解，不把示例委派工具写成已经注册的业务能力。若以后保留两种入口，应共用任务校验和幂等受理，避免同一个任务既被编排层派发、又被模型工具调用重复执行。

## 11. 例题子 Agent 怎样用 Skill 生成分层讲解

当教练不仅要例题与解析，还要求针对当前学生生成讲解草稿时，可以在既有 `examples_and_exercises` 角色中应用教学 Skill，不必新增一个“Skill 执行 Agent”。完整规程见 [Skill 示例：基于学情的例题分层讲解](Skill示例-基于学情的例题分层讲解.md)。这是对 C3 交付内容的可选扩展，不改前面的四任务计划示例，也不接管学生端原有 Workflow。

```text
主 Agent 在 C3 任务中明确“生成按学情组织的例题讲解草稿”
    ↓
执行层装配角色 Prompt、允许使用的 Skill、题目材料与相关学情证据
    ↓
examples_and_exercises 应用规程，按需补查、选择讲解深度
    ↓
返回讲解草稿、选择依据、验证计划与信息缺口
    ↓
主 Agent 汇总到教案，教练审阅
```

主 Agent 只需把目标和交付要求写进任务，不必每次重新生成整套教学规程。执行层可直接注入预定义 Skill，或通过角色已授权的读取工具按需加载；Skill 文本本身不会增加工具权限。输入优先使用 C0、C1、C2 的相关有效结果，不复制所有历史对话；若扩展涉及已确认计划的关键交付要求变化，仍按计划修订规则处理。

**固定方法交给 Skill，动态判断交给子 Agent，强制执行交给 Workflow。** Skill 固化“核对解析 → 拆知识点 → 对齐学情 → 选择策略 → 生成草稿 → 准备验证”的教学方法；子 Agent 决定如何选题、是否补查和何时结束；需要保证节点顺序、分支、等待或验收时，由程序化 Workflow 和执行层落实，而不是仅靠提示词要求。

只有答案和解析、没有有效学情时，不能直接声称已经生成了适合该学生掌握程度的讲解。应标明掌握未知，返回诊断建议或条件分层草稿；学生实际作答、理解验证与阶段推进继续由既有课堂或学生端 Workflow 管理。如果输入已完整且任务只是一次固定生成，主 Agent 直接使用 Skill 也可以，Skill 本身不是必须委派子 Agent 的理由。
