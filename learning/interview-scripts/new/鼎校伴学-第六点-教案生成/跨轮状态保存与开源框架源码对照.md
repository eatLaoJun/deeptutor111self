# 跨轮状态怎样保存：教案场景与开源框架源码对照

更新日期：2026-10-10

> 本文回答：缺课时时保存什么、谁来保存、下一轮怎么恢复，以及这与 Workflow 有什么区别。
> 教案字段与动作均为说明示例，不声明项目已有数据库表或真实接口名称。框架部分查阅官方仓库源码，只做静态对照，不代表已运行验证。
> 学习顺序：先读第 1、2 节；想看实际保存代码，先看第 4 节的 RAGFlow，再看 LangGraph 和 Hermes。无需因此引入任何框架，也不需要阅读本地 DeepTutor 实现。

## 1. 先明确：不是把四句话放在 Prompt 里，就叫保存状态

你看到的内容：

```text
当前任务：教案生成
当前阶段：等待补充信息
已确认条件：教材、目标词表
待补字段：课时
```

对应的是一个由应用维护的任务记录，而不是模型内部的一份永久记忆：

| 给人看的描述 | 程序记录的内容示例 | 谁负责最终确认 |
| --- | --- | --- |
| 当前任务：教案生成 | `task_type = lesson_planning` | 按钮入口或受理后的规划 ToolCall 确定 |
| 当前阶段：等待补充信息 | `phase = waiting_input` | 执行层受理澄清动作后写入 |
| 已确认教材、目标词表 | `request_constraints` 中的已知字段 | 来自用户输入或可信业务数据，经程序校验 |
| 缺课时 | `pending_fields = [lesson_minutes]` | 必填规则检查，或模型提出后由程序检查 |

**模型可以提出“还缺什么、下一步问什么”，但最终状态由程序保存。** 如果模型只输出“请问这节课多长”，而程序没有记录任务与问题，不能认为数据库里就已经有了待回复状态。

必填项也不必全部由模型判断。例如，按钮表单没有传课时，程序可以直接发现缺项；自然语言需求中的条件提取、模糊要求与额外信息缺口，则可以交给模型提出候选结果。

## 2. 用缺课时的场景，看一条完整保存与恢复链路

### 2.1 第一次请求：先形成候选动作，再提交任务状态

```text
用户点击“生成教案”或在对话中触发规划 Tool
    ↓
程序建立/关联任务 P1，并校验已有教材、词表与授权范围
    ↓
必填规则发现缺课时，或模型返回“需要补充课时”的结构化动作
    ↓
执行层检查缺项、允许动作和任务当前版本
    ↓
保存 P1：已有约束 + 待补字段 + 待回复问题 + 恢复阶段
    ↓
向用户显示：“这节课计划多长？”
结束本次模型调用，等待新的用户输入
```

模型请求澄清，可以通过已经注册的询问 Tool，也可以使用规定格式的结构化输出；二者都是把候选动作交给程序。这里不要求模型直接调用数据库，也不要求增加一个专门的“保存状态 Agent”。

以下是一份最小任务记录。`P1`、`S1`、`T1`、`W1`、`Q1` 都是示例标识；学生与老师的授权关联在实际业务中还要记录和校验，本例省略：

```json
{
  "task_id": "P1",
  "session_id": "S1",
  "task_type": "lesson_planning",
  "phase": "waiting_input",
  "resume_phase": "planning",
  "prompt_profile": "lesson_planning",
  "request_constraints": {
    "textbook_ref": "T1",
    "target_word_list_ref": "W1",
    "lesson_minutes": null
  },
  "pending_fields": ["lesson_minutes"],
  "pending_interaction": {
    "interaction_id": "Q1",
    "kind": "clarification",
    "question": "这节课计划多长？"
  },
  "plan": null,
  "task_version": 1
}
```

这不是 Plan。此时连课时都没确认，保存的是**规划前的任务上下文**，还没有生成或执行子任务。

### 2.2 保存到哪里：普通业务存储就能承担

可以将 `task_id`、会话关联、任务类型和状态设为便于查询的字段，将约束、待回复问题和计划等放在 JSON 字段或拆分记录中。具体选已有业务数据库还是其他持久化存储，要看项目现有设施；并不需要为这几个字段引入 LangGraph。

- 内存对象能承接同一进程内的等待，但进程退出会丢失。
- 数据库任务记录适合跨用户轮次读取；实际重启恢复还取决于恢复入口、权限校验与未完成任务的处理。
- Redis/Kvrocks 等也可用于状态或检查点，但过期时间、持久化配置和可用性决定能保留多久，不能只看到一次 `set` 就承诺永不丢失。

保存动作是程序里的普通存储调用。可以把等待状态与待回复问题一并提交，成功后再可靠地显示问题；若保存失败，要明确报错或有限重试，不能让用户回答一个程序已经忘记的问题。这是教案场景的处理原则，不声称下面三个框架都采用同一种事务。

### 2.3 下一轮“45 分钟”：读出原任务，合并后重新调用模型

```text
收到用户回复“45 分钟”
    ↓
按会话/任务关联找到 P1，检查归属、权限、Q1 和任务是否仍有效
    ↓
判断这是 Q1 的回答，而不是一个新需求
    ↓
提取候选课时 45，程序校验后写入 request_constraints
    ↓
清除已解决的待补字段与待回复问题
    ↓
必要条件齐全：phase 从 waiting_input 更新为 planning
    ↓
按 prompt_profile 与阶段装配指令，再调用主 Agent 生成候选 Plan
```

数字解析可以由程序完成；自然语言较复杂时可以让模型提取候选字段，再由程序校验。对于“改成复习语法，课时先不定”等回复，不能只机械抽一个数字，必须先识别是否修改了任务。

下一次模型看到的输入来自重新装配：

```text
主 Agent 基础职责
+ 本阶段规划指令
+ 已确认教材、词表和 45 分钟课时
+ 允许选择的子 Agent 角色目录
+ Plan 输出契约
```

`prompt_profile` 是预定义指令配置的标识，不是让用户或模型随意写入新的 System Prompt。程序读取任务并准备下一次模型请求，不需要先等模型发一个“请读取我的任务”的 Function Call。

### 2.4 任务状态、聊天记录和学生记忆不要混为一谈

| 内容 | 用途 |
| --- | --- |
| 聊天记录 | 保留用户说过什么、模型回答了什么、工具返回了什么 |
| 教案任务状态 | 明确当前处理哪个任务、等待什么、约束和版本是什么 |
| 学生长期记忆 | 保留经确认的学习事实、偏好与薄弱点等跨任务信息 |

聊天记录可以辅助理解，却不是任务状态的唯一来源。即使聊天历史被裁剪，程序仍能拿到 P1 的待补字段；一次备课任务里的“等待课时”也不应默认写成学生长期画像。

## 3. 三个项目是否有类似机制

有，但并不是三个项目都原生提供“教案任务 + 待补课时”这个业务模型：

| 本次选取的源码路径 | 已有机制 | 与教案场景的关系 |

## 4. RAGFlow：先看它怎样把一次运行标为“等待用户”

### 4.2 更完整的保存与恢复链路

```text
配置中的 UserFillUp 节点需要用户输入
    ↓
UserFillUpNodeBody 返回中断
    ↓
配置好的 Eino 执行与检查点机制保存执行状态
    ↓
服务层记录 interrupt_id、等待状态，并保存会话/DSL 信息
    ↓
后续请求读回 interrupt_id 与用户输入
    ↓
ResumeWithData + 相同检查点标识
    ↓
UserFillUp 节点收到恢复数据，继续产生输出
```

## 5. LangGraph：图状态由检查点保存，用户输入用来恢复中断

### 5.1 主链路

```text
应用定义 State，并写入需要保留的业务字段
    ↓
某节点需要用户输入，调用 interrupt(问题)
    ↓
没有恢复值：抛出图中断，由运行时配合 checkpointer 保存检查点
    ↓
应用向用户显示问题
    ↓
用户回复后：使用相同 thread_id，提交 Command(resume=回复)
    ↓
读取该线程的检查点，重新执行中断节点
    ↓
interrupt 得到恢复值，应用校验并继续
```

相同线程、配置 checkpointer，以及中断节点从头执行的语义，见 [官方 Interrupts 说明](https://docs.langchain.com/oss/python/langgraph/interrupts)。

### 5.2 对应源码：重点看“谁存”和“谁读”

| 源码位置 | 功能与阅读要点 |
| --- | --- |
| [`libs/langgraph/langgraph/types.py:1004-1046`](https://github.com/langchain-ai/langgraph/blob/6aa0afba682b0308fbcace31f66fb532978d4dca/libs/langgraph/langgraph/types.py#L1004-L1046)，`interrupt` 的执行部分 | 有恢复值则返回；没有则抛出 `GraphInterrupt`。这个函数本身不是直接执行数据库写入 |

| [`libs/langgraph/langgraph/pregel/_loop.py:1762-1817`](https://github.com/langchain-ai/langgraph/blob/6aa0afba682b0308fbcace31f66fb532978d4dca/libs/langgraph/langgraph/pregel/_loop.py#L1762-L1817)，同步运行入口 | 调用 checkpointer 读取已有检查点，并恢复运行所需状态；未配置 checkpointer 时没有这条持久化读取路径 |

**能借鉴什么：** 应用负责定义和更新业务状态，框架负责检查点与运行恢复。不是模型把自然语言一说，框架就自动识别、校验并存入 `pending_fields`。

**两个容易误解的点：**

- 使用内存 checkpointer 不等于能跨进程恢复；采用 PostgreSQL 等持久化后端还要正确配置与使用。普通局部变量也不会因为用了框架就全部被保存。
- 中断节点会重新执行，不是简单保留 Python 调用栈后从下一行续跑。中断前的副作用需要拆开或处理幂等，不能据此承诺“绝不重复执行”。

LangGraph 可以承载动态路由和模型生成的任务，但允许的节点、状态契约及调用接口仍由程序提供。使用图框架，不代表每个任务的业务步骤都必须完全固定；不使用它，也不代表无需管理状态。

```text
模型选择澄清工具
    ↓
平台回调记录待回复问题，等待 Event
    ↓

    ↓

```

这证明**动态询问不必预先写成固定的教案业务 Workflow**。但是，就这个 Gateway 等待实现而言，内存字典和 Event 本身不会因会话记录存入 SQLite，就自动变成跨重启可恢复的执行检查点。

这里用户发来下一条消息，可能是在完成同一个正在等待的工具调用，而不是新启动一次主 Agent 任务。与第 2 节“结束本次调用，持久化任务后等待下一请求”的方案有区别；等待过程中不代表模型持续生成。

补充：Hermes 也会[保存 System Prompt 内容及其哈希](https://github.com/NousResearch/hermes-agent/blob/dce1e9b37581dd62e480a9064dc04a709c2940d3/hermes_state.py#L512-L520)，并可[随会话读取](https://github.com/NousResearch/hermes-agent/blob/dce1e9b37581dd62e480a9064dc04a709c2940d3/hermes_state_sessions.py#L866-L876)。这属于应用存储与恢复输入，仍不是模型服务自动永久保留该 Prompt。

## 7. 所以，这算 Workflow 吗？哪些东西由模型决定？

**可以说有“有状态编排”，但不能直接说“整个分层都由模型自己决定”。** 要区分三件事：

| 层次 | 作用 | 是否由模型临时生成 |
| --- | --- | --- |
| 业务 Workflow | 如学生辅导的诊断、讲解、练习与理解验证，规定业务阶段和通过条件 | 该固定业务骨架不是临时生成的 |
| 运行状态管理 | 如运行中、等待用户、完成、失败；负责保存、续接、取消和执行边界 | 允许的状态与执行机制由程序提供 |
| 本次 Plan / Agent 决策 | 如是否补课时、研究哪些内容、委派谁、任务依赖、是否收反馈 | 可以由模型按需求和结果提出，再由程序校验 |

例子：

```text
模型决策：本次缺课时，需要先询问用户
程序动作：受理询问，保存 waiting_input 和待回复问题

模型决策：教材材料与学情可以先查，个性化例题等它们返回后再做
程序动作：校验计划，按已确认的依赖安排子任务

模型决策：本次草稿值得收集教练反馈
程序动作：关联提问与草稿版本，记录等待；收到回复后再续接
```

模型决定或提出的是**下一步业务动作与本次任务组织**；程序执行的是**受限状态转换、存储、等待和调度**。任务记录里的 `phase` 更像“进度标记”，不是把四个子 Agent 的固定调用顺序重新命名一遍。

如果把所有编排都广义称作 Workflow，也可以；但面试中最好说清：**固定的是运行机制和治理边界，动态的是本次计划、任务依赖与反馈选择。** 有 `waiting_input` 状态，并不能单独证明存在一套固定教学 Workflow。

### 面试口述

> 我把教案规划做成有状态任务。模型可以识别信息缺口并提出澄清动作，执行层校验后保存已确认约束、待补字段和待回复问题。用户下一轮回复时，程序关联原任务、合并校验输入，再重新装配对应阶段的 Prompt。这里固定的是状态管理、权限和预算，动态的是计划内容、子任务依赖和是否征求反馈，不是把每份教案的步骤全部写死，也不依赖模型自己记住上一轮。
