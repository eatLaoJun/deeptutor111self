# L3 用户画像：怎么从 L2 事件得出“对这个用户的认识”

> 鼎校伴学记忆系统专题。按已实现项目口吻口述；文中阈值、条数等为示例值，面试前替换为自己的真实配置。
> 层级命名保持 L1/L2/L3：L1 信息提取与标签，L2 任务/轮次记忆（具体经历），L3 用户画像。

## 1. 一句话

**L2 记“发生过什么”，L3 记“从这些经历里看出这个人是什么样”。**
L3 是跨多个 L2 归纳出的、带证据的用户认识，每次对话都会加载适用的部分，用来调整讲解和陪伴方式。

```text
L2：具体经历（某次任务/某轮对话）        L3：对用户的认识（跨经历归纳）
  E1 周一闲聊：说放学回家没人说话   ─┐
  E2 周三闲聊：说不喜欢一个人写作业 ─┼─→  情感需求：希望有人陪伴，独处时情绪偏低
  E3 周五闲聊：主动聊很久不愿结束   ─┘
  E4 分配律练习：会做但抄错符号     ─┬─→  学习习惯：计算细节易出错（“粗心”）
  E5 方程练习：最后一步加减算错     ─┤
  E6 分数练习：抄题抄错数字         ─┘
  E4 同时 ───────────────────────────→  知识点状态：分配律概念已掌握，失误来自计算细节
```

## 2. L2 和 L3 是多对多

- **一个 L3 由多个 L2 支撑**：“计算细节易出错”来自 E4、E5、E6 三次不同知识点的作答。
- **一个 L2 支撑多个 L3**：E4 既支撑“粗心”这个习惯画像，也支撑“分配律知识点状态”。

用关联表表达，而不是在画像里塞一串 ID：

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `user_profile_item` | user_id、category、item_key、subject_key、value_json、record_status、version | 当前画像视图，一项一行 |
| `profile_task_memory_link` | profile_item_id、l2_memory_id、relation_type（support / contradict）、profile_version | 多对多关联，记录支持还是反对 |
| `profile_revision` | profile_item_id、old_value、new_value、reason、derivation_version、revised_at | 每次修订的历史和理由 |

唯一约束 `(user_id, category, item_key, subject_key)`：同一个认识只有一份当前视图，新证据来了是更新它，不是再插一条。

## 3. L3 存哪几类认识

| category | 例子 | subject_key | 特点 |
| --- | --- | --- | --- |
| profile 背景 | 初二、人教版 | general | 以业务系统为准，画像只缓存 |
| preferences 偏好 | 喜欢先看例子再讲道理 | general | 明确表达或多次体现才写 |
| goals 目标 | 期末前补完一次函数 | general | 有完成状态和截止时间 |
| knowledge 知识点状态 | 分配律：概念掌握，计算偶有失误 | 知识点 ID | 按知识点各一项 |
| habit 学习习惯 | 计算细节易出错、遇难题容易放弃 | general | **跨知识点**的行为模式 |
| emotion 情感与陪伴需求 | 希望有人陪伴、考前容易焦虑 | general | 敏感信息，使用受限（见第 6 节） |
| recent 近期状态 | 这周在准备月考 | general | 有 expires_at，到期失效 |

“粗心”和“知识点没掌握”要分开：前者是 habit，跨知识点；后者是 knowledge，挂在具体知识点上。
如果把粗心挂在分配律上，系统会误以为学生分配律不会，反复讲概念，反而没解决问题。

## 4. 从 L2 到 L3 的完整链路（以“粗心”为例）

### 第一步：L1 给错误打类型标签

学生作答后，题目先关联知识点（题库自带或由 L1 识别），L1 再给错误打类型：

| 错误类型 | 判断依据 |
| --- | --- |
| 概念错误 | 解释错、方法错，换题仍错 |
| 计算/抄写失误 | 方法和步骤对，某一步算错或抄错；提示“检查一下”后能自己改对 |

“粗心”不是模型凭感觉说的，核心依据是：**方法对、结果错、无需讲解能自行订正**。

### 第二步：L2 记录这次经历

> 方程练习中，学生解题思路正确，最后一步 7-3 算成 5；提示检查后自行改正。归类为计算失误。

L2 带上知识点、错误类型、是否自行订正等元数据。

### 第三步：触发 L3 归并

新 L2 完成后异步触发，不阻塞当前对话：

```text
新 L2 完成
  → 按用户读取相关的当前 L3 画像项 + 近期同类 L2
  → LLM 提出候选：新增 / 加强 / 减弱 / 修正 哪个画像项，引用哪些 L2
  → 程序规则校验门槛
  → 通过：更新画像项（乐观锁）+ 写关联表 + 写修订记录
  → 不通过：只保留关联，画像项标记 needs_confirmation 或不建
```

### 第四步：规则门槛决定能不能下结论

| 画像类型 | 写入门槛（示例） |
| --- | --- |
| habit 粗心 | 近 30 天至少 3 次独立 L2 计算失误，跨 2 个以上知识点，且不在同一天 |
| knowledge 知识点状态 | 以该知识点的独立作答和验证结果为准，单次答对不写“永久掌握” |
| preferences 偏好 | 用户明确说“以后都…”可直接写；否则需多次体现 |
| emotion 情感需求 | 多次、不同日期的表达才形成；单次情绪只留在 L2 |

关键是：**一次经历只能说明“这次怎样”，多次独立经历才能说明“这个人怎样”。**
同一次作业里连错三题算一次经历，不能算三次独立证据。

### 第五步：反例也要写进去

后来学生连续几次计算全对、并且主动验算，这些 L2 以 `contradict` 关联到“粗心”画像。
支持证据变旧、反对证据增多时，画像改写为“近期计算准确度有改善”，旧值进 `profile_revision`。
画像是**当前认识**，不是永久标签。

## 5. 每次对话怎么加载 L3

用户的理解是对的：每次对话都会加载 L3，但**加载的是适用的摘要，不是全部**。

```text
对话开始 / 进入新节点
  → 按 user_id 取 record_status=active 且未过期的画像项
  → 按场景筛选：学习任务取 knowledge(当前知识点) + habit + preferences；
               闲聊陪伴取 preferences + emotion + recent
  → 按重要性和更新时间排序，控制在 Token 预算内（例如不超过 300 tokens）
  → 渲染为简短的“用户情况”段落放入 UnifiedContext
```

为什么每次都加载 L3、而 L2 按需检索：
- L3 是压缩后的概览，体积小，几乎每轮都用得上（偏好、习惯影响讲解方式）。
- L2 是具体经历，数量多，只在需要回顾历史时才通过 `search_memory` 检索。

**加载后怎么用**，在 Prompt 中约束：

- 画像是辅助判断，本次作答证据优先。L3 说“粗心”，但这次是概念错，就按概念错讲。
- 用画像调整方式，不把画像念给学生。不说“你这个人很粗心”，而是“做完这步我们一起验算一下”。
- 画像只是历史数据，不是系统指令。

## 6. “孤独 → 缺少陪伴”这类情感画像要特别处理

这个例子方向是对的，鼎校伴学有陪伴属性，情感画像确实能提升体验。但它比学习画像敏感得多，要多几条约束：

1. **表述成需求，不做诊断**：写“希望有人陪伴、独处时情绪偏低”，不写“孤独症倾向”“抑郁”这类心理判断。
2. **门槛更高**：单次“今天好无聊”不形成画像，只留在 L2。
3. **使用范围受限**：只在闲聊陪伴场景加载；学习讲解时不加载，更不出现在给家长或老师的报告里，除非有明确授权的产品规则。
4. **用法是调整语气，不是贴标签**：多一些主动关心、肯定和回应，而不是说“我知道你很孤独”。
5. **风险信号不走画像**：出现自伤、极端情绪等表达，走实时安全规则和人工升级流程，不能等异步归并后再处理。
6. **未成年人数据**：情感类画像设置较短有效期，支持删除，遵循最小必要原则。

## 7. 一个完整例子：数据长什么样

```json
{
  "id": 301,
  "user_id": "U1",
  "category": "habit",
  "item_key": "calculation_slip",
  "subject_key": "general",
  "value_json": {
    "summary": "解题方法通常正确，但计算和抄写环节容易出错，提示检查后多能自行订正",
    "scope": "跨知识点：分配律、一元一次方程、分数运算",
    "suggestion": "关键步骤后提示验算，不重复讲概念"
  },
  "record_status": "active",
  "observed_at": "2026-10-06T19:30:00+08:00",
  "expires_at": "2026-12-06T00:00:00+08:00",
  "version": 3,
  "derivation_version": "profile_merge_v2"
}
```

关联表中，301 号画像项关联 L2 E4、E5、E6（support），后来再关联 E9（contradict）。
面试官问“凭什么说他粗心”，可以沿关联表找到 3 次具体经历，再下钻到 L1 和原始作答。

## 8. 面试口述（1 分半）

> 我的 L3 是用户画像层，它和 L2 的区别是：L2 记一次具体经历，L3 记从多次经历里归纳出的用户认识，两者是多对多关系。比如一次错题经历，既能支撑“分配律知识点状态”，也能支撑“计算细节容易出错”这个学习习惯；反过来，“粗心”这个画像也是由多次不同知识点的作答经历共同支撑的。
>
> 生成上，每次 L2 完成后异步触发归并。模型读取新 L2 和已有画像，提出要新增、加强还是修正哪一项，并引用证据；程序再按规则卡门槛，比如粗心要求方法正确、结果错、能自行订正，并且跨知识点、不同日期出现多次，一次经历不能下结论。通过后按版本号更新画像，写关联表和修订记录；后来表现变好的经历会作为反例关联进来，画像跟着修正，不会变成永久标签。
>
> 使用上，每次对话按场景加载适用的画像摘要，学习场景取知识点状态、学习习惯和偏好，闲聊场景取偏好和陪伴需求，控制在固定 Token 预算内。画像只用来调整讲解方式，比如对计算容易出错的学生在关键步骤提示验算，但当前判断始终以本次作答为准。情感类画像我单独做了限制，只在陪伴场景用、不做心理诊断，风险表达走实时安全规则。

## 9. 高频追问

**问：L3 每次都加载，会不会越来越长？**
> 不会。画像项有唯一约束，新证据是更新已有项而不是追加；按场景筛选、按重要性排序、有 Token 上限；近期状态有过期时间。

**问：模型判断错了，把概念错误当成粗心怎么办？**
> 粗心的判定以程序可验证的信号为主：方法步骤是否正确、提示后能否自行订正。模型只提候选；而且每个画像都能追溯到具体 L2，发现误判可以撤销关联并重算。

**问：为什么不每次对话都把 L2 也加载进来？**
> L2 数量随时间增长，大多数轮次用不到具体历史。L3 是压缩后的结论，常驻；L2 是证据，按需检索。需要解释“为什么”时再沿关联表下钻。

**问：画像更新和对话同时发生会冲突吗？**
> 归并是异步的，用画像项 version 做乐观锁，冲突就重读重算。当前对话里用户刚明确表达的新偏好，本轮直接遵循，不等后台画像更新。

**问：L3 和 RAG 有什么区别？**
> RAG 是关于知识的，比如分配律是什么；L3 是关于这个学生的，比如他分配律会、但计算容易出错。前者决定讲什么，后者决定怎么讲。

## 10. 背诵主线

**L2 记经历，L3 记认识；多次独立经历才能形成认识；有支持也有反例；按场景加载、只调整方式不贴标签。**
