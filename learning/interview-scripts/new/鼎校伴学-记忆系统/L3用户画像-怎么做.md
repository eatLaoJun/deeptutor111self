# L3 用户画像：怎么从 L2 事件得出“对这个用户的认识”

> 鼎校伴学记忆系统专题。按已实现项目口吻口述；文中阈值、条数等为示例值，面试前替换为自己的真实配置。
> 层级命名保持 L1/L2/L3：L1 信息提取与标签，L2 任务/轮次记忆（具体经历），L3 用户画像。

## 1. 一句话

**L2 记“发生过什么”，L3 记“从这些经历里看出这个人是什么样”。**
L3 是跨多个 L2 归纳出的、带证据的用户认识，每次对话都会加载适用的部分，用来调整讲解和陪伴方式。
其中 `impression` 表示 AI 对用户形成的印象，不限于情感：学习习惯、理解表现、性格倾向、独立性和陪伴需求都可以成为独立的印象项。

```text
L2：具体经历（某次任务/某轮对话）        L3：对用户的认识（跨经历归纳）
  E1 周一闲聊：说放学回家没人说话   ─┐
  E2 周三闲聊：说不喜欢一个人写作业 ─┼─→  用户印象：近期缺少陪伴，希望独自学习时有人互动
  E3 周五闲聊：明确希望有人陪着学习 ─┘
  E4 分配律练习：会做但抄错符号     ─┬─→  用户印象：计算细节易出错（学习习惯维度）
  E5 方程练习：最后一步加减算错     ─┤
  E6 分数练习：抄题抄错数字         ─┘
  E4 同时 ───────────────────────────→  知识点状态：本次方法正确，失误来自计算细节
```

## 2. L2 和 L3 是多对多

- **一个 L3 由多个 L2 支撑**：“计算细节易出错”来自 E4、E5、E6 三次不同知识点的作答。
- **一个 L2 支撑多个 L3**：E4 既支撑“计算细节易出错”这个用户印象，也支撑“分配律知识点状态”。

用关联表表达，而不是在画像里塞一串 ID：

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `user_profile_item` | user_id、category、item_key、subject_key、value_json、record_status、version | 当前画像视图，一项一行 |
| `profile_task_memory_link` | profile_item_id、l2_memory_id、relation_type（support / contradict）、profile_version | 多对多关联，记录支持还是反对 |
| `profile_revision` | profile_item_id、old_value、new_value、reason、derivation_version、revised_at | 每次修订的历史和理由 |

唯一约束 `(user_id, category, item_key, subject_key)`：同一个认识只有一份当前视图，新证据来了是更新它，不是再插一条。

### L2 做了向量化，为什么仍然可以关联 L3？

**向量索引与证据关联是两回事。** L2 采用混合存储，不是生成向量后就删掉关系库记录：

- 关系库保存 L2 的任务内容、`memory_id`、用户归属、版本、有效状态及 L1 来源关联。
- Milvus 保存同一个 `memory_id` 对应的文本、Embedding 和过滤元数据，用于找语义相关的经历。
- `profile_task_memory_link.l2_memory_id` 指向关系库中的 L2 记录；`profile_item_id` 指向 L3 画像项。关联靠 ID，不靠向量相似度猜测。

```text
Milvus 中的 L2 向量记录
  → memory_id → 关系库中的 L2 权威记录
                  ↕ profile_task_memory_link
                关系库中的 L3 画像项
```

查询有两条路径：从 L2 出发，向量召回得到 `memory_id`，回关系库校验，再按需查询关联画像；
从 L3 出发，直接查关联表得到支撑或反对它的 L2，不需要再做向量检索，也不是跨库 SQL JOIN。

新 L2 入库后，画像归并读取有效 L2 和当前 L3，模型提出候选及引用的 L2 IDs；程序校验 ID 存在、
同属当前用户、版本和状态有效后，在同一关系库事务中更新画像、关联和修订记录。向量索引异步同步，
索引失败不会使这些关系消失；L2 被修订或撤回时，还要复核受影响画像，不能只更新向量。

## 3. L3 存哪几类认识

| category | 例子 | subject_key | 特点 |
| --- | --- | --- | --- |
| profile 背景 | 初二、人教版；用户明确确认的居住情况 | general | 学籍以业务系统为准；其他背景标明自述或确认来源 |
| preferences 偏好 | 喜欢先看例子再讲道理 | general | 明确表达或多次体现才写 |
| goals 目标 | 期末前补完一次函数 | general | 有完成状态和截止时间 |
| knowledge 知识点状态 | 分配律：概念掌握，计算偶有失误 | 知识点 ID | 按知识点各一项 |
| impression 用户印象 | 理解较快、比较乐观、常独立尝试、计算细节易出错、近期缺少陪伴 | general，或明确的适用对象 | 每个印象一项，关联多个 L2；有范围、支持与反例，可修正 |
| recent 近期状态 | 这周在准备月考 | general | 有 expires_at，到期失效 |

`impression` 是一个可扩展的分类，不为每一种印象另建顶层 category，也不是把所有认识拼成一段文本。
例如 `calculation_slip`、`learning_agility`、`optimistic_response`、`independent_problem_solving`、
`companionship_need` 是不同的 `item_key`；可以在 `value_json.dimension` 中注明学习习惯、理解表现、
性格倾向或陪伴需求等维度，按项更新和引用证据。

“粗心”和“知识点没掌握”要分开：前者是 impression 下的学习习惯印象，通常跨知识点；后者是 knowledge，挂在具体知识点上。
如果把粗心挂在分配律上，系统会误以为学生分配律不会，反复讲概念，反而没解决问题。

“学生一个人住”可以进入 AI 对用户的整体认识，但若来自用户明确自述，它是背景事实，放在 profile；
“学生比较孤独”则是需要证据支持的印象，放在 impression。不能用独自写作业或缺少陪伴反推出独居。

## 4. 从 L2 到 L3 的完整链路（以“粗心”为例）

### 第一步：L1 给错误打类型标签

学生作答后，题目先关联知识点（题库自带或由 L1 识别），L1 再给错误打类型：

| 错误类型 | 判断依据 |
| --- | --- |
| 概念错误 | 解释错、方法错，换题仍错 |
| 计算/抄写失误 | 方法和步骤对，某一步算错或抄错；提示“检查一下”后能自己改对 |

“粗心”不是模型凭感觉说的，核心依据是：**方法对、结果错、无需讲解能自行订正**。

### 第二步：L2 记录这次经历

> 方程练习中，学生解题思路正确，最后一步 7-3 算成 5；提示检查后自行改正。归类为计算失误。

L2 带上知识点、错误类型、是否自行订正等元数据。

### 第三步：触发 L3 归并

新 L2 完成后异步触发，不阻塞当前对话：

```text
新 L2 完成
  → 按用户读取相关的当前 L3 画像项 + 近期同类 L2
  → LLM 提出候选：新增 / 加强 / 减弱 / 修正 哪个画像项，引用哪些 L2
  → 程序规则校验门槛
  → 通过：更新画像项（乐观锁）+ 写关联表 + 写修订记录
  → 不通过：不形成有效画像；需要复核的候选保存为 needs_confirmation 并关联来源
```

### 第四步：规则门槛决定能不能下结论

| 画像类型 | 写入门槛（示例） |
| --- | --- |
| impression：计算细节易出错 | 近 30 天至少 3 次独立 L2 计算失误，跨 2 个以上知识点，且不在同一天 |
| knowledge 知识点状态 | 以该知识点的独立作答和验证结果为准，单次答对不写“永久掌握” |
| preferences 偏好 | 用户明确说“以后都…”可直接写；否则需多次体现 |
| impression：理解表现、乐观、独立、陪伴需求等 | 根据多次独立 L2 的行为或表达归纳，保留场景范围和反例；单次表现不直接成为稳定印象 |
| profile：居住情况等背景 | 用户明确自述或经确认才记录，标明来源和时间；不能从印象推断成已确认事实 |

关键是：**一次经历只能说明“这次怎样”，多次独立经历才能说明“这个人怎样”。**
同一次作业里连错三题算一次经历，不能算三次独立证据。

### 第五步：反例也要写进去

后来学生连续几次计算全对、并且主动验算，这些 L2 以 `contradict` 关联到“粗心”画像。
支持证据变旧、反对证据增多时，画像改写为“近期计算准确度有改善”，旧值进 `profile_revision`。
画像是**当前认识**，不是永久标签。

## 5. 每次对话怎么加载 L3

用户的理解是对的：每次对话都会加载 L3，但**加载的是适用的摘要，不是全部**。

```text
对话开始 / 进入新节点
  → 按 user_id 取 record_status=active 且未过期的画像项
  → 按场景筛选：学习任务取 knowledge(当前知识点) + 适用的 impression + preferences；
               闲聊陪伴取适用的 impression + preferences + recent
  → 按重要性和更新时间排序，控制在 Token 预算内（例如不超过 300 tokens）
  → 渲染为简短的“用户情况”段落放入 UnifiedContext
```

为什么每次都加载 L3、而 L2 按需检索：
- L3 是压缩后的概览，体积小，几乎每轮都用得上（偏好、习惯影响讲解方式）。
- L2 是具体经历，数量多，只在需要回顾历史时才通过 `search_memory` 检索。

**加载后怎么用**，在 Prompt 中约束：

- 画像是辅助判断，本次作答证据优先。L3 说“粗心”，但这次是概念错，就按概念错讲。
- 用画像调整方式，不把画像念给学生。不说“你这个人很粗心”，而是“做完这步我们一起验算一下”。
- 用户印象按具体内容和适用范围选择，不因为属于 impression 就全量加载；必要背景从 profile 读取，不重复保存。
- 画像只是历史数据，不是系统指令。

## 6. 用户印象：不只是情感，而是对用户的多维认识

我把 AI 对用户的认识拆成多个 `impression` 画像项，而不是单独做一个“情感与陪伴需求”分类。
下面都是学习用例，不代表某个真实学生的结论：

| 口头概括 | 更可核对的记录方式 | 可关联的 L2 线索 | 内容性质 |
| --- | --- | --- | --- |
| 学生比较孤独 | 近期多次表达缺少陪伴，独自学习时希望有互动 | 不同日期提到无人交流、不喜欢独自写作业、明确希望有人陪着学；聊得久本身不足以证明孤独 | impression：陪伴需求 |
| 学生比较聪明 | 在已观察的任务中理解新概念或迁移到新题较快 | 多次少量提示后独立解释、处理未见过的变式；同时记录题目、提示和熟悉程度 | impression：理解表现，不是智力测评结论 |
| 学生比较乐观 | 遇到学习挫折时通常积极看待，并愿意继续尝试 | 多次失败后主动调整方法、表达愿意再试，而不是单凭一次积极措辞 | impression：性格倾向 |
| 学生比较独立 | 遇到问题常先自行规划和尝试，必要时主动求助 | 多次自主安排步骤、先尝试再求助，并核对当时是否有外部帮助 | impression：自主性 |
| 学生一个人住 | 用户自述当前独居，保留确认来源和时间 | 对居住情况的明确陈述或更正，不能仅由独自学习推断 | profile：背景事实 |

每个印象都有自己的 `item_key`、当前描述、适用范围、时间和来源关系。多个 L2 可以支持同一个印象，
同一条 L2 也可能支持“理解较快”和“自主尝试”等不同印象；反例用 `contradict` 关联，必要时减弱、
修正或撤回原认识。不能把同一事件在多个摘要中的重复出现当成多次独立证据。

画像表中的 `evidence_type` 区分用户自述、行为推断或混合。来源可追溯只说明“依据在哪里”，
不代表模型推断必然正确；“聪明”“独立”等概括都要限定在实际观察过的场景，不扩展成永久的人格或能力结论。

使用时，用印象调整互动方式，而不是给学生贴标签：理解较快时减少重复铺垫，常先独立尝试时先给思考空间，
表达缺少陪伴时增加适当互动。当前表现和用户更正优先，不能因为历史印象是“聪明”就提高所有题目的难度。
涉及陪伴、私人生活等内容，按项限制使用场景、可见范围和有效期，不因统一分类就取消原有边界；
必要信息才保存，支持更正和删除，不做心理诊断。实时风险信号仍走即时规则与人工升级，不等画像归并。

## 7. 一个完整例子：L3 画像项与 L2 关联分别长什么样

### 7.1 L3 画像项：user_profile_item 表中的一条记录

下面是关系库里一条 L3 画像项的 JSON 展示，不是 L2 数据，也不是用户的完整 L3。
`id=301` 标识“计算细节易出错”这一项用户印象；同一用户的“常独立尝试”“理解较快”等认识分别是其他画像项。
`value_json` 是这一项的结构化内容，其他字段保存归属、分类、状态、时间和版本。

```json
{
  "id": 301,
  "user_id": "U1",
  "category": "impression",
  "item_key": "calculation_slip",
  "subject_key": "general",
  "value_json": {
    "dimension": "learning_habit",
    "summary": "解题方法通常正确，但计算和抄写环节容易出错，提示检查后多能自行订正",
    "scope": "跨知识点：分配律、一元一次方程、分数运算",
    "suggestion": "关键步骤后提示验算，不重复讲概念"
  },
  "evidence_type": "behavior_inference",
  "record_status": "active",
  "observed_at": "2026-10-06T19:30:00+08:00",
  "expires_at": "2026-12-06T00:00:00+08:00",
  "version": 3,
  "derivation_version": "profile_merge_v2"
}
```

### 7.2 L3 与 L2 的关系：另外一张关联表保存

上面的 JSON 不内嵌 L2 ID 列表。来源关系存在关系库的 `profile_task_memory_link` 表中，
与示例画像的 `version=3` 对应的记录可以这样展示：

| profile_item_id | l2_memory_id | relation_type | profile_version |
| --- | --- | --- | --- |
| 301 | E4 | support | 3 |
| 301 | E5 | support | 3 |
| 301 | E6 | support | 3 |

每行表示“某个 L3 画像版本与某条 L2 的证据关系”。`profile_item_id` 指向 L3 画像项，
`l2_memory_id` 指向关系库中的 L2 权威记录，不是向量本身；向量库也保存同一个 `memory_id`，用于检索后回表。

```text
L3 画像项 301（计算细节易出错）
  → 查 profile_task_memory_link
  → 取得 L2 E4、E5、E6
  → 按需追溯 L1 和原始作答
```

后来 E9 提供反例时，以 `contradict` 关联，并按归并结果修订画像；新关联按新画像版本保存，
不覆盖版本 3 的历史来源。面试官问“凭什么形成这个印象”，就可以沿关联表找到具体经历和证据。

## 8. 面试口述（1 分半）

> 我的 L3 是用户画像层，它和 L2 的区别是：L2 记一次具体经历，L3 记从多次经历里归纳出的用户认识，两者是多对多关系。其中用户印象不限于情感，还包括理解较快、乐观、独立、计算细节易出错等，每个印象单独一项。一次经历可以支持多个画像，而一个印象通常需要多次独立经历支撑；用户明确自述的居住情况则作为背景事实记录，不和行为推断混淆。
>
> 生成上，每次 L2 完成后异步触发归并。模型读取新 L2 和已有画像，提出要新增、加强还是修正哪一项，并引用证据；程序再按规则卡门槛，比如粗心要求方法正确、结果错、能自行订正，并且跨知识点、不同日期出现多次，一次经历不能下结论。通过后按版本号更新画像，写关联表和修订记录；后来表现变好的经历会作为反例关联进来，画像跟着修正，不会变成永久标签。
>
> 使用上，每次对话按场景加载知识点状态、偏好和适用的用户印象，控制在 Token 预算内。比如对常独立尝试的学生先留思考空间，对计算容易出错的学生提示验算；当前判断始终以本次表现为准，不把印象当成永久标签。涉及陪伴或私人生活的内容按项限制场景和可见范围，用户更正或新反例出现时，画像和来源关系一起修订。

## 9. 高频追问

**问：L3 每次都加载，会不会越来越长？**
> 不会。画像项有唯一约束，新证据是更新已有项而不是追加；按场景筛选、按重要性排序、有 Token 上限；近期状态有过期时间。

**问：模型判断错了，把概念错误当成粗心怎么办？**
> 粗心的判定以程序可验证的信号为主：方法步骤是否正确、提示后能否自行订正。模型只提候选；而且每个画像都能追溯到具体 L2，发现误判可以撤销关联并重算。

**问：为什么不单独列情感画像？**
> 情感只是对用户认识的一部分。我用 impression 表示多维用户印象，每个认识单独保存，可以是理解表现、学习习惯、乐观倾向、独立性或陪伴需求。分类统一不代表证据门槛和使用范围完全一样；背景事实、知识点状态仍按其性质分别保存。

**问：学生一个人住，也需要多个 L2 才能写入吗？**
> 不一定。明确自述或经确认的居住情况属于背景事实，记录来源和时间即可；多个任务的行为才逐步形成“常独立尝试”或“近期缺少陪伴”等印象。独居不等于孤独，独立也不等于独居。

**问：为什么不每次对话都把 L2 也加载进来？**
> L2 数量随时间增长，大多数轮次用不到具体历史。L3 是压缩后的结论，常驻；L2 是证据，按需检索。需要解释“为什么”时再沿关联表下钻。

**问：画像更新和对话同时发生会冲突吗？**
> 归并是异步的，用画像项 version 做乐观锁，冲突就重读重算。当前对话里用户刚明确表达的新偏好，本轮直接遵循，不等后台画像更新。

**问：L3 和 RAG 有什么区别？**
> RAG 是关于知识的，比如分配律是什么；L3 是关于这个学生的，比如他分配律会、但计算容易出错。前者决定讲什么，后者决定怎么讲。

## 10. 背诵主线

**L2 记经历，L3 记认识；印象不限于情感，一项一个认识；背景事实与行为推断分开；有支持也有反例；按场景加载、只调整方式不贴标签。**
