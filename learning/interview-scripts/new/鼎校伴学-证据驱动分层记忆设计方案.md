# 鼎校伴学：证据驱动的分层记忆与上下文治理方案

> 日期：2026-09-17 修订。
> 状态：拟议方案与面试学习材料。用户已明确 L1/L2/L3 尚未实现，不能描述为生产成果。
> 已验证范围：独立 Mem0 Demo 的模型抽取、1024 维向量、Milvus 写入及检索；未验证教学效果提升。
> 按用户原始定义：原始数据不计入三层；L1 信息提取、澄清与标签，L2 任务/任务轮次记忆，L3 用户画像。
> 本次修正此前将原始数据误计为 L1 的表述；其他旧文档若仍采用旧编号，需要按职责理解，不能混用。

## 1. 方案定位：不是记住更多，而是可靠地使用历史

一句话：**原始数据留底，L1 理清每次输入，L2 记住一次任务的过程和结果，L3 形成跨任务用户画像。**

```text
原始数据：消息、题目、作答、工具回执（不计入三层）
    ↓
L1：信息提取、指代澄清、标签与来源关联
    ↓ 按 task_id / round_id 聚合
L2：一次任务或一轮任务的经历、关键证据、结果与未解决问题
    Milvus 保存任务记忆文本、向量及过滤元数据；关系库保留权威版本和来源关联
    ↓ 跨任务归并
L3：学习背景、偏好、目标和带证据的知识点画像
```

面向错题和知识点讲解，记忆系统要回答三个问题：

1. 学生以前在这个知识点上发生过什么？
2. 哪些历史仍能支持当前的讲解策略？
3. 出现新表现时，什么可以更新，什么只能暂存为候选？

分层的意义不是给数据库换三个名字，而是让不同可信程度、粒度和生命周期的信息分开管理。
Workflow 保存阶段和执行状态；教材 RAG 提供知识依据；Memory 提供学生经历与偏好，三者不互相代替。

## 2. 借鉴 Mem0，但不直接照搬

本地安装的 mem0ai 2.0.20 新增路径会结合近期消息、相关旧记忆和抽取规则生成记忆，再向量化、去重和保存。
其主路径使用 ADD-only 抽取；已有四操作提示词不代表默认 add 自动执行 UPDATE/DELETE。
显式 update 是另外的维护接口。追加、去重、关联也不等于已经裁决哪条事实当前有效。

可核对源码：

```text
learning/demos/mem0_demo/.venv/Lib/site-packages/mem0/memory/main.py
learning/demos/mem0_demo/.venv/Lib/site-packages/mem0/configs/prompts.py
```

| 借鉴的机制 | 教育业务需要补的约束 |
| --- | --- |
| 从自然语言提取可复用记忆 | 保留学生自述、实际作答、模型推断的区别 |
| 近期消息帮助理解指代 | 明确关联哪一道题、哪轮练习，不随意跨任务归因 |
| 相关旧记忆辅助去重 | 标准化知识点和画像项优先精确查询，避免只靠相似度漏查 |
| 向量化和语义检索 | 用户权限、教材范围和有效状态先约束，再排序 |
| 记忆维护接口 | 画像更新由规则控制，保留证据、修订理由和历史版本 |

技术选型可采用 Python/FastAPI、关系数据库和 Milvus；异步队列复用已有基础设施即可。
不要求 Mem0 成为核心依赖，也不要求为了记忆系统额外引入 Multi-Agent 或图数据库。

## 3. 三层职责和数据结构

### 前置：原始数据留底，不属于 L1/L2/L3

保存或引用原始消息、题目版本、作答步骤、提示使用、评分回执和验证结果。
大对象留在原业务存储，通过引用关联，避免复制整份图片和试卷。

建议字段：`event_id、user_id、task_id、attempt_id、event_type、source_ref、occurred_at、ingested_at`。

- 事件 ID 用于幂等，用户与任务归属由服务端确定。
- 原始事件原则上追加保存；错误评分通过纠正事件表达，不静默篡改历史。
- “助手说你会了”是助手消息，不是独立的掌握证据。
- 数据保留受删除和保留策略约束，“追加”不意味着永远不能删除个人数据。

### L1：信息提取、澄清与标签层

从原始消息、作答和工具结果提取可理解的结构化信息，包括知识点、错因候选、意图、偏好范围等标签。
这是单次输入或小段交互的细粒度加工，不是一次完整任务的总结，也不只是把原文存进数据库。

“澄清”有两个层次：上下文充分时补全指代、统一对象名称；信息不足时标记待确认，交由主流程追问。
例如“这种题我又错了”要关联当前题目，不能凭空补成“分配律一直薄弱”。不要求每条消息都问用户。

```json
{
  "fact_id": "F102",
  "user_id": "U1",
  "task_id": "T1",
  "round_id": "R1",
  "knowledge_id": "KP_distributive",
  "fact_type": "observed_error",
  "claim": "本轮把 3(x-2) 写成 3x-2，存在漏乘第二项",
  "scope": "attempt:A1",
  "evidence_kind": "graded_answer",
  "status": "accepted",
  "occurred_at": "2026-09-16T10:00:00+08:00",
  "derivation_version": "extract_v1"
}
```

L1 事实记录通过独立 `fact_evidence` 关联表指向原始数据，并保留必要的引用位置。
`accepted` 表示通过既定校验，不表示系统获得了绝对真值；对评分纠正仍需支持撤回和重算。

### L2：任务记忆层，归纳一次任务或一轮任务

L2 以业务边界组织 L1，不是逐条换一种说法。它回答“这次为什么来、经历了什么、结果如何”。
同一次错题讲解可能包含题目澄清、诊断、讲解和补救验证，多条 L1 才形成一份有过程的 L2。

建议内容：`task_id、round_id、task_type、knowledge_ids、initial_problem、key_findings、
interventions、outcome、unresolved_questions、completion_status、version`。
通过 `task_memory_fact_link` 关联 L1，避免只保留无法核对的一段总结。

例如：

> 本次分配律错题讲解中，学生最初漏乘第二项，并解释“3 只乘 x”；经针对性讲解，
> 补救新题及解释验证达到本轮条件。尚未验证跨时间保持情况。

这里保留了起点、干预和结果；只写“学生漏乘”属于 L1 级信息，只写“已掌握”又过度归纳。

**一轮任务不是一轮 HTTP 请求或一对问答。** 应使用业务定义的 round_id，例如一次诊断或补救轮次。
可在轮次结束或任务结束时归纳；长任务按明确检查点保存部分记忆，标记 partial，不能提前写成已完成。
同时保存轮次记录和任务总览时，两者共享的证据不能被 L3 重复计为两次独立表现。

#### L2 向量存储：任务内容做语义匹配，元数据负责过滤与追溯

本方案采用混合存储：Milvus 保存 L2 任务文本、Embedding 和必要元数据，用于语义检索；
关系库保留 L2 权威记录、当前版本、有效状态及 L2-L1 关联。L1 和 L3 仍以关系库为主。
不是把 L2 完全迁出关系库，也不是三层都必须向量化。

```json
{
  "memory_id": "L2_100",
  "user_id": "U1",
  "session_id": "S10",
  "task_id": "T20",
  "round_id": "R2",
  "knowledge_ids": ["KP_distributive"],
  "memory_text": "本轮出现分配律漏乘，经提示和例题讲解后完成补救验证，尚未验证跨时间保持。",
  "status": "active",
  "version": 2,
  "occurred_at": "2026-09-17T10:00:00+08:00"
}
```

以上为逻辑字段示意，实际时间过滤可采用整数时间戳；向量字段由 Embedding 模型产生，不手工填写。
向量化文本应包含任务目标、知识点、关键错误、干预、结果和未解决项，不用用户 ID 等无语义字段拼成文本。
过滤元数据也不能仅埋在文本里，必须有可查询字段。

`memory_id` 是向量记录与关系库的关联入口，沿 `task_memory_fact_link` 找到 L1，再追溯原始数据。
来源很少时也可在元数据冗余 `source_l1_ids`，但完整关联以关系库为准，避免两套来源列表各自更新。

面试表述：**L2 做向量化存储和检索，关系库负责版本、状态及证据关联。**

### L3：当前画像层，是可重建的视图，不是永久标签

复用原方案的 `user_profile_item`：一个用户有多个画像项，各项独立更新。

关键字段：`user_id、category、item_key、subject_key、value_json、record_status、observed_at、expires_at、version、derivation_version`。

推荐分类：背景、偏好、目标、知识点学习状态、近期约束。权威学籍数据仍从业务系统获取，
画像最多保存引用或缓存，不变成另一套互相竞争的学籍系统。

通过 `profile_task_memory_link` 关联支持或反对该画像项的 L2；使用 `profile_revision` 保存历史值、
修改理由、来源版本和修订时间。唯一约束保证每个用户、类型、对象、适用场景只有一份当前视图。

例如当前视图应写：

> 本次曾出现分配律漏乘；补救后通过当前验证，尚需后续独立作答确认保持情况。

而不是“分配律差”或“永久掌握”。

## 4. 写路径：先保存证据，再提炼，最后批准画像更新

```text
作答/消息受理
  → 事务保存业务事件及 Outbox
  → L1：提取候选信息、澄清指代与标签
  → 结构、来源、范围及语义校验
  → L1 入库并关联原始证据
  → 轮次/任务结束或检查点：聚合相关 L1
  → L2 任务记忆入库（完整或部分）
  → 基于相关 L2 执行跨任务画像归并策略
  → L3 当前视图 + 修订记录
  → 异步同步检索索引
```

Outbox 是与业务事件同事务写入的待处理记录，避免“业务写成功，但投递丢失”。
消费者以事件 ID 和策略版本幂等处理；失败可重试，不能把队列已投递当成记忆已经更新。
模型不可用时原始数据仍可保存，L1/L2 加工可以延后，新请求回退当前上下文，不阻塞学生作答。

三层是不同粒度，不意味着每条消息都串行调用三次模型。L1 按有价值事件触发，L2 在业务边界归纳，
L3 仅在出现有效增量时更新。用户明确修改长期偏好时，可以形成短小的偏好变更任务记录，
无需等到整段聊天结束；本轮响应仍直接遵循已确认的新要求。

### 4.1 L1 抽取输入和输出

L1 是异步记忆加工，不是实时回答前必须完成的步骤。默认以目标消息为中心，使用前两条、目标消息、
后两条原始交互消息；这里“两条”按消息计，不是两个任务或两个已生成的 L1。
后续消息到齐、会话结束或达到等待上限时触发提取；窗口不足时使用已有内容，不确定的归属标记待确认。
后文可帮助澄清“刚才那题”指什么，但不能把后来答对改写成之前已经答对。
跨较远历史时按需补充候选任务摘要，不假定五条消息一定足够。实时路由只使用当时已经收到的信息。

抽取输入包含目标事件、上述局部窗口、必要的任务候选或旧事实和允许的事实类型。
不要把全部聊天历史发给模型；不允许抽取器从旧画像中凭空再生成“新证据”。

候选输出必须带：`fact_type、claim、scope、source_event_ids、evidence_spans、needs_confirmation`。
其中用户归属由服务端补充，不信任模型生成的身份字段。

抽取规则重点要求：

- 原话“我觉得会了”只能成为自述，不能成为验证结论。
- 原话“这次讲短一点”只适用于本轮，不能推断长期偏好。
- “他”“这种题”等指代不明确时保留待确认，不猜对象。
- 一条记录尽量表达一个可独立判断的事实，保留时间和适用范围。
- 不采集与学习无关、没有必要长期保存的个人信息。

L2 的输入则是同一任务/轮次的已校验 L1、已有部分任务记忆，以及可信业务结果；输出过程和结果的归纳。
L3 读取相关 L2 与当前画像进行增量修订，不能把上层摘要再次当成新发生的原始学习证据。

### 4.2 程序校验能做什么，不能做什么？

程序可以检查 Schema、事件存在、归属、原文片段是否匹配、类型是否允许、时间范围是否合理。
这些不能证明 claim 完全忠实；复杂语义仍需结合专项评测、抽样审查或额外校验。
高影响结论不能仅凭模型返回高置信度就通过。

模型提出候选，程序控制写入；对程序已有的确定性结果，例如一次判题是否通过，直接读取业务回执，
不要再调用模型重新猜一遍。

## 5. 冲突处理：分类裁决，不用一个时间分数解决所有问题

先对齐 `用户 + 事实类型 + 对象 + 场景 + 有效时期`，再区分重复、补充、变化、矛盾。

| 情况 | 处理 |
| --- | --- |
| 同一句消息重复投递 | 事件幂等拦截，不重复制造证据 |
| 多次表达相同偏好 | 合并当前画像的来源；保留不同原始事件，不把重复次数直接当可信度 |
| 临时要求不同于长期偏好 | 本轮覆盖，长期项不变 |
| 明确修改长期偏好 | 新值生效，旧值进入修订历史，记录替代关系与来源 |
| 学籍正常变化 | 按权威业务事件更新，旧状态曾经有效，不算历史错误 |
| 历史答错、现在答对 | 两条事件都成立，属于表现变化，不互相删除 |
| 自述掌握但近期多次答错 | 保留自述与行为证据差异，安排针对性验证 |
| 摘要与原始作答矛盾 | 回查来源，纠正派生摘要及受影响画像 |
| 范围不明、来源同等但相互矛盾 | 标记待确认；影响当前教学则追问，不强行选最新值 |

时间字段分开：`occurred_at` 是事件发生时间，`ingested_at` 是入库时间，`valid_from/to` 是状态有效区间。
今天补录的上月作答，不得当作今天的新表现。偏好可以被明确更正，工具结果也可能失败或过期，
不存在跨所有信息类型的一条绝对来源优先级。

知识点画像可采用“证据不足、需补救、当前验证通过、待复核”等带依据状态。
具体门槛需由题目覆盖、独立作答、提示依赖和教研规则确定；首版不声称有校准后的掌握概率。

## 6. 读路径：先定位，再检索，再裁决，最后装配

```text
当前题目/任务 + 可信用户身份
  → 确定所需记忆类型和知识点范围
  → 精确查询 L3 画像项与知识点相关的 L2 任务记忆
  → 必要时补充语义检索
  → 过滤失效、撤回、越权和重复内容
  → 保留支持证据、反例及未解决分歧
  → Token 预算内组装上下文
```

### 6.1 不把向量数据库当成唯一事实来源

- 年级、教材、标准知识点历史优先结构化查询。
- 自由文本学习目标、表达差异较大的错因可补充语义召回。
- Milvus 保存派生向量和事实 ID 等检索字段；关系数据库保留事实与状态的权威记录。
- 命中向量后回表校验权限、有效状态及最新版本，避免索引更新滞后时读到撤回事实。
- 查询知识点尚未确定时使用候选集合或先澄清，不随意按错误知识点过滤掉正确证据。

常规先用 L3 获取概览，再取相关 L2 了解过去任务；需要解释具体错误或处理冲突时，
沿引用下钻 L1 和原始数据。当前任务尚未形成 L2 时，可以使用当前已确认的 L1，不能假设每层都已生成。
无需把三层全部向量化：L1 可优先结构化查询，L2 作为任务级语义检索单元，L3 按画像项读取。

### 6.2 排序不是越新越好

#### 跨 turn / 跨会话的 L2 查询示例

用户在新会话问：“我以前是不是也有过括号里的数没乘全的问题？”

1. 从认证上下文得到 user_id，作为强制过滤条件；不从模型生成的参数中接受任意用户身份。
2. 对当前问题向量化，在该用户有效的 L2 任务记忆中寻找语义相近的经历。
3. 知识点已确定时增加知识点过滤；不确定时放宽知识点范围，避免错误标签造成漏召回。
4. 根据问题按需限制教材、时间等条件；跨会话时不强制等于当前 session_id、turn_id 或 task_id。
5. 取候选 memory_id 回关系库核对有效状态和版本，移除已撤回、过期或重复覆盖的记录；必要时有限补取。
6. 常规回答使用 L2 的任务经历；需要指出当时具体哪一步错误时，下钻 L1 及原始作答。
7. 最终按相关性、证据范围和上下文预算选取，不把最高相似度自动等同于正确结论。

**跨 turn 的基础是持久化和查询范围；向量检索解决的是不同表达之间的语义匹配。**
关系库同样能跨 turn，不能把跨会话能力归因于向量数据库。session_id、task_id 等既可过滤也可追溯，
但不应无条件限制检索范围。

例如历史写“分配律漏乘第二项”，新问题写“括号里的数没乘全”，语义检索提供候选关联；
它仍可能误匹配负号错误，因此要结合题目、来源和范围判断，必要时澄清。

#### 双存储更新与降级

L2 修订先在关系库提交新版本及待同步记录，再异步更新向量文本和元数据。
同步失败不报告索引已经可用；旧向量命中后回表发现版本不一致，排除并等待重建，
关键新事实可通过关系库精确查询补充。撤回或删除也要传播到向量索引，回表校验仅是额外防线。
Milvus 不可用时降级为用户、知识点和时间的结构化查询，并明确语义检索能力暂时不可用。

#### 排序原则

先做身份、范围和状态等硬过滤，再按任务相关性、证据性质、有效时期和覆盖性排序。
时间衰减适合近期状态，不应无差别降低长期明确偏好的权重。模型自报置信度不是可直接相加的可靠概率。
首版采用可解释规则；只有评测表明确有收益时，再增加学习排序或 Rerank。

### 6.3 上下文装配

```text
任务状态：当前等待哪一轮作答，由 Workflow 提供
当前证据：题目和学生本次步骤
相关历史：与当前知识点有关的 L2 任务记忆，必要时补 L1 细节及原始证据
当前画像：适用的讲解偏好及带范围的学习判断
教材证据：来自独立 RAG
不确定项：尚未核实的错因和冲突
```

优先保证当前题目、任务约束和必要证据，历史按预算选择，不塞全量聊天。
如果用户刚明确更正偏好，当前轮直接采用已受理的更正；后台画像尚未更新不应阻止本轮响应。
读路径采用某条信息，不意味着它自动有资格写回长期画像。

### 6.4 面试主讲流程：错题讲解中的 L2 历史召回

本节作为面试首选口径，是拟议设计，不代表 Mem0 的默认实现或当前业务已上线。
采用“结构化定位 + L2 语义召回 + 按需重排”，不为了复杂而默认增加 BM25、实体图谱和多 Agent。

**用户问题：**“这道去括号的题我又错了，以前是不是也犯过类似错误？”

```text
已有题目和用户问题
  → 取得可信用户身份、题目上下文，确定历史查询范围
  → 查询适用的 L3 画像；对问题生成 Embedding
  → Milvus 在用户隔离和必要元数据过滤下召回 L2 候选
  → 批量回关系库，校验版本、状态、范围并去重
  → 候选难区分时重排，清晰的查询跳过重排
  → 选择少量任务记忆，按需下钻 L1 与原始证据
  → 与当前题目、教材证据一起组装上下文
  → 模型生成有历史依据、保留不确定性的讲解
```

#### 第一步：准备查询，不等待当前 L1 加工

由认证信息确定 user_id，由当前题目和实时上下文确定查询内容。已有结构化知识点标签就复用，
不确定时使用题目描述进行检索或澄清，不等待异步 L1 的“后两条消息”。
“这道题”有明确题目引用时直接关联；没有题目也无明确指代时，不凭空补出一个知识点。

当前问题可以直接作为查询，指代明确且信息充分时不额外调用模型改写。
确实需要改写时，可复用已有实时意图识别的结果；要单独记录额外调用成本，不能把它隐藏在检索耗时里。

#### 第二步：限定范围，再查相关经历

- user_id 是强制条件；有租户隔离时同时校验租户。
- 知识点明确时按知识点过滤，不明确时不硬过滤错知识点。
- 时间、教材版本按当前问题决定，不默认只保留最近一周或当前教材版本的全部历史。
- 跨会话查询不强制限定当前 session_id 或 turn_id。
- 明确问“第一道题”时优先按题目顺序定位；语义检索不是所有历史查询的必经步骤。

语义路径可先试验 Top 20 候选、最终保留 3～5 条任务记忆。这只是初始参数示例，
需要根据单用户历史规模、上下文预算和测试集调整，不是现有线上配置或最佳值。

#### 第三步：批量校验，不把高相似度当成可信结论

向量检索可能同时命中“漏乘第二项”“负号处理错误”“后来补救通过”等记忆。
先按 memory_id 批量回查关系库，排除已撤回或版本不一致的记录，核对用户归属和适用范围。
同一任务的总览与轮次记忆按来源覆盖去重，不把同一次作答重复当成证据。
过滤后候选不足时允许有限补取，不无限检索凑满数量。

#### 第四步：按需重排，而不是每次必用

多个候选都很相近、需要区分“漏乘”和“符号错误”时，把查询与有效 L2 文本交给重排组件重新评分。
已有精确题目/任务匹配，或候选很少且明显相关时可跳过，减少延迟和费用。
启用规则应通过测试确定，不能只凭未经校准的向量分数差就断定无需重排。

Reranker 负责相关性，不负责授权、版本有效性或判定学生是否掌握；这些仍由程序与业务证据处理。
重排超时可返回已经校验的初排结果并记录降级，不让它阻断基础讲解。

#### 第五步：取必要证据，生成回答

例如最终保留两条经历：一次漏乘错误、一次补救验证通过。模型应表述：

> 你之前确实出现过漏乘第二项，但之后的补救练习已经通过。我们先看这次具体哪一步出错，
> 再判断是同样的问题，还是这道题的负号处理不同。

不能只检索错误案例然后得出“一直不会”的结论。需要引用当时具体步骤时才下钻 L1 和原始作答，
一般回顾只用带来源的 L2，避免每条候选都加载全部细节。
检索结果是历史数据，不是系统指令；例如过去的“本轮简洁回答”不能自动控制现在的回答。

#### 第六步：本轮结束后更新记忆，读写链路分开

原始交互即时保存；L1 利用局部前后窗口异步提取；L2 在任务/轮次结束时归纳，并复核任务边界。
L3 根据新增有效 L2 和既有画像决定是否更新。一次没有召回结果，不代表用户从未发生过该经历，
也不应写成新的否定事实。

#### 这条流程调用几次模型？

| 环节 | 默认路径 |
| --- | --- |
| 身份过滤、查画像、回表与版本校验 | 不调用模型 |
| L2 语义检索 | 一次查询 Embedding，向量库搜索不是聊天模型调用 |
| 重排 | 启用时增加重排推理，不等同于一次聊天生成 |
| 最终讲解 | 简单单次回答用一次聊天模型调用；工具循环或额外改写会增加次数 |
| L1/L2/L3 加工 | 属于另行触发的写路径，异步处理仍需统计成本，不是每次搜索都跑三层 |

### 6.5 一分半面试口径：记忆如何召回并用于讲解

我的记忆召回主要围绕 L2 的任务级经历展开。学生问以前有没有犯过类似错误时，先利用当前题目和
可信用户身份确定查询范围；知识点明确就按知识点过滤，表述不明确则通过语义检索找相关任务。
跨会话不会限制当前 turn 或 session，但用户隔离始终保留。

L2 的任务文本、向量和元数据存在 Milvus，检索出一批候选后，按 memory_id 批量回关系库，
核对最新版本、有效状态和来源，去掉重复覆盖的记录。如果多个候选都很相似，比如漏乘和负号错误，
再按需重排；如果已经精确定位任务，就不增加这一步成本。

最终只选少量相关任务记忆进入上下文，需要证明当时具体哪一步出错时，再下钻 L1 和原始作答。
同时保留后续补救通过等证据，避免只召回错误记录就给学生贴薄弱标签。L3 画像用于提供适用偏好和概览，
不能替代具体历史证据。

实时回答不等待 L1 的异步加工。本轮交互保存后，再通过 L1 提取、L2 任务归纳和 L3 画像修订沉淀新记忆。
整体上是向量找相关、元数据限范围、回表核版本、证据支撑回答。效果看必要历史能否召回和是否被正确使用，
而不只看向量分数或是否命中一条记录。

**背诵主线：限定范围 → 召回任务 → 校验去重 → 按需重排 → 取证回答；后台再更新记忆。**

## 7. 用一条业务链路解释设计价值

1. 学生首次把 `3(x-2)` 写成 `3x-2`，原始数据保存答案，不占用三层中的一个层级。
2. L1 提取当前知识点、漏乘现象和错因候选；“不理解分配律”待验证，不能直接断言乘法基础差。
3. 学生解释“3 只乘 x”，新增 L1 信息并补充澄清结果，Workflow 安排讲解和练习。
4. 补救新题及解释验证通过：原始数据与对应 L1 记录成功证据；轮次结束时 L2 归纳错误、干预、结果和未验证部分。
5. L3 结合该 L2 和其他相关任务记忆，更新为本次验证通过、后续需复核，保留来源链路。
6. 新会话再遇到相关题：查到补救和通过记录，先用一道检测题确认，不机械重讲完整内容。
7. 如果再次出错，结合新题条件更新判断，不把旧画像当成不能推翻的事实。

预期价值是减少重复问背景、避免重复讲解和陈旧标签。是否真的实现这些收益，需要第 10 节的评测，
这段流程本身不是效果证据。

## 8. 并发、一致性和可恢复性

- **至少一次消费下的幂等：** 事件 ID 去重；同事件重跑新策略时保留 derivation_version，不重复累计为多次作答。
- **画像乐观锁：** 按旧 version 条件更新；冲突时重新读取并重新归并，不能直接覆盖。
- **原子修订：** 当前画像、来源关联、修订历史在同一事务提交。
- **索引最终一致：** Outbox 同步 Milvus，失败重试和对账；读取回表过滤，关键精确查询不依赖向量已同步。
- **撤回传播：** 原始判分纠正后修订相关 L1，再检查 L2 任务归纳和 L3 画像；缓存和向量索引同步失效。
- **缓存隔离：** 缓存键包含用户、查询范围和必要版本；不能跨用户共享个性化结果。
- **删除传播：** 用户删除范围内的数据需覆盖原始引用、事实、画像、缓存、向量和受控审计保留策略。

本地 Demo 的教训是：SDK 返回 ADD 不证明持久化成功，必须检查实际结果；回查也需要考虑数据库可见性。
生产方案优先以事务记录、可靠索引任务和对账保证一致性，而不是靠无限重试或任意 sleep。

## 9. 为什么比“摘要 + 向量检索”更完整？

| 简单方案的风险 | 本方案的处理 |
| --- | --- |
| 摘要丢失限定条件 | 结构化范围与来源，摘要不替代原始证据 |
| 最新表述直接覆盖过去 | 区分纠错、状态变化、临时要求和不同事件 |
| 画像更新后解释不了原因 | 显式事实关联、策略版本与修订历史 |
| 向量搜不到就认定没有历史 | 关键对象精确查库，语义检索只作补充 |
| 助手评价被当作学生事实 | 按角色和证据类型区分，行为验证独立保存 |
| 异步任务覆盖新状态 | 幂等、乐观锁和旧证据时间校验 |

这些是设计上的防线，不代表已证实优于所有现有框架；额外表结构、标注和运维同样有成本。

## 10. “效果不错”要拿什么证明？

### 10.1 基线和分项对照

使用同一批脱敏或合成多会话案例，对比：

A. 最近若干轮原文；B. 摘要加简单检索；C. Mem0 原样抽取检索；D. 本方案。

对齐模型、可访问数据和 Token 预算；单独记录每种方案额外抽取调用的费用。
按用户划分调参与测试数据，避免同一用户高度相似记录泄漏到两边；多次运行观察模型波动。
再做去掉范围字段、去掉精确查询、去掉冲突规则的对照，判断收益来自哪个机制。

### 10.2 核心指标

| 指标 | 如何定义 |
| --- | --- |
| 事实支持率 | 抽取事实中，被来源支持且没有丢失关键限定条件的比例 |
| 必要事实召回率 | 人工标注应记住的事实中，实际正确提取的比例 |
| 相关历史 Recall@K | 当前任务所需证据中被前 K 条命中的比例 |
| 冲突决策正确率 | 标注场景中正确执行覆盖、共存、不变或待确认的比例 |
| 错误长期写入率 | 临时表达、自述和无依据推断被错误写成长期确定结论的比例 |
| 最终回答质量 | 是否利用正确历史、是否被过期画像误导，采用人工盲评及错误分类 |
| 成本与性能 | 输入 Token、抽取与检索费用、端到端 P50/P95、异步积压和索引延迟 |
| 隔离与恢复 | 越权泄漏、重复事件、晚到证据、撤回及重启恢复测试是否通过 |

命中更多并不总是更好；Recall 提高但引入冲突噪声，也可能降低最终回答质量。
引用覆盖率不等于事实支持率；Token 降低也不能以丢掉必要证据为代价。

### 10.3 首批必须包含的案例

长期偏好后出现临时反向要求；明确纠正偏好；补救前错后对；只说我会了但未验证；
跨教材版本；原始评分被纠正；旧事件晚到；同消息重复提交；两个用户相同问题；
抽取服务超时；向量库拒绝写入；索引延迟；画像并发更新。

先记录真实样本数、标注口径和失败案例，再报告结果。历史简历中出现的 37% 等数字不能直接搬用，
除非确实有对应原始评测记录。没有实测时说“预期改善”和“验证方案”，不说“已提升”。

## 11. 面试学习顺序与可选落地顺序

1. **偏好闭环：** 原始消息留底，L1 提取偏好及范围，L2 记录本次偏好确认或变更，L3 更新当前偏好。
2. **知识点历史：** 关联真实作答和知识点，先实现精确查询与证据引用。
3. **画像修订：** 规则归并、修订历史、乐观锁，验证撤回和晚到事件。
4. **L2 向量检索：** 用 Milvus 存储任务文本向量和元数据，验证跨任务同义表达召回，再按需要加入重排。
5. **可靠性和评测：** Outbox、索引对账、异常恢复、分项对照和回归。

当前以面试理论为主，先讲清各层输入、输出、触发时机和一个完整例子；以上也可以作为后续实现顺序，
不要求为了理解方案现在就编码。重点是理解职责，而不是背表名或给每一层硬套一次模型调用。

## 12. 两分钟面试口径

下面是设计讲解口径；完成实现之后，才把相关表述改成“我实现了”。

我设计的三层记忆是按信息加工粒度划分的，原始对话和作答单独保存，不算进三层。
L1 对原始信息做提取、指代澄清和标签标注；L2 按一次任务或任务轮次，归纳问题、处理过程、结果和未解决项；
L3 综合多个任务的记忆，维护用户背景、学习偏好和知识点画像。每层都保留到下层的来源关系。
Workflow 单独管理任务阶段，不让模型从摘要猜执行进度。

写入上，我借鉴 Mem0 的事实抽取思路，结合近期消息和相关旧记录理解新信息，但增加教育业务的约束。
比如学生说我会了，只能记录为自述；是否掌握还要结合独立作答和验证。“这次讲短一点”也不会直接改成长久偏好。
模型输出候选，程序校验来源与适用范围，再按规则决定新增事实、修订画像或暂存待确认。

存储上，L1 和 L3 以关系库为主，L2 的任务内容向量化存入 Milvus，同时在关系库保留版本和来源关联。
查询时，明确知识点可以直接按条件定位；用户换一种表达时，在用户隔离和必要元数据过滤下检索 L2。
跨会话不会强制限定当前 turn 或 session，命中后通过 memory_id 回查有效状态，需要细节再追溯 L1 和原始作答。
所以向量负责找相关经历，关系库负责核对当前版本和证据。结果会检查有效状态和来源，
在 Token 预算内装配到当前上下文，而不是把全部历史发给模型。历史答错和补救后答对会同时保留，
画像表达当前判断和未验证部分，避免给学生贴永久标签。

工程上，我考虑了事件幂等、画像版本控制、异步索引和来源撤回后的重算。效果需要对照简单摘要方案，
同时测事实支持率、相关历史召回、错误长期写入和最终回答质量，不能只看 Token 有没有降低。

### 面试官问“你的方案有什么亮点？”

回答：**把记忆从不可解释的摘要，设计成有来源、有适用范围、能修订和验证的学生历史系统。**
展开三个点即可：证据与推断分开；历史事实与当前画像分开；记忆检索与业务状态分开。

### 一分钟口径：重点介绍 L2 向量化

我的三层记忆按信息粒度划分：L1 从原始交互中提取信息、澄清指代和标注知识点；
L2 按一次任务或轮次归纳经历；L3 综合多个任务维护用户画像，原始数据单独保存。

其中我为 L2 设计了向量检索，把任务的问题、处理过程和结果形成记忆文本，配上用户、任务、
知识点和时间等元数据存入 Milvus。这样用户问“以前有没有括号里的数没乘全”，可以检索到
历史上“分配律漏乘”的相关任务，不要求用词完全一致。

检索始终限制用户范围，但跨会话查询不限制当前 session。候选通过 memory_id 回关系库核对版本和状态，
需要具体证据时再关联 L1 和原始作答。这样既支持跨任务语义匹配，也保留更新控制和追溯能力。

### 常见追问

- **为什么不直接向量化所有聊天？** 原文噪声和重复较多；L2 保留任务过程与结果，检索粒度更贴近学习经历。
  代价是归纳可能丢信息，所以保留 L1 和原始数据供下钻，不宣称摘要一定优于原文。
- **为什么还留关系库？** 为版本、状态、事务更新和来源关联提供统一依据，避免向量索引滞后时采用失效记忆。
- **会不会重复？** 同任务的轮次记忆与总览按来源覆盖关系去重，不能把同一作答当成多份独立支持证据。
- **查到旧偏好怎么办？** L2 中的历史要求是经历，不一定是当前指令；结合其 scope 和 L3 当前有效偏好决定使用方式。
- **怎么证明更准确？** 对比结构化查询及原文向量检索，测同义表达下的 Recall@K、无关召回、过期记忆误用与最终回答质量。
  只有实测后才能说提升多少，元数据过滤和向量化本身都不是效果保证。
