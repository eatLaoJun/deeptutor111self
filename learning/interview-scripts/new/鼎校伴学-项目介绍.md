## 三分钟口头介绍

> 以下为口述稿，时长随语速和停顿调整；已有项目能力与后续设计分开表述。

我参与的项目叫**鼎校伴学**，是一个面向 K12 学生的智能学习助手，主要提供教材问答、题目讲解，以及结合历史学习情况的个性化辅导。

同时，它也以 **Action** 的形式提供其他业务的入口：根据学生需求返回受控的入口信息，由前端展示操作按钮，学生点击后再进入对应业务流程。

这个项目要解决的，不只是让大模型回答一道题，而是三个问题：**回答有没有教材依据，系统能不能根据实际情况调用工具，以及学生之前的学习情况能不能在后续辅导中利用起来。**

技术上，我重点介绍的是 Agent Runtime、上下文和分层记忆这条主线。

首先是 Agent 的执行机制。系统会把学生当前的问题、必要的历史信息和可用工具组织成上下文，交给模型。模型可以直接回答，也可以选择教材检索、题库等工具。程序负责校验参数、执行工具，再把真实结果回填给模型，由模型决定下一步。

所以，它不是一次模型调用的简单封装，而是一个“模型决策、工具执行、结果反馈”的闭环。但我们也不希望所有问题都跑复杂循环，信息充分的任务一次调用就可以完成，需要动态补充材料时才使用 Agent Loop。

教材 RAG 是这个闭环里的证据来源。检索会结合学生的年级和教材版本，返回带章节、页码的材料。我在这部分会重点讲教材清洗和知识覆盖问题的分析，具体向量入库由对应同事负责。比如教材文章里虽然出现了某种语法结构，但不一定有解释规则的内容。这类问题需要反馈教研补充材料，而不是只调整检索参数。

在这些能力基础上，我进一步设计了**知识点学习工作流**，希望把“讲完一道题”推进到“验证学生是否理解”。

举个例子，学生把 `3(x-2)` 写成了 `3x-2`。系统先提出“可能漏乘第二项”的错因假设，通过一个短问题确认，再结合教材讲解，并安排不同形式的新题和简短解释题来验证。如果仍有问题，就进入有次数限制的补救；证据不足时，也不会强行说学生已经掌握。

这里的架构是**外层 Workflow 管流程，内层 Agent 按需处理具体问题**。诊断、讲解、练习、等待和恢复由工作流控制；需要灵活检索时，再调用 Agent Loop。模型可以提出建议，但不能随意跳过评估或者修改通过条件。

记忆方面，我采用的设计是三层组织：L1 保存原始作答和学习证据，L2 提炼一次学习中的场景事实，L3 形成带来源、可更新的用户画像，供后续辅导使用。这里特别区分了**任务状态和学习记忆**：任务状态负责“现在做到哪一步”，记忆负责“以前发生过什么”，恢复任务不能靠模型从摘要里猜。

整体来说，这个项目里我最关注的是：**把模型的灵活性放进可控的执行流程，让回答有依据、学习过程有状态、后续个性化有证据，而不只是做一个能聊天的界面。**

## 讲述取舍

- 开场先讲用户与问题，再讲实际职责；不要先背组件名或宣称整条链路都是个人实现。
- 已有能力与演进方案用“在此基础上，我进一步设计……”明确过渡。
- 三个深入方向：Runtime 执行闭环、Workflow 与 Memory 边界、教材证据覆盖问题。
- 准备具体例子而非堆工具名；SSE、Redis、HNSW 等留到相关追问，未落地就说设计方案。
- 结果优先陈述可证实的产物与能力，不把“达成本次学习目标”夸大为“长期掌握或成绩提升”。
