## 二、面试官真正想确认的三件事

### 1. 你是否能把不稳定的模型输出接入稳定的程序

结构化输出连续追问了本地修复、程序校验和模型反馈，考察点不是“知道重试”而是：

```text
识别失败类型 -> 判断能否确定性处理 -> 只对必要部分调用模型
-> 再校验 -> 有限退出 -> 留下可复查记录
```

### 2. 你是否真正掌握自己负责的系统边界

问“基于什么框架”时，需要先听到自研和复用的直接结论；问“意图提取哪些要素”时，需要听到输入、结构化结果和分支条件，不是继续介绍 Skill 名称。

### 3. 你是否能从新需求出发，而不是从熟悉技术出发

现场需求有两条链路：已有记录校验、新记录生成。RAG 是其中的证据组件，不是整个系统的业务定义；多租户也不是已给出的核心约束。

## 三、优先级

| 优先级 | 要解决的事 | 完成标准 |
| --- | --- | --- |
| P0 | GIL 与并发 | 不再出现“Python 只有一个线程池”，能按 I/O、CPU、解释器区分 |
| P0 | 结构化输出 | 能连贯说明解析、Schema、业务校验、本地修复、反馈和退出 |
| P0 | 审题和回答组织 | 第一两句话直接回答；陌生方案先确认目标和约束 |
| P1 | Agent 与 Workflow | 讲清意图理解、节点验收、业务状态不是同一件事 |
| P1 | BKT 与检索模型 | 能解释概率模型与联合评分，不只说用途 |
| P1 | Memory 冲突 | 把状态变化与事实冲突分开，知道无证据时不能猜真值 |
| P2 | 私有化部署 | 用真实职责讲经历，理解硬件后端兼容性边界 |

## 四、保留的优势与应纠正的表达

- 保留三层 Memory、学习闭环、工具执行和业务结果回流这条项目主线，不必推倒重写项目经历。
- 原理错误需要纠正，不全部归结为紧张或表达不好。
- 不再用“AI 时代不太看基础”解释不会的问题；可以直接承认具体知识点不熟，再给出已确定的部分。
- 不用“LangGraph 不支持跨轮”论证自研；用职责、业务契约和实际维护取舍论证。
- 不把“没有调用费用”理解成“没有计算量、时延或容量约束”。
- 不根据“问了入职时间”“提了 HR”推断面试已经通过。

统一回答骨架：**一句话结论 -> 两三点机制 -> 项目或例子 -> 边界与验证。**
