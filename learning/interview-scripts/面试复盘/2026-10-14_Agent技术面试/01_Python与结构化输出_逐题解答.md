## Q02：GIL 是什么？Python 到底能不能并发？

**转写定位：** `00:01:11-00:03:21`。

**当时的问题：** 把 GIL 说成“Python 只有一个线程池”，并混用了单线程、Worker 和多进程。

### 60 秒参考回答

> GIL 是传统 CPython 中的全局解释器锁。同一个解释器里，通常只有持有 GIL 的线程能执行 Python 字节码，因此多个线程不能直接让纯 Python 的 CPU 密集计算在多个核上同时执行。但这不等于 Python 只能开一个线程，也不等于不能并发。网络、数据库等 I/O 等待可以并发处理；异步接口齐全时适合 AsyncIO，只有同步接口时可以使用受限线程池。CPU 密集任务则考虑多进程，或者使用能释放 GIL 的原生扩展。还要说明这是传统启用 GIL 的 CPython 语境，不能覆盖所有解释器和构建版本。

原理依据：[Python threading](https://docs.python.org/3/library/threading.html)、[free-threaded Python](https://docs.python.org/3/howto/free-threading-python.html)。

### 用一张表分开三个概念

| 方式 | 怎样处理任务 | 合适场景 | 主要边界 |
| --- | --- | --- | --- |
| AsyncIO | 事件循环在任务等待时调度其他任务 | 异步 LLM API、异步数据库、异步网络请求 | 协作式调度，不会自动把 CPU 计算变成并行 |
| 多线程/线程池 | 多个操作系统线程共享进程内存 | 同步 I/O SDK、需要从事件循环移出的阻塞调用 | 传统 GIL 下纯 Python CPU 计算通常不能多核并行，仍有共享状态竞争 |
| 多进程/进程池 | 每个进程拥有独立运行时和内存空间 | 可拆分的 CPU 密集任务、服务多 Worker | 有通信、序列化和内存开销，不是开得越多越好 |

### 结合你的项目怎么举例

> 在 Agent 链路里，远程模型调用和检索请求包含大量 I/O 等待，独立调用适合异步调度。有依赖的调用必须分轮，不能为了并发把“先拿结果、再用结果”的两步同时执行。如果工具内部是阻塞的同步 SDK，需要明确隔离方式；CPU 密集的本地处理也不能直接塞进事件循环。

这是将并发原理映射到已有工具调度经历，不新增某个尚未确认的线程池或部署配置。

### 面试追问

**1. 写了 `async def` 就不会阻塞吗？**

不会。里面直接调用阻塞函数或长时间计算，仍会占住事件循环。`await` 也不是“看到关键字就开线程”，而是等待相应可等待对象，由事件循环协作调度。依据：[Python asyncio tasks](https://docs.python.org/3/library/asyncio-task.html)。

**2. 有 GIL，是不是就不需要业务锁？**

不是。读取、判断、更新这样的复合业务步骤仍可能发生竞争；异步任务也可能在等待点交错。状态一致性要由锁、事务、版本检查或幂等设计保障，不能依赖 GIL。

**3. FastAPI 开多个 Worker 就完全解决了吗？**

多个 Worker 通常是多个进程，能够分担请求，但不能替代正确的异步 I/O、连接池和并发限流。进程内对象也不会自动跨 Worker 共享；如果每个进程加载一份大模型，还要考虑重复内存或显存占用。

**4. Python 不是已经可以没有 GIL 了吗？**

Python 3.13 起提供可选 free-threaded 构建，部分扩展兼容性仍需具体检查。回答时先明确实际解释器和构建，不把“Python”一概等同于传统 GIL 运行方式。依据：[Python free-threading](https://docs.python.org/3/howto/free-threading-python.html)。

**一句话记忆：GIL 限制的是特定运行时里的字节码并行，不是线程数量，也不是 I/O 并发。**

## Q03：怎么把 JSON 输出可靠性做到 99%？

**转写定位：** `00:03:21-00:06:18`。

**面试官的关注点：** 输出交给程序后能否可靠使用，不是只看模型有没有返回一段像 JSON 的文本。

### 90 秒参考回答

> 如果让我设计，我会先和业务确认成功的定义：是能解析、符合字段约束，还是在时限内通过业务校验并交付。链路上先选模型接口支持的严格结构化输出，减少格式错误；返回后仍做 JSON 解析、Schema 校验和业务校验。明确且不改变业务含义的问题先本地处理，比如受控的格式归一化；缺少事实、业务值矛盾等问题不能乱补，整理成字段级错误反馈给模型，做有限修正。最后还要有总超时、重试预算和失败出口。99% 需要用固定样本和线上统计验证，不能仅凭加了 Schema 或多试几次就保证。

### 先区分三种约束强度

| 方式 | 做了什么 | 不能据此保证什么 |
| --- | --- | --- |
| Prompt 描述输出格式 | 用自然语言和示例引导模型 | 不保证语法合法或字段完全一致 |
| JSON Object / JSON mode | 接口对 JSON 输出施加相应约束 | 不自动等于满足任意业务 Schema |
| 接口明确支持的严格 Schema / 约束解码 | 将支持的结构约束引入生成过程 | 不保证外部事实、权限、库存等业务真值，也仍须处理拒绝、截断和请求失败 |

JSON Schema 是描述约束的规范，不是“把一个 Schema 字符串交给模型就天然强制执行”。具体支持范围取决于模型和接口，不能把不支持的关键字当成已生效。依据：[阿里云结构化输出](https://www.alibabacloud.com/help/en/model-studio/qwen-structured-output)。

### 完整处理链

```text
请求输入与契约检查
  -> 调用支持相应结构约束的模型接口
  -> 检查请求状态、结束原因和输出完整性
  -> 严格 JSON 解析
  -> Schema 校验
  -> 业务校验
  -> 通过：交付下游
  -> 未通过：错误分类
       -> 可确定的低风险归一化：本地处理后重走校验
       -> 需要内容修正：最小错误反馈 + 有限模型修正
       -> 缺少真实输入：澄清或失败，不编造
       -> 预算耗尽：明确失败/人工处理，不伪造成功
```

### “99%”到底统计什么

至少拆开以下指标：

- 首次 JSON 解析通过率。
- 首次 Schema 通过率。
- 自动本地修复成功率，以及修复是否改变业务含义。
- 有限修正后，在约定时限内通过必要校验的交付率。
- 总时延、模型调用次数、人工介入率与最终失败分布。

可用的交付率口径示意：

```text
时限内通过约定校验并交付的请求数 / 预先定义的有效请求总数
```

这是指标定义示例，不是你的项目实测值。无效输入、用户取消和模型拒绝怎样计入，应事先约定；不能做完后调整分母来凑成功率。返回一个能被解析的错误对象，不等于原任务已成功。

**特别纠正：** 成功率 99% 和延迟 P99 是不同指标，不能说成“P99 可用的 JSON”。

## Q04：格式、缺字段、错类型、业务越界分别怎么处理？

**转写定位：** `00:06:18-00:09:27`。

### 直接回答

> 我会按语法、Schema 和业务规则分层处理。语法层解决能不能解析；Schema 层解决字段、类型、枚举和范围是否符合契约；业务层解决跨字段关系、数据是否存在、权限及当前业务状态。可以在 Schema 中表达的业务范围就提前表达，但动态事实和复杂业务约束仍交给程序核验。修复策略取决于错误含义，不是所有失败都重新调用模型，也不是所有缺失都给默认值。

### 分类表

| 错误例子 | 所属层次 | 合理处理 |
| --- | --- | --- |
| JSON 前后多了解释或 Markdown 包裹 | 语法/封装 | 在契约允许、且只有唯一完整候选时受控提取，再严格解析 |
| 尾逗号、非标准引号 | 语法 | 可评估本地语法修复，不能全局字符串替换后直接执行 |
| 根对象缺少必填字段 | Schema | 从可信上下文能确定时补齐，否则反馈修正或澄清 |
| 字段名与契约不一致 | Schema | 只有预先声明的一对一别名才归一化；冲突不能静默选择 |
| 数值字符串替代整数 | 类型 | 仅在业务允许无损转换时转换；金额、编号、日期等不能一概处理 |
| 枚举不支持、数量超过静态范围 | Schema 或业务规则 | 报错并修正，不直接把值截断到边界 |
| 开始时间晚于结束时间 | 跨字段规则 | 返回具体违反的关系，要求修改或补充依据 |
| 引用不存在、没有权限、动态资源不足 | 业务规则 | 查询可信业务数据，拒绝越权；缺事实不能靠模型猜 |
| HTTP 429、网络超时 | 调用/传输层 | 限流、退避、重试或降级；不是 JSON 格式修复 |

### Schema 具体要说到什么程度

以一个假设任务为例，可以约定：

- `file_name` 必填且非空。
- `task_type` 只能取已支持枚举。
- `count` 是受范围约束的整数。
- 不允许契约之外的额外字段。
- `start_at <= end_at` 由交叉字段校验保证。

`properties` 中声明字段，不自动表示它是必填；额外字段也需要明确允许还是拒绝。依据：[JSON Schema object](https://json-schema.org/understanding-json-schema/reference/object)。

使用 Pydantic 时还要明确严格校验还是允许转换。默认转换便利，不代表适合所有业务；必要时启用 strict mode，再加入业务校验器。依据：[Pydantic strict mode](https://docs.pydantic.dev/latest/concepts/strict_mode/)。

### 还可以主动补充的边界

- 重复键不能默认由“后一个覆盖前一个”蒙混过去；严格交付场景应检测并拒绝歧义。
- 超大输出、过深嵌套和截断需要单独限制，不能只检查结尾是不是大括号。
- 解析成功后仍不能直接执行工具。用户身份、权限和可操作对象应由服务端可信上下文决定。
- 不用 `eval` 执行模型文本来代替解析。

## Q05：格式错误一定要再调模型吗？不写无数正则还能怎么做？

**转写定位：** `00:09:27-00:10:22`、`00:12:01-00:13:07`。

**当时的问题：** 一直围绕正则展开，没有清晰提出“解析器/语法修复器 + 风险限制 + 重校验”。

### 60 秒参考回答

> 不一定。格式错误可以先走本地解析和修复。例如单一 Markdown 包裹可以按明确规则去掉，唯一完整 JSON 可以用解析器提取；尾逗号等问题可以评估成熟的 JSON repair 工具，而不是堆正则。但修复器使用了启发式，修复成合法 JSON 不代表原始业务内容就完整或正确。因此我会保留原文，限制允许的修复范围，修复后重新走 Schema 和业务校验；截断、缺失事实、多个候选冲突等情况，不用自动补空值来伪造成功，必要时才回模型或要求补充输入。

工具依据：[json_repair 作者仓库](https://github.com/mangiucugna/json_repair)。这里推荐的是一种方案，不声称你项目已经使用该库。

### 本地处理不是只有正则

可以分三档：

1. **明确的外层归一化**：移除契约允许的包裹、处理已声明别名、做无损类型归一化。
2. **基于语法的受限修复**：利用理解字符串、转义、嵌套结构的解析器或修复器处理格式问题。
3. **需要猜内容的补全**：未知字段值、截断后的列表、相互矛盾的事实。这不再是单纯语法修复，应升级处理。

正则可以处理少量已知包裹，但不适合作为通用 JSON 解析器。例如 JSON 字符串自己可能包含花括号、转义引号和逗号，简单截取“第一个 `{` 到最后一个 `}`”会误判。

### 能修与不能乱修的例子

下面都是教学例子，不是项目真实数据。

| 输入问题 | 允许的处理方向 | 风险边界 |
| --- | --- | --- |
| 单一 JSON 被完整代码块包裹 | 按规则移除包裹后解析 | 发现多个候选时不能随便取第一个 |
| 对象末尾多一个逗号 | 语法工具受限修复，再校验 | 不能删除字符串内部有意义的逗号 |
| `name` 应为 `file_name` | 预先定义别名后转换 | 两字段同时出现且不同，应该报歧义 |
| `count` 为 `"3"` | 契约允许时做无损转换 | `"003"` 可能是编号，不能一概转整数 |
| 缺少业务必需的目标对象 | 从可信输入确定，或问用户 | 不能让修复器补空值后就认为任务有效 |
| 长数组因长度限制被截断 | 根据结束原因和业务完整性处理 | 补个 `]` 只能补语法，不能恢复没生成的数据 |

### 上线时如何控制修复风险

- 保存原始输出、修复后的内容、修复原因和修复工具版本。
- 严格限制自动接受的修复类别，不能只看库有没有返回结果。
- 对数量、金额、身份、引用和任务对象等关键字段保持更严的校验。
- 不知道是否改变了含义时，不自动交付；修复成本低不等于风险低。
- 所有修复路径回到同一校验链，不为“修复成功”单开免检通道。

**面试收口：程序解决可确定的格式问题，模型解决需要语义判断的修正，缺失事实由真实输入和业务系统补。**

## Q06：校验结果怎样反馈模型，才能比直接重试更有效？

**转写定位：** `00:10:22-00:12:01`。

### 直接回答

> 程序先把错误定位到具体字段，反馈字段路径、错误类型、期望约束和经过脱敏的实际值，再提供原始任务和必要上下文，让模型只返回修正后的完整对象。不是直接塞一整段堆栈，也不是只告诉模型“500 错误”。修正后仍然全部重新校验，且所有修正共享同一个次数和时间预算。

Pydantic 的校验错误可以提供 `loc`、`type`、`msg` 等信息，便于转换成面向模型的简短错误清单。依据：[Pydantic error handling](https://docs.pydantic.dev/latest/errors/errors/)。

### 一个最小错误反馈示例

下面是自定义协议示例，不是 Pydantic 原样输出，也不是你的现有接口。

```json
{
  "status": "validation_failed",
  "errors": [
    {
      "path": "items[0].count",
      "code": "out_of_range",
      "expected": "integer between 1 and 20",
      "actual": 30
    },
    {
      "path": "file_name",
      "code": "missing_required_field",
      "expected": "non-empty string"
    }
  ],
  "instruction": "Return one complete corrected object. Do not invent missing facts."
}
```

### 为什么这比“再生成一次”好

- 程序已确定哪里不符合契约，模型不必从长日志中猜问题。
- 不把无关堆栈、内部地址或其他用户数据放进模型上下文。
- 反馈的是可操作约束，而不是“服务失败”这样的模糊状态。
- 可以记录错误是否重复出现，持续相同错误时及时停止，而不是一直浪费调用。

### 两个不能省的边界

**1. 类型合法不代表内容正确。**

把 `count` 从字符串改成整数，只修正了类型；如果真实业务要求来自另一份数据，还需要业务校验。

**2. 没有真实值，就不该逼模型猜一个合法值。**

如果缺失的是用户没有提供的必要业务事实，应澄清或返回可解释失败。否则可能拿到一个完全合法但内容虚构的对象。

默认要求模型返回完整修正对象更容易一致校验。若设计补丁式修正，还要校验补丁路径、对象版本和合并冲突，不能认为“只回一个字段”天然更安全。

## Q07：为什么三次尝试不能直接宣称 99.9%？退避怎么说才准确？

**转写定位：** `00:04:32-00:06:18`、`00:07:32-00:09:27`。这是对当时回答的纠正。

### 先纠正概率计算的适用条件

如果每次尝试的失败概率始终为 10%，且尝试之间相互独立，那么“总共尝试三次，至少成功一次”的概率是：

```text
1 - 0.1^3 = 99.9%
```

但真实失败通常不是独立的。同样的缺失输入、错误 Schema、模型能力边界和持续服务故障，会让后续失败概率仍然很高。

更一般的表达是：

```text
三次都失败的概率
= P(F1) * P(F2 | F1) * P(F3 | F1, F2)
```

仅知道第一次成功率 90%，不能推出后两个条件失败概率。给模型加入错误反馈会改变后续条件，但改善幅度也要实测。“第一次调用 + 三次重试”还一共是四次，不能和“总共三次尝试”混写。

### 45 秒参考回答

> 三次尝试得到 99.9% 只是特定独立同分布假设下的演算，不能当作工程承诺。实际错误有相关性，所以我要区分可恢复错误，先做确定性修复，再对必要错误有限重试，并统计修复后的真实成功率。同时设置总时限和调用预算，避免成功率看起来提高了，但时延和成本不可接受。

### 退避、修复和澄清不是一种动作

| 情况 | 主要动作 | 原因 |
| --- | --- | --- |
| 暂时限流、网络抖动 | 根据服务约定退避、限次重试 | 等待可能让服务恢复 |
| 字段类型或取值违反契约 | 本地处理或带错误反馈修正 | 单纯多等一会儿不会纠正内容 |
| 用户没提供必要条件 | 澄清、暂停或失败 | 重复生成不能创造真实输入 |
| 没有权限或永久不支持 | 明确拒绝操作或能力边界 | 不是瞬时故障，继续重试没有意义 |

常见指数退避的教学表达：

```text
cap_n = min(max_delay, base_delay * 2^n)
sleep_n = 在 [0, cap_n] 中加入随机抖动
```

若响应提供 `Retry-After`，按接口契约尊重其要求，并受总时限约束。指数退避不是把 `0.1` 不断平方；那样会越等越短。

### 工程追问：一次超时后能直接重做吗？

不一定。如果操作带副作用，客户端超时不代表服务端没有成功。需要幂等键、状态查询或去重机制，防止重复创建、重复提交。模型内容修正也不应带着整条下游业务链反复执行。

**最后记住：重试是补救策略，不是正确性证明；明确失败也比输出一个假成功更可靠。**
