## Q08：到底用了什么框架？为什么不直接用 LangGraph？

**转写定位：** `00:13:35-00:17:12`、`00:25:30-00:26:49`。

**当时的问题：** 没先回答自研还是复用；把 LangGraph 描述成固定 DAG、不能很好跨轮，理由不成立。

### 30 秒项目口述

> 核心业务编排和 Agent Runtime 是我们自己建设的，我参与了模型决策、工具执行、结果回填和异常收敛这条闭环。模型接入和检索等基础能力复用现有 SDK、模型服务和组件，不是所有基础设施都重写。主链采用一个受控 Agent Loop，确定性学习业务通过 Action 进入独立服务，业务结果再回流会话和记忆。

### 2 分钟展开

> 我们把运行时按职责拆开：外层管理一次用户回合的数据和生命周期，准备层装配 Prompt、历史、画像、工具及预算，Agent Loop 负责多轮决策，Tool Runtime 负责真正执行工具并回填结果。模型可以建议调用什么工具，但解析、权限、可信参数、超时和退出都由程序控制。
>
> 这里的自研重点是业务执行契约和学习服务的衔接，而不是重新实现模型或者向量检索。确定性测评和学情任务有自己的状态与验收规则，不需要所有业务都在一个自由 Agent 中完成。
>
> LangGraph 本身支持图状态、条件分支、循环、持久化以及中断恢复，所以我不会用“它不支持跨轮”解释我们的选择。是否引入它，要比较已有业务状态模型、接入与迁移成本、团队维护成本，以及需要复用多少图运行能力。自研也有代价，恢复、并发一致性和可观测能力都要自己负责，不能只说比框架更灵活。

LangGraph 能力依据：[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)。

### 哪些概念不能混着说

| 概念 | 回答边界 |
| --- | --- |
| ReAct | 推理与行动交替的组织方式，不是完整应用框架的名字 |
| CoT | 推理方法概念，不是拿来“集成几个模块就有了”的调度器 |
| Agent Loop | 同一用户回合内可多次模型调用与工具调用的执行循环 |
| Workflow | 显式业务步骤、状态与验收规则，不要求是 DAG，也不要求每步都调模型 |
| Skill | 可复用的任务说明与操作知识，是否带有程序执行链取决于实现 |
| Subagent | 有明确任务边界与独立执行上下文的代理，不等于加载一段 Skill |
| Planner | 显式产出计划并交给执行层；多轮 Tool Calling 不自动等于独立 Planner |

当前项目不把独立 Planner、通用 DAG 调度器或 Subagent 扩展包装成已有主链成果。

### 面试官继续追问时

**“不就是一个 while 循环吗？”**

> 循环只是控制结构。工程难点在消息协议、工具调用配对、可信参数、失败隔离、状态和预算边界，以及最后能明确完成或失败。我会举一次工具错误如何回填、模型如何调整、何时停止的具体流程，而不是强调循环代码有多少行。

**“自研就一定比 LangGraph 好吗？”**

> 不一定。业务状态和现有系统衔接是我们的主要取舍；如果将来需要大量复用复杂图调度和持久化能力，引入框架可能降低总成本，需要按实际需求比较。

## Q09：意图识别怎么设计？具体提取哪些要素？

**转写定位：** `00:13:07-00:13:35`、`00:17:12-00:18:42`、`00:21:06-00:24:42`。

**面试官的关注点：** 需要什么输入，提取什么结构，什么条件才能进入下一条分支。

### 先按已有项目直接回答

> 我们没有在 Chat Agent 前额外调用一次分类模型。Agent Loop 的首轮结合当前消息、历史、业务上下文和可用工具，完成任务理解并决定直接回答还是调用工具。需要进入确定性学习服务时，用受控 Action 返回业务入口，后端校验对象和权限，用户确认入口后由业务服务执行。Tool Calling 是意图理解的落点，但不等于已经解决了槽位缺失、歧义和未知意图等所有问题。

### 如果面试官问“独立设计一套完整意图识别”，再展开

下面是对此题的结构化设计，不额外声明已经部署了一个独立分类器。

```text
当前输入 + 对话上下文 + 活跃任务状态 + 能力清单
  -> 理解任务意图与必要槽位
  -> 判断信息完整性、歧义、支持范围
  -> 运行时校验对象、权限和当前状态
  -> 执行 / 澄清 / 闲聊侧答 / 暂停 / 取消 / 能力边界说明
```

可以在同一次模型决策中提取这些信息，不必为每个字段再调一个模型。

### 应提取的要素

| 要素 | 例子 | 作用 |
| --- | --- | --- |
| 任务类型 | 题目讲解、知识点学习、普通问答 | 判断需要什么能力 |
| 任务对象 | 附件、题目 ID、知识点、当前练习 | 确定到底对什么执行 |
| 限定条件 | 年级、教材版本、目标、范围 | 避免对错对象、错教材执行 |
| 指代与来源 | “这题”“刚才那个”指向哪里 | 判断能否由上下文唯一定位 |
| 流程控制意图 | 继续、暂停、恢复、取消、换题 | 决定业务状态，而不只选择工具 |
| 信息缺口与歧义 | 缺题干、多个候选知识点 | 决定是否需要澄清 |
| 多意图及先后关系 | 先讲这题，再暂停练习 | 决定顺序或要求用户确认优先级 |

`user_id`、租户归属和工具权限不应由模型自由生成后直接信任，应从认证与服务端业务上下文注入。

### 例子：用户说“这题我不会，给我讲一下”

假设上一轮已有唯一题目附件，这是讲解示例：

```json
{
  "intent": "explain_problem",
  "slots": {
    "problem_ref": "current_attachment"
  },
  "task_action": "start_or_continue",
  "missing_slots": [],
  "decision": "offer_supported_action"
}
```

运行时还要检查附件确实属于当前用户、内容是否足够、业务是否支持。如果没有题目也没有可解析指代，就先问“请发一下题目”，不能凭空选一题。

### 分支标准比分类名称更重要

1. **支持且信息完整**：进入合适工具或受控业务入口。
2. **支持但缺必要槽位**：只问当前缺失的关键问题。
3. **多个可能意图或指代不唯一**：澄清，不强行路由。
4. **普通闲聊**：在边界内回答，原业务状态保持不变。
5. **明确暂停、取消或恢复**：校验目标任务后处理，不强迫用户继续学习。
6. **不支持或越权**：明确说明边界，必要时给可选能力，不无限自由生成。

如果使用置信度或分类分数，它应经过验证集校准；不能把模型自己说“我有 0.95 信心”直接当成真实可靠性指标。是否澄清也可结合槽位完整性、候选差异和操作风险判断。

**一句话记忆：意图回答“想做什么”，槽位回答“对谁、用什么条件做”，策略回答“现在能不能做”。**

## Q10：用户跑题或不在意图范围内，除了自由回答还有什么兜底？

**转写定位：** `00:18:42-00:21:06`、`00:24:04-00:25:30`。

**当时的问题：** 把“不进入下一节点、聊一句再拉回”当作主要答案，漏掉不同未知情况的分流。

### 60 秒参考回答

> 我会先区分为什么没匹配上。缺信息就补槽位，有歧义就澄清；普通闲聊可以短答，保持原任务不推进；用户明确暂停或取消，就按他的控制意图处理；不支持的业务要说明边界，必要时给菜单或转人工。不能把所有情况都放进自由聊天，也不能把“不相关”直接解释成“学生没有掌握”。兜底既要给用户合理响应，也要守住原任务的状态和权限边界。

### 几个具体输入

| 用户输入 | 判断 | 合理响应 | 学习任务状态 |
| --- | --- | --- | --- |
| “今天的天气真好” | 可能只是闲聊，不是答题 | 简短回应；需要时询问是否继续 | 不因闲聊推进或判错 |
| “查一下今天的天气” | 明确外部信息请求 | 有相应工具才查询，没有就说明能力边界 | 原任务可以保持或按用户要求暂停 |
| “先不做了，等会继续” | 暂停控制意图 | 确认暂停并保留可恢复状态 | paused，示意状态 |
| “取消这次练习” | 取消控制意图 | 按风险与业务要求确认取消 | cancelled，示意状态 |
| “帮我处理一下” | 缺目标与动作 | 问一个必要澄清问题 | 不启动新任务 |
| “改一下成绩” | 可能越权或不支持 | 说明权限与受理方式，不绕过业务系统 | 不执行修改 |

这些是补强设计示例，不代表你的生产系统已经有全部天气工具或全部兜底分支。

### 为什么“没达到评分阈值”还不够

评分通常回答的是“这次作答是否满足当前节点验收”，意图识别回答的是“用户现在要做什么”。用户明确说“暂停”，不应该先当成一次不会做的回答扣分。

合适的顺序是：

```text
先识别控制意图、任务相关性与必要信息
  -> 确实是当前任务的有效作答
  -> 再按节点量规或确定性规则验收
```

原始聊天可以保留，但跑题内容不应因此变成一次错误作答，也不应回流 BKT 降低掌握概率。

### 其他可用的兜底手段

- 展示系统支持的能力或可点击选项，降低用户表达成本。
- 对连续澄清失败设置次数边界，不让对话陷入反复询问。
- 高风险或业务不确定场景转人工，或明确记录无法自动完成。
- 用户希望换任务时说明当前任务的状态，而不是每次强行拉回。

## Q11：跨轮 Workflow 怎样推进？暂停和恢复要保存什么？

**转写定位：** `00:14:54-00:17:12`、`00:19:15-00:20:55`。这是对原回答的机制补全。

### 先把三个不同的“状态”分开

| 状态 | 生命周期 | 例子 |
| --- | --- | --- |
| 一次 Turn 内的执行状态 | 一条用户消息处理期间 | 模型调用轮次、待执行工具、预算、结束原因 |
| 跨轮业务任务状态 | 多次用户输入之间持续存在 | 当前知识点、讲解/练习/理解验证节点、暂停状态 |
| 长期用户状态 | 跨任务、跨会话复用 | 掌握概率、偏好、目标与有证据的学习事实 |

**不能说：ChatPipeline 靠模型评分维护所有这些状态。** 现有项目资料中，ChatPipeline 是运行准备层，确定性学习流程由业务服务管理。

### 项目口述

> 我实现的分工是，Chat Agent 理解需求并通过受控 Action 连接学习服务，学习服务管理自己的任务步骤和作答验收，完成后将结果回流 Session 和记忆。一个 Turn 结束，不代表跨轮学习任务也结束。Workflow 的本次验收和长期 BKT 掌握状态也不是同一个变量，不能用模型一句“听懂了”直接覆盖长期掌握率。

### 如果白板上补充最小状态模型

下面是设计示意，不是新增数据库表名：

```text
task_id / user_id / session_id
task_type / current_node / status
confirmed_inputs / accepted_outputs
pending_question / referenced_evidence
state_version / updated_at
```

跨轮继续时，先从业务状态读取当前节点与缺失信息，再结合本轮输入装配上下文；不是每轮把整段聊天重新交给模型猜进度。

### 节点是否完成，由什么判断

- 格式、必填值、正式作答提交等确定性条件由代码判断。
- 开放式复述可以由量规辅助评分，但应有结构化结果与证据，不把模型自报完成当作唯一依据。
- 缺信息、无关内容和工具失败，应有明确分支，不默认为完成。
- 节点推进和长期掌握更新分开；同一作答重复送达也不能被吸收多次。

### 暂停与恢复的补强设计

1. 明确目标任务，记录当前节点、已确认输入、已接受结果和待回答问题。
2. 暂停后不继续启动新的业务副作用；已发出的操作要检查执行状态，不能假定全部撤销。
3. 恢复时校验用户归属、任务版本及依赖数据是否过期。
4. 重新装配必要上下文，而不是无限保留整个模型内部运行过程。
5. 对重复恢复和并发提交做幂等或版本保护，避免重复推进。

LangGraph 也能实现跨轮持久化与人工中断；使用其 `interrupt()` 时，恢复可能从节点开头重新执行，因此中断前的写操作仍需控制副作用。依据：[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)。

## Q12：三层 Memory 怎样设计？和短期上下文是什么关系？

**转写定位：** `00:26:49-00:29:27`。

### 90 秒项目口述

> 我实现的三层记忆不是按时间长短分三个缓存，而是按原始证据、场景归纳和跨会话用户模型分层。L1 保存原始事件或业务数据引用，再异步提取标签；L2 按场景把一组事件整理成可复用记忆，并关联来源 L1；L3 用当前画像和新增 L2 做增量归并，形成偏好、目标和学习状态等综合用户模型。
>
> 运行时我还单独保留近期原始对话，解决“刚刚那个”这样的指代；当前会话的 L2 压缩更早内容，L3 提供跨会话个性化。长期记忆不是聊天记录的替代品，画像也不是未经验证的永久结论。

本项目口径依据：[三层 Memory 学习稿](../../DeepTutor三层记忆多时长介绍.md)，按用户确认的真实项目经历使用。

### 每一层的职责

| 层 | 内容 | 为什么需要 | 不应该做什么 |
| --- | --- | --- | --- |
| L1 原始事件与标签 | 对话/作答/工具结果的原始依据或引用，以及派生标签 | 能回溯发生过什么，允许标签重跑 | 为了一个总结覆盖掉原始证据 |
| L2 场景记忆 | 一段讲解、练习或任务中的目标、过程与结果 | 压缩跨多轮事件，保留任务语义 | 把所有场景混成没有来源的长摘要 |
| L3 综合用户模型 | 当前可复用偏好、目标、学习事实 | 跨会话个性化和长期连续性 | 根据一次表现贴永久性格或能力标签 |

一条 L2 可以引用多个 L1；同一 L1 也能支撑多条 L2。L3 同样需要保留支撑它的 L2 来源，便于发现归纳错误后回查。

### 为什么异步提炼

原始事件先保存，模型提炼失败不应导致证据丢失，也不应阻塞当次回答。后续归并读取新增数据和已有结果，避免每次重扫全部历史。

需要进一步讨论可靠性时，可以补充：归并提交与处理游标要保持一致，任务可重试但结果不能无控制重复。这是工程可靠性说明，不把一个游标字段本身当作 exactly-once 保证。

### 为什么不直接用向量库保存全部记忆

当前需要的近期历史、当前会话 L2 和用户 L3 可以按用户和会话精确读取，关系存储就能表达来源关系与更新边界。向量召回可以是未来面对海量历史和同义查询时的优化，不是“有 Memory 就必须有向量库”。

### 画像里优先记录什么

- “希望先给提示，再给答案”这样的可观察偏好。
- “当前在复习某知识点”这样的任务事实。
- 有明确作答证据支持、且说明条件的学习状态。

尽量不把短时情绪直接归纳成“孤独、胆小、某种性格”。即使产品需要陪伴感，也不等于可以不加证据地推断心理特质。

## Q13：学生先错后对又错，怎么更新知识点掌握？

**转写定位：** `00:29:27-00:32:17`。

### 先纠正问题分类

“先错后对又错”通常是同一知识点上的新观测，不是必须删除旧值的事实冲突。先检查题目是否映射到同一知识点、是否独立作答、是否受提示，再决定如何吸收证据。

### 60 秒项目口述

> 我在学习闭环里用 BKT 更新学生的知识点掌握状态，不把一次答对等同于已经掌握。模型把掌握看成隐藏状态，把答对答错看成带猜测和失误的观测。在线收到一条有效作答，先做贝叶斯观测更新，再考虑学习转移；下一次从上次状态继续递推。参数来自离线估计，线上更新的是这个学生、这个知识点的状态，不是每道题重训一遍模型。

### 四个参数与一个在线状态

| 符号 | 含义 |
| --- | --- |
| `P(L0)` | 初次跟踪该知识点时已经掌握的先验概率 |
| `P(T)` | 未掌握者经过一次学习机会后转为掌握的概率 |
| `P(G)` | 未掌握时仍答对的概率，通常不只包含随机猜选项 |
| `P(S)` | 已掌握时仍答错的概率 |
| `p_t` | 当前学生在当前知识点上的掌握概率，是随作答递推的状态 |

经典四参数 BKT 可以表示为两状态 HMM。依据：[pyBKT 原始论文](https://educationaldatamining.org/EDM2021/virtual/static/pdf/EDM21_paper_237.pdf)。

### 在线更新公式

设作答前掌握概率为 `p`，猜测率为 `G`，失误率为 `S`，学习转移率为 `T`。

```text
预测本次答对：
P(correct) = p * (1 - S) + (1 - p) * G

观测到答对后：
q_correct = p * (1 - S) / [p * (1 - S) + (1 - p) * G]

观测到答错后：
q_wrong = p * S / [p * S + (1 - p) * (1 - G)]

加入学习转移：
p_next = q + (1 - q) * T
```

### 一个手算例子

仅作演算，取 `p=0.3, G=0.2, S=0.1, T=0.1`，不是项目训练结果。

```text
若本次答对：
q = 0.27 / (0.27 + 0.14) ≈ 0.6585
p_next ≈ 0.6927

若同一起点本次答错：
q = 0.03 / (0.03 + 0.56) ≈ 0.0508
p_next ≈ 0.1458
```

这不是给答对固定加分、答错固定减分；观测更新和学习转移描述的是两个不同机制。

### 追问 1：经典 BKT 不考虑遗忘，为什么概率还会下降？

无遗忘是潜在状态转移的假设，不是规定系统的判断只能上涨。新错误可能让系统发现之前高估了掌握程度，于是降低后验信念；这不等于模型已经包含“掌握后遗忘”的转移。

### 追问 2：掌握率 80%，是不是下题就有 80% 概率答对？

不是。预测答对还要考虑 guess 和 slip，按上面的 `P(correct)` 计算。你在面试里提到的 80% 还应被解释成业务可能采用的决策阈值，而不是 BKT 理论规定的合格线。

### 追问 3：提示后答对、复述正确也都更新 BKT 吗？

不应当作同类独立观测无条件混入。提示、答案曝光、重复作答需要保留条件；Workflow 的复述验收不直接等于 BKT 的一次独立答对。同一作答按事件标识幂等处理，避免重放造成虚假的掌握提升。

这些项目边界已在 [BKT 面经](../../new/BKT/面试准备/面经-BKT.md) 中统一，不需要新增“某次面试后才实现”的说法。

## Q14：BKT 是大模型、神经网络还是传统模型？EM 是什么？

**转写定位：** `00:32:17-00:32:48`。

**当时的明确错误：** 把经典 BKT 说成神经网络，并把 EM 混进模型类别。

### 45 秒参考回答

> 我这里使用的是经典 BKT，属于概率知识追踪模型，可以表示成两状态隐马尔可夫模型，不是大语言模型，也不是神经网络。EM 是估计这类带隐变量模型参数的常见算法，HMM 中常见的是 Baum-Welch。离线根据学生作答序列估计参数；线上用已发布参数对个人掌握状态做递推，两者要分开。

依据：[pyBKT 原始论文](https://arxiv.org/abs/2105.00385)、[参数约束论文](https://educationaldatamining.org/edm2024/proceedings/2024.EDM-long-papers.2/2024.EDM-long-papers.2.pdf)。EM 是方法解释，不据此擅自认定你的训练库。

### 为什么会用到 EM

训练数据知道学生答对还是答错，但不知道每个时刻到底是否掌握。因此需要用当前模型估计隐藏状态，再更新参数，使模型更好地解释训练序列。

```text
初始化参数
  -> E 步：根据训练序列和当前参数，计算状态与转移的期望统计
  -> M 步：根据统计量更新参数
  -> 反复迭代，检查收敛、参数约束和验证表现
```

训练时可以用完整训练序列做前向/后向计算；线上预测只能用当时已发生的历史，不能把未来答案提前喂进去。

### 项目里怎样讲自己的工作

> 我把群体参数估计与个人状态递推分开，并处理了知识点样本稀疏时的组级参数、回退和平滑。共享的是参数，不是把所有学生的状态混成一个值。每个学生、每个知识点的状态仍独立维护。

这是已有项目口径。具体用过哪个库、哪种初始化、多少迭代以及训练耗时，要据真实记录补充，不用论文里的实验数字替代。

### 面试官追问“怎么证明它有用”

- 与正确率等简单基线比较，不因模型更复杂就声称更好。
- 预测本题之前先计算预测，收到答案之后再更新状态，避免泄漏。
- 新学生泛化与同一学生未来预测是不同评估任务，要说清切分方式。
- 看真实预测与校准表现，并把“预测更好”和“学生学得更好”分开。
- 参数边界、稀疏组和充足组应分别检查，不能只看训练拟合变好。

## Q15：9 月 10 日、20 日、15 日开学，事实冲突怎么处理？

**转写定位：** `00:32:48-00:34:46`。

**当时已有的正确方向：** 发现冲突后向用户确认。

**需要纠正：** 最新、说得最多、已经到期，不自动等于事实最真实。

### 60 秒参考回答

> 我会先确认这些说法是不是同一学年、同一类开学事件，避免把报到和正式上课混为冲突。如果确实是同一事实，就保留各条来源，判断是用户纠正、学校改期还是无法核实的矛盾。当前证据只有 10 日和 20 日时，系统并不知道真实日期是 15 日，所以会问用户或查询允许使用的权威来源；没核实时标为待确认，不用时间权重静默选一个。确认后更新当前画像，原始记录仍然保留，方便追溯为什么改过。

### 正确区分三类变化

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 事实纠正 | “之前说错了，实际是 15 日” | 记录更正及来源，更新当前结论 |
| 现实发生变化 | 原定 10 日，后来正式改为 20 日 | 保存适用时间和变化原因，不把过去记录当作全错 |
| 证据冲突 | 两条说法不同，但没有解释 | 保留候选并澄清，未核实不强行确定 |

### 在已有三层记忆上怎样补强冲突治理

已有主线是 L1 保留原始事件、L2 关联证据、L3 做增量归并。若需要更严格的事实治理，可以补充以下信息；这是本题的增强方案，不声称已建设复杂版本链：

```text
事实对象与属性：同一用户、同一学年、同一种事件
事实值：日期等结构化内容
source_refs：来自哪些 L1/L2 或业务记录
recorded_at：什么时候被系统记录
valid_time：这条事实适用于什么时间
status：待确认 / 已确认 / 被纠正等状态
```

### 时间和频率还能不能用

可以用于排序、检索、判断信息是否需要重新确认，但不能单独裁决事实真伪。

- 新消息可能只是记错了，不能自动覆盖已确认的可靠记录。
- 同一来源重复三次，不等于三份独立证据；模型自己重复总结也不增加事实权威性。
- TTL 到期表示当前使用价值可能下降，不说明这条历史记录从未真实发生。
- 用户明确更正通常比含糊推断更有用，但仍要对齐对象、事件和上下文。

### 两个适合跨行业追问的例子

- 用户以前不吃辣，后来表示“这周可以吃一点”：可能是带有效期的偏好或限制变化，不该直接抹掉历史。
- 某订单此前待支付，随后业务接口显示已支付：当前业务状态应以可信业务系统为准，不由聊天次数投票。

**一句话记忆：学习状态靠新证据递推，事实冲突靠来源与澄清；时间衰减不是事实裁判。**
