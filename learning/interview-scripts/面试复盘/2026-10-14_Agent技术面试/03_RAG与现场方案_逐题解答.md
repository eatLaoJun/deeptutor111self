## Q16：Embedding 和 Reranker 的本质区别是什么？

**转写定位：** `00:34:46-00:36:45`。

**当时的问题：** 回答了“召回和重排”“模型大小和成本”，但没有解释输入结构和计算方式。

### 60 秒参考回答

> 典型 Dense 召回使用 Bi-Encoder，把 Query 和文档分别编码成向量，文档向量可以离线算好，在线只编码 Query，再用向量索引检索。典型 Cross-Encoder Reranker 则把 Query 和候选文档联合输入，直接计算这一对内容的相关性，能进行更细的条件化匹配，但一般要逐候选计算。所以常见架构是先高效召回，再对小候选集精排。区别不在于前者一定小、后者一定大，也不是所有 Reranker 都只能是某一种结构。

依据：[Sentence-BERT 原论文](https://arxiv.org/abs/1908.10084)、[Sentence Transformers 检索与重排](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)。

### 白板上怎么画

```text
典型 Bi-Encoder：
Query -> Encoder -> q
Doc   -> Encoder -> d（文档向量可以预计算）
                     -> similarity(q, d) / ANN 检索

典型 Cross-Encoder：
[Query, Doc] -> 联合模型计算 -> relevance_score
```

Bi-Encoder 的“双塔”不必代表两套不同权重，也不一定是两个独立服务；关键是检索时可分别编码。

### 可以对照讲的四点

| 维度 | 典型 Dense Bi-Encoder | 典型联合评分 Reranker |
| --- | --- | --- |
| 模型输入 | Query、Doc 分别进入编码 | Query 与当前候选联合输入 |
| 输出 | 可复用的向量表示 | 与当前 Query 相关的匹配分数 |
| 离线复用 | 文档向量可预计算并建索引 | 不能把任意 Query 下的最终相关性分数预先算完 |
| 在线主要工作 | Query 编码、ANN 检索与过滤 | 对每个候选进行模型打分，可批处理 |

### 接回你的真实项目

> 我在鼎校伴学中采用 Qdrant Dense 召回和 BM25 关键词召回，两路候选经 RRF 融合后，再交给 Qwen-Rerank 做内容相关性重排。教材年级、版本、册别等先做范围约束，避免召回内容虽然相似却不是用户当前教材。

这里用已有组件口径，不补充尚未确认的 Qwen 模型 ID，也不带入没有在本次任务核验的效果数字。

### 一个常见概念陷阱

“Embedding 模型”是较宽的概念，“Reranker”描述任务角色。面试中的典型对比是独立编码召回与联合评分精排，不意味着世界上所有检索模型都只能分成两个固定结构。

例如 Qwen3-Reranker 官方模型卡就展示了生成模型式相关性评分。它是说明架构多样性的例子，不代表你的生产环境使用的就是该具体型号。依据：[Qwen3-Reranker 官方模型卡](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)。

## Q17：为什么不直接对全库 Rerank？本地部署还考虑什么成本？

**转写定位：** `00:36:45-00:37:40`。

### 45 秒参考回答

> 因为联合相关性评分依赖当前 Query，对全库每个文档都打分通常需要大量模型计算，无法像文档向量那样一次离线编码、长期复用。即使本地部署没有按次 API 账单，也仍然消耗算力、显存、吞吐和时延预算，所以通常先用索引缩小候选，再精排。不过如果只有几十个短片段，直接全部重排也可能更简单，不是绝对不能用。

依据：[Sentence Transformers 检索与重排](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)。

### 用数量级解释，而不是编造毫秒数

下面只是容量示例，不是项目实际规模或延迟：

```text
文档集合：100 万条

全库联合评分：
当前 Query 与约 100 万条文档分别组成候选对进行打分

先召回再重排：
Query 编码 + 向量/关键词索引检索
  -> 例如得到 50 条候选
  -> 只对这 50 条做联合评分
  -> 返回例如 Top 10
```

实际耗时还受文本长度、模型结构、批大小和硬件影响。ANN 也不是“免费”，但索引复用和候选收缩使计算方式不同；批处理可以改善重排吞吐，不会让需要处理的全部候选自动消失。

### 进一步追问

**“反正硬件已经买了，不就是没成本吗？”**

> 固定硬件仍有容量上限。一个请求占满计算会影响其他请求的排队、并发与体验，资源的机会成本并不会因为没有按次账单消失。

**“全部重排一定更准吗？”**

> 不一定。最终质量还受模型、文本截断和数据噪声影响，必须评估；大集合全打分即使能找到相关文档，也可能超出线上时限。小集合可以直接尝试，用实测比较，而不是把两阶段检索当作不可改变的教条。

**“Reranker 能补救所有召回遗漏吗？”**

> 不能。相关文档没进候选，它通常就没有机会打分。所以要分别看候选召回质量和候选内部排序质量。

## Q18：为什么 Reranker 通常能精排？RRF 又为什么放在它之前？

**转写定位：** `00:37:40-00:37:59`。RRF 是结合你的项目追加的相关追问，不是面试官当时的独立原题。

### 为什么能精排

> 典型独立编码会把文档压缩成与具体 Query 无关的表示，再通过较简单的相似度函数匹配；联合评分模型能在看到当前 Query 的条件下阅读候选正文，更细地判断限定条件、否定关系和问题对应的细节。这通常有利于排序，但不是因为名字叫 Reranker 就一定更准，仍要看训练目标、数据和验证结果。

对于典型 BERT Cross-Encoder，可以解释 Query/Doc token 的联合注意力；但不要把这种双向可见的具体结构硬套到所有生成式 Reranker。Qwen3 一类模型还可以利用相关性标签的条件得分，不能统一说成“都是 BERT 加分类头”。依据：[Sentence Transformers 官方说明](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)、[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)。

### 一个教材例子

用户问某个限定版本、限定章节的概念区别，两个 Chunk 都含有关键词：

- 一个只是目录或概念名称列表。
- 一个给出了对应条件下的完整解释。

向量召回可以把两者找进来，联合评分再判断哪个正文更能回答当前问题。但教材版本等已知硬条件，仍应优先用元数据过滤，不能指望重排自动修正一切范围错误。

### RRF 和 Reranker 分别做什么

```text
Dense 候选 + BM25 候选
  -> 按 chunk_id 等稳定标识去重
  -> RRF 按两路名次融合
  -> Reranker 读取 Query 与候选正文重新打分
```

RRF 不直接把向量相似度和 BM25 分数相加，因为两者量纲和分布不同。一个常见表达是：

```text
RRF(d) = sum_i 1 / (c + rank_i(d))
```

`c` 是平滑常量，不是最终返回条数；缺席某一路的文档在该路不贡献分数。RRF 根据排名融合，Reranker 根据文本内容与 Query 再评分，两者并不重复。依据：[RRF 原论文](https://cormack.uwaterloo.ca/cormack/cormacksigir09-rrf.pdf)。

### 如何证明重排有收益

- 固定语料、查询集和候选集，再比较排序变化。
- 检查 Top K 证据命中、MRR 或 nDCG 等适合任务的指标，以及推理耗时。
- 区分“从未召回到”和“召回了但排得低”，分别定位问题。
- 重排分数不一定是校准过的概率，不给所有模型统一套用一个看似通用的分数阈值。

## Q19：怎样回答现场的“规则校验 + 结构化方案生成”需求？

**转写定位：** `00:38:17-00:47:35`，其中需求主体在 `00:38:59-00:42:59`。

**当时的问题：** 过早归纳成企业知识库问答，并引入未确认的组织隔离；没有突出规则执行和最终验证。

下面抽象为通用的“资源配置记录”系统，讨论软件契约、规则管理和验证链，不展开具体领域参数。全部属于现场参考设计，不是你的既有业务经历。

### 第一件事：准确复述需求

> 我理解这里有两条链路：第一条是接收其他系统已经生成的 XML，检查其结构和内容是否满足当前有效规则；第二条是把自然语言需求转成候选配置，再验证并输出符合下游契约的 XML。两条链路应该复用同一套内部数据模型和规则服务。知识库提供来源依据，但校验系统不能只依赖模型读到几段文字后给一个“通过”。

这一段先说出来，比先报向量库、Agent 框架和多租户更对题。

### 先问清五个问题

1. **交付契约是什么？** 有现成 XML 样例、XSD、字段含义和下游接口吗？输出是“可解析”，还是必须通过特定业务验收？
2. **哪些规则必须准确执行？** 哪些是硬约束，哪些只是建议；现有规则是否已有结构化表达？
3. **规则由谁发布和审核？** 来源冲突、版本、生效时间及例外如何裁决，更新频率如何？
4. **生成失败怎么办？** 信息缺失、规则矛盾或不存在可行结果时，能否澄清、返回不可行，是否必须人工审核？
5. **运行约束是什么？** 数据量、时限、并发、离线环境、动态数据来源，以及正式提交前是否需要用户确认？

不必在面试中连续问完才开口，可以先说明“我先按已有 XSD、硬规则需确定性执行、候选结果需审核这几个假设展开”，再给方案。

### 总体设计：四个职责分开

| 组件 | 核心职责 | 不该代替谁 |
| --- | --- | --- |
| 文档与规则知识层 | 解析资料、检索证据、追溯来源 | 检索到的 Top K 文本不等于全部适用规则 |
| 结构化规则与事实服务 | 提供已审核规则和可信当前事实 | 不能把模型临时编出的规则自动发布 |
| LLM / Agent | 理解自然语言、提出候选、解释错误、协调受控工具 | 不单独裁决硬约束，不自行越权提交 |
| 确定性校验与序列化 | 检查结构、引用、范围、跨字段及动态事实，输出契约格式 | 不因模型说“通过”就绕过验证 |

### 1. 文档入库：不只是切块放向量库

```text
PDF / Word / Excel / 图片
  -> 文本、表格和必要 OCR 解析
  -> 保留页码、表格单元、来源和原始文件引用
  -> 清理并按语义结构组织内容
  -> 检索索引：用于找依据和解释
  -> 候选规则提取：对象、条件、限制、单位、例外、来源
  -> 规则审核与测试
  -> 发布版本化的可执行规则
```

表格和图片里的单位、条件、否定词、例外不能在提取时丢掉。模型可以辅助提取规则，但提取正确与否需要审核和用例验证，不是入向量库就完成了规则治理。

### 2. 区分规则与事实

- 规则回答“允许什么、不允许什么、在什么条件下允许”。
- 动态事实回答“目前有哪些资源、当前状态是什么”。
- 规则和事实都应有来源、适用范围与版本/时间；它们不应该无条件合成一段无法追溯的 Prompt。
- 同一任务校验应绑定明确版本或快照，避免生成时与审核时使用互相不一致的条件。

出现冲突，按业务定义的权威性、适用范围和生效规则处理；没有确定优先级就返回冲突待处理，不让模型在后台随意挑一条。

### 3. 校验已有 XML 的链路

```text
外部 XML
  -> 受限解析与基础完整性检查
  -> 按下游契约做 XSD 校验
  -> 映射到统一内部对象
  -> 根据对象属性与上下文选择全部适用规则
  -> 读取规则版本与可信事实
  -> 执行确定性校验
  -> 返回通过 / 不通过 / 无法确定，以及证据和错误定位
```

**最重要的一点：** 硬约束应通过明确的适用性规则查全，不能只靠语义 Top K 检索到几条。未检索到约束，不等于没有约束。

检索可以帮助理解文档、补充说明和定位条款；规则服务负责可执行约束的完整选择和执行。

### 4. 从自然语言生成 XML 的链路

```text
自然语言需求
  -> 结构化需求：目标、对象、范围、必要条件与缺失信息
  -> 缺关键条件：澄清，不编造
  -> 加载适用规则与可信事实
  -> 构造候选内部对象
       可采用模型辅助 + 模板/程序/约束求解等合适机制
  -> Schema 与确定性业务校验
  -> 不通过：定向修正、澄清或返回不可行，限制循环
  -> 通过：用程序序列化为 XML
  -> 再做输出 XSD 校验和必要一致性检查
  -> 审核/确认后交付下游
```

你当时提到“先生成 JSON，再转 XML”是可以保留的方向，但要补全：JSON 只是中间表示；关键是类型化对象、映射规则和最终 XML 契约。JSON Schema 通过，不自动代表 XML 满足 XSD，更不代表业务内容正确。

### 5. 大批量条目不要一次全交给模型写

转写中提到数千条记录的规模要求。回答时应从系统容量角度说明：

- 让模型理解高层需求、生成受约束的结构，而不是一次吐出所有重复记录。
- 重复性展开、唯一标识生成和格式序列化由程序处理。
- 任务按作业执行并跟踪进度，受总时间和资源预算约束。
- 局部数据分批处理后，仍需做全局一致性检查，不能每批都合法就宣称整体合法。
- 有不可满足的硬约束时返回原因，不为了“必须生成一个结果”悄悄放宽条件。

具体采用模板、规则程序还是约束求解，要由问题结构决定，不是看“Agent 能调用几个工具”。

### 6. 校验报告应返回什么

下面是通用报告协议示例，不是面试中真实系统的接口：

```json
{
  "status": "failed",
  "ruleset_version": "example-v1",
  "violations": [
    {
      "record_id": "record-001",
      "field_path": "items[0].count",
      "rule_id": "example-capacity-rule",
      "actual": 12,
      "expected": "must not exceed the approved limit",
      "source_ref": "example-document#section-2"
    }
  ]
}
```

报告要能回答：哪里违反了哪条规则、依据在哪里、使用了哪个版本。缺数据无法判断时应显式标记 unknown，不能和 pass 混为一谈；正式发布是否允许带未知项，由验收约定决定。

### 7. XML / XSD 能保证什么

- XML 可解析：说明文档基本语法完整。
- XSD 校验通过：说明符合所用 Schema 版本能够表达的结构、类型等约束。
- 业务校验通过：说明在给定规则与事实下，已执行的领域约束满足。

XSD 自身也能表达某些键、引用及断言约束，不必把它说成“只看标签”。但依赖外部动态数据、复杂领域逻辑的判断仍需要应用校验。具体用 XSD 1.0 还是 1.1，以已有系统与解析器支持为准。依据：[W3C XSD 规范](https://www.w3.org/TR/xmlschema11-1/)。

### 8. 技术栈怎么说才不过早选型

先给职责，再给可选组件：

- 服务层承接作业、查询和校验接口，适配项目已有后端体系。
- 类型模型和校验层保证内部契约，XML 库负责解析、XSD 和序列化。
- 关系存储管理规则、来源、版本、审核与作业状态。
- 检索层支持关键词与语义查询，用于找证据，不替代规则完整性。
- 本地模型服务负责理解与候选生成，受控工具负责业务读写。
- 后台作业支持大任务执行与进度记录，日志能关联输入、规则、模型和结果版本。

不需要在需求尚未明确时列一串产品名。已有系统若已经有规则服务，应优先复用，不默认重新造一套。

### 9. 怎样验证系统，而不是只演示一个“看起来对”的例子

1. 准备合法样例、每类违规样例、规则冲突样例和缺失事实样例。
2. 单独验证文档提取与规则审核，尤其检查表格、单位和例外。
3. 验证一条已有 XML 从输入到报告的完整路径。
4. 验证自然语言生成后必经同一套校验，不能走旁路。
5. 检查规则更新后相同输入能否复查旧结果，并得到新版本判断。
6. 评估错误放行、错误拦截、未知比例、人工介入与端到端时延，不只统计模型输出率。

### 可直接口述的 2 分钟答案

> 我会先把需求分成已有方案校验和新方案生成两条链路，并确认 XML 契约、硬约束、规则来源与人工审核要求。
>
> 文档侧不仅做 RAG 入库，还会把规则整理成可审核、可追溯、可执行的规则集。原始文档和检索索引用于找依据，规则服务负责选择全部适用规则，动态数据从可信业务系统读取。
>
> 对已有 XML，先解析和做 XSD 校验，再映射到统一内部对象，运行确定性规则，输出带字段位置、规则编号和来源的校验报告。对自然语言生成，先抽取结构化需求，信息不够就澄清，再构造候选对象；候选通过同一套校验后，由程序转换成最终 XML 并再次检查输出契约。大量重复条目由程序展开，不让模型一次生成所有明细。
>
> LLM 负责理解、辅助生成和解释，RAG 提供证据，程序负责硬约束；如果条件矛盾或规则不全，要能返回不可行或无法确定，而不是编一个通过的结果。最后用正常、违规、冲突和缺数据用例验证两条链路。

### 本题最应避免的三个开头

- “这就是企业知识库问答，先搭个向量库。”——遗漏核心校验责任。
- “这里先做多租户、按组织划知识库。”——把未确认需求当成核心约束。
- “把规则给模型，让它判断对不对。”——没有明确硬约束的执行与验证边界。

## Q21：H100 和国产加速卡区别不大吗？

**转写定位：** `00:48:11-00:48:56`。

**当时的问题：** 把模型权重概念上的相同，等同于运行栈和部署流程可以照搬。

### 45 秒参考回答

> 模型参数和业务输入输出可以相似，但部署环境不能因此视为相同。不同硬件涉及驱动、运行时、算子、精度、通信和推理框架后端支持；量化、长上下文和并发能力也要分别验证。我接触过 H100 环境，但没有独立做过国产加速卡迁移，所以不会直接承诺照搬。实际迁移会先查目标硬件的完整兼容组合，验证模型正确性，再测业务长度和并发下的资源与时延。

不同硬件后端和插件的依赖要求可见 [vLLM GPU 安装文档](https://docs.vllm.ai/en/latest/getting_started/installation/gpu/index.html)、[vLLM Ascend 安装文档](https://docs.vllm.ai/projects/ascend/en/main/getting_started/installation.html)。这里只引用兼容性原理，不认定项目使用了这些框架。

### 迁移主要核对什么

- **能不能运行**：模型架构、算子、运行时和框架版本是否在支持范围。
- **输出是否可信**：精度或量化变化是否影响业务质量、结构化输出与相关协议。
- **资源是否够用**：模型权重之外，还需考虑 KV Cache、运行临时空间及并发。
- **性能是否满足**：按相同输入输出长度与并发比较 TTFT、吞吐和端到端时延，不能只比峰值算力。
- **能不能维护**：离线依赖、监控、版本回退和问题定位是否可操作。

国产加速设备也不是一套统一技术栈；例如部分是 NPU，不能默认所有卡都使用同一种 GPU 软件生态。
