# 鼎校伴学 Agent Runtime 面试口述稿

> 对应简历第一条职责：参与 Agent Runtime 核心能力建设。
>
> 使用原则：先讲业务问题，再讲 Runtime 分层和执行闭环，最后讲稳定性与复用价值。
> 面试官没有追问时，不主动强调单批工具数量、内部类名或过多实现细节。

## 3 分钟版本

鼎校伴学面向 K12 学习场景，除了普通问答，还包括英语三合一、单词测评、
试卷学情分析等约 7 类学习服务。这些场景都会涉及模型调用、知识检索、OCR、
题库查询和结果回写。如果每个场景分别实现一套调用流程，重复代码多，异常处理和
上下文规范也不统一，所以我们建设了一套统一的 Agent Runtime。我主要参与
Agent Loop、工具调度协议以及任务收敛机制。

我把 Runtime 的职责分成两层。Agent Runtime 管理整个任务生命周期，包括上下文
组装、模型推理、多轮决策和最终结束；Tool Runtime 管理一次或一批工具调用，包括
参数校验、运行时参数注入、异步执行、结果封装和异常隔离。

具体执行时，请求首先被组装成 UnifiedContext，里面包含当前问题、近期对话、
用户画像、知识库和附件等信息。Agent Loop 根据这些信息构造 Prompt 和工具 Schema，
然后调用模型。如果模型可以直接回答，本轮就结束；如果模型返回 Tool Call，Runtime
会根据工具名称从 Tool Registry 找到对应实现并执行，再把结果统一封装成
`role=tool` 消息回填给模型。模型读取工具结果后继续判断，是继续调用工具，还是生成
最终回答，这样形成“模型推理、工具调用、结果回填、继续决策”的闭环。

工具调度方面，不是简单地把所有工具串行 `await`。同一轮中没有依赖关系的工具会
通过异步任务和 `asyncio.gather` 并发执行；有前后依赖的工具则由模型分轮调用。例如
试卷学情分析需要先完成 OCR，拿到题目结构后，下一轮才能进行教材 RAG 和知识点匹配。
单个工具异常会被转换成结构化的失败 ToolResult，而不是直接打断整批任务。模型可以
根据错误选择重试、降级到其他工具，或者基于已有信息回答。

最后是任务收敛。我们通过可配置的最大执行轮次、批内重复调用去重、上下文裁剪和
Forced Finish，避免模型反复调用工具或者一直不输出答案。Forced Finish 会关闭工具
调用，让模型基于当前已经获得的信息生成一次 best-effort 回答。同时通过统一 Trace
记录模型轮次、工具名称、状态、耗时和异常，便于定位问题。

最终这套 Runtime 被复用到约 7 类学习服务中。不同业务主要接入自己的 Prompt、工具
和数据源，不需要重复实现 Agent Loop，稳定性策略也可以在 Runtime 层统一升级。

## 5 分钟版本

鼎校伴学是一个面向 K12 场景的智能伴学平台。它不只是聊天问答，还要支撑英语三合一、
单词测评、试卷学情分析、题目讲解等约 7 类学习服务。这些场景的共同特点是，一个用户
请求通常不能靠单次模型调用完成，而是需要模型结合对话上下文，调用 OCR、教材 RAG、
题库、用户画像或者学习任务服务，再根据工具结果继续做决策。

如果每个学习服务都单独编写模型调用、工具执行和异常处理代码，会出现三个问题。第一是
重复建设，不同服务都有自己的循环；第二是协议不统一，工具返回结构、错误处理方式不同；
第三是任务不可控，模型可能重复调用工具、上下文持续增长，甚至一直没有最终结果。因此
我们把这些通用能力下沉成统一 Agent Runtime。我主要参与 Agent Loop、Tool Calling
调度、异常隔离、任务收敛和执行 Trace 这几部分。

从整体架构上，我把它理解为两个运行时。

第一层是 Agent Runtime，负责整个任务从开始到结束的生命周期。请求进来以后，先通过
UnifiedContext 统一承载当前问题、近期对话、用户画像、知识库选择、附件和运行配置。
ChatOrchestrator 再根据当前场景选择对应能力，默认问答会进入 Chat Agent Loop，复杂
能力也可以进入专门的 Capability。

进入 Agent Loop 后，每一轮主要做三件事。第一，基于 UnifiedContext 和当前循环状态
组装模型消息及可用工具 Schema；第二，调用模型进行决策；第三，根据模型返回判断是结束
还是执行工具。如果模型没有返回 Tool Call，并且有有效文本，就把文本作为最终答案结束；
如果返回了 Tool Call，就进入工具调度，执行完成后把结果作为 `role=tool` 消息追加到
当前消息列表，再进入下一轮模型推理。

第二层是 Tool Runtime。它不负责决定“为什么调用工具”，这个决定由模型做；它负责
“选中的工具如何安全、统一地执行”。我们通过 Tool Registry 管理工具定义和实例，对
模型只暴露名称、描述和 JSON 参数 Schema，不会把具体代码交给模型。Dispatcher 收到
Tool Call 后，会完成 JSON 参数解析、工具查找以及服务端参数注入。例如模型只传业务参数，
用户、Session、知识库和沙箱等可信参数由 Runtime 注入，避免模型伪造。

工具执行不是简单地逐个 `await`。如果模型同一轮返回多个彼此独立的 Tool Call，
Dispatcher 会将它们创建为异步任务，通过 `asyncio.gather` 并发等待；如果工具之间存在
依赖，则不会强行并行，而是让模型通过多轮完成。例如在试卷学情分析中，第一轮先调用
OCR 获得题目结构；结果回填以后，模型第二轮才能基于题目内容调用教材 RAG、知识点匹配
或者题库服务。这里并行解决的是同一决策批次中的独立任务，Agent Loop 解决的是有依赖
关系的多阶段任务。

Tool Runtime 还有一个关键能力是失败隔离。每个工具调用都有统一的 ToolResult，包含
成功状态、返回内容、错误信息以及 pause、terminate 等控制信号。普通工具抛出异常时，
Runtime 会捕获并转换成失败结果，所以同一批次中的一个工具失败，通常不会取消其他工具，
也不会直接导致整个 Agent Loop 崩溃。失败结果仍然回填给模型，模型可以选择修改参数重试、
换用其他工具，或者根据已经拿到的证据完成回答。失败隔离不等于一定恢复成功，而是把故障
从“程序异常”转换为“模型可以继续处理的观察结果”。

第三个重点是任务收敛。Agent 不能只会循环，还必须明确结束。我们设置了可配置的最大执行
轮次；同一批次中相同工具和相同参数只实际执行一次，避免模型一次生成重复调用；上下文
接近窗口限制时，会优先裁剪较早的工具原文，保留摘要和关键结果。如果达到轮次上限，或者
已经执行过若干轮后模型调用发生异常，Runtime 会进入 Forced Finish：关闭工具 Schema，
并明确要求模型基于当前已有材料直接给出回答。Forced Finish 保证的是有界结束和
best-effort 输出，不保证答案一定正确。

在可观测性方面，我们统一记录 Session、Turn、模型调用和 Tool Call 的关联关系，以及
工具名称、脱敏参数、成功状态、耗时和异常。这样线上出现问题时，可以判断是模型没有正确
选择工具、工具本身执行失败、结果回填异常，还是 Agent Loop 没有正常收敛，而不是只看到
一句“回答失败”。

这套 Runtime 最终复用到了约 7 类学习服务。它的核心价值不是单纯提高某一次调用速度，而是
把模型推理、工具调度、异常处理和任务结束规则统一起来。新场景主要扩展 Prompt、工具和
领域服务，不需要重新实现 Agent Loop；同时 Runtime 层的稳定性改进可以被所有学习场景共享。

## 速记主线

> 业务重复建设问题 -> Agent Runtime 与 Tool Runtime 分层 -> 模型和工具多轮闭环 ->
> 独立工具批内并发、依赖工具分轮执行 -> 失败隔离 -> 收敛与 Trace -> 约 7 类服务复用。

## 面试表达边界

1. 不说“工具异常后一定能恢复”，而说“异常被结构化回填，模型可以重试、降级或基于已有结果继续处理”。
2. 不把重点放在单批工具数量，并发上限只是保护参数，核心是独立工具批内并发、依赖工具分轮执行。
3. Forced Finish 保证任务有界结束和尽量给出结果，不代表能够保证答案正确。
4. 团队架构使用“我们建设”，个人职责使用“我主要参与”，不要把团队成果全部表述为个人独立完成。
