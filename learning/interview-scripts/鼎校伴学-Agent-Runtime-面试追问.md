# 鼎校伴学 Agent Runtime 面试追问与回答

> 配合《鼎校伴学 Agent Runtime 3 分钟与 5 分钟口述稿》使用。
> 回答顺序：先给结论，再解释设计取舍，最后用一个学习场景举例。
> 本文是面试准备稿，不是新增功能的实现记录。标为“扩展设计”的内容，不应表述成已经上线。

## 一、先统一项目边界

鼎校伴学是面向鼎校甄选用户的 AI 伴学项目。主链通过 Agent Loop 支持对话、知识工具调用，
并通过受控 Action 连接约 7 类学习服务。个人重点参与词汇量检测、英语三合一和试卷学情分析。

| 主题 | 本文采用的回答边界 |
| --- | --- |
| Agent Runtime | 按已讨论的执行闭环、工具调度、异常隔离、收敛和 Trace 展开 |
| 主 Agent | 负责当前对话的任务理解、工具选择、结果整合和最终响应 |
| Subagent | 尚未在已确认项目描述中体现，按概念和扩展设计准备，不默认声明已使用 |
| Skill | 讲清与 Tool、Subagent 的区别；若没有实际加载链路，不宣称已经建设 Skill 系统 |
| DAG | 能解释依赖关系，不等于已经实现通用 DAG 调度器 |
| Plan 模式 | 多轮 Tool Calling 不等于已实现独立的“计划、确认、执行”模式 |
| 量化结果 | 以下给测量口径，不新增或认证实测数字；此前拟定的模拟值不能作为评测证据 |

## 二、Runtime 与 Agent 分工

### 1. 你做的 Runtime 和直接调用一次大模型有什么区别？

**可以这样回答：**

> 单次模型 API 负责生成文本或工具调用请求，Runtime 管的是这些请求如何真正执行。
> 它维护一个用户回合中的工作上下文，执行工具并回填结果，管理多轮决策、预算、错误与
> 结束状态。我的工作不是换个 API 包装，而是把模型输出转成可执行、可追踪、可约束的任务过程。

追问到组件时再讲：TurnOrchestrator 管回合生命周期，ChatPipeline 做运行准备，
Agent Loop 驱动决策，Tool Runtime 执行工具，外层 Turn Runtime 管会话数据与持久化。
Agent Runtime 是整体体系，不是其中某一个类，也不只是 try/except。

### 2. 主 Agent 和 Subagent 有什么区别？

**可以这样回答：**

> 主要区别是责任范围和执行上下文，而不是一个模型大、另一个模型小。主 Agent 面向用户，
> 理解整体目标并整合最终结果；Subagent 接受一个边界明确的子任务，在自己的上下文中完成
> 局部推理或工具调用，再把结果交回主 Agent。两者可以使用同一个模型，也不一定是独立进程。

这里采用“独立工作上下文、任务委派、结果回传”的 Subagent 定义，可参考
[Anthropic 的 Subagent 说明](https://code.claude.com/docs/en/sub-agents)。这是概念参考，
不是说鼎校伴学已经接入该产品。

**项目中的扩展示例：**

用户要求综合分析一份多学科试卷时，主 Agent 可以把不同学科的证据核对交给专门 Subagent，
最后汇总成报告；每个 Subagent 只拿到本学科题目和相关证据。简单的 OCR API 调用或一次
教材检索仍然是 Tool，不需要为每个步骤都创建 Agent。

#### Subagent 如何定义：模板不等于运行实例

工程上可以预先注册 Subagent 模板，也可以用一个通用模板承接动态子任务。预定义的是角色、
模型、工具范围和执行约束，运行时生成的是具体委派任务与执行实例，不需要临时生成一套
Agent 源代码或训练新模型。以下是自定义 Runtime 的设计示意，不是任何框架的可直接运行配置：

```yaml
name: exam_analyzer
description: 分析试卷中的知识点薄弱项，返回有证据的结论
system_prompt: 只依据题目、作答和可验证证据分析，缺失信息需注明
model: inherit
allowed_tools: [rag, query_question_bank]
max_rounds: 5
output_schema: ExamAnalysisResult
```

主 Agent 可以只看到可委派对象的名称与说明，再提出这样的调用请求：

```text
delegate(
  agent_type="exam_analyzer",
  task="分析这份数学试卷的薄弱知识点",
  input_ref="exam_123"
)
```

Runtime 从已注册模板取配置，校验权限与预算，创建或恢复子任务运行状态，再把本次任务
和必要证据放进子任务上下文。同一个 exam_analyzer 模板可以用于很多次不同的试卷分析，
每次运行都有自己的任务 ID、消息状态和结果。

“必须预定义每一种专用角色”不是 Subagent 的本质要求。也可以只预定义通用执行模板，
由主 Agent 提供不同目标；如果支持模型提出新配置，仍应由 Runtime 校验并限制权限。
动态生成任务说明不等于允许模型自行扩大工具权限，也不等于必须动态生成 Agent 代码。

### 3. 为什么你的主链不直接做成多 Agent？

**可以这样回答：**

> 我优先按任务复杂度设计，而不是按业务数量拆 Agent。约 7 类学习服务不代表需要 7 个
> Agent。问答和服务入口引导，用一个主 Agent 配合工具就可以完成；正式测评等确定性流程
> 仍由业务服务负责。过早拆成多 Agent 会增加模型调用、上下文传递和结果冲突处理成本。
> 当子任务确实需要独立的多轮探索、专门权限或大段工作上下文时，我才考虑引入 Subagent。

选择依据：任务能否独立完成、输入输出能否明确约定、隔离收益是否超过调度成本。
同批调用多个工具只是工具并发，不自动等于多 Agent 协作。

### 4. 如果扩展 Subagent，你会怎么设计？

**扩展设计，不是已实现功能：**

1. 明确委派协议：传入子任务目标、输入证据、允许工具、输出 Schema、轮次与时间预算。
2. 隔离工作上下文：按需传递相关消息，不默认复制主 Agent 的全部历史；记录父子任务 ID。
3. 约束权限与资源：子任务只能使用分配的工具；子任务用量计入父任务总预算，并限制并发和深度。
4. 结构化回传：返回状态、结论、证据引用、缺失信息和用量，而不是把全部内部过程塞回主上下文。
5. 校验结果：主 Agent 整合输出，Runtime 检查结构与来源；多个子任务结论冲突时不能直接拼接。
6. 隔离副作用：优先让子任务产生分析或变更建议，由受控业务服务统一提交，避免并发重复写入。
7. 传播取消：父任务取消时停止继续派发，取消可取消的子任务；已发生的外部写入仍需核对或补偿。

不能承诺“用了 Subagent 总 Token 一定下降”。它可能减少主上下文占用，但新增模型调用和
子任务输入会提高总成本，需要比较相同任务集下的质量、总费用和耗时。

## 三、Skill、Tool 与 Subagent

### 5. Skill 和 Subagent 有什么区别？

**可以这样回答：**

> Skill 是可复用的做事方法和资源包，Subagent 是承担子任务的执行者。Skill 可以包含
> 指令、示例、脚本和参考材料，Agent 按需加载后依照它执行；Skill 本身不等于一个独立
> Agent Loop。Subagent 则有自己的工作上下文和执行过程，也可以加载 Skill。

Skill 的资源包与渐进加载概念参考
[Agent Skills 官方说明](https://agentskills.io/home)。不要把 Skill 限定成“只有一段 Prompt”，
也不要把加载 Skill 描述成“启动一个子 Agent”。

| 对象 | 解决的问题 | 学情分析中的例子 |
| --- | --- | --- |
| Skill | 按什么方法做 | 先检查证据，再按知识点解释薄弱项，最后给建议的分析规范 |
| Tool | 能执行什么动作 | OCR、教材检索、查询题库、返回业务入口 |
| Subagent | 哪个执行单元承担子任务 | 独立核对数学部分并返回结论和引用的分析 Agent |
| 主 Agent | 如何围绕用户目标整合 | 判断是否委派，整合结果并向用户解释 |

一个 Tool 内部可以封装 Subagent，所以“作为工具暴露”和“内部是 Agent”并不矛盾。
反过来，一个工具内部调用了 LLM，也不足以证明它就采用了独立 Subagent 架构。

#### 都可以预定义，为什么仍然不同？

是否提前定义、由人还是模型编写、使用 Markdown 还是 YAML，都不是核心区分依据。
两者可能都有 name、description、适用场景和 Prompt，关键在于 Runtime 读取后做什么：
Skill 是供执行者消费的说明和资源；Subagent 模板是用来配置一个子任务执行者的。

以同样的“试卷学情分析规范”为例，Skill 可以描述“校验题目与作答、查教材证据、按知识点
汇总薄弱项、注明不确定结论”，主 Agent 读取后自己完成这些步骤。它也可以包含辅助脚本，
但单纯加载这份 Skill 不会自动生成一个拥有独立消息状态的 Agent。

```text
使用 Skill：
主 Agent 的 messages + 分析规范 -> 主 Agent 自己检索、分析、回答

使用 Subagent：
主 Agent -> Runtime 启动分析子任务 -> 子任务独立检索、分析
         <- 收到结论与证据引用 <- 子任务结束或返回
```

| 比较点 | 单纯加载 Skill | 委派 Subagent |
| --- | --- | --- |
| 加载的东西 | 方法、资源与操作约定 | 用于子任务执行的角色与运行配置 |
| 谁来分析 | 当前 Agent | 被委派的子 Agent |
| 工作上下文 | 指令进入当前 Agent 的上下文 | 创建或恢复子任务自己的消息状态，可按需继承部分父上下文 |
| 生命周期 | Skill 本身不是一个运行任务 | 子任务有开始、执行、返回、失败或取消等状态 |
| 结果回到哪里 | 当前 Agent 直接使用自己的工具观察 | 通过父子任务协议返回结果，内部轨迹按需要另存 |

独立上下文不代表独立数据库 Session、进程、机器或模型权重，也不代表一定并行。
主 Agent 可以等待一个 Subagent 执行完再继续。

两者可以组合：Runtime 启动 exam_analyzer 子任务后，让它加载 exam_analysis Skill。
前者决定“谁在什么约束下执行”，后者决定“按什么规范做”。如果某个框架支持把 Skill
放到子 Agent 中运行，实际是把两种机制组合起来，而不是两个概念变成同一个东西。

**面试一句话：**

> 两者都可以提前定义，但定义的对象不同。Skill 定义可复用的方法和资源，Subagent 模板
> 定义子任务执行者的角色与运行约束。真正使用时，Skill 通常由当前 Agent 加载并执行，
> Subagent 则由 Runtime 创建或恢复独立的子任务上下文，运行后将结果交回主 Agent。

### 6. 为什么不把所有 Skill 一次性放进 Prompt？

**设计回答：**

> 全量注入会增加 Token，并让无关规则干扰当前任务。我会先提供名称和适用场景，匹配后
> 再读取完整说明及必要资源；既保留可发现性，也控制上下文规模。规则可以指导模型，但
> 不能代替服务端权限校验，Skill 中的脚本也必须经过工具执行层的权限和资源限制。

若项目没有使用 Skill，可以说：当前将场景规范放在 Prompt 与工具描述中，已了解这种按需
加载的抽象；当规则数量和复用需求增长后再引入，而不是临时宣称已经实现。

## 四、DAG 与工作流

### 7. 你的 Agent Loop 是 DAG 吗？

**可以这样回答：**

> 不是同一个概念。DAG 是有向无环的依赖图，用来表达哪些节点先完成、哪些可以并行。
> Agent Loop 则会根据每轮工具结果反复决策，它的控制流有循环，不能直接说成静态 DAG。
> 业务服务内部的固定阶段可以用 DAG 建模，某个节点也可以封装一个带轮次预算的 Agent Loop。

不能因为链路可以画成箭头图，就说已经建设通用 DAG 引擎；多 Agent 的委派关系也不自动
等于 DAG。图式工作流可以有回路，但有回路时就不能叫 DAG。

### 8. 如果让你设计试卷学情分析 DAG，你会怎么做？

**扩展设计示例，不代表当前已部署 DAG 调度器：**

```text
A 试卷 OCR 与结构化
  -> B 题目、作答和来源校验
       -> C 知识点匹配 ---------+
       -> D 得分与错题统计 -----+-> E 学情汇总 -> F 报告生成 -> G 结果落库
```

D 的统计要有可靠的评分或答案依据，不能把 OCR 识别结果直接当作已批改成绩；依据缺失时
补充评分/人工复核步骤，或明确标为待确认。这里并行的是 B 完成后的 C 与 D。

**可以这样回答：**

> 我先把业务拆成有明确输入输出的节点，再定义 depends_on。启动前校验节点 ID、工具
> 白名单、输入引用和依赖是否成环。调度时只释放依赖满足的节点，无依赖冲突的节点在并发
> 配额内执行。节点结束后校验结果，再更新状态和释放下游；必需节点失败时，依赖它的下游
> 不能当作成功继续跑，可选节点则按预先定义的降级规则处理。

建议的节点元信息：

```text
id, handler, depends_on, input_refs, output_schema,
timeout, retry_policy, required, side_effect
```

图描述和运行状态分开存：定义保存节点和边，运行记录保存 run_id、node_id、attempt、状态、
输入/输出引用与错误。重试计入节点执行次数，不随意加入反向依赖边；变更计划时用新版本。
写入节点还需要业务幂等键，恢复调度不等于允许外部操作重复执行。

拓扑排序和就绪节点的基础机制可参考
[Python graphlib 文档](https://docs.python.org/3/library/graphlib.html)。拓扑排序只解决依赖顺序，
持久化、失败传播、重试和业务幂等仍需单独设计。

### 9. DAG 一定要由模型生成吗？

**可以这样回答：**

> 不需要。试卷解析、校验和落库等稳定流程更适合代码或配置定义。对于开放式任务，模型
> 可以提出结构化计划，但必须由 Runtime 校验依赖、预算和权限之后才执行。规划权不等于
> 执行权限，不能把模型输出的任意工具名和参数直接当成合法任务。

## 五、Plan 模式

### 10. 你这个项目有 Plan 模式吗？

**沿用目前主链的回答：**

> 当前介绍的主链是模型逐轮决策、工具执行后继续调整，没有把“计划、用户确认、执行”
> 作为独立模式来强调。它具有多步决策能力，但这不等于已经实现一个可持久化、可审批的
> Plan 模式。普通问答和服务入口引导不需要每次都先多调一次 Planner。

模型输出一段学习计划、运行时维护待办列表、系统进入受限的 Plan 模式，是三种不同能力。
也不应把模型内部的推理过程当成可审计、可执行的计划。

### 11. 如果要增加 Plan 模式，怎么设计？

**扩展设计：**

> 我会把计划和执行分开。Plan 阶段允许必要的只读检索，产出包含目标、步骤、依赖、预期
> 输出和资源预算的结构化计划。Runtime 做协议、权限和预算校验；需要用户确认的操作，
> 通过确认后才进入 Execute。执行中遇到前提变化再修订计划，而不是无限重新规划。

1. 明确模式状态，例如 planning、awaiting_approval、executing、completed、failed、cancelled。
2. Plan 阶段限制可用工具，并在服务端阻止业务写入，不只在 Prompt 中写“禁止修改”。
3. 确认绑定具体计划版本和操作范围；涉及新增副作用的计划变更不能沿用旧确认。
4. Execute 根据执行结果校验步骤是否完成，而不是只看模型说“我做完了”。
5. 给规划、重规划和执行共同设置总预算，避免每次重新规划都重置限制。

学习建议可以作为聊天内容直接返回；真正触发测评、保存计划或修改学习安排时，仍要区分
展示内容和业务副作用，不能因为模型生成了计划就默认已经执行。

## 六、项目指标与验证

### 12. 你这个项目的核心指标是什么？

**可以这样回答：**

> 我把指标分为业务效果、能力质量和运行稳定性。业务上看用户能否找到合适的学习服务，
> 以及进入后是否完成任务；能力质量看工具选择是否正确、教材证据是否召回、个性化信息
> 是否准确；Runtime 看是否有任务超时悬挂、工具失败是否被隔离，以及每轮调用成本。
> 不能把返回 DONE 当成任务成功，也不能把用户拿到测评入口当成完成测评。

以下是建议采用的测量定义，不是已经取得的测量结果：

| 指标 | 分母与分子 | 需要保留的证据 |
| --- | --- | --- |
| 决策/服务选择准确率 | 正确选择回答、澄清或目标服务，且关键参数正确的样本数 / 标注样本数 | query、必要上下文、允许动作与参数、模型实际动作 |
| 入口点击率 | 窗口内点击入口的去重会话数 / 实际展示入口的去重会话数 | exposure、click、session_id、action_id、统计窗口 |
| 学习任务完成率 | 固定完成窗口内成功完成的任务数 / 同一批启动任务数 | task_id、started_at、completed_at、业务状态 |
| 未终止 Turn 比例 | 超过定义截止时间仍没有终态的 Turn 数 / 符合口径的启动 Turn 数 | started_at、deadline、终态和结束时间；取消/失败单独分类 |
| 工具执行结果 | 按工具统计成功、超时、参数错误和服务异常；区分单次 attempt 与重试后的逻辑调用 | turn_id、call_id、attempt、status、error_type |
| 长会话输入成本 | 固定样本中第 10 个用户回合之后，主 Agent 每次模型调用的平均 input_tokens | 每次调用 usage、session/turn/round、版本 |
| RAG Recall@5 | 每题 Top 5 命中的相关 Chunk 数 / 该题全部 Gold Chunk 数，再按预定方式汇总 | query、gold_chunk_ids、Top 5、语料和索引版本 |
| 画像事实命中率 | 被正确使用的标注事实数 / 回答所需的全部标注事实数 | 跨会话问题、必要画像事实、实际输入和回答 |

入口点击率按会话统计时，一个会话多次点击只计一次；若按单个服务计算，要明确是否改为
session_id + action_id 去重。学习完成率按 task_id 统计，不能把会话数当任务数。
仍在正常完成窗口内的任务不能过早记为失败，测试流量、重复事件和取消的处理规则须固定。

### 13. 简历里的数字应该怎么解释？

**规模数据：** 约 7 类服务、个人参与的 3 类服务、891 本教材属于覆盖范围。需要说明
教材版本如何去重、是否全部完成入库；规模不能单独证明质量提升。

**Token 降低 37%：** 比较固定长会话样本在旧版和新版配置下的主 Agent 单次模型调用
平均输入 Token，公式是 `(旧均值 - 新均值) / 旧均值`。用户回合与模型 round 分开统计，
避免把一次聊天的总 Token 当单次输入。模型、工具和样本尽量保持可比，并检查回答质量。
若要说总成本下降，摘要、画像抽取、重试和子任务等额外调用也必须计入，不能只报主调用。

**600 条 RAG 标注问题：** 应标注支持答案的 Gold Chunk，而不只是知道正确答案。问题
按真实场景、学科和问法分层抽样，包含基线漏召回问题，固定语料和索引版本，测试集不用于调参。
如果每题只有一个 Gold Chunk，Top 5 是否包含它的比例与该设定下 Recall@5 相同；多 Gold
时不能把“任意命中一个”的 Hit Rate 当成完整 Recall。

**画像命中率：** 如果 200 条问题每题各有一个关键事实，可以按命中问题数统计；若每题
含多个事实，要明确按事实微平均还是按问题宏平均。准确读取事实与最终正确使用事实是两层
指标，不能混报；过期、冲突或误用其他用户画像也应单独检查。

**点击率提升 22%：** “达到 22%”“相对提升 22%”“提高 22 个百分点”不同。
相对提升公式为 `(新 CTR - 旧 CTR) / 旧 CTR`，百分点变化为新旧百分数之差。
没有旧版基线或合理对照，就只能说观察到的点击率，不能断言是 Runtime 导致的提升。

**RAGAS Faithfulness：** 衡量回答中的声明能否由检索上下文支持，不是端到端答案正确率。
需要固定评测器、模型和版本并人工抽查。概念与计算方式参考
[Ragas Faithfulness 文档](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)。

此前学习草稿中的若干百分比明确标注为模拟值，且不同稿件存在不同版本。没有评测报告、
查询脚本或埋点记录时，不要将其描述为线上实测；可以先讲机制、覆盖范围和验证方案。

### 14. 怎么证明 Runtime 提高了稳定性？

**设计回答，不把待做测试说成已完成：**

> 我会用固定任务回放和故障注入验证。重点不是最终是否返回一段文字，而是工具异常有没有
> 被正确回填、无关任务是否还能完成、错误是否对用户可见、预算是否有效，以及外部业务操作
> 有没有重复执行。业务完成和 Runtime 正常终止需要分开判断。

建议准备的验证案例：

1. 一批工具中一个返回服务错误，其他工具成功；检查每个 call_id 都有对应结果。
2. 工具一直不返回；验证超时和取消机制，而不是期待轮次限制起作用。
3. 模型产生重复调用；验证批内去重，并区分它与跨轮业务幂等。
4. 已经完成部分检索后模型请求失败；检查是否合理降级，且不伪造未完成结果。
5. 返回空文本或非法参数；验证有限纠正和明确失败，不进入无限重试。
6. 用户取消或网络断开；按产品策略验证任务终态、事件回放，以及未取消的外部副作用。

## 七、项目亮点和个人贡献

### 15. 你认为项目最大的亮点是什么？

**建议只讲三个，不堆模型和框架名称：**

> 第一是把自然语言交互连接到已有学习服务，而不是再做一个孤立的聊天框。普通问答由
> Agent 处理，测评和分析等确定性流程通过受控入口接入，不把所有业务强行改成 Agent。
>
> 第二是建设可控的执行闭环。模型负责决策，Runtime 统一工具协议、失败隔离、上下文和
> 结束边界，让新增工具共享同一套执行和观测机制。
>
> 第三是有教育场景的数据与结果回流。教材 RAG 提供可追溯证据，OCR/多模态将试卷转成
> 可处理内容，学习任务结果再进入会话与用户画像，为后续个性化对话提供依据。

这些是项目取舍和工程价值，不必声称是行业首创。相比“用了多个 Agent”，更重要的是说明
为什么当前设计适合业务，如何验证，以及自己完成了哪些具体工作。

### 16. 你的个人贡献是什么？最难的点是什么？

个人贡献先报可确认范围：参与 Runtime 核心能力建设，同时参与词汇量检测、英语三合一和
试卷学情分析的方案设计与开发。随后选一个真正能讲到代码、测试或联调细节的案例，不将
“我们设计”全部改成“我独立完成”。

可准备的案例方向：

| 案例 | 面试官会追问 |
| --- | --- |
| 工具失败隔离 | 原始异常如何影响执行？你改了哪里？如何验证其他工具和结果配对未受影响？ |
| Action 业务入口 | 如何区分要解释与要测评？参数由谁校验？用户不点击或点两次怎么办？ |
| 上下文治理 | 裁掉什么、保留什么？如何防止缺证据？压缩开销算不算总成本？ |
| OCR 学情分析 | 识别错误怎样进入后续链路？低置信度如何复核？哪些环节由你实现？ |

案例采用“遇到的问题 -> 我的具体修改 -> 验证方法 -> 实际结果 -> 剩余限制”来讲。
没有真实故障经历，不要把假设的故障注入例子描述成亲历线上事故。

## 八、其他高频追问速答

| 问题 | 回答要点 |
| --- | --- |
| await 就是并发吗？ | 逐个 await 通常是串行；多个协程先调度再统一等待才能形成并发，同步阻塞不能直接占住事件循环 |
| 一个工具报错，gather 会怎样？ | 区分工具内部已捕获的普通异常和未处理异常；gather 本身不会自动把所有异常转换成 ToolResult |
| 工具失败后都可以重试吗？ | 只读检索与业务写入分开；写入结果未知时先查状态或使用幂等键，不能盲目重试 |
| 参数符合 Schema 就安全了吗？ | Schema 只管结构，身份、权限、数据范围和业务前置条件必须由服务端核验 |
| Subagent 会提高准确率吗？ | 不必然；需要在固定任务集比较质量和成本，还要处理信息丢失及多个结果冲突 |
| 工具输出越完整越好吗？ | 大结果可保存引用和摘要，按需读取；不能把所有原文无限回填到模型上下文 |
| RAG 与用户画像有什么区别？ | RAG 提供领域证据，画像提供用户信息；来源、时效、更新方式不同，不能检索到什么都晋升为画像 |
| 什么算用户任务完成？ | 回答、展示入口、完成测评、结果回流分层定义，不能用统一 DONE 替代所有业务完成标准 |
| 为什么不直接用现成框架？ | 结合团队已有运行时和实际需求解释取舍；避免引入重复状态模型，但也承认自维护调度、恢复和观测的成本 |
| 模型返回计划就能执行吗？ | 先校验动作、依赖、权限和预算；涉及业务副作用时按照确认与幂等规则执行 |

## 九、练习顺序

1. 先熟练回答 Runtime 本质、为什么主链不用多 Agent、Tool/Skill/Subagent 区别。
2. 再画一个明确标为扩展设计的 DAG，讲清依赖、并发、失败传播、重试和幂等。
3. 练习回答是否有 Plan 模式，能区分当前能力与后续方案。
4. 选业务、质量、稳定性各一个指标，讲清分母、基线、时间范围和证据。
5. 最后用一个真实个人案例支撑三项项目亮点，不逐条复述简历。
