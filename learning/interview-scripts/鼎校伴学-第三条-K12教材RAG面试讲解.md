# 鼎校伴学第三条：K12 教材 RAG 面试讲解

> 对应简历第三条职责。讲解主线：教材如何可靠入库、证据如何准确召回、回答如何忠于证据、
> 指标如何评测。

## 指标版本提醒

最新版简历 `岳明哲 (11).pdf` 使用 `Recall@5 73% -> 94%`，较早的 STAR 学习稿使用
`73% -> 86%`。本文按最新版的 **94%** 准备，正式面试前必须统一所有简历和口述稿。
只有真实评测中保留了三级消融结果时，才能进一步解释为“Dense-only 73%、加入 BM25 和
RRF 后 86%、再加入 Qwen-Rerank 后 94%”；不能为了兼容两份旧稿临时编造中间实验。

鼎校伴学的简历口径已确认使用 **Qdrant** 承载教材 Dense 向量检索，并调用
Qwen-Rerank 做候选重排。当前 DeepTutor 学习仓库使用 FAISS，只用于理解检索流程，不能把
它说成鼎校伴学的生产选型。正式面试前还要以生产调用配置确认准确的 Rerank 模型 ID。
仓库也没有 600 条 Gold 标注、两版逐题结果或 RAGAS 报告，因此 `891 本教材`、
`18.2 万页`、`32 万个 Chunk` 和质量提升数字都需要由实际业务报表与评测产物支撑。

## 3 分钟追问版

> 我在 RAG 方面主要参与 K12 教材知识库和检索链路建设。这个场景的难点是教材规模较大，
> 而且同一知识点在不同年级、学科、出版社和上下册中的内容比较相似。如果只做普通向量
> 检索，容易召回语义相近但教材版本不匹配的内容。
>
> 在入库阶段，我们对 891 本、约 18.2 万页教材进行解析和结构化。解析后清理页眉、页脚、
> 页码等噪声，保留正文、章节标题、公式和页码信息，再按章节、小节和语义边界切分为约
> 32 万个 Chunk。每个 Chunk 补充教材 ID、学科、年级、版本、册别、章节和页码等元数据，
> 既用于检索过滤，也用于最终回答的来源追溯。
>
> 检索阶段最初使用 Dense 向量召回。它适合用户问法与教材原文不一致的语义问题，但对公式、
> 课文标题、知识点名称和章节编号等精确关键词不够稳定。因此我们增加 BM25 关键词召回，
> 两路并行获取候选结果。由于向量相似度和 BM25 分数不在同一个量纲上，我们没有直接相加，
> 而是使用 RRF 按排名进行融合。融合后只对候选集合调用 Qwen-Rerank，让模型联合读取 Query
> 和 Chunk 正文并重新计算相关性，最后收敛为 Top 5 证据。检索前还会根据当前年级、学科和
> 教材版本过滤候选范围，降低错误版本和无关内容对回答的干扰。
>
> 评测方面，我们按学科、年级、教材版本和问题类型分层抽取 600 条问题，并为每条问题人工
> 标注能够支持答案的 Gold Chunk。固定语料、切块配置和索引版本后，对比 Dense-only 与
> 最终的 Dense + BM25 + RRF + Qwen-Rerank 链路，Recall@5 从 73% 提升到
> 94%。生成侧固定模型和 Prompt，使用 RAGAS 检查回答中的陈述是否能被检索上下文支持，
> Faithfulness 从 0.82 提升到 0.90。
>
> 在线运行时，RAG 作为 Agent Loop 中的一个 Tool。检索结果被封装为 ToolResult，并按
> `tool_call_id` 回填为 `role=tool` 消息。模型基于教材证据生成讲解、题目或学习建议，同时
> 输出教材名称、章节和页码，形成可追溯的回答。

## 完整链路

```text
教材 PDF / 外部 OCR
  -> 页面解析与结构化
  -> 清洗页眉、页脚和异常字符
  -> 按章节、小节和语义边界切块
  -> 补充教材、年级、学科、版本、章节和页码元数据
  -> 在 Qdrant 建立 Dense 向量索引，并建立 BM25 关键词索引

用户问题
  -> 根据当前教材信息做元数据过滤
  -> Dense Top 10 与 BM25 Top 10 并行召回
  -> RRF 排名融合
  -> Qwen-Rerank 对候选正文重新打分
  -> 收敛为 Top 5 教材证据
  -> ToolResult 回填 Agent Loop
  -> 生成带教材、章节和页码来源的回答
```

## 四层拆解

### 1. 教材入库层

页面解析成功率应定义为：符合统计范围的页面中，成功生成有效结构化内容并完成入库的页面
比例。它衡量解析流水线是否完成，不代表 OCR 的每个字符都正确。空白页、封面、目录页是否
进入分母必须预先固定，不能评测结束后再调整口径。

Chunk 不只保存正文，还应保存以下元数据：

```text
book_id / subject / grade / publisher / volume
chapter / section / page_no / chunk_id
content_hash / index_version
```

章节元数据用于避免跨教材误召回；页码和稳定标识用于引用、增量更新以及离线评测定位。
重新切块可能改变 `chunk_id`，因此 Gold 数据最好同时保存 `source + page + content_hash`。

#### 切块策略

K12 教材更适合“结构优先、长度兜底”，而不是把所有内容机械切成固定的 1000 Token：

```text
教材解析结果
  -> 先按章、节、知识点、题目或自然段划分语义块
  -> 超长语义块再按段落或句子递归切分
  -> 只在同一小节内保留少量重叠，避免上下文被边界截断
  -> 过短且同主题的相邻块合并
  -> 公式、表格、例题与对应解析尽量保持完整
```

建议把 **500～700 Token 作为检索 Chunk 的目标长度，800～1000 Token 作为硬上限，重叠
控制在 50～100 Token**。这些数值是待验证的起始配置，不应表述为行业标准；最终应固定语料和
问题集，对比不同 Chunk 长度下的 Recall@5、重排效果、重复召回率和上下文 Token 成本。

如果业务已经使用 1000 Token，可以将口径改成“1000 Token 是上限而不是固定长度”。另一种
可扩展方案是父子切块：使用约 400～600 Token 的子块做精准召回，命中后补充其 800～1200
Token 的父章节用于生成。第一版没有实际需求时不必引入父子索引。

章节和知识点标签是合理的，但要区分两个位置：稳定的教材属性保存在 Qdrant `payload` 中，用于
过滤、引用和追踪；精简的标题路径可以拼入待编码文本，让章节语义参与向量召回。例如：

```text
[人教版｜六年级上册｜数学｜第三章 分数除法｜知识点：倒数]
Chunk 正文……
```

`payload` 本身不会自动参与 embedding 相似度计算。年级、版本、册别等确定性标签可以作为硬
过滤条件；如果知识点标签由 LLM 推断且可能出错，更适合用于软增强或记录置信度，避免错误硬
过滤导致漏召回。长度预算应按“标题路径 + 正文”的实际 embedding 输入计算，而不是正文已经
达到 1000 Token 后再额外追加大量标签。

#### Qdrant 入库过程

入库时先使用选定的 Embedding 模型把每个 Chunk 转换成定长浮点向量，再以一个 Chunk 一个
Point 的方式批量 `upsert` 到 Qdrant：

```text
point.id      = 稳定 chunk_id
point.vector  = embedding(标题路径 + Chunk 正文)
point.payload = 正文、教材 ID、学科、年级、版本、章节、页码、content_hash、索引版本
```

Collection 的向量维度必须与 Embedding 模型输出一致，并配置 `Cosine` 作为距离度量。更准确的
说法是“**将 Embedding 向量入库，并使用余弦相似度检索**”，而不是“把余弦向量入库”。查询时
必须用同一 Embedding 模型和版本编码用户问题，再与库中向量计算相似度。更换模型或向量维度
时，应重建索引或使用独立的版本化向量字段，不能直接混用旧向量。

面试中可以概括为：

> 我们不是固定每 1000 Token 生切，而是先按章节和知识点保持语义完整，超长内容再递归切分；
> 1000 Token 作为上限，检索块目标控制在 500 到 700 Token，并保留少量同章节重叠。每个
> Chunk 会拼接精简的章节路径生成 Embedding，再把向量、正文和教材元数据作为一个 Qdrant
> Point 批量写入。Qdrant Collection 配置余弦距离，因此入库的是 Embedding 浮点向量，余弦是
> 检索时采用的相似度度量。

### 2. 混合检索层

Dense 向量检索将 Query 和 Chunk 映射到向量空间，擅长召回“用词不同但意思接近”的内容。
BM25 根据词频、稀有度和文档长度进行排序，擅长公式、专有名词、课文标题和章节编号等精确
匹配。两者解决的问题互补，不是简单用 BM25 替代 Embedding。

RRF 不直接比较两路原始分数，而是按照每个候选在各路中的排名累加分数：

```text
RRF(chunk) = sum(1 / (k + rank_i(chunk)))
```

这里的 `k` 是平滑常数，不是最终返回数量。某个 Chunk 在一路排名很高，或者同时进入两路
前列，融合排名通常会更靠前。RRF 只根据名次融合，不重新理解正文；随后调用的
Qwen-Rerank 才会联合读取 Query 和候选 Chunk，输出新的相关性分数。只对小候选集调用重排
模型，是为了控制外部模型调用的延迟和成本。

#### 向量库口径

鼎校伴学使用的是 **Qdrant**，不是 Milvus 或 Chroma。Qdrant 中保存 Chunk 的 embedding、
稳定 ID 和教材元数据 payload，并通过年级、学科、出版社、册别等条件过滤候选，再按照向量
相似度召回。BM25 负责关键词检索，两路结果使用 `chunk_id` 去重并进行 RRF 融合。

选择 Qdrant 的原因不能只说“业务量小”。更完整的解释是：当前教材数据量和检索 QPS 使用
单节点部署即可满足需求，Qdrant 的部署维护相对简单，并原生支持向量检索和 payload 过滤；
Milvus 更强的分布式扩展能力在当前阶段没有带来足够收益，反而会增加部署和运维成本。如果
后续数据规模、并发或高可用要求明显增长，再根据压测评估集群化或迁移，而不是预先堆复杂度。

Qdrant 是教材 RAG 的向量存储，不是 L1/L2/L3 长期记忆的存储。三层记忆仍按 Session 或
user_id 从关系数据库读取，这两个技术选择不存在冲突。

面试中可以简化为：

> 我们使用 Qdrant 保存和检索教材 Dense 向量，BM25 负责
> 关键词召回，RRF 融合后再调用 Qwen-Rerank 重排候选。

### 3. 证据生成层

元数据过滤优先限制年级、学科、教材版本和册别，防止召回“内容正确但版本错误”的教材。
重排后最终只给模型 Top 5，是召回覆盖、上下文噪声和 Token 成本之间的取舍，不代表 Top 5
在所有场景都最优。若面试官追问，应说明通过 Top 3、Top 5、Top 10 对照评测后再确定，而
不是凭经验写死。

Faithfulness 只衡量回答中的陈述能否被检索证据支持，不等于答案整体正确率。要把
`0.82 -> 0.90` 归因于检索优化，需要固定生成模型、Prompt、问题集和评审配置，只改变检索
方案；否则无法排除模型版本或 Prompt 变化带来的影响。

### 4. 离线评测层

600 条不是随便收集的历史问答，而是带有 Gold Chunk 的检索评测问题。建议按照学科、年级、
教材版本、问题类型和问法难度分层抽样，同时包含 Dense-only 曾经漏召回的困难问题，但不能
只挑优化后能够命中的成功案例。用于调参的问题与最终测试集应分开。

每条评测记录至少保存：

```json
{
  "query": "六年级上册分数除法的计算方法是什么？",
  "gold_chunk_ids": ["chunk_001"],
  "dense_top5": ["chunk_101", "chunk_001"],
  "hybrid_top5": ["chunk_001", "chunk_087"],
  "corpus_version": "k12_2026_01",
  "index_version": "hybrid_v2"
}
```

## 指标计算

### Recall@5

如果每道问题只有一个 Gold Chunk，Recall@5 等价于前 5 条结果是否命中该 Chunk：

```text
Dense-only：600 * 73% = 438 道命中
Hybrid：   600 * 94% = 564 道命中
增加命中：126 道
绝对提升：21 个百分点
相对提升：(94% - 73%) / 73% = 28.8%
```

如果一道问题有多个 Gold Chunk，则先计算每题覆盖率，再对全部问题求平均：

```text
单题 Recall@5 = Top 5 中命中的 Gold Chunk 数 / 该题全部 Gold Chunk 数
```

此时不能把 73% 和 94% 直接换算成命中问题数量，也不能把“至少命中一个”的 Hit Rate 当成
Recall。

### Faithfulness

RAGAS Faithfulness 通常先从回答中拆出可验证陈述，再判断这些陈述能否由检索上下文支持，
最后聚合为 0 到 1 的分数。`0.82 -> 0.90` 是提高 0.08，不能口述成“答案正确率达到 90%”。

## 高频追问

### 为什么不只使用 Dense Embedding？

> Dense 擅长语义匹配，但教材中存在大量公式、专有名词、课文标题和章节编号。BM25 对这些
> 精确词更敏感，两路召回能够覆盖不同类型的问题。

### 为什么不直接把两个分数加起来？

> 向量相似度与 BM25 分数的范围和分布不同，直接相加需要做归一化和权重调参。RRF 只依赖
> 排名，对两路分数尺度不一致的问题更稳健，也便于先快速落地。

### 为什么选 Top 5？

> Top K 太小可能漏证据，太大会引入错误版本和无关内容，还会增加 Token。我们通过固定
> 问题集比较不同 K 值下的 Recall、Faithfulness 和上下文成本，再选择 Top 5 作为折中。

### 如何防止召回错误教材版本？

> 优先从用户当前选择的教材、班级或业务页面获得年级、学科、出版社和册别，作为服务端
> 可信过滤条件，再在过滤后的候选集合中做双路召回。来源信息不明确时应扩大检索或询问用户，
> 不能由模型无依据地猜一个版本。

### 94% 为什么能提升这么多？

> 提升主要应通过逐题失败分析解释，例如旧方案遗漏精确章节名、公式或版本过滤，而 BM25 和
> 元数据约束补回这些问题。不能只说“换成混合检索所以提升了”。需要能展示 Dense-only 与
> Hybrid 的逐题 Top 5、Gold Chunk 和典型错误案例，并排除测试集泄漏。

### RRF 是不是 Reranker？

> RRF 属于 Rank Fusion，按照多路候选的排名做融合；Cross-Encoder Reranker 会同时读取 Query
> 和候选正文重新计算相关性。两者不是同一个东西。我们的链路先使用 RRF 融合 Dense 与 BM25，
> 再调用独立的 Qwen-Rerank 对融合候选做语义重排，最终选择 Top 5。

### 使用的是什么向量库？

> 鼎校伴学使用 Qdrant 保存教材 Chunk 的 embedding 和元数据，并使用余弦相似度做 Dense
> 召回；BM25 负责关键词召回。当前规模使用单节点 Qdrant 已能满足需求，因此没有引入运维
> 成本更高的 Milvus 集群。这里的 Qdrant 只用于教材 RAG，不用于三层长期记忆。

### RAG 结果会进入长期记忆吗？

> 本轮检索证据通过 Tool Result 进入 Agent Loop，默认不把全部 passage 原文写入长期记忆。
> 知识库原文和索引本身持久化，检索 Trace 可以保存 query、chunk_id、rank、score 和版本，
> 便于评测与问题定位；真正稳定的用户事实再经过验证后进入用户画像。

## 面试表达边界

1. 页面解析成功率不等于 OCR 字符准确率。
2. Recall 衡量是否找到了 Gold 证据，Faithfulness 衡量回答是否忠于已给证据。
3. RRF 是排名融合，Qwen-Rerank 才是读取 Query 与候选正文的独立语义重排阶段。
4. `73% -> 94%` 是提升 21 个百分点，不是提升 21%。
5. 600 条问题必须绑定 Gold Chunk、语料版本和索引版本，不能只保存标准答案。
6. 当前代码配置只能证明检索链路如何运行，不能自动证明业务规模和质量指标。
